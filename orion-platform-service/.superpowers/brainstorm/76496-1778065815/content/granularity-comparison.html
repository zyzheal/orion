配置化启用粒度方案对比

基于 130+ 服务、95 路由、8 横切关注点的实际架构分析

方案 A：功能域级

优点

  • 管理简单，40 个配置域即可覆盖
  • 边界清晰，不会破坏依赖链
  • 与 UnifiedConfigService 现有结构一致
  • 用户认知成本低（"关闭 AI 模块"）

缺点

  • 粒度太粗，无法精细控制
  • 同域内不需要的服务也被加载
  • 例：只想用 ChaosExperiment，但 FaultInjector 也必须加载

适用场景：小型团队，资源受限，不需要精细控制

方案 B：服务级

优点

  • 最大灵活性，精确控制每个服务
  • 按需加载，内存占用最小
  • 可以为每个服务独立配置 DB/事件总线

缺点

  • 130+ 个服务需要配置，管理复杂度高
  • 可能破坏依赖链（A 启用，B 未启用 → 崩溃）
  • 配置验证困难，组合爆炸
  • 用户需要理解内部架构才能正确配置
  • 配置文件可能比代码还长

适用场景：大型平台，多租户按需分配，专业运维团队

方案 C：路由级

优点

  • 实现最简单，只需修改 routes.ts
  • 不改变服务加载行为，零破坏性
  • API 暴露控制，安全边界清晰

缺点

  • 服务仍然加载到内存，不节省资源
  • 定时任务/后台调度器仍会运行
  • 只是"看不见"，不是"不加载"
  • 无法阻止 EventBus 订阅和事件发布

适用场景：快速 API 控制，临时功能开关，不适合真正的模块化

方案 D：混合粒度（推荐）

优点

  • 三层架构：核心/功能域/服务，各司其职
  • 管理复杂度可控（~50 个配置点 vs 130+）
  • 依赖安全：核心不可禁用，域级有依赖校验
  • 用户友好：大部分用户只看到域级开关

缺点

  • 实现复杂度中等，需要分层配置解析
  • 需要配置依赖校验逻辑
  • 边界划分需要仔细设计

适用场景：Orion 平台的实际需求 — 93 个服务、多个可选功能域

四层分层方案

层级粒度配置点可禁用说明
L0 核心横切关注点8✗ 不可Auth/RBAC/Tenant/DB/EventBus/Audit/Config/Degradation
L1 功能域大组12✓ 可AI/Chaos/FinOps/Community/Federation/MultiCloud 等
L2 服务级单个服务~30✓ 可仅限无强依赖的服务（10 个无路由 + 部分独立服务）

总计配置点：~100 个（自动从 UnifiedConfigService 生成，用户不需要手动管理）

推荐方案的核心设计

配置化启用架构

1. 配置格式 — 三层嵌套，自动推导依赖：

moduleConfig:
  core:           # L0 - 自动加载，不可禁用
    auth: { enabled: true }
    tenant: { enabled: true }
    ...
  domains:        # L1 - 功能域级开关
    ai: { enabled: true, autoStart: true }
    chaos: { enabled: false }  # 整个混沌工程模块不加载
    finops: { enabled: true, services: { costTracking: false } }
  services:       # L2 - 服务级细粒度
    adaptivePipeline: { enabled: true }
    consistency: { enabled: false }
服务生命周期管理

2. 服务生命周期 — register → validate → start → stop

每个服务实现统一的 ServiceLifecycle 接口：

  • register() — 注册自身的路由、定时任务、EventBus 订阅
  • validate() — 检查依赖是否满足（如：chaos 依赖 monitoring）
  • start() — 懒加载，仅在首次请求时初始化
  • stop() — 清理路由、取消定时任务、取消 EventBus 订阅
依赖安全机制

3. 依赖安全 — 启动时校验，运行时懒加载：

  • 启动时构建依赖图，检测不满足的依赖 → 报错或自动启用
  • 运行时首次调用时加载服务（懒加载）
  • 禁用服务的路由不注册，EventBus 不订阅，定时任务不启动
  • 提供 /api/v1/system/modules 端点查看当前加载状态
