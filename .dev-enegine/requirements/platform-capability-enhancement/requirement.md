# 平台能力提升方案

## 需求背景

Orion 平台当前已具备基础的事件总线、缓存服务、数据库故障切换、备份恢复等基础设施能力。但这些能力在生产级可用性方面仍存在以下缺口：

1. **熔断器能力分散**：现有 `CircuitBreaker` 仅存在于 AI Gateway 服务内部（`src/services/ai/CircuitBreakerManager.ts`）和通用工具（`src/utils/rate-limit-circuit-breaker.ts`），缺乏**面向所有微服务通用的熔断基础设施**。所有业务服务（pipeline、tenant、config 等）调用外部依赖时没有统一的熔断保护。

2. **消息队列未落地**：EventBus 已实现（`src/services/event-bus/`），支持 NATS JetStream 事件总线和 PostgreSQL 持久化。但缺少**面向业务的消息队列基础设施**——包括任务队列、延迟队列、死信队列、消费者组等消息队列核心能力。

3. **缓存策略缺乏治理**：Redis Cache（`src/services/redis-cache.ts`）和 CacheService（`src/services/cache/CacheService.ts`）已实现基本的 get/set/del 操作，但缺少统一的**缓存策略治理**——无多级缓存（L1 内存 + L2 Redis）、无缓存预热/失效策略、无缓存穿透/击穿/雪崩防护、无缓存一致性保障。

4. **CI/CD 增强能力不足**：Pipeline 引擎（`src/services/pipeline/`）已实现完整的 pipeline 定义、执行、日志流、重试、质量门等能力。但在以下方面有待增强：
   - 缺乏 Pipeline 运行时的熔断保护
   - 缺乏跨 Pipeline 的事件驱动编排
   - 缺乏 Pipeline 级别的缓存加速

5. **容灾设计不完整**：数据库故障切换（`src/services/database/DatabaseFailoverHandler.ts`）和备份恢复（`src/services/backup/`）已实现基础功能。但缺少：
   - 全平台容灾策略引擎
   - RTO/RPO 统一管理与监控
   - 容灾演练自动化
   - 跨可用区容灾设计

## 功能范围

| 优先级 | 模块 | 状态 | 说明 |
|--------|------|------|------|
| P0 | 通用熔断器服务 | 需新建 | 面向所有微服务的通用熔断器 |
| P1 | 消息队列基础设施 | 需新建 | 基于 Redis/NATS 的任务队列 |
| P1 | 缓存策略治理 | 需增强 | 多级缓存 + 防护策略 + 一致性 |
| P2 | CI/CD 增强 | 需增强 | 熔断集成 + 事件编排 + 缓存加速 |
| P2 | 容灾设计完善 | 需增强 | 容灾引擎 + 演练 + 监控 |

## 用户场景

### 场景 1：Pipeline 调用外部 API 时自动熔断
当 Pipeline 调用外部 SCM（GitHub/GitLab）或镜像仓库时，如果外部服务不可用，自动触发熔断避免级联失败。

### 场景 2：异步任务通过消息队列调度
构建任务、通知发送、数据同步等耗时操作通过消息队列异步执行，支持重试、延迟、死信处理。

### 场景 3：热点数据多级缓存加速
高频查询数据（配置、用户权限、Pipeline 模板）通过 L1（内存）+ L2（Redis）多级缓存加速，自动防穿透/击穿/雪崩。

### 场景 4：容灾演练验证恢复能力
定期自动执行容灾演练，验证备份可用性和 RTO/RPO 达标率。

## 验收标准

1. **熔断器**：通用 CircuitBreaker 可被任意服务注入使用，支持 3 状态转换 + 指标采集 + 事件通知
2. **消息队列**：支持任务入队/消费、延迟队列、死信队列、消费确认/重试、消费者组
3. **缓存策略**：实现 L1+L2 多级缓存，具备防穿透（空值缓存）、防击穿（互斥锁）、防雪崩（随机 TTL）能力
4. **CI/CD 增强**：Pipeline 执行支持熔断保护 + 缓存加速 + 事件驱动触发
5. **容灾设计**：统一容灾策略引擎，支持 RTO/RPO 监控 + 自动演练 + 报告生成
