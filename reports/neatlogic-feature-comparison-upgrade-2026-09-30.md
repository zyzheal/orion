# NeatLogic ITOM vs Orion 功能详细对比与升级提炼方案

> **生成日期**: 2026-09-30
> **分析对象**: `git@gitee.com:neat-logic/neatlogic-itom-all.git`（v3.x 主线）
> **分析依据**:
> - NeatLogic README 完整功能清单（381 项功能点，8 大模块）
> - 已有分析报告：`neatlogic-benchmark-analysis-2026-07-22.md`（2589 行）
> - 已有分析报告：`neatlogic-itom-deep-analysis-2026-07-22.md`（1202 行）
> - 已有分析报告：`neatlogic-itom-supplement-analysis-2026-07-22.md`（1439 行）
> - 已有分析报告：`docs/analysis/neatlogic-autoexec-vs-orion.md`（200 行）
> **分析结论**: Orion 现有能力覆盖 NeatLogic **~70%** 功能域，但 **深度**（自定义能力、插件生态、参数传递链、审计完备度）仍有系统性差距；本次提炼聚焦"高价值 + 中低工时"的升级项。

## 5. 关键架构模式借鉴

### 5.1 参数传递链（最优先借鉴）

**NeatLogic 模型**:
```
上游 Stage 输出 (Output Parameters)
    ↓ 引用 `${phase1.output.result.ip}`
下游 Stage 参数绑定
    ↓
下游 Stage 执行
```

**Orion 实现方案**:
```go
// internal/pipeline/engine/param_chain.go
type ParamRef string

// 支持的引用语法
// ${stage.<name>.output.<key>}    上游 stage 输出
// ${job.params.<key>}             作业参数
// ${global.<key>}                 全局参数
// ${target.<key>}                 当前 target 属性

type ParamResolver struct {
    upstreamOutputs map[string]map[string]interface{}
    jobParams       map[string]interface{}
    globalParams    map[string]interface{}
}

func (r *ParamResolver) Resolve(ref ParamRef) (interface{}, error) {
    // 解析 ${stage.x.output.y}
    // 递归解析嵌套引用
}
```

### 5.2 剧本 Playbook 层次继承

**NeatLogic 三级**: 应用实例层级 > 子系统环境层级 > 子系统层级

**Orion 实现方案**:
```go
type PlaybookScope string
const (
    PlaybookScopeAppInstance PlaybookScope = "app_instance"
    PlaybookScopeAppEnv      PlaybookScope = "app_environment"
    PlaybookScopeApp         PlaybookScope = "application"
)

// 查找优先级：AppInstance → AppEnv → App → Global
func (s *PlaybookService) Resolve(ctx context.Context, appID, envID, scope PlaybookScope) ([]Playbook, error)
```

### 5.3 采集插件 SPI（可插拔架构）

**NeatLogic 280+ 插件** → 抽象为:

```go
// internal/cmdb-collector/spi.go
type CollectorPlugin interface {
    Name() string                     // e.g., "mysql", "redis", "huawei_vrr"
    Category() CollectorCategory      // Database/Middleware/Network/OS
    Protocol() CollectorProtocol      // SSH/SNMP/HTTP/Agent
    Detect(target *Target) (bool, error)   // 探测目标是否支持
    Collect(ctx context.Context, target *Target, cfg CollectConfig) (*CollectResult, error)
    Meta() CollectorMeta              // 描述/图标/风险等级
}

// 插件注册
type CollectorRegistry struct {
    plugins sync.Map  // name → CollectorPlugin
}
func (r *CollectorRegistry) Register(p CollectorPlugin)
func (r *CollectorRegistry) Find(name string) (CollectorPlugin, bool)
func (r *CollectorRegistry) DetectAndCollect(target *Target) (*CollectResult, error)
```

### 5.4 通知处理器工厂（已实现，需扩展）

已有 `NotifyHandler` 接口 + Factory 模式，需扩展:
- 通知模板引用变量（工单号/标题/状态等）
- 通知动作点自定义（激活/转交/完成/回退）
- 定时催办通知

### 5.5 全局锁 + 条件引擎

借鉴 NeatLogic `GlobalLockManager` + `ConditionDSL`:
- 已具备 Redis 锁基础，可扩展为 `GlobalLockManager` 抽象
- 条件 DSL 用于流程/巡检判断，可基于现有 `expression` 库扩展

## 7. 风险与不采纳项

### 7.1 不采纳项（NeatLogic 有但 Orion 不建议模仿）

| 项 | 原因 |
|----|------|
| **Java + Spring** | 技术栈与 Orion TS/Go 冲突，不迁移 |
| **三库分租户（neatlogic/neatlogic_{tenant}/neatlogic_{tenant}_data）** | Orion PostgreSQL Schema + RLS 更优雅 |
| **MyBatis `@{DATA_SCHEMA}` 动态 SQL** | PG RLS 自动隔离，无需切换 |
| **Tomcat 部署** | Orion Fastify/K8s 部署 |
| **Fair-code 许可** | 无影响，仅参考其模块化思想 |
| **i18nhelper IDE 插件** | Orion 已有独立 i18n 方案 |
| **MongoDB 采集库** | Orion PG 单一存储，无需 Mongo |
| **Nacos 配置中心** | Orion 使用 K8s ConfigMap + Vault |
| **RustFs 附件存储** | Orion 使用 S3/OSS 兼容方案 |

### 7.2 主要风险

| 风险 | 概率 | 影响 | 缓解 |
|------|------|------|------|
| Runner Agent 远程执行安全边界 | 中 | 高 | 严格白名单 + SSH key + Agent 双向认证 |
| 参数链引用循环 | 中 | 中 | 递归深度限制 + 环检测 |
| 图形化流程设计器工时爆炸 | 高 | 中 | 参考现有 React Flow/AntV X6 库，不重复造轮子 |
| CMDB 280+ 插件生态不可能一次做完 | 高 | 中 | 分 Phase，先做 20 个高频插件覆盖 80% 场景 |
| 剧本 Playbook 层次继承数据一致性 | 中 | 中 | 单表 + scope 字段，事务保证 |
| 数据仓库模型复杂度高 | 高 | 中 | 从最简数仓建模开始，逐步增强 |
| 多语言脚本执行沙箱 | 中 | 高 | 容器隔离 + 资源限制 + 超时 |
| 前端设计器工作量 | 中 | 中 | 复用 AntV X6 + 现有组件库 |
