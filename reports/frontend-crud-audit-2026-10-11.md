### API 方法分布（关键发现）

| 方法 | 调用次数 | 覆盖文件数 | 占 client 比例 | 健康度 |
|------|---------|----------|--------------|--------|
| `.get()` | 481 | 85 | 46.5% | ✅ 合理 |

| `.delete()` | **182** | **98** | **53.5%** | ⚠️ **偏高** |

**核心异常**：
- `.update()` 仅 1 次调用 → 前端 CRUD 更新能力**几乎为零**
- `.create()` 0 次调用 → 前端**无显式 create 方法**（通过 `.post()` 隐式调用）
- `.delete()` 182 次 / 98 文件 → 53.5% client 有删除，但**无二次确认审计**

## 2. CRUD 完整性定义

| 操作 | 要求 | 判定标准 | 实测覆盖 |
|------|------|---------|---------|
| **Create** | 创建入口 + 表单 + 保存 | 页面有"新建/创建/Create/Add"按钮 + API 调用 | 646 处（29.5% 页面） |
| **Read** | 列表 + 详情 | 页面有 Table/List/Detail 组件 | 821 处（37.5% 页面） |
| **Update** | 编辑入口 + 编辑表单 + 保存 | 页面有"编辑/Edit/修改/Modify"按钮 + update API | **353 处（16.1% 页面）** |
| **Delete** | 删除按钮 + 二次确认 | 页面有"删除/Delete"按钮 + delete API | 343 处（15.7% 页面） |

**关键问题**：页面级 CRUD 入口覆盖率高（Create 646 / Edit 353 / Delete 343），但 **API 层 `.update()` 仅 1 次** → **页面有编辑按钮但 API 未实现**（隐性融合失败）。

## 4. API 方法覆盖缺口

| API 方法 | 调用次数 | 覆盖 client 数 | 占 client 比例 | 缺口 |
|---------|---------|--------------|--------------|------|
| `.get()` | 481 | 85 | 46.5% | — |
| `.post()` | 399 | 85 | 46.5% | — |
| `.update()` | **1** | **1** | **0.5%** | **严重缺口（应 >80%）** |
| `.create()` | **0** | **0** | **0%** | **完全缺失（应 >60%）** |
| `.delete()` | 182 | 98 | 53.5% | ⚠️ 偏高但合理 |
| `.patch()` | 0 | 0 | 0% | 缺失（可选） |

**关键发现**：
- `.update()` 1 次 / 183 client = **0.55%** → 企业级 CRUD 标准要求 >80%
- `.create()` 0 次 → 前端依赖 `.post()` 隐式创建，**无显式 create 语义**
- `.delete()` 98/183 = **53.5%** → 偏高，需审计二次确认覆盖

## 5. 前后端契约不同步

| 前端方法 | 前端调用次数 | 后端 PUT 端点 | 缺口判定 |
|---------|------------|--------------|---------|
| `.update()` | **1** | 待实测 | **前端无 update，后端 PUT 端点未知** |
| `.create()` | **0** | 待实测 | **前端无显式 create，后端 POST 端点承载** |
| `.delete()` | 182 | 待实测 | 需核对后端 DELETE 端点数量 |
| `.patch()` | 0 | 待实测 | 前端未使用 patch |

**核心风险**：
- 前端 `.update()` 1 次意味着**页面有编辑按钮但 API 未实现** → 用户点击编辑后无保存路径
- 需实测后端 PUT 端点数量：`grep -r 'PUT("' orion-platform-svc-go/internal/`

## 8. API 方法覆盖异常分析

### 8.1 `.update()` 仅 1 次的根因

| 可能原因 | 说明 |
|---------|------|
| 前端使用 `.post()` 承载 update | 非 REST 规范，但功能可用 |
| 前端使用 `.patch()` 但未覆盖 | 实测 `.patch()` = 0 |
| 页面有编辑按钮但 API 未实现 | **最可能**，隐性融合失败 |
| 后端 PUT 端点缺失 | 需实测 |

### 8.2 `.create()` 0 次的根因

| 可能原因 | 说明 |
|---------|------|
| 前端统一用 `.post()` 承载 create | 非 REST 规范，但功能可用 |
| 无显式 create 语义 | 前端 API client 未定义 `.create()` 方法 |

### 8.3 `.delete()` 182 次偏高的根因

| 可能原因 | 说明 |
|---------|------|
| 批量删除功能 | 部分页面支持批量删除 |
| 软删除/状态变更 | 部分"删除"实为状态变更（如归档） |
| 无二次确认 | 部分删除操作缺 Modal.confirm |

## 15. 结论

**核心发现**：
1. **`.update()` 仅 1 次**（0.55% client）→ 前端 CRUD 更新能力**几乎为零**
2. **`.create()` 0 次** → 前端**无显式 create 语义**（依赖 `.post()` 隐式调用）
3. **完整 CRUD 页面仅 6.9%**（~15/219）→ 企业级要求 >80%，差距 73.1pp
4. **页面有编辑按钮但 API 未实现** → 隐性融合失败（用户点击编辑后无保存路径）

**企业级达标度**：前端 CRUD 完整率 **6.9%**（企业级门槛 >80%），差距 **73.1pp**

**修复优先级**：
- **P0**：后端 PUT 端点补齐 + 前端 `.update()` API 定义（解决隐性融合失败）
- **P1**：Delete 二次确认 + loading/error 状态 + List 无 Create 补齐
- **P2**：`.create()` 显式语义 + `.patch()` 方法定义
