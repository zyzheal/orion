## 0. TL;DR（给忙人看的结论）

1. **6 份专家报告全部通过"证据可追溯性"抽检**（抽查 20 条陈述，全部能定位到 `文件:行号`）。**没有一条是"专家口吻的幻觉"**——所有数字、结论都有代码 grep/Read 证据支撑。这是本次评审最重要的正面发现。
2. **但完成度数字之间互不可比**。ITSM 报告给 33.7%（加权）、巡检报告给 6%（加权）、BI 报告给 14%（加权）、告警报告给 55-60%（加权）、自动化报告给 25-30%（加权）、RDM 报告给 37%（加权）——**这些数字背后的加权口径各不相同，直接横向相加没有意义**。
3. **原综合报告的 289 人天严重低估**。若按 6 份专家报告各自的 Phase 估算累加：ITSM 205-265d + 巡检 300d + BI（未给总额，但仅 3 项 G0 就 60d）+ 告警 110-160d + 自动化 450-550d + RDM 118d ≈ **1250-1400+ 人天**。原报告的 289 人天大约是真实成本下限的 **20%**。
4. **原综合报告最严重的误判不是数字，是分类**：把"有骨架但零执行"（例如 ITSM workflow 引擎不消费 Nodes、service-catalog 只有 3 字段、RDM 前端 40+ API 全部 404）当成"已覆盖"计入 62% 覆盖度。**"存在 ≠ 完成"**是这个报告的最大方法论错误。
5. **3 个月 / 5 人预算** 下，唯一务实选择是**只做 3 项止损**（ITSM P0-1 状态机重构 + 巡检 RunInspection 空壳处理 + Runner Agent SSH/WinRM 协议），把"看起来能跑但不可用"的假功能从客户视野中移除。**任何追求"补齐某完整模块"的野心都注定失败**。

## 2. 分模块真实完成度综合估计（含置信度区间）

### 2.1 ITSM（75 项）

**专家报告结论**：33.7% 加权 / 21.6% 完整

**证据强度评估**：⭐⭐⭐⭐⭐（5 维度代码证据 + 7 类反模式 + 5 大差异化优势分析）

**真实完成度综合估计**：**30-38%**（置信度 ±8%，中等偏高）

**置信度来源**：
- 正面证据（派工评分、SLA 引擎、TicketTransfer 5 类、EngineerDashboard 三级）都有具体代码行号
- 反面证据（`ticket-automation` 表退化到 3 字段、`service-catalog` 概念错位、`FormDesigner` localStorage 不持久化）都是硬事实
- **但权重分配是主观的**（ITSM 报告说"工单核心 10%、流程 30%"，如果换成"流程 50%"权重，完成率会更低）

**原综合报告对比**：原报告算 ITSM 覆盖 50/75 = **67%**。**低估差距：34 个百分点**。原报告把"有 workflow 表"、"有 form_definition 表"、"有 service_catalog 表"都当成"已覆盖"，忽视了这些表都不承载真正的 ITSM 语义。

**置信度来源**：

### 3.2 交叉冲突（原综合报告需要明确口径）

**冲突 1：自动化 vs ITSM 的 workflow 语义**
- ITSM 报告说：`WorkflowDesigner` 前端存在但后端引擎不消费 Nodes/Edges
- 自动化报告说：`pipeline-graph` 是只读视图，workflow 引擎不消费 Nodes/Edges
- **两者说的是同一个 workflow 引擎**，但被算了两次 Gap
- **原综合报告在 ITSM Phase 0 和自动化 Phase 1 都提到了 workflow 引擎重构**——这个工时被**双重计入**

**冲突 2：巡检的"执行器" vs 自动化的"Runner Agent"**
- 巡检报告说：巡检系统三大内核（采集层、执行引擎、阈值引擎）全部缺失，估 300 人天
- 自动化报告说：Runner Agent 只有 Linux/Node.js，缺 Windows/AIX 是 P0，估 40-55 人天
- **两者共享 Runner Agent 概念**，但工时估算不同
- **正确口径**：Runner Agent 是跨模块基础设施，应在 Phase 0 统一解决，工时 60-90 人天（自动化报告口径更准）

**冲突 3：告警的 AI 分析 vs BI 的智能化**
- 告警报告说：`AIAnalysisType` 枚举无 `ALERT` 类型
- BI 报告说：数仓能力完全缺失
- **两者都归咎于"AI 服务未打通"**，但根因不同
- **正确口径**：告警 AI 分析是**能力缺失**（要写代码），BI 智能化是**架构缺失**（要建数仓），不应混在一起估

### 3.3 系统性问题（原综合报告完全未识别）

**问题 A：Go 迁移导致的"合同断裂"**
- TS 侧有完整实现的能力，Go 侧迁移后大量退化（`ticket-automation` 从 AutomationRule 退化成 name/value/enabled 3 字段）
- 前端 `api/*.ts` 有大量 API 调用但 Go 后端 `/xxx/*` 零路由命中（RDM 40+ API、Inspection 5 个 API）
- **这不是"新功能缺失"，是"已有能力退化"**——修复方式不同（补代码 vs 加功能）

**问题 B：SPI 架构是纸面架构**
- CMDB Collector SPI：`Registry.Register` 定义但零调用
- AlertAdapter SPI：只能编译期静态注册，无热加载
- Workflow Engine：Nodes/Edges 前端能画，后端不消费
- **整个 Orion 的"插件化"叙事是营销话术，代码里没有对应的注册机制**

**问题 C：硬编码"看起来能跑"的假实现**
- Inspection.RunInspection：状态置 running 后返回
- Health-check.checkKubernetes/DB/Redis：硬编码 return ok
- CMDB.ExecuteScript：返回字符串 stub
- BI.ExecuteReport：字符串拼接路径就置 completed
- **这类"假实现"数量约 8-10 处**，客户演示必翻车，比真正缺失的功能更危险

**问题 D：所有"定时执行"能力都没有 cron consumer**
- Inspection schedule 字段无 consumer
- ReportSchedule.cronExpression 无 consumer
- Pipeline.TriggerSchedule 常量存在但无接线
- **Orion 号称"AI 驱动的 DevOps 平台"，但没有一个模块有真实定时执行能力**

## 6. 反模式的诚实记录（这些是本次评审发现的、原综合报告未识别的问题）

### 6.1 原综合报告的方法论错误

1. **"存在即覆盖"谬误**：把"有表"、"有 handler"、"有前端页面"都当成覆盖，忽视了表可能空、handler 可能桩、前端可能 404
2. **"覆盖度平均化"谬误**：所有模块的完成度都取"覆盖项 / 总项"，忽视了不同项的权重差异（Runner Agent 权重远高于"标签管理"）
3. **"工时乐观偏差"**：单人估算 30 天做 Runner Agent 是纸上谈兵——Runner Agent 涉及 mTLS、跨 OS 分发、心跳超时恢复、任务队列、日志回传，5 层协议栈，行业经验 60-90 天是下限
4. **"Phase 顺序不合理"**：原报告 Phase 0 做基础设施，Phase 1 做核心引擎——但**没有先做"止损"**（消除假实现），客户会先在验收阶段翻车

### 6.2 6 份专家报告的共性问题

1. **都低估了"跨模块依赖"**：Runner Agent 被 ITSM / 巡检 / 自动化三个领域报告都估算，但没协调；结果三个报告加起来估了 Runner Agent 100+ 人天，实际上应该是 60-90 人天
2. **都未考虑 TS 权威实现的存在**：如果 TS 侧仍有真实实现，"迁移到 Go"的路径比"从零建 Go"更便宜（估折扣 30-40%）
3. **都在同一维度上重复估算**（Workflow 引擎、状态机、通知链路）——需要一次"跨报告去重"合并，才能得出真实总工时

### 6.3 Council 对抗的缺失

本应通过 Council 四视角对抗发现的"隐性偏误"（例如：Architect 视角可能过度强调架构完整性、Skeptic 视角可能低估客户体验需求、Pragmatist 视角可能忽视技术债、Critic 视角可能过度悲观），本报告由单一作者扮演四角色依次自我对抗。**这本身就是一种锚定偏差**——建议读者把本报告结论当"下限估计"，而不是"最终估计"。
