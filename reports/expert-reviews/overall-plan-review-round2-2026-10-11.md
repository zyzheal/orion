### 不足 2.1：§13 新增 17 项任务未纳入 S0-S8 依赖 DAG（P0）

**具体依赖问题**：
1. **P1-4（前端 CRUD）依赖后端 PUT 端点**：`.update()` 实测只有 3 次，需要后端提供 PUT 端点。但方案中后端 PUT 端点新增任务**未列入 17 项**（G1 §2.5 R-P0-06 是 API 治理，但不针对 PUT 端点补齐）
2. **P1-5（OpenAPI 契约）依赖所有后端模块 API 稳定**：应依赖 S4-S6 完成，但 Y 手册 §13.5 P1-5 未标注前置依赖

4. **P0-5（CLAUDE.md 契约修正）已完成**（`CLAUDE.md:187` 已改为 81 项、`CLAUDE.md:188` 已改为 699-765 全部空号），但 §13.6 未反映最新状态

**方案层缺失**：§13 新增任务**没有独立 DAG**，也未合并入 §5.1 主 DAG，执行时会遗漏依赖关系。

### 不足 2.2：ADR-011 依赖链被过度串行化（P1）

**事实依据**：
- `CLAUDE.md:191` 推荐执行入口：ADR-011 → ADR-013 → ADR-014 → ADR-010 → ADR-012
- Y 手册 §4.2 S0-T2 依赖 ADR-011；S0-T4 依赖 ADR-012；S2-T3 依赖 ADR-013
- 但 ADR-010/012/014 之间**技术上无强依赖**（AlertBreaker、Factory Handler、ArtifactBus 是独立模块）

**方案层问题**：串行化会把 4 个 ADR 变成 4×N 周期而非 max(N) 周期。大厂并行实践会：
- Wave 1 并行：ADR-011（多租户，最重）+ ADR-013（CMDB，独立）
- Wave 2 并行：ADR-012（Factory，独立）+ ADR-014（ArtifactBus，需要 ADR-012 前置）
- Wave 3：ADR-010（AlertBreaker，依赖 ADR-012 的 Handler 注册表模式）

**影响**：方案估计 44 天，实际按 DAG 依赖可压缩到 32-36 天（约 20% 提速）。

### 不足 2.3：S7 RDM 止损阶段前置依赖不完整（P1）

**事实依据**：
- Y 手册 §4.8 S7-T3 声明"前置依赖：S7-T1 + S7-T2 + S2-T10"
- 但 S2-T10 是"RDM 前端 4 Tab 契约"，其 API 依赖 `internal/rdm/reporting`、`internal/rdm/code-review` 两个后端模块
- 实测 `find internal/rdm -name "*.go"` 只有 15 个文件，且 reporting/code-review 模块**实际不存在**

**方案层缺失**：S7-T3 依赖"后端 2 个模块先创建"，但这个前置任务**未在 DAG 中标注**。S7 应依赖 S2-T10 完成 + 后端 rdm/reporting 与 rdm/code-review 模块创建（这两个模块当前完全不存在）。

### 不足 2.4：跨批次任务并行度不足（P2）

**事实依据**：
- Y 手册 §4.11 分批 8 批共 39 子域
- 但分批策略是**按模块**串行（第 2 批 CMDB → 第 3 批 ITSM → ... → 第 8 批 RDM）
- 大厂经验：模块之间无强耦合，可以 3-4 批并行

**具体例子**：
- 第 2 批 CMDB（4 子域，`cmdb-import`/`cmdb-drift`/`cmdb-sync`/`cmdb-lineage`）
- 第 4 批 BI（3 子域，`bi-dashboard`/`bi-report`/`bi-semantic`）
- 第 5 批告警（3 子域，`alert-dedup`/`alert-inhibit`/`alert-escalation`）
- **这 3 批在技术方案上完全无依赖**，可并行执行

**影响**：48 子域分批补齐从 8 波串行 → 可压缩到 3-4 波并行，节约 40-60% 执行周期。

## 维度 5：可执行性

### 不足 5.1：35 项门控中 20+ 项是 grep 验证，缺乏失败降级策略（P0）

**事实依据**：
- 40 个 `# 门控` 标注（Y 手册 §4），全部或大部分是 grep 验证
- 例如 S0-T1 门控："grep ALL_CAPS error codes"
- 但 grep 验证的**基线对照缺失**：例如"aria-label ≥ 200 处"——如果当前是 20 处，加到 200 处后如果 ESLint 报错怎么办？门控的失败降级策略是什么？

**方案层缺失**：门控应有 3 层：
1. **主验收标准**（grep 具体数字）
2. **失败降级策略**（例如：aria-label 无法到 200 时，是否降级到 100？还是先跳过阻塞 ESLint？）
3. **回滚步骤**（当前多数任务有回滚，但门控本身无回滚——门控失败后怎么恢复？）

### 不足 5.2：门控期望值数字与实测不一致（P0）

## 维度 7：度量与验收

### 不足 7.1：门控期望值多为"数字目标"，缺乏"质量目标"（P0）

**事实依据**：
- Y 手册 §6.1 每阶段出口检查项（第 1876 行）多数是"grep 数字达标"
- 例如 S1-T1 门控：`aria-label >200`、`tabIndex >50 处 = 0`
- 但**"完成"的质量定义缺失**：
  - aria-label >200 处**质量达标**的标准是什么？是"每个 button 都有 aria-label"还是"每个交互元素都有关联 label"？
  - tabIndex >50 处 = 0 只是**位置约束**，不保证键盘导航可用性

**方案层问题**：门控是**数量化验收**，但缺少**质量化验收**。大厂经验：数量化验收应配合抽样验证（例如随机抽 20 个 button 验证 aria-label 语义正确）。

### 不足 7.2：无阶段间"回归验证"机制（P1）

**事实依据**：
- Y 手册 §5.1 依赖 DAG（第 1774 行）只标"前置依赖"，未标"回归验证"
- 例如 S3 完成新模块后，是否要回归 S2 的 CMDB CI？是否要回归 S0 的 TenantContext？
- 大厂经验：每完成一个阶段，应触发**全链路回归测试**（至少覆盖前 3 个阶段的门控）

**方案层问题**：方案未定义阶段间的回归测试范围。执行到 S3 时可能不知道要回归 S0/S1/S2 的检查项。

### 不足 7.3：98 项任务中约 20% 无独立 DoD（P1）

**事实依据**：
- Y 手册 §4.11 分批 8 批共 39 子域任务卡（第 1574 行开始）
- 每个任务卡仅列"目标路径 / API 契约 / Migration / grep 验证"，**无独立 DoD**
- 例如 §4.11.1 第 2 批 CMDB 4 子域（`cmdb-import`/`cmdb-drift`/`cmdb-sync`/`cmdb-lineage`）每张任务卡只有 grep 命令，无"完成定义"

**方案层问题**：39 子域任务卡是"任务描述"而非"任务定义"，执行者按描述做可能做出不同结果。

### 不足 7.4：无跨文档一致性回归（P1）

**事实依据**：
- INDEX v5.4、G1 v1.1、Y v5.6、ADR-010~015、CLAUDE.md 5+ 份文档
- 5+ 份文档之间存在多处口径不一致（本轮发现 5 处）
- 但**方案无"每次修改文档后自动同步到其他文档"的机制**

**具体不一致**（本轮实测）：
1. CLAUDE.md 契约条款 2："Y = 81 项"，实际 Y v5.6 = 98 项
2. CLAUDE.md 契约条款 5："Stage Gate 35 项"，实际 Y 手册 `# 门控` = 40 项
3. Y 手册 §1 声明 81 项，§13.6 声明 98 项
4. G1 §2.2 声明"68 项"，G1 §2 声明"134 项"，去重后 98 项
5. ADR-015 状态"待决策"但已产出骨架，是否应改为"提案中"？

**方案层问题**：文档一致性依赖人工同步，无自动化工具。大厂经验：文档间的口径一致性应该用 CI 校验（例如脚本检查 "任务数 = 81" 在所有文档中一致）。

### 不足 7.5：v5.6 §13 新增 17 项任务无独立验证命令（P1）

**事实依据**：
- Y 手册 §13 新增 17 项任务（第 2500-2730 行）每项有"验证方式"字段
- 但**没有独立的 bash 命令**（相比 §4.1 S0-T1 有完整 grep 命令）
- 例如 P0-5 "CLAUDE.md 契约条款 2/3 修正"的验证方式：`grep -n "任务数口径差异\|Migration 号段" CLAUDE.md`——**无具体 grep 模式**，实际验证困难

### 不足 7.6：验收标准无"负向验证"（P2）

**事实依据**：
- 大多数门控是"某字段存在"（正向验证）
- 但缺少"某字段不应存在"（负向验证）
- 例如 S0-T1 门控应有"throw new Error 不应存在"，但只写了"ALL_CAPS error codes 存在"

**方案层问题**：负向验证是发现隐藏问题的关键（例如：某个遗留文件偷偷用了 `throw new Error`）。

## 关键结论

### 方案整体评估

- **优点**：Y 手册 v5.6 已建立较完整的执行框架（98 项任务 + 40 门控 + 完整 DAG + 每任务 grep 验证 + 每任务回滚）；v5.6 §13 主动引入 17 项新增任务，说明方案有演进机制
- **致命问题**：
  1. **契约一致性 4/10**：4 份文档 5 处口径矛盾（Y 版本、任务数、门控数、ADR 数、状态），执行时会出现"我不知道按哪个执行"
  2. **方案-工程脱节 3/10**：98 项任务中 6 项与实测代码状态冲突（CMDB attribute 不存在、Migration 699-765 空号、alert-adapter-v2 无迁移决策、Repository 92.9% 与方案 69.9% 差异）
  3. **对第一轮评审吸收率仅 8%**：12 项 P0/P1 建议只吸收了 1 项（P0-2 Migration 号段）
- **不可持续**：若不做本轮修正，方案进入执行阶段后**大概率在第 1 周卡死**（因 Migration 699-765 空号 + 契约矛盾无法收敛）
