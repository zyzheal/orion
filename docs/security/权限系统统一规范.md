## 1. 认证设计（JWT）

> 权威来源：`docs/security/认证授权与数据加密设计.md`

### 1.1 双 Token 架构

| 属性 | Access Token | Refresh Token |
|------|-------------|---------------|
| 有效期 | **5 分钟** | 7 天 |
| 签名算法 | **RS256**（非对称） | HS256（对称） |
| 存储位置 | **HttpOnly Cookie**（前端不可访问） | 服务端 Redis（前端不存储，通过 HttpOnly Cookie 传递） |
| 包含信息 | user_id, roles, tenant_id, permissions, exp, jti | user_id, device_id, exp, jti |
| 用途 | API 请求认证 | 刷新 Access Token |

### 1.2 JWT Payload 结构

```json
// Access Token Payload
{
  "sub": "user_123",
  "user_id": "12345",
  "tenant_id": "tenant_001",
  "roles": ["developer", "tech_lead"],
  "permissions": ["pipeline:run", "approval:view"],
  "team_ids": ["team_001", "team_002"],
  "iat": 1712736000,
  "exp": 1712736300,
  "jti": "unique_token_id"
}

// Refresh Token Payload
{
  "sub": "user_123",
  "user_id": "12345",
  "device_id": "device_abc",
  "jti": "unique_token_id_refresh",
  "iat": 1712736000,
  "exp": 1713340800
}
```

### 1.3 Token 刷新流程

```
前端检测 Access Token 即将过期（过期前 2 分钟）
    │
    ▼
POST /auth/refresh
Cookie: refresh_token=xxx
    │
    ▼
服务端验证：
  1. 检查 Redis 黑名单
  2. 验证 Refresh Token 签名
  3. 检查设备 ID 匹配
  4. Redis Lua 原子操作检测并发刷新
    │
    ▼
验证通过 → 生成新 Token 对
  • 新 Access Token (5 分钟)
  • 新 Refresh Token (7 天，轮换)
  • 旧 Refresh Token 立即失效
    │
    ▼
Set-Cookie: access_token=xxx; HttpOnly; Secure; SameSite=Strict
Set-Cookie: refresh_token=xxx; HttpOnly; Secure; SameSite=Strict
```

### 1.4 并发刷新保护（P0 安全修复）

> 来源：`docs/security/安全与权限详解.md` P0 修复章节

```lua
-- Redis Lua 脚本：并发刷新检测
local current = redis.call('GET', key)
if current == token then
    return redis.call('SET', key, new_token)
else
    -- 并发刷新检测，全部吊销
    redis.call('DEL', key)
    return 'REVOKED'
end
```

### 1.5 Token 吊销

- **存储**：Redis（快速查找）+ DB（持久化）
- **Key 格式**：`token:blacklist:{jti}`
- **TTL**：Token 剩余有效期
- **触发场景**：用户登出、密码修改、账号禁用、异常登录、密钥泄露

### 1.6 算法迁移路线

| 阶段 | 状态 | 说明 |
|------|------|------|
| 当前 | HS256（对称） | Go 实现现状 |
| Phase 1 | HS256 + RS256 双支持 | 新 Token 用 RS256 签发，旧 Token 仍可验证 |
| Phase 2 | RS256 Only | 所有 HS256 Token 过期后，移除 HS256 支持 |

## 4. ABAC 属性模型

> 权威来源：`docs/architecture/rbac-abac-unified-implementation.md` 第 5 章

### 4.1 语义定义

**ABAC 是 deny-only 约束层**：
- RBAC 是基础准入——角色有权限则通过，无权限则拒绝
- ABAC 是额外约束——仅当有匹配的 **deny 策略**时才拒绝
- 无匹配的 allow 策略时**不拒绝**（避免新资源类型因缺少 ABAC 策略而被误拒）
- `super_admin`（`*:*`）跳过 ABAC 检查

### 4.2 预置 ABAC 策略

| # | 策略 ID | 名称 | 效果 | 条件 | 优先级 |
|---|---------|------|------|------|--------|
| 1 | `resource-owner-full-control` | 资源所有者完全控制 | allow | `resource.owner == user.id` | 100 |
| 2 | `tenant-isolation` | 租户隔离 | deny | `resource.tenantId != user.tenantId` | 99 |
| 3 | `restricted-resource-access` | 敏感资源访问限制 | allow | `resource.sensitivity == 'restricted'` AND (`user.role in [admin,security]` OR `user.department == resource.department`) | 90 |
| 4 | `external-network-restriction` | 外部网络写操作限制 | deny | `environment.network == 'external'` AND `action in [create,update,delete,execute]` | 80 |
| 5 | `working-hours-restriction` | 关键操作时间限制 | deny | `action.impact in [high,critical]` AND NOT 工作时间(9-18) AND `user.role != admin` | 70 |
| 6 | `cross-department-restriction` | 跨部门访问限制 | deny | `resource.department != user.department` AND `user.role != admin` | 60 |

### 4.3 决策流程

```
请求进入
  │
  ├─ [0] 认证检查: JWT 有效？→ 无效 → 401
  │
  ├─ [1] 用户状态: disabled/suspended？→ 403
  │
  ├─ [2] RBAC: 角色是否有 resource:action 权限？
  │     └─ deny → 403
  │     └─ allow → 继续
  │
  ├─ [3] ABAC: 评估 deny-only 策略
  │     └─ 有 deny 匹配 → 403
  │     └─ 无 deny 匹配 → 继续
  │
  ├─ [4] 关系检查: 是否 owner/项目成员？
  │     └─ deny → 403
  │     └─ allow → 继续
  │
  └─ [5] 全部通过 → 放行 + 审计日志
```

**合并策略**：Deny Override（拒绝优先）— 任何一层拒绝即最终拒绝。

## 5. 租户隔离

> 权威来源：`docs/cross-cutting/architecture/tenant-isolation-implementation-design.md`

### 5.1 三层隔离架构

```
Layer 1: API Gateway     → 验证 JWT，注入 X-Tenant-ID header
Layer 2: Auth Middleware  → 从 JWT 提取 tenant_id 到 context
Layer 3: Repository 基类 → 所有查询强制 WHERE tenant_id = $1
Layer 4: PostgreSQL RLS  → 即使代码绕过也有 DB 层拦截
```

### 5.2 当前实现状态

| Layer | 状态 | 说明 |
|-------|------|------|
| Layer 1 (Gateway) | 部分实现 | API Gateway 有 JWT 验证 |
| Layer 2 (Middleware) | **已实现** | `orion-go-common/pkg/auth/middleware.go` |
| Layer 3 (Repository) | **已实现** | `orion-go-common/pkg/database/repository.go` 强制 tenantID |
| Layer 4 (RLS) | **未实现** | 需要 PostgreSQL RLS 策略 |

### 5.3 实施路线

| 阶段 | 时间 | 内容 |
|------|------|------|
| Phase 1 | 当前 | Application-level 隔离（Layer 2+3），审查所有自定义 SQL 补漏 tenant_id |
| Phase 2 | 3-6 个月 | PostgreSQL RLS（Layer 4）作为纵深防御 |
| Phase 3 | 6-12 个月 | K8s NS Pool（Layer 1 增强） |

## 6. SSO 与认证集成

> 权威来源：`docs/security/安全与权限详解.md` 第 1-2 章

### 6.1 SSO 登录流程

```
浏览器 → 302 → SSO 登录
    │
    ▼
SSO 回调 → Orion 换取 Token
  a. 验证 state 防 CSRF
  b. POST /token 换取 Access Token
  c. GET /userinfo 获取用户信息
  d. 查询用户是否存在 → 不存在则自动创建
  e. 从 HR 系统同步用户角色和部门
  f. 生成 Orion Session Token (JWT)
  g. 设置 HttpOnly Cookie
```

### 6.2 支持的认证方式

| 方式 | 状态 | 说明 |
|------|------|------|
| 用户名/密码 | **已实现** | `orion-auth-svc` Login handler |
| LDAP | **Stub** | 框架在，需接入真实 LDAP 服务器 |
| 企业微信 | **Stub** | 框架在，需接入真实 WeChat Work API |
| SSO/OIDC | **未实现** | 需要实现标准 OIDC 流程 |

### 6.3 HR 自动同步

- 新入职 → 自动创建账号 + 分配默认角色
- 转岗 → 更新部门和权限
- 离职 → 自动禁用账号 + 转移待审批

## 7. 审计与防篡改

> 权威来源：`docs/security/安全与权限详解.md` 第 5 章

### 7.1 防篡改三重保障

1. **链式 Hash**：每条日志包含前一条的 Hash，修改任意一条 → 后续所有 Hash 不匹配
2. **定期签名**：每小时用私钥对日志块签名
3. **三重存储**：Elasticsearch（可搜索）+ S3 Object Lock（WORM）+ 独立日志服务器

### 7.2 权限审计日志

```sql
CREATE TABLE permission_audit_logs (
  id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id       UUID REFERENCES tenants(id),
  user_id         UUID REFERENCES users(id),
  resource_type   VARCHAR(100),
  resource_id     UUID,
  action          VARCHAR(50),
  decision        VARCHAR(10) CHECK (decision IN ('allow', 'deny')),
  decision_source VARCHAR(50),  -- 'rbac', 'abac', 'relationship', 'rls'
  reason          TEXT,
  evaluated_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

## 8. UEBA 异常行为检测

> 权威来源：`docs/security/安全与权限详解.md` 第 6 章

| 规则 | 条件 | 严重级别 | 动作 |
|------|------|---------|------|
| 大量数据导出 | 1h 内导出 > 10 次 | HIGH | 告警 + 拦截 |
| 越权尝试 | 30min 内权限拒绝 > 20 次 | CRITICAL | 告警 + 锁账号 |
| 非工作时间访问敏感资源 | 非 9-18 点 + 访问 prod/secrets | MEDIUM | 告警 |
| API 调用模式异常 | ML 异常分数 > 0.8 | MEDIUM | 告警 |
| 多地同时登录 | 同一账号 > 3 个不同 IP | MEDIUM | 告警 |
| 服务账号滥用 | 服务账号被人类直接使用 | HIGH | 告警 + 吊销 |

## 10. Go 微服务实现规范

### 10.1 认证中间件

所有 Go 服务使用 `orion-go-common/pkg/auth` 包：

```go
import "orion/go-common/pkg/auth"

// 路由组使用 Auth 中间件
v1 := r.Group("/api/v1")
v1.Use(auth.Auth(auth.AuthConfig{
    JWTSecret:   cfg.JWTSecret,
    RedisClient: rdb,
    SkipPaths:   []string{"/healthz", "/auth/login"},
}))
```

### 10.2 RBAC 路由守卫

```go
// 仅 admin 可访问
admin := v1.Group("/admin")
admin.Use(auth.RequireAnyRole("super_admin", "platform_admin", "tenant_admin"))

// 特定角色可访问
pipeline := v1.Group("/pipelines")
pipeline.POST("", auth.RequireAnyRole("super_admin", "org_admin", "tech_lead"), handler.Create)
pipeline.PUT("/:id", auth.RequireAnyRole("super_admin", "org_admin", "tech_lead"), handler.Update)
pipeline.DELETE("/:id", auth.RequireRole("super_admin"), handler.Delete)
pipeline.GET("", handler.List) // 所有已认证用户可读
```

### 10.3 租户隔离

```go
// Handler 层从 context 获取 tenant_id
func (h *Handler) List(c *gin.Context) {
    tenantID := auth.GetTenantID(c)
    items, err := h.repo.ListByTenant(ctx, tenantID)
    // ...
}

// Repository 层所有查询强制 tenant_id
func (r *Repo) ListByTenant(ctx context.Context, tenantID string) ([]Model, error) {
    var items []Model
    err := r.db.SelectContext(ctx, &items,
        "SELECT * FROM items WHERE tenant_id = $1 AND status != 'deleted'", tenantID)
    return items, err
}
```
