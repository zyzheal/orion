## 执行摘要 (Executive Summary)

本设计文档详细描述 Orion 平台 AI 能力的成本控制体系。随着 AI 功能在平台中的广泛应用（智能代码生成、自动化测试、智能问答、日志分析等），Token 消耗成本呈指数级增长，亟需建立完善的成本管控机制，实现"成本可视、预算可控、优化可行"的目标。

### 成本管控核心目标

| 目标维度 | 当前状态 | 目标状态 | 衡量指标 |
|---------|---------|---------|---------|
| **成本可视性** | 无统一计费，无法追溯 | 实时计量，按维度分摊 | 100% 成本可追溯 |
| **预算控制** | 无预算限制，无限消耗 | 多级预算，分级告警 | 预算超支率<5% |
| **成本优化** | 无优化策略，大模型优先 | 智能路由，缓存复用 | 单位成本降低 30% |
| **ROI 评估** | 无法评估 AI 投入产出 | 工时节省量化，ROI 计算 | ROI>1.5 |

### 预期收益量化

| 指标 | 实施前 | 实施后目标 | 改善幅度 |
|------|--------|-----------|---------|
| 月度 AI 成本 | 无管控，$50,000+/月 | 预算内，$35,000/月 | 30% 降低 |
| 成本可追溯率 | <20% | 100% | 5x |
| 预算超支事件 | 频发（月均 3-5 次） | 罕见（<1 次/季度） | 80% 降低 |
| Token 利用率 | 60%（重复调用多） | 85%（缓存复用） | 42% 提升 |
| 小模型占比 | 15% | 50% | 3.3x |

## 一、设计背景与问题分析 (Background and Problem Analysis)

### 1.1 AI 成本增长趋势分析

随着 Orion 平台 AI 能力的深度集成，Token 消耗呈现爆发式增长：

| 季度 | AI 调用量 (万次/月) | Token 消耗 (亿/月) | 月度成本 (美元) | 环比增长 |
|------|-------------------|------------------|----------------|---------|
| 2025 Q4 | 50 | 2.5 | $12,500 | - |
| 2026 Q1 | 120 | 6.0 | $30,000 | 140% |
| 2026 Q2 | 200 | 10.0 | $50,000 | 67% |
| 2026 Q3 (预测) | 350 | 17.5 | $87,500 | 75% |

**问题**: 成本增速超过业务价值增速，亟需建立成本管控体系。

### 1.2 当前问题分析

#### 1.2.1 成本黑洞问题 (Cost Black Hole)

| 问题表现 | 影响范围 | 严重程度 |
|---------|---------|---------|
| 无法追溯哪个租户消耗最多 | 财务无法分摊成本 | 高 |
| 无法识别哪个 AI 功能最烧钱 | 无法优化高成本功能 | 高 |
| 无法评估 AI 投入产出比 | 无法决策资源投入 | 高 |
| 无法预测月度成本 | 预算编制困难 | 中 |

#### 1.2.2 预算失控问题 (Budget Overrun)

| 场景 | 当前行为 | 期望行为 |
|------|---------|---------|
| 租户 A 单日用量超月预算 | 无限制，继续调用 | 触发限流，告警通知 |
| 项目 B 预算耗尽 | 无感知，继续消耗 | 自动降级，申请追加 |
| 部门 C 多项目共享预算 | 无法拆分统计 | 按项目分摊，独立核算 |

#### 1.2.3 资源浪费问题 (Resource Waste)

| 浪费类型 | 占比 | 原因分析 |
|---------|------|---------|
| 重复调用相同 Prompt | 25% | 无缓存机制，相同问题重复调用 |
| 大模型处理简单任务 | 35% | 无智能路由，一律调用最大模型 |
| Prompt 冗余过长 | 20% | 无压缩优化，上下文包含无关信息 |
| 失败重试无限制 | 10% | 无重试策略，无限重试消耗 |
| 闲置连接占用 | 10% | 连接池管理不当 |

### 1.3 业界最佳实践参考

| 公司 | 实践案例 | 关键经验 |
|------|---------|---------|
| **GitHub Copilot** | 按用户分级配额 + 企业预算池 | 个人配额防止滥用，企业池保证协作 |
| **Cursor** | 本地缓存 + 小模型优先路由 | 相同上下文复用，简单任务用小模型 |
| **Replit** | 实时成本展示 + 预算告警 | 用户实时看到消耗，主动控制用量 |
| **Amazon Bedrock** | 按 Token 类型差异化计费 | 输入/输出 Token 成本分开计算 |
| **Azure OpenAI** | 租户级配额 + 速率限制 | 多层级限流防止突发流量 |

## 二、设计目标与原则 (Design Goals and Principles)

### 2.1 设计目标

#### 2.1.1 业务目标

| 目标 | 当前状态 | 目标状态 | 衡量指标 |
|------|---------|---------|---------|
| 成本可控 | 无预算限制 | 多级预算管控 | 预算执行率 95-105% |
| 成本可溯 | 20% 可追溯 | 100% 可追溯 | 按租户/项目/用户分摊 |
| 成本优化 | 无优化策略 | 智能优化 | 单位成本降低 30% |
| ROI 可视 | 无法评估 | 量化评估 | ROI 报告月产出 |

#### 2.1.2 技术目标

| 目标 | 当前状态 | 目标状态 | 衡量指标 |
|------|---------|---------|---------|
| 计费精度 | 无计费 | 实时计费 | 误差率<0.1% |
| 告警延迟 | 无告警 | 实时告警 | 告警延迟<10s |
| 限流响应 | 无限流 | 毫秒级限流 | 限流响应<100ms |
| 数据采集 | 无采集 | 全量采集 | 数据完整率 100% |
| 系统开销 | - | <5% | 成本控制自身成本<5% |

### 2.2 设计原则

| 原则 | 说明 | 验证标准 | 违反示例 |
|------|------|---------|---------|
| **实时性优先** | 成本数据实时采集、实时计算 | 延迟<10 秒 | T+1 出账单 |
| **精度保证** | Token 计数精确到个位 | 误差率<0.1% | 估算用量 |
| **多级预算** | 租户 - 项目 - 用户三级预算 | 支持任意层级独立预算 | 单一预算池 |
| **分级告警** | 50%/80%/100% 三级告警 | 告警准确率>99% | 仅 100% 告警 |
| **优雅降级** | 预算超支后有限服务 | 核心功能可用 | 直接拒绝服务 |
| **成本透明** | 用户实时可见消耗 | Dashboard 实时更新 | 月度账单 |
| **优化自动** | 系统自动选择最优策略 | 无需人工干预 | 手动配置规则 |

### 4.3 计费公式定义

```
// 单次调用费用计算
单次调用总费用 = 输入 Token 费用 + 输出 Token 费用

输入 Token 费用 = (输入 Token 数 / 1000) × 输入 Token 单价
输出 Token 费用 = (输出 Token 数 / 1000) × 输出 Token 单价

// 考虑折扣（企业协议）
实际费用 = 单次调用总费用 × (1 - 折扣率)

// 预算扣减
租户预算扣减 = 实际费用 × 租户分摊比例
项目预算扣减 = 实际费用 × 项目分摊比例
用户配额扣减 = 实际费用 × 用户分摊比例

// 成本分摊（多租户场景）
总成本 = Σ(各租户实际费用)
租户 A 分摊成本 = 总成本 × (租户 A 用量 / 总用量)
```

### 4.4 Token 计数策略

| 策略 | 说明 | 实现方式 | 精度 |
|------|------|---------|------|
| **精确计数** | 使用 LLM 提供商官方 Tokenizer | 各语言 SDK 内置 | 100% |
| **估算计数** | 字符数/TOKEN 比率估算 | 英文 4 字符≈1 Token | 90-95% |
| **缓存命中** | 相同 Prompt 直接返回缓存 Token 数 | Prompt Hash 匹配 | 100% |
| **流式累加** | 流式响应逐段累加 | SSE 事件累加 | 100% |

### 6.2 分摊规则定义

| 分摊场景 | 分摊规则 | 计算公式 | 适用场景 |
|---------|---------|---------|---------|
| **租户分摊** | 按实际用量比例 | 租户分摊 = 总成本 × (租户用量/总用量) | 多租户共享成本池 |
| **项目分摊** | 按项目归属直接分摊 | 项目分摊 = 租户成本 × 项目占比 | 项目独立核算 |
| **用户分摊** | 按用户调用量分摊 | 用户分摊 = 项目成本 × (用户用量/项目用量) | 个人成本核算 |
| **公共成本** | 按用量比例二次分摊 | 二次分摊 = 公共成本 × (个体用量/去除公共后总量) | 共享资源分摊 |

## 八、预算告警与限流设计 (Budget Alert and Rate Limiting)

### 8.1 分级告警机制

| 告警级别 | 触发条件 | 通知渠道 | 响应要求 | 升级机制 |
|---------|---------|---------|---------|---------|
| **P3 (提示)** | 预算使用率 50% | 邮件 | 24 小时内 | 无 |
| **P2 (警告)** | 预算使用率 80% | 邮件 + 钉钉 | 4 小时内 | 超时未处理升级 P1 |
| **P1 (严重)** | 预算使用率 100% | 邮件 + 钉钉 + 短信 | 30 分钟内 | 超时未处理电话通知 |
| **P0 (紧急)** | 预算超支 120% + 大额 | 邮件 + 钉钉 + 短信 + 电话 | 立即 | 升级至部门负责人 |

### 8.2 限流策略设计

限流采用四层防护架构：

```
限流决策流程 (四层防护):

AI 请求 → Layer 1: 租户级限流 (令牌桶，100 RPS, Burst 200)
         ↓
         Layer 2: 项目级限流 (滑动窗口，50 RPS)
         ↓
         Layer 3: 用户级限流 (固定窗口，10 RPS)
         ↓
         Layer 4: 预算状态限流 (动态调整)
         ↓
         放行到 LLM

限流响应码:
├── 200: 正常放行
├── 429: 频率限制 (Too Many Requests)
├── 402: 预算不足 (Payment Required)
└── 503: 服务降级 (Service Unavailable)
```

### 8.3 限流算法实现

| 算法 | 适用场景 | 实现方式 | 优势 |
|------|---------|---------|------|
| **令牌桶** | 租户级限流 | Redis + Lua 脚本 | 支持突发流量 |
| **滑动窗口** | 项目级限流 | Redis SortedSet | 精确控制 |
| **固定窗口** | 用户级限流 | Redis String | 简单高效 |
| **动态限流** | 预算状态限流 | 规则引擎 + 配置中心 | 灵活调整 |

### 8.4 优雅降级策略

| 预算状态 | 降级策略 | 影响范围 | 恢复条件 |
|---------|---------|---------|---------|
| **正常** | 无降级，全功能 | 无 | - |
| **警告** | 软降限，非核心功能限流 | 非核心功能 RPS 减半 | 预算追加/使用率<80% |
| **耗尽** | 核心功能限流 | 仅保留核心功能，RPS 限制 20% | 预算追加 |
| **严重超支** | 硬限制 | 全部拒绝 (除白名单) | 预算追加 + 审批 |

## 九、成本优化策略设计 (Cost Optimization Strategy)

### 9.1 成本优化策略决策树

```
成本优化决策流程:

AI 请求 → Step 1: 缓存检查
         ├─ 缓存命中 → 直接返回 (成本：$0)
         └─ 缓存未命中 → Step 2: 任务复杂度评估
                        ├─ 简单任务 (分类/提取) → 小模型优先
                        │  ├─ GPT-3.5 / Claude-Haiku / 自研 Small
                        │  └─ 成本：$0.0005/1K
                        └─ 复杂任务 (推理/生成) → 大模型优先
                           ├─ GPT-4-Turbo / Claude-Sonnet / 自研 Large
                           └─ 成本：$0.01/1K

         → Step 3: Prompt 优化 (Prompt 压缩 + 上下文裁剪)
         → Step 4: 执行调用
         → Step 5: 结果缓存 (相同 Prompt+Context)
         → 返回结果

优化收益估算:
├── 缓存命中：节省 100% 成本
├── 小模型替代：节省 80-95% 成本
├── Prompt 压缩：节省 20-40% 成本
└── 综合优化：预计降低 30-50% 总成本
```

### 9.2 缓存复用策略

| 缓存类型 | 缓存键生成 | 有效期 | 适用场景 |
|---------|-----------|--------|---------|
| **Prompt 缓存** | Hash(Prompt 模板) | 24 小时 | 相同模板重复使用 |
| **上下文缓存** | Hash(Prompt + Context) | 1 小时 | 短时会话场景 |
| **结果缓存** | Hash(Prompt + Context + Model) | 根据内容类型 | 确定性输出 |
| **Embedding 缓存** | Hash(Text + Model) | 永久 | 向量化复用 |

```
│  ┌───────────────────────────────────────────────────────────┐ │
│  │ 任务：Java 代码问题分析和修复建议                              │ │
│  │ 类型：Spring Boot UserService                              │ │
│  │ 代码：public class UserService { ... }                      │ │
│  │ 要求：指出问题 + 修复代码                                    │ │
│  └───────────────────────────────────────────────────────────┘ │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘

压缩技术:
├── 模板变量化：固定部分模板化，减少重复 Token
├── 上下文裁剪：移除无关背景，保留核心信息
├── 结构化压缩：使用结构化格式 (JSON/YAML) 替代自然语言
└── 语义蒸馏：LLM 摘要长文本，提取关键信息
```

### 9.4 小模型优先路由

| 任务类型 | 推荐模型 | 备选模型 | 成本对比 |
|---------|---------|---------|---------|
| **简单分类** | GPT-3.5 / Claude-Haiku | GPT-4 / Claude-Sonnet | 节省 95% |
| **信息提取** | Claude-Haiku / 自研 Small | Claude-Sonnet | 节省 90% |

## 十、ROI 评估设计 (Return on Investment Evaluation)

### 10.1 AI 功能投入产出比模型

**ROI 计算公式**:

```
ROI = (收益 - 成本) / 成本 × 100%

其中:
├── 收益 = 工时节省价值 + 质量提升价值 + 效率提升价值
└── 成本 = Token 成本 + 基础设施成本 + 研发成本 + 运维成本
```

**工时节省计算**:

| 场景 | 人工耗时 | AI 耗时 | 节省工时 | 节省价值 ($50/小时) |
|------|---------|--------|---------|-------------------|
| 代码生成 | 2 小时/功能 | 15 分钟/功能 | 1.75 小时 | $87.5/功能 |
| 代码审查 | 1 小时/PR | 5 分钟/PR | 55 分钟 | $46/PR |
| 测试生成 | 3 小时/用例集 | 20 分钟/用例集 | 2.67 小时 | $133/用例集 |
| 文档生成 | 4 小时/文档 | 30 分钟/文档 | 3.5 小时 | $175/文档 |
| 日志分析 | 2 小时/问题 | 10 分钟/问题 | 1.83 小时 | $91/问题 |

**质量提升量化**:

| 提升项 | 提升幅度 | 价值估算 |
|--------|---------|---------|
| Bug 发现率 | +30% | Bug 减少数 × $500/个 |
| 测试覆盖率 | +25% | 回归缺陷减少 × $300/个 |
| MTTR 降低 | -60% | 问题定位时间节省 × $50/小时 |

### 10.2 ROI 评估指标体系

| 指标类别 | 指标名称 | 计算方法 | 目标值 |
|---------|---------|---------|-------|
| **成本指标** | AI 总成本 | Token 成本 + 基础设施 + 研发 | <$35,000/月 |
| | 单次调用成本 | 总成本/总调用数 | <$0.10 |
| | 人均 AI 成本 | 总成本/活跃用户数 | <$100/人/月 |
| **收益指标** | 工时节省总量 | Σ (各场景节省工时) | >500 小时/月 |
| | 工时节省价值 | 工时节省 × 人力单价 | >$25,000/月 |
| | Bug 减少价值 | Bug 减少数 × 平均修复成本 | >$5,000/月 |
| **效率指标** | 代码生成占比 | AI 生成代码/总代码 | >20% |
| | AI 辅助覆盖率 | 使用 AI 用户/总用户 | >80% |
| | 用户满意度 | NPS 调研得分 | >40 |
| **ROI 指标** | 整体 ROI | (收益 - 成本)/成本 | >1.5 |
| | 分功能 ROI | 功能收益/功能成本 | >1.0 |
| | 投资回收期 | 累计投入/月收益 | <6 个月 |
