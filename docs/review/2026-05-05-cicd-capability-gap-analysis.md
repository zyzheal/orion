## 二、P0 — 关键遗漏 (必须修复)

### P0-1: 数据库迁移编号体系混乱

**问题**: 规格文档中的迁移编号与实际文件严重不一致:
- Phase 1 规格计划 080-085, 实际存在 080, 082, 083, 084, 086, 087, 088, 089, 090
- 缺少 081 (artifact 应为 081, 实际用了 090)
- 缺少 085 (env mgmt 应为 085, 实际用了 089)
- Phase 2 计划 086-091, 实际 086 已被 quality-gate 使用 (应为 Phase 1)
- Phase 3/4 计划 101-120, 实际最高只到 090
- **092-100 区间完全空白**

**影响**: 新开发者按规格文档创建迁移会编号冲突或跳号, 导致迁移顺序混乱。

**建议**: 统一迁移编号, 以实际文件为准更新规格文档。建议:
- 已到位的 080-090 保持不变
- Phase 2/3/4 的新迁移从 091 开始连续编号

### P0-2: EventBus 未真实集成

**问题**: CLAUDE.md 明确记录 "No real EventBus integration: Event publishers exist but are not wired to NATS"。EventBus 是 Phase 2 自主管道、Phase 3 跨域编排、Phase 2 可观测性的基础依赖。

**影响**: 所有依赖事件驱动的能力 (自适应管道、告警关联、跨域编排) 都无法真正工作。

**建议**: 在 Phase 2 开始前优先完成 NATS JetStream 集成。`jetstream-manager.ts` 和 `event-bus-service.ts` 已存在骨架, 需要完成:
- NATS 连接管理
- 事件发布/订阅实现
- 事件持久化与重放

### P0-3: 租户隔离未全覆盖

**问题**: 规格文档中大量 API 缺少 `tenant_id` 参数和 RLS 策略。现有 073_enable_rls_policies.sql 仅覆盖基础表, 新增表 (Phase 1-4) 均未包含 RLS。

**影响**: 多租户数据泄露风险。

**建议**: 所有 Phase 1-4 新增迁移必须包含 RLS policy, 参考 073 的模式。

### P0-4: 双重 ArtifactService 职责重叠

**问题**: CLAUDE.md 指出 `services/artifact/` 和 build 相关服务存在职责重叠。Phase 1 artifact spec 和 Phase 3 artifact-operations spec 进一步加剧了这种混乱。

**建议**: 明确职责边界:
- `artifact/` = 制品生命周期管理 (上传/下载/版本)
- `build/` = 构建过程管理
- `internal-library/` = 内部制品库
- 在规格文档中注明职责边界

## 三、P1 — 重要改进 (强烈建议)

### P1-1: 规格文档与已实现能力的对齐

**问题**: 规格文档描述为 "Orion 当前已实现" 的部分与实际代码存在偏差:
- Phase 1 deploy spec 声称已实现 "部署状态追踪", 但 smart-deploy 服务仅为骨架
- Phase 2 observability spec 声称已实现 "基础 Prometheus 集成", 实际 monitoring 服务功能有限
- Phase 3 多个规格引用了不存在的 "基础能力"

**建议**: 更新规格文档的 "现状评估" 部分, 反映真实完成度。

### P1-2: Phase 3/4 重叠能力域的合并

**问题**: 以下 3 个能力域在 Phase 3 和 Phase 4 各有一份规格:
- 联邦调度: Phase 3-03 (103) vs Phase 4-04 (119)
- 多云/混合云: Phase 3-04 (104) vs Phase 4-05 (120)
- 社区生态: Phase 3-11 (111) vs Phase 4-03 (118)

虽然定位为 "基础 → 进阶" 的演进, 但规格间缺乏明确的递进关系描述。

**建议**: 将重叠规格合并为单一文档, 按成熟度等级分章节 (L1 基础 / L1.5 进阶 / L2 高级), 避免维护两份文档。

### P1-3: API 路径命名规范不统一

**问题**: 各规格 API 路径风格不一致:
- Phase 1: `/api/v1/pipeline-templates` (kebab-case)
- Phase 2: 未明确定义 base path
- Phase 3: `/api/v1/chaos-experiments` (kebab-case)
- Phase 4: `/api/v1/governance` (无版本号前缀)
- 实际 routes.ts 使用 `/v1/...` (无 `/api` 前缀)

**建议**: 统一为 `/api/v1/` 前缀或 `/v1/` 前缀, 全平台保持一致。以 routes.ts 现有的 `/v1/` 为准更新所有规格文档。

### P1-4: 前端技术栈未明确

**问题**: 所有规格文档的 "前端设计" 部分仅提供了 ASCII 线框图, 未指定:
- 组件库版本 (Ant Design 4.x vs 5.x)
- 状态管理方案 (zustand/redux/Context)
- 微前端集成方式 (wujie 的具体集成模式)

**建议**: 在规格文档补充 "前端技术规范" 章节, 或引用前端架构文档。

## 四、P2 — 功能增强 (建议考虑)

### P2-1: AI 能力前置依赖

Phase 2 大量依赖 AI 能力 (SHAP 解释、XGBoost 风险预测、自适应算法), 但当前:
- `ai/` 服务已存在 AIGateway 和熔断
- `risk-assessment` 服务已存在
- 但 ML 模型训练/部署流程未定义

**建议**: 增加 "AI 模型管理" 子规格, 涵盖模型训练数据、特征工程、模型版本、在线推理。

### P2-2: 数据管道 (Phase 3-09) 的引擎选型

Phase 3-09 "数据管道" 是唯一完全没有服务骨架的全新能力域。规格中提到了 Flink/Spark/Kafka Streams 但未做选型。

**建议**: 明确技术选型:
- 如果 Orion 已有 Tekton, 可考虑用 Tekton Pipeline 做数据管道编排
- 如果需要实时流处理, 考虑引入 Flink (与现有 Knative 兼容)
- 避免引入过多技术栈, 优先考虑复用现有组件

### P2-3: 多模态触发 (Phase 3-12) 的集成点

Phase 3-12 描述了 Git/Webhook/Chat/CLI/定时/API 六种触发方式, 但:
- Webhook 服务已存在 (`services/webhook/`)
- 定时触发已有 Cron 服务 (migration 036)
- Chat 触发已有 ChatOps (migration 033, 055)

**建议**: 规格应聚焦于 "统一触发编排层", 而非从零实现各触发方式。复用已有的 webhook/chatops/cron 能力。

### P2-4: 数字孪生 (Phase 4-01) 的可行范围

数字孪生规格要求 "生产快照 + 流量录制回放 + 变更沙箱", 这在 DevOps 平台中是非常重的能力。

**建议**: 分阶段实施:
- 阶段一 (L1): 环境快照 (已有 deployment 数据可作为基础)
- 阶段二 (L1.5): 配置沙箱 (复用 config-mgmt)
- 阶段三 (L2): 流量录制回放 (需额外引入流量捕获组件)

## 五、P3 — 创新机会 (探索方向)

### P3-1: AI Agent 与 Pipeline 深度融合

当前 `agent/` 和 `agent-run-service.ts` 已存在, 但未与 Pipeline Engine 深度集成。

**创新方向**:
- AI Agent 作为 Pipeline Stage 运行 (AgentStage)
- Pipeline 失败时自动触发 Agent 诊断
- Agent 生成修复方案后自动创建 PR + 触发重跑

### P3-2: GitOps 闭环

当前 IaC 服务 (`services/iac/`) 已存在, 迁移 032/044 已创建表, 但缺少:
- Git 仓库与基础设施状态的自动同步
- Git PR 自动触发 IaC plan
- IaC drift 自动检测 + PR 修复

**创新方向**: 实现 "Git 为单一事实源" 的 GitOps 闭环。

### P3-3: 预测性运维

结合已有的 risk-assessment (XGBoost) 和 efficiency 服务, 可实现:
- Pipeline 失败预测 (提前预知高风险 Pipeline Run)
- 资源瓶颈预测 (预测未来 24h 资源竞争)
- 部署风险评估 (部署前自动评估失败概率)

### P3-4: 开发者体验 (DX) 度量

Phase 2 效率运营和 Phase 1 开发者门户的基础上, 可引入 DX (Developer Experience) 度量:
- SPACE 框架 (Satisfaction, Performance, Activity, Communication, Efficiency)
- 开发者反馈闭环 (Pipeline 失败 → 自动收集上下文 → 推荐修复方案)

## 六、跨 Phase 问题

### 跨-1: 数据库迁移依赖顺序

```
Phase 1: 080-090 (部分到位)
  ↓ (依赖)
Phase 2: 需要 086-091 (部分与 Phase 1 重叠/冲突)
  ↓ (依赖)
Phase 3: 需要 101-115 (全部未创建)
  ↓ (依赖)
Phase 4: 需要 116-120 (全部未创建)
```

**问题**: Phase 3 的 chaos-engineering (101) 与 Phase 1 的 pipeline (080) 有外键依赖, 但编号 101 > 080, 执行顺序正确。但 Phase 2 的编号与 Phase 1 重叠。

**建议**: 重编号 Phase 2 迁移为 091-096, Phase 3 为 097-111, Phase 4 为 112-116。

### 跨-2: 服务间依赖未显式声明

规格文档未声明服务间依赖关系。例如:
- Phase 2 自主管道 → 依赖 Phase 1 Pipeline 版本
- Phase 3 灰度流量 → 依赖 Phase 1 部署发布
- Phase 4 API 治理 → 依赖 Phase 1 Pipeline 版本

**建议**: 在规格文档增加 "前置依赖" 章节, 或在 `routes.ts` 中用注释标明依赖顺序。

### 跨-3: 测试覆盖率目标不一致

| Phase | 规格要求的覆盖率 | 当前实际覆盖率 |
|-------|:----------------:|:--------------:|
| Phase 1 | 80% | ~40% (估算) |
| Phase 2 | 80% | ~35% |
| Phase 3 | 75% | ~20% |
| Phase 4 | 75-80% | ~15% |

**建议**: 先提升现有测试覆盖率, 再新增功能测试。否则新增功能的测试质量无法保证。
