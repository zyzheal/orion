# Orion Pipeline 能力提升 — 评审方案

> 日期: 2026-04-21
> 阶段: 评审准备

## 评审目标

对 7 个从 GitHub Actions 借鉴的改进方向进行正式评审，确认：
1. 技术设计是否合理
2. 优先级是否正确
3. 实施路线图是否可行
4. 是否有遗漏的风险或依赖

## 评审要点

### 架构层面
- [ ] 矩阵展开算法是否正确处理 exclude/include？
- [ ] 模板引用的三来源 (local/git/registry) 是否覆盖场景？
- [ ] Webhook 签名验证机制是否充分？
- [ ] 缓存 key 模板的 hashFiles 实现是否高效？
- [ ] 审批流状态机是否有遗漏状态？

### 数据层面
- [ ] Stage 表新增 5 个字段是否需要全部索引？
- [ ] 4 张新表的外键约束是否合理？
- [ ] git_trigger_records 的 UNIQUE 约束是否能防止重复触发？

### 安全层面
- [ ] 模板来源白名单如何维护？
- [ ] Webhook 端点是否需要 CSRF 保护？
- [ ] 缓存内容是否需要加密（含敏感信息时）？
- [ ] 审批权限是否与现有 RBAC 集成？

### 性能层面
- [ ] 矩阵 50 子 Stage 并发是否超出 Runner 容量？
- [ ] 缓存 100MB 文件的压缩/解压时间是否可接受？
- [ ] 模板下载是否会阻塞 Pipeline 创建？

### 体验层面
- [ ] DAG 如何展示矩阵展开的子 Stage（分组 vs 平铺）？
- [ ] 审批 UI 是否需要批量操作？
- [ ] 错误信息如何区分用户错误 vs 系统错误？

## 评审流程

1. **技术设计审阅** (1-2 天) — 阅读 `pipeline-improvement-tech-design.md`
2. **问题收集** (1 天) — 评审人提交问题/建议
3. **评审会议** (1 小时) — 讨论争议点
4. **修订方案** (1-2 天) — 根据反馈修改技术设计
5. **最终确认** — 评审人签字确认后进入 Phase 3 任务拆分

## 建议评审人

| 角色 | 关注点 |
|------|--------|
| 后端工程师 | 架构设计、数据模型、API 契约 |
| 前端工程师 | DAG 展示、审批 UI、日志体验 |
| DevOps | Git webhook 集成、Runner 容量规划 |
| 安全工程师 | 签名验证、模板安全、缓存加密 |
