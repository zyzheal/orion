> 评审维度: 架构师 / SRE / 安全专家 / 前端专家 / 后端专家 / AIOps 专家

## 一、架构师评审（评分: 7.5/10）

### ✅ 做得好的

1. **分层架构清晰** — 前端层 / 后端服务层 / 数据层 / 外部 IM 层，边界明确
2. **AIOps 模块隔离良好** — 4 个引擎各有独立的数据表和 API，无循环依赖
3. **模块协作关系图 (§12.5) 清晰** — Baseline → RCA → Runbook → ChatOps 的流水线设计合理
4. **Phase 分解逻辑合理** — 规则驱动 → 数据驱动 → AI 驱动，渐进式演进

### ⚠️ P0 问题

| # | 问题 | 章节 | 建议 |
|---|------|------|------|
| A-1 | **Phase 1 任务数过多 (51 个)** | §13 | 51 个任务远超单个 Phase 可承载量。建议拆分为 Phase 1a (ChatOps 核心 24 项) + Phase 1b (AIOps 引擎 27 项)，先交付前端+基础 API，再交付智能引擎 |
| A-2 | **缺少 ChatOps 与 SelfHealing 的集成** | §2.1 | SelfHealing 模块设计已完整但 0% 实现。ChatOps 触发自愈应该是核心场景之一，但文档仅在 §8.2 表格中提到"手动干预"，未描述集成方式。建议: ChatOps 推荐操作中包含"触发自愈策略"按钮，调用 SelfHealing API |
| A-3 | **缺少 EventBus 集成说明** | §2.1 | 平台已有 EventBus 框架 (NATS 15% 实现)。ChatOps 的事件订阅 (推荐面板、升级策略) 应该复用 EventBus 而非自建轮询机制。文档中推荐面板用轮询 (30s)，应该改为 EventBus 驱动 |

### ⚠️ P1 问题

| # | 问题 | 章节 | 建议 |
|---|------|------|------|
| A-4 | **`aiops_rca_results` 表缺少外键约束** | §12.1.3 | `alert_group_id` 应 `REFERENCES aiops_alert_groups(id)`，确保数据一致性 |
| A-5 | **`aiops_alert_groups.member_alert_ids` 使用 UUID[] 而非关联表** | §12.1.3 | 当告警组包含大量告警时，数组更新效率低。建议改为 `aiops_group_members(group_id, alert_id)` 关联表 |
| A-6 | **Runbook 表缺少版本字段** | §12.2.3 | Runbook 步骤变更后无法追溯历史版本。建议增加 `version INT DEFAULT 1` 和 `previous_version_id UUID` |
| A-7 | **变更影响分析缺少 API diff 的具体实现** | §12.4.2 | "OpenAPI/Swagger diff" 需要具体的实现方案。建议使用 `openapi-diff` 库或类似工具，否则仅是概念 |

## 二、SRE 专家评审（评分: 7/10）

### ✅ 做得好的

1. **告警风暴降噪 (§9.3)** — 聚合规则覆盖了同资源/同项目/重复告警三种场景
2. **升级策略 (§9.5)** — 3 级时间阶梯 (15/30/60min) 符合业界标准 (PagerDuty 默认策略)
3. **DND 免打扰 (§9.2)** — 支持固定时段 + 重复模式 + Critical 例外
4. **基线引擎冷启动策略** — 风险表中提到"冷启动期使用固定阈值"，这是务实的做法

### ⚠️ P0 问题

| # | 问题 | 章节 | 建议 |
|---|------|------|------|
| S-1 | **推荐面板刷新频率过高 (30s)** | §8.3 | 如果 100 个用户同时在线，每秒 3.3 次查询。建议改为 60s + WebSocket 推送。且推荐数据可按事件驱动: 仅在新告警/状态变化时推送更新 |
| S-2 | **升级策略引擎缺少执行间隔** | §9.5 | 如果告警在 14min 被确认，15min 的升级不应该触发。当前设计仅说"超过时间→通知"，没有描述"已确认则停止升级"的具体实现。应在 `chatops_alert_states` 中记录 `escalation_stopped` 标志 |
| S-3 | **缺少 ChatOps 自身的监控指标** | 全局 | ChatOps 作为运维中枢，自身必须有可观测性: 响应时间、命令解析成功率、权限拒绝率、RCA 分析准确率、推荐面板展示次数等。建议增加 `/api/chatops/metrics` 端点 |

### ⚠️ P1 问题

| # | 问题 | 章节 | 建议 |
|---|------|------|------|
| S-4 | **告警组分组策略未定义** | §12.1.3 | 什么条件下将多条告警归为一组？建议: 同一服务 + 5 分钟窗口 或 拓扑关联的多个服务 + 3 分钟窗口 |
| S-5 | **DND 期间 DND 结束后"统一推送摘要"未定义格式** | §9.2 | 摘要应该是什么格式？聚合展示还是逐条展示？建议: 按严重程度排序的摘要卡片 |
| S-6 | **降噪阈值静态化** | §9.3 | 固定阈值 (5min > 3 条) 在告警风暴初期可能不够敏感。建议引入动态阈值: 根据历史告警密度自适应 |

## 三、安全专家评审（评分: 8/10）

### ✅ 做得好的

1. **双层权限校验 (§5)** — 命令级 + 资源级串联，覆盖了运维安全核心需求
2. **对话原文加密存储 (§7.4)** — 使用 pgcrypto 对称加密，密钥通过环境变量管理
3. **权限审计日志永久存储** — 符合审计合规要求
4. **所有操作仍需用户确认** — 风险表中明确提到"所有操作仍需用户确认 + 双层权限校验"

### ⚠️ P0 问题

| # | 问题 | 章节 | 建议 |
|---|------|------|------|
| SE-1 | **`chatops_messages.parsed_command` 以明文存储** | §7.2 | 结构化命令 (如 deploy 的目标环境、版本号) 以明文存储，可能被用于审计绕过。如果命令包含敏感信息 (如密码、API Key)，即使 content_encrypted 加密了，parsed_command 仍暴露了操作意图。建议: parsed_command 中的敏感字段 (password, secret, token) 应额外脱敏 |
| SE-2 | **pgcrypto 对称加密密钥轮换机制缺失** | §7.4 | 如果 `CHATOPS_ENCRYPTION_KEY` 泄露，所有历史对话可被解密。建议: 增加 `encryption_key_version` 字段，支持密钥轮换时重新加密 |
| SE-3 | **ChatOps 命令注入风险** | §4.1 | 自然语言输入可能被构造为恶意命令 (如 "部署 v2.1; rm -rf /")。命令解析引擎必须有严格的白名单校验，不允许执行任意 shell 命令。建议: 所有命令参数必须通过 JSON Schema 校验，拒绝包含特殊字符的输入 |

### ⚠️ P1 问题

| # | 问题 | 章节 | 建议 |
|---|------|------|------|
| SE-4 | **升级策略中的邮件通知可能泄露敏感信息** | §9.5 | "通知直属 Leader" 的邮件内容如果包含告警详情 (如数据库连接池密码泄露导致的告警)，邮件本身可能成为信息泄露渠道。建议: 邮件通知仅发送摘要，详情需登录 ChatOps 查看 |
| SE-5 | **审计日志缺少防篡改机制** | §7.2 | `chatops_audit_logs` 永久存储但无防篡改保护。被入侵者可删除审计记录掩盖攻击。建议: 增加 HMAC 签名链 (每条记录包含前一条的 hash) |

## 四、前端专家评审（评分: 7.5/10）

### ✅ 做得好的

1. **组件拆分合理** — 9 个子组件职责清晰，符合单一职责原则
2. **浅色主题使用 Orion Design Token** — 与平台整体视觉一致
3. **上下文感知机制** — 从路由提取资源上下文，提升交互体验
4. **悬浮按钮 3 种状态** — 正常/告警/执行中的视觉区分度高

### ⚠️ P0 问题

|---|------|------|------|
| F-1 | **侧边栏宽度 400px 对小屏幕不友好** | §3.2 | 在 1366px 宽度屏幕上，400px 侧边栏 + 主内容区 = 拥挤。建议: 最小宽度 360px，最大宽度 480px，支持拖拽调整 |
| F-2 | **RCA 影响链可视化组件仅一句话** | §13, 前端第 12 项 | "RCA 影响链可视化组件" 需要具体设计方案。400px 宽度的侧边栏中如何展示 5+ 层影响链？建议: 垂直时间线布局，每层一个节点，支持折叠 |
| F-3 | **SmartRecommend 推荐面板条件显示逻辑未定义** | §3.2 | 什么条件下显示/隐藏推荐面板？无告警时是否显示空面板？建议: 无推荐时显示"当前无异常"占位 + 快捷命令入口 |

### ⚠️ P1 问题

| # | 问题 | 章节 | 建议 |
|---|------|------|------|
| F-4 | **对话历史区无滚动位置记忆** | §3.2 | 打开面板后自动滚动到底部，但用户向上查看历史消息时，新消息推送会跳回底部。建议: 用户手动向上滚动时暂停自动滚动，显示"新消息"提示 |
| F-5 | **ChatInput 的 Slash 命令补全交互未设计** | §3.3 | 输入 `/dep` 时的补全提示框样式、键盘交互 (↑↓选择、Enter确认) 未描述。建议参考 Ant Design `AutoComplete` 组件 |

## 五、后端专家评审（评分: 7/10）

### ✅ 做得好的

1. **数据表设计覆盖全面** — 12+ 张表，覆盖会话、消息、审计、TTL、降噪、升级、订阅、RCA、Runbook、基线、变更分析
2. **TTL 分层策略** — 项目 > 角色 > 全局优先级链设计合理
3. **API 路径规范** — `/api/chatops/` 统一前缀，符合 REST 惯例

### ⚠️ P0 问题

| # | 问题 | 章节 | 建议 |
|---|------|------|------|
| B-1 | **缺少数据库索引定义** | §7.2, §12 | 所有表只有 PRIMARY KEY，缺少业务查询所需索引。关键缺失: `chatops_sessions(user_id)`, `chatops_messages(session_id)`, `chatops_executions(user_id, created_at)`, `aiops_alert_groups(status)`, `aiops_rca_results(alert_group_id)`, `chatops_notification_preferences(user_id)`。Phase 1 必须包含索引创建 |
| B-2 | **`chatops_messages.content_encrypted` 使用 TEXT 类型** | §7.2 | PGP 加密后的内容可能很大 (长对话)，TEXT 在单行过大时影响查询性能。建议: 使用 BYTEA 或考虑对话分片 (每 50 条消息一个 session) |
| B-3 | **执行 API 缺少幂等性保证** | §5.3 | `POST /api/chatops/execute` 如果用户重复点击发送按钮，可能触发两次部署。建议: 增加 `idempotency_key` 请求头，或前端 debounce + 后端操作去重 |
| B-4 | **推荐面板 API 缺少聚合数据来源定义** | §8.1 | `/api/chatops/recommendations` 需要从 Monitoring、Pipeline、Deploy、SelfHealing、FinOps 等多个模块聚合数据，但文档未描述数据获取方式 (直接查询? EventBus 订阅? 缓存?)。建议: 定义内部服务接口或事件订阅机制 |

### ⚠️ P1 问题

| # | 问题 | 章节 | 建议 |
|---|------|------|------|
| B-5 | **`aiops_baseline_snapshots` 无唯一约束** | §12.3.3 | 同一个 metric/service/env 可能被多次计算快照。建议: `UNIQUE(metric_name, service_name, environment, computed_at::date)` |
| B-6 | **升级策略引擎的定时任务间隔未定义** | §9.5 | 检查未处理告警的 cron 间隔? 每分钟? 每 5 分钟? 建议: 每 2 分钟检查一次，与 level1 (15min) 粒度匹配 |
| B-7 | **TTL 清理任务缺少分批处理** | §7.3 | 一次性 `DELETE ... WHERE expires_at < NOW()` 可能锁表。建议: 分批删除 (LIMIT 1000) + 事务 |

## 六、AIOps 专家评审（评分: 7/10）

### ✅ 做得好的

1. **Phase 1 不使用 ML 的务实决策** — 拓扑关联 + 时间差即可覆盖 60%+ 根因分析场景
2. **EWMA 基线算法选择恰当** — 比移动平均更敏感，比 ML 更轻量
3. **Runbook 三层演进** — 手动 → RAG → LLM，每一步都有明确的触发条件
4. **变更影响分析复用 CMDB 拓扑** — 不重复造轮子

### ⚠️ P0 问题

| # | 问题 | 章节 | 建议 |
|---|------|------|------|
| AI-1 | **RCA 引擎缺少拓扑数据同步机制** | §12.1.6 | "直接使用 CMDB 已有服务依赖数据" — CMDB 的拓扑数据格式是什么？同步频率？增量还是全量？文档中 `aiops_service_topology` 表是独立存储，但没有描述同步逻辑。建议: 增加定时同步任务，或提供 CMDB 事件驱动的实时更新 |
| AI-2 | **因果权重计算算法过于简化** | §12.1.6 | "时间一致性 × 拓扑匹配度" 的公式未定义。如果两个服务没有时间关系但有拓扑关系呢？建议: 定义明确的评分公式，如 `score = w1 × time_score + w2 × topology_score + w3 × historical_correlation` |
| AI-3 | **Runbook 成功率统计在样本量少时不可靠** | §12.2.3 | 一个 Runbook 执行 2 次、成功 1 次 = 50% 成功率，但这在统计学上无意义。建议: 增加 `confidence_interval` 字段，或使用 Wilson score 而非简单比率 |
| AI-4 | **变更影响分析缺少 diff 数据源** | §12.4.2 | "API 变更: OpenAPI/Swagger diff" — diff 数据从哪里获取？Git commit? Pipeline artifact? 需要明确数据来源。建议: 集成 Git diff API 或从 Pipeline artifact 获取 OpenAPI spec 差异 |

### ⚠️ P1 问题

| # | 问题 | 章节 | 建议 |
|---|------|------|------|
| AI-5 | **基线引擎缺少数据质量检查** | §12.3.2 | EWMA 对异常值敏感，一个极端值会拉高后续基线。建议: 先做异常值过滤 (如 IQR 方法)，再计算 EWMA |
| AI-6 | **RCA 引擎缺少多根因支持** | §12.1.2 | 真实场景中可能有多个独立根因 (如 DB 问题 + 网络问题同时发生)。当前设计只输出单一 rootCause。建议: 改为 `rootCauses: RootCause[]`，支持多根因 |
