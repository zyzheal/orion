## 1. 服务等级目标（SLO）定义

### 1.1 SLI 四类基本定义（Google SRE Book Ch.4）

| SLI 类别 | 计算方式 |
|---------|---------|
| **可用性** | `2xx / total`（5xx 视为失败）|
| **延迟** | P50/P95/P99 三档，Histogram bucket 计算 |
| **吞吐量** | `sum(rate(request_total{status="2xx"}[5m]))` |
| **正确性** | 领域特定（SLO 命中比例 / 巡检一致率 / 推理准确率）|

### 1.2 8 服务 SLO 目标矩阵（滚动 30 天窗口）

> **测量窗口**：所有 SLO 采用**滚动 30 天**（Rolling 30-day），符合 Google SRE Workbook Ch.2 推荐。
> **错误预算**：`ErrorBudget = 100% - SLO`，用于触发发布冻结。
> **P95/P99 分位**：P95 为主指标（SRE 团队日常关注），P99 为尾延迟守门（关键路径关注）。

| 服务 | SLI（Google SRE 四分类）| P95 目标 | P99 目标 | 可用性 SLO | 错误预算 | 测量窗口 |
|------|------------------------|---------|---------|-----------|---------|---------|
| **API Gateway** | 可用性 + 延迟 | <100ms | <300ms | 99.99% | 0.01% | 30 天滚动 |
| **Pipeline Engine** | 吞吐量（执行成功率）+ 延迟（启动）| <500ms 触发 | <30s 执行完毕 | 99.5% | 0.5% | 30 天滚动 |
| **Alert System** | 可用性 + 延迟 + 正确性（投递率）| <100ms | <300ms | 99.95% | 0.05% | 30 天滚动 |
| **CMDB** | 延迟 + 正确性（一致性）| <200ms | <500ms | 99.9% | 0.1% | 30 天滚动 |
| **ITSM / Ticket** | 延迟 + 正确性（SLA 计算）| <300ms | <1s | 99.9% | 0.1% | 30 天滚动 |
| **Inspection** | 吞吐量（执行率）+ 正确性（结果准确）| <1s | <3s | 99.5% | 0.5% | 30 天滚动 |
| **DevOps / Deploy** | 吞吐量（部署成功率）+ 延迟（回滚）| 成功率 99.5% | 回滚 <15min | 99.5% | 0.5% | 30 天滚动 |
| **AI Service** | 延迟（推理）+ 正确性（准确率）| <2s 首 token | <10s 完整响应 | 99.0% | 1.0% | 30 天滚动 |

### 1.3 SLO 目标的企业级基准引用

所有 SLO 数值均来自公开企业级基准，**不引用任何未经审计的 NeatLogic 一手证据**（参照系审计：ADR-010/013/014 已证伪）。

| 服务 | 关键 SLO | 对标基准 |
|------|---------|---------|
| API Gateway 99.99% + P95<100ms | 4 个 9 是网关级 SLA 主流值 | AWS API Gateway / 阿里云 API 网关 SLA / Cloudflare Edge P95<100ms |
| Alert System 99.95% + P95<100ms | 告警系统严格度高于一般 API | PagerDuty SLO 99.95% / Google SRE Ch.4 案例 / Prometheus Remote Write |
| CMDB 99.9% + 强一致 | CI 强一致是下游正确性基础 | ServiceNow CMDB SLA 99.9% |
| Pipeline 99.5% + 500ms 触发 | 触发 vs 执行分离 | Argo Workflows / GitLab CI 99.9% |
| ITSM P95<300ms | 工单系统响应目标 | ServiceNow ITSM 参考值 |
| Inspection 99.5% + P99<3s | 巡检长尾（SSH/网络探测）| 阿里云 ECS 巡检 SLA 99.5% |
| DevOps 回滚 <15min | MTTR 可接受阈值 | Google SRE Book Ch.15 / AWS Well-Architected R3 |
| AI Service 99.0% + 2s 首 token | 模型推理波动大 | OpenAI 多模型编排参考 99.0% |

### 1.4 关键 SLO 说明

- **API Gateway 是入口 SLI 收敛点**：所有下游服务（Pipeline/Alert/CMDB/…）的可用性都包含 API Gateway 的可用性；因此其 SLO 最严（99.99%）。
- **Alert 系统 99.95% 是 P0 级**：ADR-010 已接受 AlertBreaker 用 PG 行锁；SLO 违约 1 分钟即触发 On-call（见 §3.3）。
- **CMDB 强一致是下游正确性的基础**：CI 类型 + 关系若不一致，Alert/Inspection 的目标选择会漂移（风险登记册 §9.2）。
- **AI Service 99.0% 是初始宽松值**：模型推理延迟波动大，待 S0 后压测数据校准。
- **Pipeline 触发 vs 执行分离**：500ms 是触发受理，30s 是端到端执行；不允许把长任务耗时算入 API 延迟。

## 2. SLA（服务等级协议）定义

> **SLA vs SLO 的区别**：SLO 是内部工程目标，SLA 是对客户/租户的外部承诺并含违约赔偿。
> 所有 SLA 数值均为**建议初始值**，客户合同签署前须过法务评审。

### 2.1 SLA 承诺层级（3 档）

| SLA 类型 | 承诺 | 违约赔偿 |
|---------|------|---------|
| **可用性 SLA**（Standard）| 99.9%（月度允许 ≤ 43 分钟停机）| 月度服务积分：停机 >43min 扣 10%、>120min 扣 25%、>600min 全额退款当月费用 |
| **可用性 SLA**（Premium）| 99.95%（月度允许 ≤ 21 分钟停机）| 月度服务积分：停机 >21min 扣 15%、>60min 扣 30% |
| **可用性 SLA**（Enterprise，含 ADR-011 Schema 隔离）| 99.99%（月度允许 ≤ 4 分钟停机）| 月度服务积分：停机 >4min 扣 20%、>15min 扣 50% |
| **性能 SLA** | 关键服务 P99 延迟达标率 ≥ 99%（详见 §1.2）| 性能积分：单月 P99 未达标率 > 1% 扣 5% |
| **响应 SLA** | P1 < 15min / P2 < 30min / P3 < 4h（首次响应时间）| 响应积分：P1 未达标扣 10%、P2 未达标扣 5% |
| **数据 SLA**（ADR-011 相关）| 数据持久性 ≥ 99.99999999%（11 个 9）+ 数据一致性 RPO ≤ 5min / RTO ≤ 30min | 数据积分：数据丢失事件扣 30%、RPO/RTO 未达标扣 15% |

### 2.2 SLA 服务等级映射

| SLA 层级 | 适用服务 | ADR-011 隔离模式 |
|---------|---------|----------------|
| Standard | BI、Inspection、AI Service | Shared-schema（ADR-0004）|
| Premium | Pipeline、DevOps、Automation | Shared-schema 或 Schema-per-tenant（可选）|
| Enterprise | API Gateway、Alert、CMDB、ITSM | Schema-per-tenant 强制（ADR-011 §3.1）|

### 2.3 SLA 排除条款

SLA 承诺**不包含**以下情况导致的不可用（对齐 AWS Well-Architected Reliability Pillar Exclusion 惯例）：

1. 计划内维护窗口（须提前 72h 通知，累计 ≤ 8h/月）
2. 客户自身操作或数据引起的故障
3. 第三方依赖故障（模型推理 API、SMTP 供应商等），若已启用降级则不计
4. 不可抗力（自然灾害、大规模基础设施运营商事故）
5. 混沌工程实验预声明窗口（须提前 24h 通告）

### 2.4 违约赔偿积分的兑换

- 月度积分自动累积到租户账户
- 可用于抵扣次月账单（1% 积分 = 1% 账单抵扣）
- 连续 3 个月违约触发 SLA 重签条款评估（含降级方案或退款）

## 3. SLO 违规响应机制

### 3.1 错误预算消耗分档与响应动作

| 错误预算消耗比例（30 天窗口）| 系统状态 | 响应动作 |
|---------------------------|---------|---------|
| **< 50%** | 正常 | 允许所有变更发布；SRE 团队按季度审查 |
| **50% - 80%** | 预警 | 限制非关键变更（feature flag 灰度）；开启 SLO 日报 |
| **80% - 100%** | 冻结 | 冻结非关键变更（仅允许 P0 bug fix + 安全补丁）；启动 SRE 复盘 |
| **> 100%** | 全面冻结 | 全量冻结变更；触发 P0 Incident；启动 RCA + 修复计划 |

### 3.2 烧灼率（Burn Rate）监控（Google SRE Workbook Ch.2）

- **快烧灼**：过去 1h 消耗 ≥ 14.4×（意味着 1% 预算 1h 内消耗完，14.4h 内 SLO 违约）→ **P0 立即响应**
- **慢烧灼**：过去 3d 消耗 ≥ 6×（意味着 3d 内消耗 50%+ 预算）→ **P1 24h 内响应**
- **正常**：其他 → 记录并等待月度复盘

### 3.3 SLO 违约升级路径（对齐风险登记册 §9.3）

| 违约持续时长 | 响应级别 | 通知渠道 |
|-------------|---------|---------|
| ≤ 5min | Warning | Slack `#orion-slo` |
| 5-30min | Critical | PagerDuty → On-call SRE |
| 30min-2h | P1 Incident | ITSM 建单 + 模块负责人 |
| > 2h | P0 Incident | On-call 主管 + VP Eng |

**关键差异**：Alert System 的 P1 阈值缩短到 **1min**（ADR-010 AlertBreaker 是 S4 pre 门控关键，违约即刻响应）。

### 3.4 SLO 变更管理

所有 SLO 目标修改须经 **SRE + 模块 owner 双签**，同步更新本文件、风险登记册 §9、Grafana Dashboard/Alert Rule，24h 内通告到 `#orion-slo`。

## 4. SLO 监控指标（Prometheus）

### 4.1 指标命名规范

**命名规则**：`orion_<service>_<metric>_<unit>`，全小写、下划线分隔。
所有指标必须携带标准标签：`tenant_id`, `service`, `status`, `endpoint`, `version`。

### 4.2 每服务 5 项必备指标

以下 8 服务统一遵循此结构，服务名替换为 `<service>`：

| 指标 | 类型 | 语义 |
|------|------|------|
| `orion_<service>_request_total{status, method, endpoint}` | Counter | 总请求数（按 HTTP 状态码分组）|
| `orion_<service>_latency_seconds{endpoint, quantile}` | Histogram | 端到端延迟（bucket: 10ms, 50ms, 100ms, 200ms, 500ms, 1s, 3s, 10s, 30s）|
| `orion_<service>_error_total{code, endpoint}` | Counter | 错误总数（按业务错误码 + HTTP 状态码）|
| `orion_<service>_availability_ratio` | Gauge | `(2xx) / (total)` 滑动 5min 平均值 |
| `orion_<service>_slo_burn_rate{window="1h"\|"3d"}` | Gauge | 错误预算烧灼率（当前速率 / SLO 目标速率）|

### 4.3 `<service>` 替换值

`gateway`（API Gateway）/ `pipeline`（Pipeline Engine）/ `alert`（Alert System）/ `cmdb`（CMDB）/ `ticket`（ITSM）/ `inspection`（Inspection）/ `deploy`（DevOps）/ `ai`（AI Service）。替换 §4.2 中的 `<service>` 即得完整 5 项指标名。

### 4.4 领域特定补充指标（可选）

| 服务 | 补充指标 |
|------|---------|
| Alert | `orion_alert_delivery_success_ratio` / `orion_alert_breaker_locked_total`（ADR-010 锁占用）|
| CMDB | `orion_cmdb_consistency_check_ratio` / `orion_cmdb_tenant_isolation_violation_total`（ADR-011）|
| ITSM | `orion_ticket_sla_breach_total` / `orion_ticket_state_transition_latency` |
| Pipeline | `orion_pipeline_stage_failure_total` / `orion_pipeline_artifact_size_bytes` |
| AI | `orion_ai_first_token_latency_seconds` / `orion_ai_inference_accuracy` |
| DevOps | `orion_deploy_rollback_time_seconds` / `orion_deploy_canary_failure_total` |

### 4.5 Prometheus 抓取配置

- `scrape_interval: 15s` / `evaluation_interval: 30s`（对齐风险登记册 §6.1）
- 保留期：Hot 30 天（SLO 计算）+ Cold 180 天（审计）
- 告警规则位置：`orion-platform-svc-go/internal/observability/alert_rules.yaml`

## 8. 认知边界

- **初始目标值**：所有 SLO 未经生产数据验证，S0 完成后须校准
- **AI Service 波动大**：模型推理延迟对硬件/网络/模型版本敏感，99.0% 目标可能过宽或过严
- **多租户 SLO 分层未量化**：ADR-011 混合方案下 Shared-schema vs Schema-per-tenant 租户的 SLO 差异需 P0-7 配合确定
- **SLA 法律效应**：本文档 SLA 值未经法务评审，客户合同签署前必须重新确认
- **混沌场景覆盖度**：Y 手册 P0-8 的 8 场景是最低要求，实际需更多边缘案例
