# 向量存储生产方案设计

> 版本：v1.0  
> 创建日期：2026-04-10  
> 适用范围：Orion 平台 AI 功能（AI Skill 检索、根因分析、语义搜索）

---

## 1. 背景与目标

Orion 平台 AI 功能需要向量存储支持语义检索和相似度匹配。当前使用 Chroma 作为开发和测试环境的向量存储，但生产环境需要评估更成熟的替代方案（Milvus / Qdrant）。

**核心目标：**
- 评估 Chroma、Milvus、Qdrant 三款向量数据库的生产适用性
- 设计向量索引策略以平衡查询性能与资源消耗
- 建立向量数据同步、检索、监控的完整流程
- 提供可扩展的分片与复制策略

---

## 2. 向量存储使用场景

### 2.1 场景总览

| 场景 | 描述 | 向量维度 | 数据规模 | QPS 要求 | 延迟要求 |
|------|------|----------|----------|----------|----------|
| AI Skill 检索 | 根据用户问题语义匹配最佳 AI Skill | 768/1536 | 1000-5000 | 50+ | < 100ms |
| 根因分析匹配 | 日志/故障向量相似度匹配 | 768 | 10 万 + | 20+ | < 200ms |
| 语义搜索 | 文档/代码/配置语义搜索 | 768/1536 | 50 万 + | 100+ | < 150ms |

### 2.2 AI Skill 检索

**流程描述：**
1. 用户输入自然语言问题
2. 嵌入模型将问题转换为向量
3. 在向量库中检索最相似的 AI Skill 描述
4. 返回 Top-K 匹配结果及置信度

**数据特点：**
- 向量数量少（千级），但查询频率高
- 需要支持元数据过滤（如按服务、标签筛选）
- 向量更新频率低（Skill 变更时更新）

### 2.3 根因分析匹配

**流程描述：**
1. 采集故障日志/告警/指标
2. 生成故障特征向量
3. 与历史故障库进行相似度匹配
4. 返回相似历史故障及解决方案

**数据特点：**
- 向量数量中大型（十万级）
- 持续增量写入（新故障不断产生）
- 需要时间范围过滤（如只匹配近 1 年故障）

### 2.4 语义搜索

**流程描述：**
1. 用户输入搜索关键词
2. 嵌入模型生成查询向量
3. 在文档/代码向量库中检索
4. 结合关键词得分与向量得分排序

**数据特点：**
- 向量数量大（百万级）
- 高并发查询
- 需要混合检索（向量 + 关键词 + 元数据）

## 3. 向量数据库对比分析

### 3.1 候选方案

| 方案 | 类型 | 开源协议 | 开发语言 | 发布时间 |
|------|------|----------|----------|----------|
| Chroma | 嵌入式/服务端 | Apache 2.0 | Python | 2022 |
| Milvus | 分布式服务 | Apache 2.0 | Go/C++ | 2019 |
| Qdrant | 分布式服务 | Apache 2.0 | Rust | 2021 |

### 3.2 功能对比

| 功能维度 | Chroma | Milvus | Qdrant |
|----------|--------|--------|--------|
| **索引类型** | HNSW、Flat | HNSW、IVF、PQ、SCANN | HNSW、Flat |
| **相似度度量** | L2、Cosine、IP | 全部 | 全部 |
| **元数据过滤** | 基础键值 | 复杂表达式 | 复杂表达式 |
| **混合检索** | 不支持 | 支持 | 支持 |
| **分布式部署** | 不支持 | 支持 | 支持 |
| **数据持久化** | SQLite/Parquet | 独立存储 | RocksDB |
| **备份恢复** | 手动导出 | 原生支持 | 原生支持 |
| **多租户** | 通过 Collection | 通过 Partition | 通过 Payload |

### 3.3 性能对比

| 性能指标 | Chroma | Milvus | Qdrant |
|----------|--------|--------|--------|
| **单节点 QPS** | 100-500 | 1000-5000 | 500-3000 |
| **P99 延迟** | 50-200ms | 10-50ms | 20-80ms |
| **百万向量内存** | ~8GB | ~4GB（带 PQ） | ~6GB |
| **写入吞吐** | 低 | 高 | 中 |
| **扩展能力** | 垂直扩展 | 水平扩展 | 水平扩展 |

### 3.4 运维对比

| 运维维度 | Chroma | Milvus | Qdrant |
|----------|--------|--------|--------|
| **部署复杂度** | 低（单进程） | 高（多组件） | 中（单二进制） |
| **依赖组件** | 无 | etcd、MinIO、Pulsar | 无 |
| **监控支持** | 基础指标 | Prometheus + Grafana | Prometheus + Grafana |
| **社区活跃度** | 中 | 高 | 中高 |
| **生产案例** | 较少 | 大量 | 较多 |

### 3.5 综合评分

| 评估维度 | 权重 | Chroma | Milvus | Qdrant |
|----------|------|--------|--------|--------|
| 功能完整性 | 20% | 6 | 9 | 8 |
| 查询性能 | 25% | 5 | 9 | 8 |
| 扩展能力 | 20% | 3 | 9 | 8 |
| 运维成本 | 15% | 9 | 5 | 7 |
| 社区生态 | 10% | 6 | 9 | 7 |

- Chroma: 5.85

## 4. 选型建议与决策理由

### 4.1 推荐方案：Milvus

**决策理由：**

1. **性能最优**：在百万级向量场景下，Milvus 的 HNSW+PQ 组合提供最佳性能/内存比
2. **扩展性强**：原生分布式架构，支持水平扩展，适合 Orion 平台未来增长
3. **功能完整**：支持混合检索、复杂过滤、多 Partition，满足多场景需求
4. **生态成熟**：社区活跃，生产案例多，问题排查资源充足

### 4.2 备选方案：Qdrant

**适用场景：**
- 向量规模在 50 万以下
- 希望降低运维复杂度（单二进制部署）
- 对 Rust 技术栈有偏好

### 4.3 不推荐：Chroma

**原因：**
- 不支持分布式部署，无法水平扩展
- 性能和功能在生产规模下存在瓶颈
- 适合开发/测试环境，不推荐生产使用

### 4.4 分阶段采用策略

| 阶段 | 向量规模 | 推荐方案 | 说明 |
|------|----------|----------|------|
| 开发/测试 | < 10 万 | Chroma | 快速迭代，零运维 |
| 生产初期 | 10 万 -50 万 | Qdrant（单节点） | 简化部署，性能足够 |
| 生产成熟 | 50 万 + | Milvus（分布式） | 水平扩展，高可用 |

## 5. 向量索引策略

### 5.1 索引类型对比

| 索引类型 | 全称 | 适用场景 | 构建速度 | 查询速度 | 内存占用 |
|----------|------|----------|----------|----------|----------|
| Flat | 暴力搜索 | < 1 万向量 | 无需构建 | 慢 | 低 |
| HNSW | Hierarchical Navigable Small World | 高精度、低延迟 | 慢 | 最快 | 高 |
| IVF | Inverted File Index | 大规模、可接受精度损失 | 快 | 快 | 中 |
| PQ | Product Quantization | 超大规模、内存敏感 | 中 | 中 | 最低 |

### 5.2 推荐索引配置

#### 5.2.1 AI Skill 检索（千级向量）

```yaml
索引类型：HNSW
参数配置:
  m: 16              # 每个节点的连接数
  efConstruction: 200 # 构建时搜索范围
  efSearch: 64       # 查询时搜索范围
理由：向量少，追求最高查询精度和速度
```

#### 5.2.2 根因分析匹配（十万级向量）

```yaml
索引类型：HNSW + 可选 PQ
参数配置:
  m: 32
  efConstruction: 256
  efSearch: 128
  PQ 编码：可选（内存紧张时启用）
理由：平衡精度与资源，支持增量更新
```

#### 5.2.3 语义搜索（百万级向量）

```yaml
索引类型：IVF_PQ 或 HNSW_PQ
参数配置:
  IVF 桶数：4096
  PQ 子向量数：16
  训练样本：10 万
理由：大规模场景下最优内存/性能比
```

### 5.3 索引参数调优指南

| 参数 | 调大效果 | 调小效果 | 调优建议 |
|------|----------|----------|----------|
| HNSW.m | 精度提升，内存增加 | 精度下降，内存减少 | 从 16 开始，按精度调整 |
| HNSW.efConstruction | 索引质量提升，构建变慢 | 索引质量下降，构建变快 | 设为 m 的 10-15 倍 |
| HNSW.efSearch | 召回率提升，查询变慢 | 召回率下降，查询变快 | 从 64 开始，按延迟调整 |
| IVF.nlist | 适合更大数据量 | 适合较小数据量 | 设为向量数的 4-16 倍 |

### 6.2 MySQL 数据同步流程

**适用场景：** AI Skill 元数据、配置信息、结构化数据

**同步模式：**

| 模式 | 说明 | 适用场景 |
|------|------|----------|
| 全量同步 | 定期全量重建向量 | 初始化、数据修复 |
| CDC 增量 | 监听 Binlog 实时同步 | 生产环境主模式 |
| 应用层双写 | 业务代码同时写入 | 简单场景、低延迟要求 |

**CDC 增量同步流程：**

```
1. MySQL Binlog → Debezium/Kafka Connect
2. Kafka → 向量化服务（消费消息）
3. 向量化服务 → 调用嵌入模型生成向量
4. 向量化服务 → 批量写入向量数据库
5. 写入状态 → 回写 MySQL（可选）
```

**元数据映射示例：**

```yaml
MySQL 表：ai_skills
向量数据库字段映射:
  id → vector_id (主键)
  name → payload.name
  description → 向量化字段
  category → payload.category
  tags → payload.tags[]
  enabled → payload.enabled
  created_at → payload.timestamp
  updated_at → payload.updated_at
```

### 6.3 ClickHouse 数据同步流程

**适用场景：** 日志向量、故障特征向量、时序数据

**同步模式：**

| 模式 | 说明 | 适用场景 |
|------|------|----------|
| 物化视图 | ClickHouse 内预处理 | 实时性要求高 |
| 定期导出 | 定时任务导出 Parquet/CSV | 批量处理 |
| Kafka 桥接 | ClickHouse → Kafka → 向量化 | 实时流式 |

**推荐流程（Kafka 桥接）：**

```
1. ClickHouse → Kafka (使用 Kafka Engine)
   - 按时间窗口聚合日志
   - 提取关键字段（message、level、service）

2. Kafka → 向量化服务
   - 消费日志聚合消息
   - 生成日志语义向量

3. 向量化服务 → 向量数据库
   - 写入向量及元数据（时间、服务、级别）
   - 设置 TTL（如保留 1 年数据）
```

### 6.4 数据一致性保障

| 一致性级别 | 实现方式 | 适用场景 |
|------------|----------|----------|
| 最终一致 | 异步同步，容忍短暂延迟 | 大多数场景 |
| 强一致 | 同步写入，事务保障 | Skill 配置等关键数据 |
| 可配置 | 按数据类型选择 | 混合场景 |

**数据校验机制：**

```yaml
校验频率: 每小时
校验内容:
  - 向量数量对比（MySQL vs 向量库）
  - 关键字段哈希校验
  - 最近 N 条数据内容比对
告警规则:
  - 数量差异 > 1% → WARNING
  - 数量差异 > 5% → CRITICAL
  - 校验失败持续 3 次 → 触发告警
```

### 6.5 向量更新与删除

**更新策略：**

| 更新类型 | 处理方式 |
|----------|----------|
| 向量变更 | 删除旧向量 + 插入新向量 |
| 元数据变更 | 仅更新 payload（Qdrant）/ 重建（Milvus） |
| 软删除 | 更新元数据标记 deleted=true |
| 硬删除 | 从向量库物理删除 |

**批量处理建议：**

```yaml
批量大小：1000
并发度：4
重试策略:
  最大重试：3
  退避：指数退避 (1s, 2s, 4s)
  死信：失败消息入 DLQ
```

## 7. 相似度检索流程

### 7.1 检索流程总览

```

│                    相似度检索流程                                │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  1. 请求接入                                                     │
│     用户查询 → API Gateway → 检索服务                           │
│                     │                                            │
│                     ▼                                            │
│  2. 查询预处理                                                   │
│     - 文本清洗/标准化                                            │

│     - 元数据过滤条件解析                                         │
│                     │                                            │
│                     ▼                                            │
│  3. 向量化                                                     │
│     查询文本 → 嵌入模型 → 查询向量                              │
│                     │                                            │
│                     ▼                                            │
│  4. 向量检索                                                   │
│     查询向量 + 过滤条件 → 向量数据库 → Top-K 结果               │
│                     │                                            │
│                     ▼                                            │
│  5. 后处理                                                     │
│     - 分数归一化                                                 │

```

### 7.2 检索 API 设计

**请求参数：**

```yaml
/search:
  method: POST
  body:
    vector: [0.1, 0.2, ...]    # 查询向量（可选，与 query 互斥）
    query: "用户问题文本"        # 查询文本（可选，与 vector 互斥）
    collection: "ai_skills"    # 目标集合
    top_k: 10                  # 返回数量
    filters:                   # 元数据过滤（可选）
      category: "code-review"
      enabled: true
      tags: ["python", "security"]
    score_threshold: 0.6       # 最低相似度阈值（可选）
```

**响应格式：**

```yaml
{
  "code": 0,
  "message": "success",
  "data": {
    "total": 10,
    "latency_ms": 45,
    "results": [
      {
        "id": "skill-001",
        "score": 0.92,
        "payload": {
          "name": "Python 代码审查",
          "description": "...",
          "category": "code-review",
          "tags": ["python", "security"]
        }
      }
    ]
  }
}
```

### 7.3 混合检索策略

**适用场景：** 语义搜索（向量 + 关键词）

**检索流程：**

```
1. 向量检索 → 获取 Top-N 候选（N > top_k）
2. 关键词检索（BM25） → 获取 Top-N 候选
3. 候选合并 → 去重得到并集
4. 分数融合：
   final_score = α * vector_score + β * keyword_score
   (α + β = 1，通常 α=0.7, β=0.3)
5. 重排序 → 返回 Top-K
```

### 7.4 缓存策略

**缓存层级：**

| 层级 | 缓存内容 | TTL | 适用场景 |
|------|----------|-----|----------|
| L1 | 热点查询结果 | 5 分钟 | 高频相同查询 |
| L2 | 查询向量 | 1 小时 | 避免重复向量化 |
| L3 | 元数据 | 10 分钟 | 减少回表查询 |

**缓存键设计：**

```
cache_key = hash(vector + collection + filters + top_k)
```

## 8. 向量存储监控指标

### 8.1 监控指标总览

| 指标类别 | 指标名称 | 告警阈值 | 说明 |
|----------|----------|----------|------|
| **可用性** | 服务健康状态 | down → P0 | 服务是否可访问 |
| **性能** | 查询 P99 延迟 | > 200ms → P1 | 查询延迟 |
| **性能** | 写入 P99 延迟 | > 500ms → P1 | 写入延迟 |
| **性能** | QPS | 突增/突降 50% → P2 | 查询量异常 |
| **容量** | 向量总数 | 接近上限 80% → P2 | 容量预警 |
| **容量** | 内存使用率 | > 80% → P1 | 内存压力 |
| **容量** | 磁盘使用率 | > 80% → P1 | 磁盘压力 |
| **质量** | 索引构建进度 | 停滞 > 1h → P2 | 索引异常 |
| **质量** | 搜索召回率 | < 90% → P2 | 索引质量下降 |
| **同步** | 同步延迟 | > 5min → P2 | 数据延迟 |
| **同步** | 同步失败率 | > 1% → P1 | 同步异常 |

## 9. 扩展与分片策略

### 9.1 扩展模式

| 扩展模式 | 说明 | 适用阶段 |
|----------|------|----------|
| 垂直扩展 | 增加单节点资源（CPU/MEM） | 初期 |
| 水平扩展 | 增加节点数量 | 成长期 |
| 读写分离 | QueryNode 与 DataNode 分离 | 高读负载 |
| 分片集群 | 按 Collection 分片 | 多租户 |

### 9.2 Milvus 分片策略

**分片键选择：**

| 分片键 | 说明 | 适用场景 |
|--------|------|----------|
| Collection | 每 Collection 独立分片 | 多租户隔离 |
| Partition | 按时间/业务分区 | 时序数据 |
| Shard | 数据自动分片 | 超大规模 |

**推荐配置：**

```yaml
# Milvus 集群配置
集群规模:
  初始：3 节点
  扩展：最多 10 节点
  
分片配置:
  每 Collection Shard 数：2-4
  每 Shard 目标大小：10-50GB
  
副本配置:
  QueryNode 副本数：2（高可用）
  DataNode 副本数：1（数据在对象存储）
```

### 9.3 数据分布策略

**AI Skill 检索：**
```yaml
分片策略：单分片（数据量小）
副本数：2
部署：与检索服务同可用区
```

**根因分析匹配：**
```yaml
分片策略：按时间 Partition
  - partition_pattern: "log_{YYYYMM}"
  - 保留策略：自动删除 12 个月前数据
分片数：2
副本数：2
```

**语义搜索：**
```yaml
分片策略：按业务分片
  - 代码搜索：code_shards (2)
  - 文档搜索：doc_shards (2)
  - 配置搜索：config_shards (1)
副本数：2
部署：多可用区
```

### 9.4 容量规划

| 组件 | 初始配置 | 1 年预期 | 3 年预期 |
|------|----------|----------|----------|
| 向量总数 | 10 万 | 100 万 | 500 万 |
| 存储需求 | 10GB | 100GB | 500GB |
| 内存需求 | 8GB | 32GB | 128GB |
| 节点数量 | 3 | 5 | 10 |
| QPS 峰值 | 100 | 500 | 2000 |

### 9.5 扩展操作流程

**水平扩展（增加节点）：**

```
1. 准备新节点（相同配置）
2. 加入集群（etcd 注册）
3. 数据重平衡（自动）
4. 验证集群状态
5. 更新监控配置
```

**缩容操作（减少节点）：**

```
1. 确认目标节点可安全下线
2. 数据迁移到其他节点
3. 从集群移除（etcd 注销）
4. 销毁节点资源
5. 更新监控配置
```
