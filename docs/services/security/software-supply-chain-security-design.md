# Orion 软件供应链安全详细设计方案

## 1. 背景与问题

### 1.1 供应链安全现状

当前 Orion 平台在软件供应链安全方面存在严重缺失：

| 问题领域 | 当前状态 | 风险等级 |
|---------|---------|---------|
| SBOM（软件物料清单） | 无 | 🔴 高危 |
| 镜像签名 | 无 | 🔴 高危 |
| 漏洞扫描 | 手动、 sporadic | 🟡 中危 |
| 构建环境隔离 | 共享构建节点 | 🟡 中危 |
| 依赖版本锁定 | 部分锁定 | 🟡 中危 |
| SLSA 合规 | 未评估 | 🟡 中危 |

### 1.2 行业安全事件案例

**SolarWinds 事件（2020）**
- 攻击者入侵构建系统，在 Orion 软件更新中植入后门
- 影响 18000+ 组织，包括美国财政部、商务部
- 损失估计超过 1 亿美元

**CodeCov 事件（2021）**
- CI/CD 脚本被篡改，导致客户凭证泄露
- 影响 29000+ 客户代码库
- 暴露 Docker 密钥、云服务凭证、API 密钥

**Log4j 漏洞（2021）**
- 广泛使用的日志库存在远程代码执行漏洞
- 影响 Java 生态系统数百万应用
- 根本原因：依赖传递性不透明，无法快速定位受影响组件

**XZ Utils 后门事件（2024）**
- 攻击者通过长期贡献获取信任，在压缩库中植入后门
- 几乎影响所有 Linux 发行版
- 暴露开源供应链"信任但验证"机制缺失

### 1.3 合规驱动

| 法规/标准 | 要求 | 截止期限 |
|----------|------|---------|
| 美国行政令 14028 | SBOM + SLSA Level 2+ | 已生效 |
| 欧盟 Cyber Resilience Act | 软件成分披露 + 漏洞报告 | 2027 |
| 中国等保 2.0 | 供应链安全控制 | 已生效 |
| GDPR | 数据处理组件可追溯 | 已生效 |
| 金融行业规范 | 第三方组件风险评估 | 已生效 |

## 2. SLSA 框架集成

### 2.1 SLSA 概述

SLSA（Supply-chain Levels for Software Artifacts）是由 Google、Google Cloud、Red Hat 等联合制定的软件供应链安全框架，定义从源码到构建的可验证路径。

### 2.2 Orion SLSA Level 3 目标架构

```
┌─────────────────────────────────────────────────────────────────────┐
│                        SLSA Level 3 要求                             │
├─────────────────────────────────────────────────────────────────────┤
│  1. 源码版本控制        │ 所有代码在版本控制系统中追踪              │
│  2. 可重现构建          │ 构建过程可审计、可重复                    │
│  3. 构建环境隔离        │ 构建在可信、隔离环境中执行                │
│  4. 构建证明（Provenance）│ 生成加密签名的构建溯源文件              │
│  5. 完整性验证          │ 消费者可验证构建证明                      │
└─────────────────────────────────────────────────────────────────────┘
```

### 3.1 SBOM 标准选择

| 特性 | CycloneDX | SPDX | SWID |
|-----|-----------|------|------|
| 格式 | JSON/XML | Tag-Value/RDF/JSON | XML |
| 大小 | 轻量级 | 较详细 | 中等 |

| 工具生态 | 丰富 | 丰富 | 有限 |

## 4. 镜像签名与验证

### 4.1 签名方案选择

采用 **Sigstore cosign** 进行无密钥（keyless）签名：

| 特性 | Cosign | Notary v2 | Docker Content Trust |
|-----|--------|-----------|---------------------|
| 密钥管理 | OIDC 无密钥 | 外部 KMS | 本地密钥 |
| 透明度 | ✅ Rekor | ⚠️ 可选 | ❌ |
| 身份绑定 | ✅ OIDC 身份 | ⚠️ 证书 | ❌ |
| Kubernetes 集成 | ✅ 成熟 | ⚠️ 中等 | ⚠️ 中等 |
| 社区生态 | CNCF 毕业 | CNCF 沙盒 | Docker 专有 |

### 4.3 签名策略定义

```yaml
# 签名策略配置 (cosign-policy.yaml)
apiVersion: policy.sigstore.dev/v1
kind: ClusterImagePolicy
metadata:
  name: orion-global-policy
spec:
  images:
  - glob: "harbor.orion.local/orion/**"
  authorities:
  - keyless:
      url: https://fulcio.sigstore.dev
      identities:
      - issuer: "https://github.com/login/oauth"
        issuerRegExp: ".*"
        subjectRegExp: "https://github.com/orion-design/.*"
  - key:
      secretRef:
        name: cosign-signing-key
    name: release-signing-key
  policy:
    type: cue
    data: |
      // 策略规则
      package main
      import "time"
      
      // 签名必须在最近 24 小时内
      age := time.parse(time.RFC3339, body.Signature.Timestamp)
      age > time.subtract(time.now(), "24h")
      
      // 必须有 Rekor 审计证明
      hasRekorEntry := true
```

## 5. 漏洞扫描与修复

### 5.1 扫描工具选型

采用 **Trivy + Grype** 双引擎策略：

| 维度 | Trivy | Grype |
|-----|-------|-------|
| 扫描对象 | 容器/FS/Git/VM | 容器/FS |
| 漏洞数据库 | Aqua Security | Anchore |
| 速度 | 快 | 中等 |
| 误报率 | 低 | 低 |
| SBOM 支持 | ✅ CycloneDX/SPDX | ✅ CycloneDX/SPDX |
| Kubernetes 集成 | ✅ | ⚠️ |
| 许可证检测 | ✅ | ✅ |
