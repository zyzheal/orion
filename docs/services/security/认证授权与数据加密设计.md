## 一、JWT 管理设计

### 1.1 JWT 结构与存储

```
┌─────────────────────────────────────────────────────────────────┐
│              JWT Token 结构与管理                                │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  双 Token 架构                                                   │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │                                                         │   │
│  │  Access Token (短期令牌)                                  │   │
│  │  ┌───────────────────────────────────────────────────┐ │   │
│  │  │ • 有效期：15 分钟                                   │ │   │
│  │  │ • 用途：API 请求认证                               │ │   │
│  │  │ • 存储：HttpOnly Cookie (前端不可访问)             │ │   │
│  │  │ • 包含：user_id, roles, permissions, exp         │ │   │
│  │  │ • 签名：RS256 (非对称加密)                         │ │   │
│  │  └───────────────────────────────────────────────────┘ │   │
│  │                                                         │   │
│  │  Refresh Token (长期令牌)                                 │   │
│  │  ┌───────────────────────────────────────────────────┐ │   │
│  │  │ • 有效期：7 天                                     │ │   │
│  │  │ • 用途：刷新 Access Token                          │ │   │
│  │  │ • 存储：服务端 Redis (前端不存储)                   │ │   │
│  │  │ • 包含：user_id, device_id, exp, jti             │ │   │
│  │  │ • 签名：HS256 (对称加密)                           │ │   │
│  │  └───────────────────────────────────────────────────┘ │   │
│  │                                                         │   │
│  └─────────────────────────────────────────────────────────┘   │

### 1.2 Token 刷新流程

```
┌─────────────────────────────────────────────────────────────────┐
│              Token 刷新流程                                      │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  正常刷新流程                                                    │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │                                                         │   │
│  │  T-2 分钟 (Access Token 过期前 2 分钟)                       │   │
│  │       │                                                 │   │
│  │       ▼                                                 │   │
│  │  前端检测到 Access Token 即将过期                          │   │
│  │       │                                                 │   │
│  │       ▼                                                 │   │
│  │  前端调用 /auth/refresh 接口                             │   │
│  │  请求：POST /auth/refresh                               │   │
│  │  Cookie: refresh_token=xxx                              │   │
│  │       │                                                 │   │
│  │       ▼                                                 │   │
│  │  服务端验证 Refresh Token                                │   │
│  │  • 检查签名是否有效                                      │   │
│  │  • 检查是否过期                                          │   │
│  │  • 检查是否在吊销列表中                                  │   │
│  │  • 检查设备 ID 是否匹配                                   │   │
│  │       │                                                 │   │
│  │       ▼                                                 │   │
│  │  验证通过 → 生成新 Token 对                                │   │
│  │  • 新 Access Token (15 分钟)                              │   │
│  │  • 新 Refresh Token (7 天，轮换)                          │   │
│  │  • 旧 Refresh Token 立即失效                              │   │
│  │       │                                                 │   │
│  │       ▼                                                 │   │
│  │  返回新 Token                                             │   │
│  │  • Set-Cookie: access_token=xxx; HttpOnly; Secure      │   │
│  │  • Set-Cookie: refresh_token=xxx; HttpOnly; Secure     │   │
│  │       │                                                 │   │
│  │       ▼                                                 │   │
│  │  前端继续正常请求                                         │   │
│  │                                                         │   │
│  └─────────────────────────────────────────────────────────┘   │
│                                                                 │
│  刷新失败处理                                                    │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │                                                         │   │
│  │  失败场景 1: Refresh Token 过期                            │   │
│  │  处理：                                                  │   │
│  │  • 返回 401 Unauthorized                                │   │
│  │  • 清除所有 Cookie                                       │   │
│  │  • 前端跳转到登录页                                      │   │
│  │                                                         │   │
│  │  失败场景 2: Refresh Token 无效 (被吊销/篡改)               │   │
│  │  处理：                                                  │   │
│  │  • 返回 401 Unauthorized                                │   │
│  │  • 记录安全事件到审计日志                                 │   │
│  │  • 发送安全告警 (可能的 Token 泄露)                        │   │
│  │  • 清除所有 Cookie                                       │   │
│  │  • 前端跳转到登录页                                      │   │
│  │                                                         │   │
│  │  失败场景 3: 用户已被禁用                                  │   │
│  │  处理：                                                  │   │
│  │  • 返回 403 Forbidden                                   │   │
│  │  • 记录审计日志                                          │   │
│  │  • 通知管理员                                            │   │
│  │                                                         │   │
│  └─────────────────────────────────────────────────────────┘   │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 1.3 Token 吊销机制

```
┌─────────────────────────────────────────────────────────────────┐
│              Token 吊销机制                                      │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  吊销场景                                                        │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │                                                         │   │
│  │  场景 1: 用户主动登出                                      │   │
│  │  吊销范围：该用户所有设备的 Token                          │   │
│  │  生效时间：立即                                          │   │
│  │                                                         │   │
│  │  场景 2: 用户密码修改                                      │   │
│  │  吊销范围：该用户所有设备的 Token                          │   │
│  │  生效时间：立即                                          │   │
│  │  额外动作：发送安全通知邮件                               │   │
│  │                                                         │   │
│  │  场景 3: 用户离职/账号禁用                                 │   │
│  │  吊销范围：该用户所有设备的 Token                          │   │
│  │  生效时间：立即                                          │   │
│  │  额外动作：转移待审批、通知主管                           │   │
│  │                                                         │   │
│  │  场景 4: 异常登录检测                                      │   │
│  │  吊销范围：可疑设备的 Token                                │   │
│  │  生效时间：立即                                          │   │
│  │  额外动作：发送安全告警、要求重新认证                     │   │
│  │                                                         │   │
│  │  场景 5: 安全事件 (密钥泄露)                               │   │
│  │  吊销范围：所有用户的 Token                                │   │
│  │  生效时间：立即                                          │   │
│  │  额外动作：轮换密钥、全面审计                             │   │
│  │                                                         │   │
│  └─────────────────────────────────────────────────────────┘   │
│                                                                 │
│  吊销列表管理                                                    │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │                                                         │   │
│  │  存储：Redis                                             │   │
│  │  结构：                                                  │   │
│  │  • Key: token:jti:{jti}                                │   │
│  │  • Value: {user_id, reason, revoked_at}               │   │
│  │  • TTL: Token 剩余有效期                                 │   │
│  │                                                         │   │
│  │  同步机制：                                              │   │
│  │  • 所有 API 服务订阅 Redis 吊销列表更新                     │   │
│  │  • 每次 API 请求检查 Token 的 jti 是否在吊销列表             │   │
│  │  • 检查延迟：< 1 秒                                       │   │
│  │                                                         │   │
│  │  清理机制：                                              │   │
│  │  • Token 过期后自动从吊销列表删除                         │   │
│  │  • 每日凌晨清理过期吊销记录                              │   │
│  │                                                         │   │
│  └─────────────────────────────────────────────────────────┘   │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

## 二、密钥管理设计

### 2.1 密钥分层管理

```
┌─────────────────────────────────────────────────────────────────┐
│              密钥分层管理架构                                    │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  密钥层级                                                        │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │                                                         │   │
│  │  Level 1: 主密钥 (Master Key)                             │   │
│  │  ┌───────────────────────────────────────────────────┐ │   │
│  │  │ • 用途：加密数据密钥                                │ │   │
│  │  │ • 存储：HashiCorp Vault (HSM 硬件加密模块)           │ │   │
│  │  │ • 访问：仅密钥管理员可访问                          │ │   │
│  │  │ • 轮换：每年 1 次                                    │ │   │
│  │  │ • 备份：多地离线备份 (保险柜)                        │ │   │
│  │  └───────────────────────────────────────────────────┘ │   │
│  │                                                         │   │
│  │  Level 2: 数据密钥 (Data Key)                             │   │
│  │  ┌───────────────────────────────────────────────────┐ │   │
│  │  │ • 用途：加密实际数据                                │ │   │
│  │  │ • 存储：Vault (加密存储)                           │ │   │
│  │  │ • 访问：应用服务按需申请                            │ │   │
│  │  │ • 轮换：每 90 天                                     │ │   │
│  │  │ • 数量：每个数据类型独立密钥                        │ │   │
│  │  └───────────────────────────────────────────────────┘ │   │
│  │                                                         │   │
│  │  Level 3: 会话密钥 (Session Key)                          │   │
│  │  ┌───────────────────────────────────────────────────┐ │   │
│  │  │ • 用途：加密单次会话数据                            │ │   │
│  │  │ • 存储：内存 (不持久化)                             │ │   │
│  │  │ • 访问：会话期间有效                                │ │   │
│  │  │ • 轮换：每次会话                                    │ │   │
│  │  │ • 生成：使用数据密钥派生                            │ │   │
│  │  └───────────────────────────────────────────────────┘ │   │
│  │                                                         │   │
│  └─────────────────────────────────────────────────────────┘   │
│                                                                 │
│  密钥类型与用途                                                  │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │                                                         │   │
│  │  JWT 签名密钥：                                           │   │
│  │  • 算法：RS256 (非对称)                                  │   │
│  │  • 用途：签名和验证 JWT                                  │   │
│  │  • 私钥：Vault 存储，仅认证服务可访问                     │   │
│  │  • 公钥：所有 API 服务可访问                              │   │
│  │                                                         │   │
│  │  数据加密密钥：                                          │   │
│  │  • 算法：AES-256-GCM                                    │   │
│  │  • 用途：加密敏感数据 (密码/Token/PII)                   │   │
│  │  • 存储：Vault 加密存储                                  │   │
│  │  • 访问：需要加密/解密的服务申请                          │   │
│  │                                                         │   │
│  │  TLS 证书密钥：                                          │   │
│  │  • 算法：ECDSA P-256                                    │   │
│  │  • 用途：HTTPS/TLS 通信                                  │   │
│  │  • 管理：cert-manager 自动管理                           │   │
│  │  • 轮换：每 90 天 (Let's Encrypt)                         │   │
│  │                                                         │   │
│  └─────────────────────────────────────────────────────────┘   │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 2.2 密钥轮换流程

```
┌─────────────────────────────────────────────────────────────────┐
│              密钥轮换流程                                        │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  JWT 签名密钥轮换 (每 90 天)                                       │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │                                                         │   │
│  │  T-7 天 (轮换前 7 天)                                      │   │
│  │       │                                                 │   │
│  │       ▼                                                 │   │
│  │  生成新密钥对                                            │   │
│  │  • 在 Vault 中生成新 RSA 密钥对                            │   │
│  │  • 新私钥标记为"pending"                                 │   │
│  │  • 新公钥分发给所有 API 服务                              │   │
│  │       │                                                 │   │
│  │       ▼                                                 │   │
│  │  T-1 天 (轮换前 1 天)                                      │   │
│  │       │                                                 │   │
│  │       ▼                                                 │   │
│  │  双密钥并行期                                            │   │
│  │  • 旧密钥标记为"deprecated"                              │   │
│  │  • 新密钥标记为"pending"                                 │   │
│  │  • 认证服务仍用旧密钥签名                                 │   │
│  │  • API 服务接受新旧两个密钥验证                           │   │
│  │       │                                                 │   │
│  │       ▼                                                 │   │
│  │  T+0 (轮换日)                                            │   │
│  │       │                                                 │   │
│  │       ▼                                                 │   │
│  │  切换新密钥                                              │   │
│  │  • 新密钥标记为"active"                                  │   │
│  │  • 认证服务开始用新密钥签名                               │   │
│  │  • API 服务优先用新密钥验证                               │   │
│  │       │                                                 │   │
│  │       ▼                                                 │   │
│  │  T+7 天 (轮换后 7 天)                                      │   │
│  │       │                                                 │   │
│  │       ▼                                                 │   │
│  │  清理旧密钥                                              │   │
│  │  • 旧密钥标记为"revoked"                                 │   │
│  │  • 从 API 服务移除旧公钥                                  │   │
│  │  • 旧私钥归档 (保留 1 年用于审计)                          │   │
│  │       │                                                 │   │
│  │       ▼                                                 │   │
│  │  轮换完成                                                │   │
│  │                                                         │   │
│  └─────────────────────────────────────────────────────────┘   │
│                                                                 │
│  密钥泄露应急预案                                                │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │                                                         │   │
│  │  检测阶段：                                              │   │
│  │  • 监控异常密钥使用模式                                  │   │
│  │  • 接收密钥泄露报告                                      │   │
│  │  • 确认泄露范围和影响                                    │   │
│  │                                                         │   │
│  │  响应阶段 (1 小时内):                                     │   │
│  │  • 立即吊销泄露密钥                                      │   │
│  │  • 生成新密钥并激活                                      │   │
│  │  • 吊销所有现有 Token (强制用户重新登录)                  │   │
│  │  • 发送安全通知给所有用户                                 │   │
│  │                                                         │   │
│  │  恢复阶段 (24 小时内):                                    │   │
│  │  • 审计泄露原因                                          │   │
│  │  • 修复安全漏洞                                          │   │
│  │  • 编写事故报告                                          │   │
│  │  • 更新安全策略                                          │   │
│  │                                                         │   │
│  └─────────────────────────────────────────────────────────┘   │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

## 三、数据加密设计

### 3.1 传输加密

```
┌─────────────────────────────────────────────────────────────────┐
│              传输加密设计                                        │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  外部通信加密 (用户 → API)                                       │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │                                                         │   │
│  │  协议：TLS 1.3                                           │   │
│  │                                                         │   │
│  │  证书管理：                                              │   │
│  │  • 证书颁发：Let's Encrypt                               │   │
│  │  • 自动续期：cert-manager (到期前 30 天续期)                │   │
│  │  • 证书存储：K8s Secret                                  │   │
│  │  • 最低加密套件：TLS_AES_256_GCM_SHA384                 │   │
│  │                                                         │   │
│  │  强制 HTTPS:                                             │   │
│  │  • HTTP 自动重定向到 HTTPS                                │   │
│  │  • HSTS 头：max-age=31536000; includeSubDomains         │   │
│  │  • 禁用 HTTP 的方法：OPTIONS 除外                          │   │
│  │                                                         │   │
│  │  证书吊销检查：                                          │   │
│  │  • OCSP Stapling 启用                                    │   │
│  │  • CRL 定期更新                                          │   │
│  │                                                         │   │
│  └─────────────────────────────────────────────────────────┘   │
│                                                                 │
│  内部通信加密 (服务 → 服务)                                       │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │                                                         │   │
│  │  协议：mTLS (双向 TLS)                                    │   │
│  │                                                         │   │
