# CI/CD 平台能力域优化设计

> **日期**: 2026-05-05
> **状态**: 已评审
> **作者**: Claude (Brainstorming)
> **评审日期**: 2026-05-05

## 一、背景

在整理 CI/CD 平台能力域过程中，我们识别出 42 个能力域。经过深入分析，发现存在以下问题：
- 能力域粒度过细，存在大量重叠
- 缺乏层次划分和优先级判断依据
- 缺少能力成熟度模型
- 遗漏若干关键能力

本文档提出优化方案：将 42 个域合并为 32 个，补充遗漏能力，并定义能力成熟度模型。

## 二、现状分析

### 2.1 当前 Orion 架构

| 维度 | 当前实现 |
|------|----------|
| **后端架构** | Node.js/Fastify 单体（48 routes, 70+ services, 38 repos） |
| **前端架构** | React 18 + Vite + Ant Design 5 + wujie 微前端（57+ pages） |
| **数据层** | PostgreSQL（70+ migrations）+ Redis + NATS（optional） |
| **流水线引擎** | PipelineEngine → StageExecutor → TaskRunner |
| **已实现能力** | 核心流水线、质量门禁、部署发布、可观测性、安全合规、AI 智能化、平台工程、环境管理 |

### 2.2 Orion 理念边界

Orion 的核心理念是 **"不替代现有工具链，而是让现有工具链变聪明"**。基于此：
- **自建能力**：编排层、决策层、可视化层（Orion 核心）
- **集成能力**：Tekton（执行引擎）、Prometheus（监控）、Gitleaks（安全扫描）等通过插件接入
- **插件市场**（25）是与现有工具集成的入口，不是替代

### 2.3 42 个能力域存在的问题

| 问题类型 | 具体表现 | 影响 |
|----------|----------|------|
| **重叠** | 成本智能 vs 成本精细化管控、可观测性 vs 运营可观测性 | 理解复杂，可能重复建设 |
| **缺乏层次** | 未区分核心/增值/生态能力 | 优先级判断困难 |
| **缺少成熟度模型** | 无 L1-L5 等级定义 | 无法量化建设进度 |
| **遗漏关键能力** | 开发者门户、审批工作流、灰度流量控制等 | 功能不完整 |

## 三、能力域优化方案

### 3.1 合并规则

| 合并前 | 合并后 | 理由 |
|--------|--------|------|
| 14. 成本智能 + 20. 成本精细化管控 | **成本运营** | 功能高度重叠 |
| 5. 可观测性 + 21. 运营可观测性 | **全栈可观测** | 运营可观测是可观测性的子集 |
| 18. 环境即服务 + 37. 环境管理面板 | **环境管理** | 面板是环境的展示层 |

## 四、能力成熟度模型

### 4.1 成熟度等级定义（CI/CD 领域定制）

| 等级 | 名称 | CI/CD 判据 | 示例 |
|:----:|------|------------|------|
| **L0** | 未实现 | 无任何相关功能 | 联邦调度、多云部署 |
| **L1** | 初始 | 基础功能可用，手动操作为主，无自动化 | 有环境管理界面，但创建需手动配置 |
| **L2** | 可重复 | 功能稳定可重复，有执行记录和基础监控，手动配置为主 | 流水线可重复执行，有日志可查 |
| **L3** | 已定义 | 功能覆盖完整场景，有模板库，部分自动化，80% 常见场景有预定义模板 | DAG 编排、模板库、嵌套流水线 |
| **L4** | 已管理 | 有度量指标，可自动优化，数据驱动决策，执行预算可控 | 动态流水线、执行预算、版本控制 |
| **L5** | 已优化 | AI 驱动自动决策，自修复，持续优化，零人工干预 | 自编排、自修复、自优化 |

### 4.2 成熟度评估示例（核心流水线）

| 等级 | 能力表现 | Orion 现状 |
|:----:|----------|:----------:|
| L1 | 支持 YAML 声明式流水线 | ✅ 已实现 |
| L2 | 支持可视化编排，有执行日志 | ✅ 已实现 |
| L3 | 支持 DAG、模板库、嵌套流水线 | ✅ 已实现（部分） |
| L4 | 支持动态流水线、执行预算、版本控制 | ❌ 待实现 |
| L5 | 自编排、自修复、自优化 | ❌ 待实现 |

### 4.3 全平台成熟度概览（修正版）

| 层级 | 当前 | 目标（6 个月） | 目标（12 个月） | 目标（18 个月） |
|------|:----:|:--------------:|:---------------:|:---------------:|
| **核心层** | L2.2 | L2.8 | L3.3 | L3.8 |
| **智能层** | L1.2 | L1.6 | L2.2 | L2.8 |
| **运营层** | L1.8 | L2.1 | L2.6 | L3.2 |
| **生态层** | L1.1 | L1.4 | L1.9 | L2.5 |

> **注**：根据 CMMI 行业实践，每提升 1 个完整等级通常需要 12-18 个月。上述目标已调整为更现实的水平。

## 八、实施建议

### 8.1 优先级矩阵

```
        高业务价值
            │
   P2: 智能化   │   P1: 夯实基础
   (技术可行低) │   (技术可行高)
                │
───────────────┼────────────────
                │
   P4: 长期愿景 │   P3: 生态扩展
   (技术可行低) │   (技术可行中)
            │
        低业务价值
```

**解读**：
- **Phase 1**（右上）：高业务价值 + 高技术可行性 → 优先建设
- **Phase 2**（左上）：高业务价值 + 低技术可行性（AI 依赖基础设施） → 重点投入
- **Phase 3**（右下）：中业务价值 + 中技术可行性 → 逐步扩展
- **Phase 4**（左下）：低业务价值 + 低技术可行性 → 长期探索

### 8.2 资源假设

| 假设 | 说明 |
|------|------|
| **团队规模** | 3-5 名后端开发 + 2-3 名前端开发 + 1 名架构师 |
| **并行度** | Phase 1 可并行开发 3 个能力域，Phase 2 开始受依赖限制 |
| **外部依赖** | 需 K8s 集群、Prometheus、NATS 等基础设施就绪 |

### 8.3 风险控制

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| 能力域过多导致开发分散 | 交付延迟 | 每个 Phase 最多并行 3 个能力域 |
| 成熟度目标过高 | 团队压力 | 已调整为 18 个月渐进目标 |
| 视觉展示与后端不同步 | 体验割裂 | 视觉能力作为展示层同步规划 |
| AI 决策引擎效果不达预期 | 智能化受阻 | 保持规则引擎作为降级方案 |

### 8.4 Go/No-Go 检查点

| 检查点 | 时间 | 验收标准 |
|--------|------|----------|
| Phase 1 完成 | 3 个月 | 核心层能力域平均达到 L2.5+ |
| Phase 2 完成 | 6 个月 | AI 决策引擎达到 L2.5+，自治流水线 L1.5+ |
| Phase 3 完成 | 12 个月 | 32 个能力域覆盖率达到 75%+ |

### 8.5 度量指标

|------|:------:|:--------------:|:---------------:|:---------------:|

| 生态层平均成熟度 | L1.1 | L1.4 | L1.9 | L2.5 |
