# Orion API 版本管理设计

> 版本：v1.0  
> 创建日期：2026-04-10  
> 适用范围：所有 REST/GraphQL/WebSocket API

---

## 一、概述

### 1.1 设计目标

建立统一的 API 版本管理机制，确保：
- API 演进过程中保持向后兼容
- 破坏性变更有清晰的迁移路径
- 多版本并存时的路由与治理
- 客户端平滑升级，无感知切换

### 1.2 术语定义

| 术语 | 定义 |
|------|------|
| 主版本 (Major) | 破坏性变更，如 v1 → v2 |
| 次版本 (Minor) | 向后兼容的功能新增，如 v1.0 → v1.1 |
| 补丁版本 (Patch) | 向后兼容的问题修复，如 v1.0.0 → v1.0.1 |
| 向后兼容 | 新版本可完全替代旧版本，客户端无需修改 |
| 破坏性变更 | 导致现有客户端无法正常工作的变更 |

## 二、API 版本标识策略

### 2.1 推荐方案：URL Path 版本化

**格式**：
```
/api/{major_version}/{resource}
示例：
  /api/v1/pipelines
  /api/v2/pipelines
```

**优点**：
- 清晰直观，易于理解和调试
- 浏览器地址栏直接可见
- 符合 REST 惯例，工具链支持完善
- 便于 API 网关路由配置

**缺点**：
- URL 结构变化，严格来说不完全 RESTful

**适用范围**：所有 REST API 的默认方案

---

### 2.2 备选方案一：Header 版本化

**格式**：
```
请求头：
  Orion-API-Version: 1.0
  或 Accept: application/orion.v1+json

请求：
  GET /api/pipelines
  Header: Orion-API-Version: 2.0
```

**优点**：
- URL 保持干净
- 符合 HTTP 语义

**缺点**：
- 不够直观，调试不便
- 浏览器直接访问困难
- 缓存层可能忽略 Header

**适用范围**：
- 内部服务间调用
- 对 URL 洁癖有要求的场景
- 小版本迭代（v1.0 → v1.1）

---

### 2.3 备选方案二：Query Param 版本化

**格式**：
```
GET /api/pipelines?version=1
GET /api/pipelines?api-version=2.0
```

**优点**：
- 实现简单
- 便于临时测试

**缺点**：
- 与业务参数混淆
- 缓存键可能不一致
- 不够正式

**适用范围**：不推荐作为主方案，仅用于：
- 临时灰度测试
- 内部调试工具

---

### 2.4 版本标识选择矩阵

| 场景 | 推荐方案 | 理由 |
|------|----------|------|
| 主版本变更 (v1→v2) | URL Path | 清晰、明确、易路由 |
| 次版本变更 (v1.0→v1.1) | Header | 向后兼容，无需改 URL |
| 补丁版本 (v1.0.0→v1.0.1) | 无需标识 | 服务端透明升级 |
| GraphQL API | Header | GraphQL 自有版本机制 |
| WebSocket API | 握手 Header | 连接建立时协商 |

## 三、版本演进规则

### 3.1 向后兼容变更（无需升级主版本）

以下变更被视为**向后兼容**，可通过次版本（v1.x）发布：

| 变更类型 | 说明 | 示例 |
|----------|------|------|
| 新增资源 | 添加新的 API 端点 | 新增 `/api/v1/reports` |
| 新增字段 | 响应中增加可选字段 | Response 新增 `description` 字段 |
| 新增查询参数 | 支持新的过滤/排序选项 | 新增 `?sort=priority` |
| 扩展枚举值 | 增加新的状态/类型枚举 | `status` 新增 `pending_review` |
| 放宽验证 | 减少必填字段或放松约束 | 某字段从必填改为可选 |
| 性能优化 | 不改变接口行为 | 响应速度提升 |
| Bug 修复 | 修正不符合文档的行为 | 修复边界条件处理 |

**发布流程**：
1. 直接部署，无需版本升级
2. 更新 API 文档标注 `since v1.x`
3. 变更日志记录

---

### 3.2 破坏性变更（必须升级主版本）

以下变更被视为**破坏性**，必须升级主版本（v1 → v2）：

| 变更类型 | 说明 | 示例 |
|----------|------|------|
| 删除资源/端点 | 移除现有 API | 删除 `/api/v1/legacy-endpoint` |
| 删除字段 | 响应中移除字段 | 移除 `user_name` 字段 |
| 重命名 | 修改资源/字段名称 | `user_name` → `username` |
| 类型变更 | 字段数据类型变化 | `id` 从 int → string |
| 语义变更 | 相同输入产生不同输出 | 排序规则改变 |
| 新增必填字段 | 请求需要额外必填参数 | POST 新增必填 `region` 字段 |
| 收紧验证 | 增加约束条件 | 密码长度从 6 位 → 8 位 |
| 错误码变更 | 修改错误响应结构 | 错误码重新编号 |
| 认证方式变更 | 修改认证机制 | Bearer Token → OAuth2 |

---

### 3.3 破坏性变更处理流程

```
┌─────────────────────────────────────────────────────────────────┐
│                    破坏性变更处理流程                            │
└─────────────────────────────────────────────────────────────────┘

Step 1: 评估影响
  ├─ 识别受影响的客户端/集成
  ├─ 评估影响范围（团队/项目/外部用户）
  └─ 确定迁移成本

Step 2: 设计 v2 API
  ├─ 实现新功能同时保留 v1
  ├─ v1 和 v2 代码可共存
  └─ 编写迁移指南

Step 3: 发布 v2（不废弃 v1）
  ├─ v2 正式上线
  ├─ v1 继续服务
  └─ 通知用户可升级

Step 4: 设置 v1 弃用时间表
  ├─ 公告弃用日期（至少 90 天后）
  ├─ 公告下线日期（至少 180 天后）
  └─ 在 v1 响应中添加弃用警告头

Step 5: 迁移支持期
  ├─ 提供迁移工具/脚本
  ├─ SDK 同时支持 v1/v2
  └─ 技术支持协助迁移

Step 6: v1 下线
  ├─ 确认无流量或强制迁移
  ├─ 下线 v1 端点
  └─ 清理 v1 代码
```

---

### 3.4 弃用警告机制

**响应头标识**：
```
HTTP/1.1 200 OK
Deprecation: true
Sunset: Sat, 15 Jul 2026 00:00:00 GMT
Link: </api/v2/pipelines>; rel="successor-version"
X-API-Deprecation-Notice: 此 API 版本将于 2026-07-15 停止支持，请升级至 v2
```

**响应体警告（可选）**：
```json
{
  "code": 0,
  "message": "success",
  "data": { ... },
  "warnings": [
    {
      "code": "DEPRECATED_VERSION",
      "message": "此 API 版本将于 2026-07-15 停止支持",
      "migration_guide": "https://orion.internal/docs/migration/v1-to-v2"
    }
  ]
}
```

## 四、多版本并存策略

### 4.1 版本共存架构

```
┌─────────────────────────────────────────────────────────────┐
│                      API Gateway                             │
└─────────────────────────────────────────────────────────────┘
                              │
          ┌───────────────────┼───────────────────┐
          │                   │                   │
          ▼                   ▼                   ▼
   ┌─────────────┐    ┌─────────────┐    ┌─────────────┐
   │  /api/v1/   │    │  /api/v2/   │    │  /api/v3/   │
   │   Router    │    │   Router    │    │   Router    │
   └─────────────┘    └─────────────┘    └─────────────┘
          │                   │                   │
          ▼                   ▼                   ▼
   ┌─────────────┐    ┌─────────────┐    ┌─────────────┐
   │  Service    │    │  Service    │    │  Service    │
   │  (v1.5.0)   │    │  (v2.1.0)   │    │  (v3.0.0)   │
   └─────────────┘    └─────────────┘    └─────────────┘
          │                   │                   │
          └───────────────────┼───────────────────┘
                              │
                              ▼
                    ┌─────────────────┐
                    │  Shared Data    │
                    │  Layer          │
                    └─────────────────┘
```

### 4.2 版本路由规则

| 请求路径 | 路由目标 | 说明 |
|----------|----------|------|
| `/api/v1/*` | v1 服务集群 | 生产流量 |
| `/api/v2/*` | v2 服务集群 | 生产流量（主力） |
| `/api/v3/*` | v3 服务集群 | 灰度/Beta |
| `/api/latest/*` | 最新稳定版 | 内部使用 |
| `/api/next/*` | 下一版本预览 | 测试环境 |

### 4.3 版本支持策略

| 版本状态 | 支持等级 | SLA | 维护内容 |
|----------|----------|-----|----------|
| Current (当前) | 完全支持 | 99.9% | 功能更新 + Bug 修复 + 安全补丁 |
| Maintenance (维护) | 有限支持 | 99% | 仅安全补丁 + 严重 Bug 修复 |
| Deprecated (弃用) | 尽力支持 | 无 SLA | 仅迁移协助 |
| Sunset (下线) | 不支持 | - | 请求返回 410 Gone |

### 4.4 最多支持版本数

- **同时支持的主版本数**：最多 2 个（Current + Maintenance）
- **例外情况**：特殊客户可协商延长，但需额外计费

## 五、版本弃用与迁移流程

### 5.1 弃用时间线

```
T0: v2 发布
    │
    ├─ v1 标记为 "Current"
    └─ v2 标记为 "Current" (新版本)

T0 + 90 天：v1 标记为 Deprecated
    │
    ├─ 发布公告通知
    ├─ v1 响应添加弃用警告
    └─ 开始迁移协助

T0 + 180 天：v1 标记为 Sunset
    │
    ├─ 停止 v1 新建资源
    ├─ 仅允许读取操作
    └─ 强制迁移提醒

T0 + 210 天：v1 下线
    │
    ├─ v1 返回 410 Gone
    ├─ 重定向文档页面
    └─ 清理 v1 代码
```

### 5.2 弃用通知渠道

| 渠道 | 触发时机 | 内容 |
|------|----------|------|
| API 响应头 | 每次 v1 请求 | 弃用警告 + 截止日期 |
| 开发者门户 | 持续展示 | 弃用公告 + 迁移指南 |
| 邮件通知 | T-90/T-60/T-30 天 | 分级提醒 |
| SDK 警告 | 使用 v1 SDK 时 | 控制台警告日志 |
| Dashboard 弹窗 | 登录管理平台 | 高优先级通知 |

### 5.3 迁移指南文档结构

```
迁移指南：v1 → v2

1. 变更概述
   - 主要变更点列表
   - 影响评估

2. 认证与授权变更
   - 新的认证流程
   - 权限模型变化

3. 端点映射表
   | v1 端点 | v2 端点 | 变更说明 |
   |---------|---------|----------|

4. 请求/响应变更
   - 字段映射表
   - 数据结构对比

5. 错误码映射
   - v1 错误码 → v2 错误码

6. SDK 升级指南
   - 各语言 SDK 升级步骤

7. 常见问题
8. 技术支持联系方式
```

## 六、API 兼容性测试策略

### 6.1 兼容性测试类型

| 测试类型 | 目标 | 执行时机 |
|----------|------|----------|
| 向后兼容测试 | 验证新版本不破坏旧客户端 | 每次发布前 |
| 契约测试 | 验证 API 符合 OpenAPI 规范 | CI 流水线 |
| 回归测试 | 验证现有功能正常 | 每次发布前 |
| 并行测试 | v1/v2 同时运行对比结果 | 大版本发布前 |
| 消费者驱动测试 | 从客户端视角验证兼容性 | 持续进行 |

### 6.2 向后兼容测试流程

```
┌─────────────────────────────────────────────────────────────┐
│                   向后兼容测试流程                           │
└─────────────────────────────────────────────────────────────┘

Step 1: 捕获生产流量
  ├─ 录制真实请求/响应
  └─ 脱敏处理后存入测试数据集

Step 2: 回放测试
  ├─ 用 v1 请求访问 v2 服务
  └─ 验证 v2 能正确响应

Step 3: 差异对比
  ├─ 对比 v1/v2 响应结构
  ├─ 识别破坏性变更
  └─ 生成兼容性报告

Step 4: 自动化回归
  ├─ 所有历史测试用例通过
  └─ 新增用例补充边界场景
```

### 6.3 兼容性检查清单

**发布前必须验证**：

- [ ] 所有 v1 请求在 v2 上能正常响应
- [ ] 响应中 v1 字段保持不变
- [ ] 新增字段均为可选
- [ ] 错误码映射正确
- [ ] 认证/授权逻辑兼容
- [ ] 分页/过滤/排序参数兼容
- [ ] 速率限制行为一致
- [ ] 超时设置合理

### 6.4 测试工具链

| 工具 | 用途 | 集成方式 |
|------|------|----------|
| OpenAPI Diff | 对比规范差异 | CI 流水线 |
| Postman/Newman | 接口回归测试 | CI 流水线 |
| Pact | 消费者驱动契约测试 | 单元测试 |
| VCR | HTTP 录制回放 | 集成测试 |
| 自研兼容性平台 | 全量回归测试 | 发布流程 |

## 七、客户端 SDK 版本管理

### 7.1 SDK 版本策略

**版本同步规则**：
- SDK 主版本与 API 主版本保持一致
- SDK 次版本可独立于 API 迭代（工具类改进）

**示例**：
| API 版本 | SDK 版本 | 说明 |
|----------|----------|------|
| v1.0 | @orion/sdk@1.0.x | 初始发布 |
| v1.1 | @orion/sdk@1.1.x | 新增 API 支持 |
| v2.0 | @orion/sdk@2.0.0 | 破坏性变更 |

### 7.2 SDK 多版本支持

```
SDK 支持矩阵:

@orion/sdk@1.x
  ├─ 支持 API v1 全部端点
  └─ 维护模式（仅安全更新）

@orion/sdk@2.x
  ├─ 支持 API v2 全部端点
  └─ 活跃维护

@orion/sdk@latest
  ├─ 指向最新稳定版
  └─ 自动升级推荐
```

### 7.3 SDK 弃用通知

**运行时警告**：
```javascript
// 使用已弃用的 SDK 版本时
import { OrionClient } from '@orion/sdk@1.x';

// 控制台输出：
// [ORION SDK DEPRECATION WARNING]
// You are using SDK v1.x which will be sunset on 2026-07-15.
// Please upgrade to v2.x: npm install @orion/sdk@latest
// Migration guide: https://orion.internal/docs/migration/v1-to-v2
```

### 7.4 SDK 发布流程

```
1. API 规范发布
   └─ OpenAPI Spec 更新

2. SDK 代码生成
   └─ 基于规范自动生成

3. 人工审核
   └─ 补充手写方法/工具类

4. 测试验证
   └─ 集成测试 + 示例验证

5. 发布到包管理
   └─ npm/Maven/PyPI 等

6. 通知用户
   └─ Release Notes + 升级指引
```

### 7.5 支持的语言 SDK

| 语言 | 包名 | 仓库 |
|------|------|------|
| JavaScript/TypeScript | @orion/sdk | GitHub |
| Python | orion-sdk | PyPI |
| Go | github.com/orion/sdk-go | GitHub |
| Java | com.orion:sdk | Maven Central |
| CLI | orion | npm/Homebrew |

## 八、API 网关版本路由配置

### 8.1 网关架构

```
用户请求
   │
   ▼
┌─────────────────────────────────────────┐
│            API Gateway (Kong/APISIX)     │
│                                         │
│  ┌─────────────────────────────────┐    │
│  │        路由匹配层               │    │
│  │  /api/v1/* → v1-upstream       │    │
│  │  /api/v2/* → v2-upstream       │    │
│  └─────────────────────────────────┘    │
│                                         │
│  ┌─────────────────────────────────┐    │
│  │        插件层                   │    │
│  │  - 认证/授权                    │    │
│  │  - 限流/配额                    │    │
│  │  - 日志/监控                    │    │
│  │  - 弃用警告注入                 │    │
│  └─────────────────────────────────┘    │
└─────────────────────────────────────────┘
   │
   ├─────────────┬─────────────┬─────────────┐
   ▼             ▼             ▼             ▼
v1-upstream  v2-upstream  v3-upstream  mock-upstream
```

### 8.2 路由配置示例

**Kong 配置**：
```yaml
# v1 路由
routes:
  - name: api-v1
    paths: [/api/v1]
    strip_path: false
    service: api-v1-service
    plugins:
      - name: deprecation
        config:
          sunset: "2026-07-15T00:00:00Z"
          migration_guide: "/docs/migration/v1-to-v2"

# v2 路由
routes:
  - name: api-v2
    paths: [/api/v2]
    strip_path: false
    service: api-v2-service
    plugins:
      - name: rate-limiting
        config:
          minute: 100
          policy: local

# 默认路由（未指定版本）
routes:
  - name: api-default
    paths: [/api]
    strip_path: false
    service: api-v2-service  # 默认导向最新版
```

### 8.3 网关插件清单

| 插件 | 功能 | 配置项 |
|------|------|--------|
| deprecation | 注入弃用警告头 | sunset 日期，迁移指南 URL |
| rate-limiting | 限流 | 按版本配置不同限制 |
| request-transformer | 请求转换 | v1→v2 字段映射（过渡期） |
| response-transformer | 响应转换 | 兼容性适配 |
| prometheus | 指标采集 | 按版本统计 |
| zipkin | 链路追踪 | 版本标签 |

### 8.4 灰度发布配置

**基于 Header 的灰度**：
```
if (Header: X-API-Preview == "true") {
  route to v3-beta
} else {
  route to v2-stable
}
```

**基于用户的灰度**：
```
if (User Group in ["beta-testers", "internal"]) {
  route to v3-beta
} else {
  route to v2-stable
}
```

**基于流量的灰度**：
```
v3-beta: 5% 流量
v2-stable: 95% 流量
```

## 九、监控与可观测性

### 9.1 版本相关指标

| 指标名称 | 类型 | 说明 |
|----------|------|------|
| api_requests_total | Counter | 按版本分组的请求数 |
| api_latency_seconds | Histogram | 按版本分组的延迟 |
| api_errors_total | Counter | 按版本分组的错误数 |
| deprecated_api_usage | Gauge | 弃用 API 的使用量 |
| api_version_distribution | Gauge | 各版本的流量占比 |

### 9.2 告警规则

| 告警名称 | 触发条件 | 响应 |
|----------|----------|------|
| DeprecatedAPIHighUsage | 弃用 API 流量 > 10% | 通知团队加速迁移 |
| VersionErrorSpike | 某版本错误率突增 > 5% | 排查版本问题 |
| SunsetApproaching | 下线日期前 30 天 | 提醒未迁移用户 |

### 9.3 仪表盘

**版本健康仪表盘**：
- 各版本 QPS 趋势
- 各版本延迟分布
- 各版本错误率

## 十、附录

### 10.1 版本命名规范

```
格式：{major}.{minor}.{patch}

示例：
  v1.0.0  - 初始发布
  v1.0.1  - Bug 修复
  v1.1.0  - 向后兼容功能新增
  v2.0.0  - 破坏性变更

URL 中使用简写：/api/v1/ (仅主版本)
Header 中使用完整：Orion-API-Version: 1.2.3
```

### 10.2 决策记录

| 决策点 | 选择 | 理由 |
|--------|------|------|
| 版本标识方式 | URL Path | 清晰、易路由、工具支持好 |
| 最多支持版本数 | 2 个 | 平衡维护成本与用户体验 |
| 弃用周期 | 180 天 | 给用户充足迁移时间 |
| 默认版本 | 最新稳定版 | 鼓励使用新版本 |
