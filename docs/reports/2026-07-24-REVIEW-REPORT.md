## 二、架构设计问题（5 项）

### ARC-01: 缺少扩展点框架与现有代码的集成策略

文档假设 Phase 0 完成后所有扩展点自动使用新框架，但没有说明：
- 现有 123 个 TS 服务目录如何逐步迁移？
- 现有 261 个 Go 包中的 11 个相关包如何接入扩展点框架？
- 新旧代码共存期的兼容策略？

**建议**: 新增 §5 集成策略，明确：
1. **新建扩展点直接使用框架**（Phase 0 后创建的扩展点强制使用）
2. **现有代码适配为 wrapper 模式**（不修改现有代码，通过适配器接入）
3. **灰度切换**（先在新功能中使用，再逐步迁移旧功能）

### ARC-02: 缺少扩展点框架的生命周期管理

文档只定义了 `register` / `getHandler` / `getAllHandlers` 三个 API，但缺少：
- 扩展点的**卸载/替换**能力（如热替换一个告警处理器）
- 扩展点的**优先级/排序**（多个处理器处理同一事件时）
- 扩展点的**降级/熔断**（某个处理器 panic 时不影响链中其他处理器）

**建议**: 在 Phase 0 框架设计中增加：
```typescript
interface ExtensionHandler {
  type: string;
  name: string;
  priority: number;        // 排序优先级
  version: string;         // 版本号，支持热替换
  enabled: boolean;        // 动态启用/禁用
  onRegister?(): void;     // 注册回调
  onUnregister?(): void;   // 卸载回调
}
```

### ARC-03: 缺少对现有 261 个 Go 包的架构影响评估

Phase 1-6 的 14 个增强/新建 Go 包会与 261 个现有 Go 包产生依赖关系，文档没有：
- 依赖关系图（哪些包依赖哪些包）
- 循环依赖检测
- 包引用关系变更

**建议**: 新增依赖关系图，至少标注每个新建/增强包可能影响的现有包范围

### ARC-04: 未考虑前端扩展点

30 个扩展点全部是后端扩展点，但 NeatLogic 的扩展点体系也覆盖了前端（dashboard widget、form attribute 等在前端也有渲染组件）。文档未提及：
- 前端如何消费后端扩展点？
- 前端是否需要自己的扩展点框架？

**建议**: 每个涉及前端渲染的扩展点（表单/仪表板/报表/编辑器）标注"前端"标签

### ARC-05: 未考虑数据库迁移（DB migration）

多个扩展点（CMDB 动态属性、SLA 计算、审批流程）需要数据库 schema 变更。文档未提及：
- 数据库迁移策略
- 与现有 643 个迁移文件的兼容性
- 多租户数据隔离

**建议**: 每个需要 DB 变更的扩展点标注"需 DB migration"标签

## 三、优先级评估问题（4 项）

### PRI-01: 集成处理器 (#9) 优先级应为 P0 而非 P1

集成处理器是外部系统集成的核心，直接影响所有基于扩展点的外部集成能力。没有集成处理器，告警适配器(#23)、作业来源(#24)都无法与外部系统对接。

**修正**: P1 → **P0**

### PRI-02: 表单引擎 (#12) 和条件引擎 (#13) 优先级应下调

文档说这 2 个是"部分(39 测试/16 运算符)"，但实际验证发现 TS 层 `forms/` 和 `conditions/` 目录**不存在**。综合分析后，这 2 个是新建而非增强，且 ITSM 流程步骤处理器(#11)才是核心依赖。建议先做 #11 再做 #12/#13。

**建议**: 保持 P0，但调整执行顺序：先做 #11（流程步骤处理器），再做 #12/#13（表单/条件）

### PRI-03: 全局锁 (#10) 应移除

锁是基础设施，不应作为扩展点暴露给外部开发者。全局锁应由框架内部使用，而非插件化。

**建议**: 从 30 个扩展点中移除，作为 Phase 0 框架的内部能力

### PRI-04: 方法级缓存 (#7) 优先级应上调

缓存是 ITSM 流程引擎和 CMDB 的核心性能保障。没有缓存，流程步骤处理器每次都要查询数据库。

**修正**: P2 → **P1**，并前置到 Phase 1 而非 Phase 2

## 四、命名规范问题（2 项）

### NAM-01: 扩展点接口命名仍是 Java 风格

文档 §3 的 NeatLogic 源码路径映射中，接口名全是 Java 风格的 `I*Handler`（`IProcessStepHandler`、`IAttrValueHandler` 等）。这是 NeatLogic 的命名，但文档在 §4 的 TS 代码模板中已改为 Orion 风格，前后不一致。建议在 §3 映射表中明确标注"NeatLogic 原始命名"，并在 Orion 落地时使用对应映射名。

### NAM-02: `lock` 包命名冲突

文档新增 `svc-go/internal/lock/` 引用，但实际路径是 `svc-go/internal/lock/lock.go`（单文件包）。单文件包不应作为扩展点目录。

**建议**: 将 `lock` 标记为"框架内部能力，不单独作为扩展点"

## 五、实施路线图问题（4 项）

### PLAN-01: Phase 2 粒度太粗

Phase 2（ITSM 流程引擎）包含 5 个扩展点，共 25 人天 3 周。但 5 个扩展点之间有强依赖关系：
- 表单引擎(#12) + 条件引擎(#13) → 被流程步骤处理器(#11) 依赖
- SLA 计算(#14) → 依赖流程步骤处理器(#11) 的步骤状态
- 处理人分派器(#15) → 被流程步骤处理器(#11) 的 assign 方法调用

**建议**: 将 Phase 2 拆为 2 个子阶段：
- Phase 2a（2 周）：#11 流程步骤处理器 + #15 处理人分派器（核心流程）
- Phase 2b（1 周）：#12 表单引擎 + #13 条件引擎 + #14 SLA（辅助能力）

### PLAN-02: Phase 3 告警管道前置条件不满足

告警事件管道(#21)需要 Phase 0 扩展点框架，但 Phase 0 只定义了注册/获取 API，缺少管道链式执行器。应新增 Phase 0 任务：实现管道执行器（PipelineExecutor）。

### PLAN-03: Phase 6 过于拥挤

Phase 6 包含 5 个扩展点（统计处理器、行编辑器、仪表板组件、报表数据源、巡检报告扩展），但只有 2 周 10 人天。5 个扩展点分属 5 个不同领域，没有共享依赖，不能通过并行加速。

**建议**: 将 Phase 6 拆为 Phase 6a（统计+行编辑器，1 周）和 Phase 6b（仪表板+报表+巡检，1 周），或移除 P2 的扩展点推迟到后续迭代。

### PLAN-04: 缺少验证阶段

文档没有安排"验证阶段"——当所有扩展点实现后，需要验证：
- 30 个扩展点注册是否全部成功
- 跨语言调用是否正常
- 性能是否达标
- 回归测试是否通过

**建议**: 新增 Phase 7（1 周）：全量验证 + 回归测试 + 性能基准

## 六、遗漏项（3 项）

### MISS-01: 缺少扩展点文档化策略

每个扩展点需要 API 文档、使用示例、最佳实践。文档未提及需产出 `ExtensionPoint Development Guide`。

### MISS-02: 缺少扩展点测试策略

扩展点框架需要 contract test（契约测试）确保每个扩展点实现正确。文档未提及。

### MISS-03: 缺少回滚/回退策略

如果某个扩展点实现有 bug，如何回滚？文档未提及扩展点的版本管理和回滚机制。
