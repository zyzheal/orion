# 微前端子应用接入与后端交互设计

> 版本：1.7  
> 日期：2026-05-23  
> 状态：评审修订版 v1.7（BFF 层 3 种落地方案 + 端口分配表对齐实际代码 + 端口冲突检测）

## 一、背景与目标

### 1.1 背景

Orion 平台已实现基于 Orion-MF 的微前端架构，支持子应用动态加载、CSS 隔离、配置化管理等基础能力。但在子应用接入流程、后端服务管理、版本控制、灰度发布等方面仍存在缺失，与业界标准实践存在差距。

### 1.2 目标

- **标准化子应用接入流程**：从手动配置 → 自动化注册 + CI/CD 集成
- **完善后端服务管理**：网关限流、租户注入、API ACL、全链路追踪
- **支持版本与灰度发布**：子应用多版本并存、灰度发布、一键回滚
- **提升开发者体验**：脚手架、SDK、文档、本地联调工具

### 1.3 范围

本文档覆盖以下领域：

| 领域 | 范围 |
|------|------|
| 前端子应用接入 | 注册、构建、发布、加载 |
| 后端服务管理 | API 网关、限流、路由、追踪 |
| 版本与灰度 | 版本管理、灰度策略、回滚 |
| 开发者工具 | CLI、SDK、脚手架 |
| 安全与隔离 | 租户隔离、API ACL、认证流 |
| 实时通信 | SSE 单向推送、WebSocket 双向交互 |
| 大文件传输 | 对象存储直传、分片上传、断点续传 |
| 异步任务 | 任务队列、进度追踪、结果通知 |
| 事件驱动 | 后端事件总线、声明式订阅、死信队列 |
| 跨租户访问 | 多层权限、审计日志、外部协作 |
| 批量操作 | 批量 CRUD、事务策略、异步批量 |

## 二、大厂实践对比

### 2.1 整体架构模式

| 模式 | 代表公司 | 核心思路 | 适用场景 |
|------|---------|---------|---------|
| **统一网关 + 路径前缀** | 阿里、蚂蚁 | 单网关，按 `/api/{subapp}/*` 分发 | 子应用较少，集中管理 |
| **独立网关 + 路由分发** | 字节、美团 | 每个子应用独立 Gateway | 子应用多，独立部署 |
| **BFF 层 + 聚合** | 腾讯、有赞 | 子应用通过 BFF 聚合后端数据 | 复杂业务编排 |

### 2.2 核心能力对比

| 维度 | Orion 当前 | 阿里 qiankun | 字节 Wujie | 蚂蚁 SOFAStack |
|------|-----------|-------------|-----------|---------------|
| **注册方式** | 数据库 + 管理页面 | 配置中心 + 审核 | DevOps + Git 集成 | 应用市场 + 审批 |
| **沙箱隔离** | ProxySandbox + Shadow DOM / scoped-css | ProxySandbox | iframe + WebComponent | ProxySandbox |
| **CI/CD 集成** | 手动构建 | 自动注册 + CDN | Git Hook → 自动部署 | 全流程自动化 |
| **版本管理** | 无 | 多版本 + 灰度 | 语义化版本 | 语义化 + 回滚 |
| **API 网关** | 路径前缀代理 | SOFAGateway + 限流 | OpenResty + Lua | 全功能网关 |
| **限流熔断** | 前端熔断已具备 (CrashRecovery)，网关限流缺失 | Sentinel | 自研限流 | 令牌桶 |
| **全链路追踪** | 无 | 有 | 有 | 有 |
| **开发者工具** | 脚手架/SDK 已存在，模板缺 MF 配置，SDK 覆盖不足 | CLI + SDK | galaxy-cli | sofa-cli |

### 2.3 共性模式总结

经过对比分析，大厂在以下方面高度一致：

1. **前端无感知** — 子应用前端不需要知道后端拓扑，只认路径前缀
2. **网关是中枢** — 认证、鉴权、限流、租户注入、路由全在网关层
3. **后端不信任前端** — 后端只信任网关注入的 header，不直接解析 Token
4. **跨应用走后端** — 子应用间数据依赖通过后端聚合，前端不直接跨前缀调用

### 4.2 API 路径 ACL（P0）

#### 4.2.1 现状问题

当前 Gateway 不限制子应用访问路径，存在越权访问风险。

#### 4.2.2 设计方案

**ACL 规则表**：

```sql
CREATE TABLE api_access_rules (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    subapp_key      VARCHAR(50) NOT NULL,
    allowed_prefixes JSONB NOT NULL DEFAULT '[]',  -- 允许访问的 API 前缀
    denied_prefixes  JSONB NOT NULL DEFAULT '[]',  -- 禁止访问的 API 前缀
    created_at      TIMESTAMPTZ DEFAULT NOW(),
    updated_at      TIMESTAMPTZ DEFAULT NOW()
);

CREATE INDEX idx_api_access_rules_subapp ON api_access_rules(subapp_key);
CREATE UNIQUE INDEX idx_api_access_rules_subapp_unique ON api_access_rules(subapp_key);  -- 每个子应用仅一条规则
```

**Gateway ACL 中间件**：

```typescript
// orion-api-gateway/src/middleware/api-acl.ts
import { FastifyRequest, FastifyReply } from 'fastify';
import { getAccessRules } from '../services/access-control';

/**
 * 从请求路径提取子应用标识
 * 例：/api/v1/db/config → 'dba'（通过路由匹配表）
 */
function extractSubAppKey(path: string): string | null {
  // 从 subapp_configs 的 api_paths 字段匹配
  // 例：/api/v1/db/* → 'dba'
  const routeConfigs = getCachedSubAppRoutes();
  for (const config of routeConfigs) {
    for (const apiPath of config.api_paths || []) {
      if (path.startsWith(apiPath)) return config.key;
    }
  }
  return null;
}

export async function apiACL(request: FastifyRequest, reply: FastifyReply) {
  const path = request.raw.url || '';
  const subappKey = extractSubAppKey(path);

  if (!subappKey) return; // 非子应用路径，跳过

  const rules = await getAccessRules(subappKey);
  if (!rules) return; // 无规则配置，默认允许

  // 检查禁止的前缀
  for (const prefix of rules.denied_prefixes) {
    if (path.startsWith(prefix)) {
      reply.status(403).send({
        success: false,
        error: 'ACCESS_DENIED',
        message: `Access to ${prefix} is denied for sub-app ${subappKey}`,
      });
      return;
    }
  }

  // 如果有允许的前缀配置，检查是否匹配
  if (rules.allowed_prefixes.length > 0) {
    const isAllowed = rules.allowed_prefixes.some(prefix => path.startsWith(prefix));
    if (!isAllowed) {
      reply.status(403).send({
        success: false,
        error: 'ACCESS_DENIED',
        message: `Access to ${path} is not allowed for sub-app ${subappKey}`,
      });
      return;
    }
  }
}
```

| 子应用 | 允许前缀 | 禁止前缀 |
|--------|---------|---------|
| orion-dba | `['/api/v1/db']` | `['/api/v1/knowledge', '/api/v1/visor']` |
| orion-knowledge | `['/api/v1/knowledge']` | `['/api/v1/db', '/api/v1/visor']` |

### 4.3 基础限流（P0）

#### 4.3.1 设计方案

> **已有实现**：`tenant.ts` 已有 Redis QPS 配额检查。本节限流中间件基于 Redis 实现分布式令牌桶，与 tenant.ts 的 Redis 实例复用。

**限流规则表**：

```sql
CREATE TABLE api_rate_limits (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    subapp_key      VARCHAR(50) NOT NULL,
    api_path        VARCHAR(200) NOT NULL,
    qps_limit       INTEGER DEFAULT 1000,
    burst_limit     INTEGER DEFAULT 2000,
    daily_limit     INTEGER DEFAULT 1000000,
    tenant_limit    INTEGER DEFAULT 10000,
    enabled         BOOLEAN DEFAULT true,
    created_at      TIMESTAMPTZ DEFAULT NOW()
);
```

**限流中间件（基于 Redis）**：

```typescript
// orion-api-gateway/src/middleware/rate-limit.ts
import { FastifyRequest, FastifyReply } from 'fastify';
import Redis from 'ioredis';

const redis = new Redis(process.env.REDIS_URL || 'redis://localhost:6379');

/**
 * 分布式令牌桶：使用 Redis Lua 脚本保证原子性
 * key = rate_limit:{subapp}:{path}:{tenant}
 * value = 当前令牌数
 *
 * 注意：使用 EVALSHA 缓存脚本提升性能，此处为脚本内容
 */
const consumeTokenScript = `
local key = KEYS[1]
local capacity = tonumber(ARGV[1])
local refill_rate = tonumber(ARGV[2])
local now = tonumber(ARGV[3])

-- 获取当前令牌数和上次更新时间
local tokens = redis.call('GET', key)
local last_time = redis.call('HGET', key .. ':meta', 'time')

-- 初始化：首次访问设为满容量
if not tokens then
  redis.call('SET', key, capacity)
  redis.call('HSET', key .. ':meta', 'time', now)
  redis.call('EXPIRE', key, 86400)
  redis.call('EXPIRE', key .. ':meta', 86400)
  return 1
end

tokens = tonumber(tokens)
last_time = tonumber(last_time) or now

-- 计算令牌补充
local elapsed = math.max(0, now - last_time)
local new_tokens = math.min(capacity, tokens + elapsed * refill_rate)

if new_tokens >= 1 then
  redis.call('SET', key, new_tokens - 1)
  redis.call('HSET', key .. ':meta', 'time', now)
  return 1
else
  return 0
end
`;

export async function rateLimiter(request: FastifyRequest, reply: FastifyReply) {
  const path = request.raw.url || '';
  const tenantId = (request.headers['x-tenant-id'] as string) || 'global';
  const subappKey = extractSubAppKey(path);

  if (!subappKey) return;

  const limit = await getRateLimit(subappKey, path);
  if (!limit || !limit.enabled) return;

  const key = `rate_limit:${subappKey}:${path}:${tenantId}`;
  const now = Date.now();
  const allowed = await redis.eval(
    consumeTokenScript,
    1,
    key,
    limit.burst_limit,  // capacity
    limit.qps_limit,    // refill_rate
    now,                // current timestamp
  );

  if (!allowed) {
    reply.status(429).send({
      success: false,
      error: 'RATE_LIMIT_EXCEEDED',
      message: 'API call limit exceeded, please retry later',
      retry_after: 1,
    });
    return;
  }
}
```

> **为什么用 Redis 而非内存 Map**：Gateway 可能部署多实例，内存 Map 无法跨实例共享令牌计数，导致限流失效。Redis 作为已有依赖（tenant.ts 已使用），是最优选择。

#### 4.3.2 限流策略

| 维度 | 默认值 | 说明 |
|------|--------|------|
| 子应用 QPS | 1000 | 单个子应用整体 QPS 上限 |
| 突发 QPS | 2000 | 允许短时间内的突发流量 |
| 单租户日调用量 | 10,000 | 单个租户每日调用上限 |
| 全局日调用量 | 1,000,000 | 单个子应用每日调用上限 |

#### 4.4.2 版本感知加载

```typescript
// packages/orion-mf/src/core/VersionAwareLoader.ts
interface ReleaseConfig {
  strategy: 'full' | 'canary' | 'ab';
  canaryPercent: number;
  canaryUsers: string[];
  canaryTenants: string[];
}

export class VersionAwareLoader {
  async loadSubApp(config: SubAppConfig): Promise<void> {
    const release = await this.getReleaseConfig(config.key);
    const version = this.resolveVersion(config, release);
    const entry = this.getEntryByVersion(config, version);
    await this.loadFromEntry(entry);
  }

  private resolveVersion(config: SubAppConfig, release: ReleaseConfig): string {
    if (release.strategy === 'canary') {
      const userId = this.getCurrentUserId();
      const tenantId = this.getCurrentTenantId();

      // 灰度用户返回新版本，非灰度用户返回稳定版
      if (release.canaryUsers.includes(userId)) return release.version;
      if (release.canaryTenants.includes(tenantId)) return release.version;
      if (Math.random() * 100 < release.canaryPercent) return release.version;
    }

    return config.current_version;
  }
}
```

#### 4.5.1 设计方案

**追踪 ID 传递链路**：

```
浏览器 → X-Trace-Id → Gateway → X-Trace-Id + X-Span-Id → 后端服务 → 日志/指标
```

**Gateway 追踪中间件**：

```typescript
// orion-api-gateway/src/middleware/tracing.ts
import { FastifyRequest, FastifyReply } from 'fastify';

export async function tracingMiddleware(request: FastifyRequest, reply: FastifyReply) {
  const traceId = request.headers['x-trace-id'] as string || generateTraceId();
  const spanId = generateSpanId();

  request.headers['x-trace-id'] = traceId;
  request.headers['x-span-id'] = spanId;
  reply.header('x-trace-id', traceId);

  const startTime = Date.now();

  reply.raw.on('finish', () => {
    const duration = Date.now() - startTime;
    const statusCode = reply.raw.statusCode;

    reportTrace({
      traceId,
      spanId,
      subappKey: matchSubApp(request.raw.url || ''),
      path: request.raw.url,
      method: request.method,
      statusCode,
      duration,
      tenantId: request.headers['x-tenant-id'] as string,
    });
  });
}
```

```typescript
  const manifest = JSON.parse(fs.readFileSync(options.manifest, 'utf-8'));

  const payload = {
    key: options.key,
    version: options.version,
    entry_dev: options.entryDev,
    entry_prod: options.entryProd,
    manifest,
    dependencies: manifest.shared || {},
    changelog: process.env.CHANGELOG || '',
  };

  const result = await registerSubApp(payload);
  console.log(`SubApp ${options.key}@${options.version} registered`);
  return result;
}
```

### 4.7 子应用后端服务配置（P0）

#### 4.7.1 现状问题

当前子应用的后端服务地址配置分散在两个地方：

- **Gateway 配置**：`config/index.ts` 硬编码服务 URL（如 `dba: 'http://localhost:3032'`）
- **Gateway 路由**：`routes/api.ts` 硬编码路径前缀映射
- **Gateway 动态同步**：`gateway-route-sync.ts` 的 `DOMAIN_TO_SERVICE_KEY` 硬编码映射

新增子应用需要修改代码，无法通过配置完成。

#### 4.7.2 设计方案

**在 `subapp_configs` 表中增加后端服务配置字段**：

```sql
ALTER TABLE subapp_configs ADD COLUMN IF NOT EXISTS backend_service_url VARCHAR(500);
ALTER TABLE subapp_configs ADD COLUMN IF NOT EXISTS backend_service_key VARCHAR(50);
ALTER TABLE subapp_configs ADD COLUMN IF NOT EXISTS api_paths JSONB DEFAULT '[]';
```

**字段说明**：

| 字段 | 说明 | 示例 |
|------|------|------|
| `backend_service_url` | 后端服务地址 | `http://dba-service:3032` |
| `backend_service_key` | Gateway 配置中的服务 key | `dba` |
| `api_paths` | 该子应用拥有的 API 路径前缀 | `['/api/v1/db', '/api/v1/database']` |

**子应用注册完整配置**：

```json
{
  "key": "dba",
  "name": "数据库管理",
  "framework": "vue",
  "entry_dev": "http://localhost:3030/remoteEntry.js",
  "entry_prod": "/orion-dba/assets/remoteEntry.js",
  "routes": ["/dba"],
  "backend_service_url": "http://dba-service:3032",
  "backend_service_key": "dba",
  "api_paths": ["/api/v1/db", "/api/v1/database"],
  "css_isolation": "shadow-dom",
  "use_shared": false,
  "status": "enabled"
}
```

#### 4.7.3 Gateway 动态路由改造

改造后 Gateway 从数据库读取路由配置，不再需要硬编码映射：

```typescript
// orion-api-gateway/src/services/gateway-route-sync.ts

// 改造前：硬编码
const DOMAIN_TO_SERVICE_KEY = { knowledge: 'knowledge', dba: 'dba' };

// 改造后：从 subapp_configs 动态读取
async function loadSubAppRouteConfigs(platformUrl: string) {
  const response = await fetch(`${platformUrl}/api/v1/subapps/enabled`);
  const data = await response.json();
  return data.data.map((app: SubAppConfig) => ({
    key: app.key,
    backendUrl: app.backend_service_url,
    apiPaths: app.api_paths || [],
  }));
}

async function syncRoutes(app: FastifyInstance) {
  const configs = await loadSubAppRouteConfigs(platformUrl);
  for (const config of configs) {
    for (const pathPrefix of config.apiPaths) {
      registerProxyRoute(app, {
        prefix: pathPrefix,
        target: config.backendUrl,
        timeout: 30000,
        stripPrefix: false,
      });
    }
  }
}
```

#### 4.8.4 独立访问认证

**方案 A：共享主应用 Cookie（推荐，同域场景）**

```
用户登录主应用 → Cookie 写入 .example.com 域
  ↓
子应用独立访问 → 浏览器自动携带 Cookie
  ↓
Gateway 从 Cookie 解析 Token → 正常流程
```

**方案 B：独立登录 + SSO 跳转（跨域/独立部署场景）**

```
子应用独立访问 → 检查本地 Token
  ↓
  无 Token → 重定向到 sso.example.com/login?redirect=dba.example.com
  ↓
  SSO 登录 → 跳转回子应用 + 携带 Token
  ↓
  子应用获得 Token → 正常流程
```

#### 4.8.5 前端代码适配

子应用需要感知运行模式，调整认证策略：

```typescript
// orion-dba/frontend/src/utils/auth.ts

// 检测运行模式
const isStandalone = () => {
  return !window.__POWERED_BY_ORION__ && !window.__POWERED_BY_WUJIE__;
};

// 获取 Token
export const getToken = (): string | null => {
  if (isStandalone()) {
    // 独立模式：从 Cookie 或 localStorage 获取
    return getCookie('orion_token') || localStorage.getItem('orion_token');
  }
  // 嵌入模式：从主应用注入的全局变量获取
  return (window as any).$orion?.token || localStorage.getItem('orion_token');
};

// 获取 API Base
export const getApiBase = (): string => {
  // 两种模式都使用相对路径，由 Nginx/Gateway 转发
  return '/api/v1/db';
};
```

#### 4.8.6 完整请求流对比

**嵌入模式**：

```
用户操作 → 子应用前端
  → GET /api/v1/db/config (相对路径)
  → 浏览器发到 example.com/api/v1/db/config
  → Gateway 接收（同域）
  → 认证 → 租户注入 → ACL → 限流 → DBA Service
  → 返回响应
```

**独立 SPA 模式**：

```
用户访问 dba.example.com
  → 子应用前端加载
  → GET /api/v1/db/config (相对路径)
  → 浏览器发到 dba.example.com/api/v1/db/config
  → Nginx proxy_pass → api-gateway:3000/api/v1/db/config
  → Gateway 接收
  → 认证 → 租户注入 → ACL → 限流 → DBA Service
  → 返回响应
```

**关键一致性**：无论哪种模式，子应用前端代码完全相同，都使用相对路径 `/api/v1/db/...`，差异在 Nginx/Gateway 层处理。

## 五、安全设计

### 5.1 认证流

```
主应用统一登录 → JWT Token
        ↓
  mount(props) 注入子应用
        ↓
  Axios 拦截器附加 Authorization: Bearer
        ↓
  Gateway 验签 → 注入 X-Tenant-Id / X-User-Id
        ↓
  后端服务只信任 header，不解析 Token
```

### 5.2 数据隔离

| 层级 | 实现 |
|------|------|
| 前端 | 沙箱隔离，子应用无法访问其他子应用 DOM |
| 网关 | ACL 限制，子应用只能访问自己的 API 前缀 |
| 后端 | 租户中间件自动追加 WHERE tenant_id = ? |
| 数据库 | 行级租户隔离（未来可升级为物理隔离） |

### 5.3 跨应用通信规范

| 场景 | 做法 | 禁止行为 |
|------|------|---------|
| UI 联动 | CustomEvent 事件总线 | 子应用 A 直接操作子应用 B DOM |
| 数据依赖 | 后端内部 API 聚合 | 前端直接跨前缀调用其他子应用 API |
| 共享数据 | 主应用提供公共 API | 子应用各自实现用户信息查询 |

```
     │                       │     X-User-Id           │                        │
     │                       │     X-Permissions       │                        │
     │                       ├────────────────────────┼───────────────────────►│
     │                       │                        │                        │
     │                       │                        │  7. 子应用后端验证       │
     │                       │                        │     tenantMiddleware    │
     │                       │                        │     读取 header         │
     │                       │                        │     附加 WHERE tenant_id│
     │                       │                        │                        │
     │                       │                        │  8. 返回数据            │
     │                       │                        │◄───────────────────────┤
     │                       │  9. 响应 + 注入 Trace ID│                        │
     │◄──────────────────────┼────────────────────────┤                        │
     │   X-Trace-Id: xxx     │                        │                        │
     │   200 {"data": [...]} │                        │                        │
```

#### 8.1.5 子应用与后端交互模式

本节详细分析 4 种交互模式的完整链路、安全机制、代码示例和适用边界。

##### 模式 A：前端 → Gateway → 自己后端（标准模式）

**链路图**：

```
子应用前端                 API Gateway                  子应用后端
   │                          │                            │
   │  GET /api/v1/myapp/items │                            │
   ├─────────────────────────►│                            │
   │                          │  1. Auth: 验证 JWT          │
   │                          │  2. Tenant: 解析租户        │
   │                          │  3. ACL: 检查 /myapp 权限   │
   │                          │  4. RateLimit: 令牌桶       │
   │                          │  5. Tracing: 生成 Trace ID  │
   │                          │                            │
   │                          │  GET /api/v1/myapp/items    │
   │                          │  Headers:                   │
   │                          │    X-Tenant-Id: tenant-123  │
   │                          │    X-User-Id: user-456      │
   │                          │    X-Permissions: ["read"]  │
   │                          │    X-Trace-Id: trace-abc    │
   ├─────────────────────────┼───────────────────────────►│
   │                          │                            │
   │                          │                            │  tenantMiddleware:
   │                          │                            │  1. 读取 X-Tenant-Id
   │                          │                            │  2. 验证租户状态
   │                          │                            │  3. 存入 request 上下文
   │                          │                            │
   │                          │                            │  SELECT * FROM items
   │                          │                            │  WHERE tenant_id = 'tenant-123'
   │                          │                            │
   │                          │  200 OK + X-Trace-Id       │
   │                          │  {"success":true,"data":[]}│
   │◄─────────────────────────┼───────────────────────────┤
   │                          │                            │
```

**安全机制**：

| 层级 | 机制 | 作用 |
|------|------|------|
| 认证 | JWT 验证 | 确认用户身份合法 |
| 租户隔离 | X-Tenant-Id 注入 | 确保数据按租户隔离 |
| 访问控制 | ACL 前缀匹配 | 子应用只能访问自己的 API |
| 限流 | 令牌桶（Redis Lua） | 防止单租户滥用 |
| 追踪 | X-Trace-Id 注入 | 全链路问题定位 |

**前端代码示例**：

```typescript
// 子应用前端调用自己的后端 API
import { OrionClient } from '@orion/sdk';

const client = new OrionClient({
  subappKey: 'myapp',
  apiBase: '/api/v1/myapp',
});

// 自动携带 Authorization: Bearer，Gateway 自动注入租户信息
const items = await client.get('/items');
await client.post('/items', { name: 'new item' });
```

**后端代码示例**：

```typescript
// 子应用后端路由
app.get('/api/v1/myapp/items', async (request, reply) => {
  const tenantId = (request as any).tenantId;  // 来自 tenantMiddleware
  const userId = (request as any).userId;

  // 自动附加 tenant_id 过滤
  const items = await db.query(
    'SELECT * FROM items WHERE tenant_id = $1 ORDER BY created_at DESC',
    [tenantId]
  );

  reply.send({ success: true, data: items });
});
```

**适用场景**：
- 子应用自己的数据 CRUD（数据库管理、知识库文档、监控配置）
- 子应用特有的业务逻辑（DBA 的 SQL 审核、Knowledge 的文档协作）
- 子应用独立的存储操作（文件上传、对象存储访问）

**不适用场景**：
- 需要跨子应用数据聚合（改用模式 D）
- 需要平台共享能力（改用模式 B）

---

##### 模式 B：前端 → Gateway → 平台后端（共享能力）

**链路图**：

```
子应用前端                 API Gateway                  平台后端
   │                          │                            │
   │  GET /api/v1/pipelines   │                            │
   ├─────────────────────────►│                            │
   │                          │  1. Auth: 验证 JWT          │
   │                          │  2. Tenant: 解析租户        │
   │                          │  3. ACL: 检查 platform/*    │
   │                          │     （允许所有子应用访问）   │
   │                          │  4. RateLimit               │
   │                          │                            │
   │                          │  GET /api/v1/pipelines      │
   │                          │  X-Tenant-Id: tenant-123    │
   ├─────────────────────────┼───────────────────────────►│
   │                          │                            │
   │                          │                            │  SELECT * FROM pipelines
   │                          │                            │  WHERE tenant_id = 'tenant-123'
   │                          │                            │  AND created_by IN (同租户用户)
   │                          │                            │
   │                          │  200 OK                    │
   │◄─────────────────────────┼───────────────────────────┤
   │                          │                            │
```

**ACL 规则配置**：

```sql
-- 平台 API 允许所有子应用访问
INSERT INTO api_access_rules (prefix, allowed_subapps, description)
VALUES
  ('/api/v1/pipelines', '*', 'Pipeline 管理 - 所有子应用可访问'),
  ('/api/v1/notifications', '*', '通知服务 - 所有子应用可访问'),
  ('/api/v1/users', '*', '用户管理 - 所有子应用可访问'),
  ('/api/v1/events', '*', '事件发布 - 所有子应用可访问');
```

**适用场景**：
- Pipeline 管理（CI/CD 构建、部署）
- 通知服务（邮件、Webhook、企业微信）
- 用户管理（个人信息修改、密码修改）
- 全局配置（平台级参数、功能开关）

**安全设计**：

| 维度 | 设计 | 说明 |
|------|------|------|
| ACL | `allowed_subapps = '*'` | 所有子应用可访问，但仍经过 ACL 中间件 |
| 租户隔离 | 平台后端同样按租户过滤 | 子应用 A 的用户只能看到自己租户的 Pipeline |
| 限流 | 独立限流规则 | 平台 API 有自己的 QPS 限制，不与子应用共享配额 |

##### 模式 C：子应用后端 → 平台后端（后端聚合）

**链路图**：

```
子应用前端              子应用后端                 平台后端
   │                       │                         │
   │  请求业务数据          │                         │
   ├──────────────────────►│                         │
   │                       │  需要聚合平台数据          │
   │                       │  （如获取租户全局配置）    │
   │                       │                         │
   │                       │  POST /internal/config   │
   │                       │  X-Service-Token: xxx    │
   │                       │  X-Tenant-Id: tenant-123 │
   ├───────────────────────┼────────────────────────►│
   │                       │                         │
   │                       │                         │  验证 Service Token
   │                       │                         │  查询全局配置
   │                       │                         │
   │                       │  200 {"global_config:...}│
   │                       │◄────────────────────────┤
   │                       │                         │
   │                       │  聚合业务数据 + 平台配置   │
   │  200 {"data": ...}    │                         │
   │◄──────────────────────┤                         │
   │                       │                         │
```

**认证机制**：

```typescript
// 子应用后端调用平台后端时使用内部 Service Token
import { InternalClient } from '@orion/sdk/internal';

const internalClient = new InternalClient({
  platformUrl: 'http://platform-service:3001',
  serviceToken: process.env.ORION_SERVICE_TOKEN,  // K8s Secret 注入
  tenantId: 'current-tenant-id',  // 从当前请求上下文获取
});

// 内部调用不经过 Gateway，直连平台后端
const globalConfig = await internalClient.post('/internal/config', {
  keys: ['feature_flags', 'rate_limits'],
});
```

**平台后端内部认证中间件**：

```typescript
// 平台后端验证内部 Service Token
async function internalAuthMiddleware(request: FastifyRequest, reply: FastifyReply) {
  const serviceToken = request.headers['x-service-token'] as string;
  const expectedToken = process.env.INTERNAL_SERVICE_TOKEN;

  if (!serviceToken || serviceToken !== expectedToken) {
    return reply.status(401).send({ error: 'INVALID_SERVICE_TOKEN' });
  }

  // 验证通过，存入租户上下文
  const tenantId = request.headers['x-tenant-id'] as string;
  (request as any).tenantId = tenantId;
}
```

**适用场景**：
- 子应用需要获取平台全局配置（功能开关、限流阈值）
- 子应用需要发布平台级事件（通知所有租户）
- 子应用需要调用平台内部服务（日志聚合、指标上报）
- 子应用初始化时需要租户级元数据

**与模式 B 的区别**：

| 维度 | 模式 B | 模式 C |
|------|--------|--------|
| 发起方 | 子应用前端 | 子应用后端 |
| 路径 | 经过 Gateway | 直连平台后端（内部网络） |
| 认证 | 用户 JWT + 租户 Header | Service Token |
| 延迟 | 较高（经过 Gateway 中间件链） | 较低（内部直连） |
| 可见性 | 用户可感知 | 用户无感知 |

##### 模式 D：子应用后端 ↔ 子应用后端（跨服务调用）

**链路图**：

```
子应用 A 前端          子应用 A 后端           子应用 B 后端
   │                       │                      │
   │  需要 B 的数据          │                      │
   │  （如 DBA 连接信息）    │                      │
   ├──────────────────────►│                      │
   │                       │                      │
   │                       │  GET /api/v1/dba/      │
   │                       │  connections/xxx       │
   │                       │  X-Service-Token: xxx  │
   ├───────────────────────┼─────────────────────►│
   │                       │                      │
   │                       │                      │  验证 Service Token
   │                       │                      │  查询连接信息（按租户过滤）
   │                       │                      │
   │                       │  200 {"host":"..."}   │
   │                       │◄─────────────────────┤
   │                       │                      │
   │                       │  聚合后返回             │
   │  200 {"connection":   │                      │
   │    {"host":"..."}}    │                      │
   │◄──────────────────────┤                      │
   │                       │                      │
```

**设计原则**：

```
┌─────────────────────────────────────────────────────────────────────────┐
│  跨子应用调用规则                                                        │
│                                                                         │
│  1. 前端不直接跨前缀调用                                                  │
│     ❌ 子应用 A 前端 ──► GET /api/v1/dba/connections                     │
│     ✅ 子应用 A 前端 ──► GET /api/v1/myapp/data（自己后端聚合）           │
│                                                                         │
│  2. 后端调用必须经过 Gateway                                              │
│     原因：保持 ACL、限流、追踪一致性                                       │
│     例外：高频内部调用可直连（使用 Service Token 认证）                    │
│                                                                         │
│  3. 数据必须按租户隔离                                                    │
│     子应用 A 调用子应用 B 时，只能获取同租户的数据                         │
│     Gateway 自动注入 X-Tenant-Id，子应用 B 按租户过滤                     │
│                                                                         │
│  4. 调用关系需注册                                                        │
│     subapp_dependencies 表记录：source_subapp → target_subapp           │
│     用于 ACL 规则生成和安全审计                                           │
└─────────────────────────────────────────────────────────────────────────┘
```

**依赖注册表**：

```sql
CREATE TABLE subapp_dependencies (
  id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  source_subapp   VARCHAR(50) NOT NULL,     -- 调用方
  target_subapp   VARCHAR(50) NOT NULL,     -- 被调用方
  api_prefix      VARCHAR(100) NOT NULL,    -- 调用的 API 前缀
  description     TEXT,
  created_at      TIMESTAMP DEFAULT NOW(),
  UNIQUE(source_subapp, target_subapp, api_prefix)
);

-- 示例：myapp 需要调用 dba 的连接信息
INSERT INTO subapp_dependencies (source_subapp, target_subapp, api_prefix, description)
VALUES ('myapp', 'dba', '/api/v1/dba/connections', '获取数据库连接信息用于监控');
```

**Gateway 自动 ACL 规则生成**：

```typescript
// 根据 subapp_dependencies 生成 ACL 规则
async function generateCrossSubappACLRules() {
  const deps = await db.query('SELECT * FROM subapp_dependencies');

  for (const dep of deps) {
    // 允许 source_subapp 调用 target_subapp 的特定 API
    await db.query(
      `INSERT INTO api_access_rules (prefix, allowed_subapps, description)
       VALUES ($1, $2, $3)
       ON CONFLICT (prefix) DO UPDATE SET allowed_subapps = $2`,
      [dep.api_prefix, `[${dep.source_subapp}]`, dep.description]
    );
  }
}
```

**适用场景**：
- 监控应用需要 DBA 的连接信息做性能分析
- ITSM 工单系统需要 Pipeline 的构建状态
- 知识库需要 DBA 的数据库元数据
- 多云管理需要 Visor 的监控指标

**不适用场景**：
- 简单共享能力（改用模式 B）
- 平台级全局服务（改用模式 C）

##### 模式 E：BFF 层聚合（复杂前端数据聚合）

> BFF（Backend for Frontend）层负责为特定子应用前端聚合多个后端数据源，减少前端串行请求，提升加载性能。

**为什么需要 BFF 层**：

子应用前端如果需要从多个后端获取数据（如工单详情需要 ITSM + DBA + Pipeline 数据），串行请求会导致加载缓慢：

```
❌ 无 BFF 层（前端串行请求，总延迟 = 3 × 35ms = 105ms）
前端 ──► GET /api/v1/itsm/tickets/1    (35ms)
前端 ──► GET /api/v1/dba/connections/5  (35ms)
前端 ──► GET /api/v1/pipelines/10       (35ms)

✅ 有 BFF 层（后端并行聚合，总延迟 = max(35ms) = 35ms）
前端 ──► GET /api/v1/bff/ticket-detail/1  (35ms，后端并行聚合 3 个数据源)
```

**方式一：子应用后端内聚合（当前默认，简单场景）**

适用：只需要聚合 2-3 个数据源，逻辑简单。

```typescript
// orion-myapp-backend/src/controllers/dashboard.controller.ts
import { Controller, Get, Req } from '@nestjs/common';
import { HttpService } from '@nestjs/axios';
import { firstValueFrom } from 'rxjs';

@Controller('api/v1/myapp')
export class DashboardController {
  constructor(private readonly http: HttpService) {}

  @Get('dashboard')
  async getDashboard(@Req() req) {
    const tenantId = req.headers['x-tenant-id'] as string;
    const userId = req.headers['x-user-id'] as string;

    // 并行请求多个数据源
    const [pipelines, alerts, deployments] = await Promise.all([
      firstValueFrom(this.http.get(`http://platform:3001/api/v1/pipelines`, {
        params: { tenant_id: tenantId, limit: 5 }
      })),
      firstValueFrom(this.http.get(`http://platform:3001/api/v1/alerts`, {
        params: { tenant_id: tenantId, status: 'active' }
      })),
      firstValueFrom(this.http.get(`http://platform:3001/api/v1/deployments`, {
        params: { tenant_id: tenantId, limit: 5 }
      })),
    ]);

    // 聚合并格式化响应
    return {
      pipelines: pipelines.data.data.slice(0, 5),
      activeAlerts: alerts.data.data.length,
      recentDeployments: deployments.data.data.slice(0, 5),
      updatedAt: new Date().toISOString(),
    };
  }
}
```

**方式二：独立 BFF 服务（复杂聚合场景）**

适用：需要为多个子应用提供统一的聚合能力，聚合逻辑复杂。

```typescript
// orion-bff/src/routes/registry.ts
// BFF 注册表：声明式定义每个子应用的聚合规则
export interface BFFConfig {
  subappKey: string;
  route: string;
  sources: {
    name: string;
    url: string;
    method: 'GET' | 'POST';
    params?: Record<string, string>;
    required?: boolean;  // false 表示失败时不影响整体响应
  }[];
  transform: (results: Record<string, any>) => any;
}

// 工单详情聚合：ITSM + DBA + Pipeline
export const ticketDetailBFF: BFFConfig = {
  subappKey: 'itsm',
  route: '/api/v1/bff/ticket-detail/:ticketId',
  sources: [
    {
      name: 'ticket',
      url: 'http://platform:3001/api/v1/itsm/tickets/:ticketId',
      required: true,  // 工单信息必须成功
    },
    {
      name: 'connection',
      url: 'http://dba:3040/api/v1/dba/connections/:connectionId',
      required: false,  // 连接信息可选
    },
    {
      name: 'pipeline',
      url: 'http://platform:3001/api/v1/pipelines/:pipelineId',
      required: false,
    },
  ],
  transform: (results) => ({
    ticket: results.ticket.data,
    connection: results.connection?.data || null,
    pipeline: results.pipeline?.data || null,
  }),
};
```

```typescript
// orion-bff/src/server.ts
// BFF 服务实现
import Fastify from 'fastify';
import { BFFConfig, ticketDetailBFF } from './routes/registry';

const app = Fastify();
const bffRegistry = new Map<string, BFFConfig>([
  ['ticket-detail', ticketDetailBFF],
]);

app.get('/api/v1/bff/:configKey/:resourceId', async (request, reply) => {
  const { configKey, resourceId } = request.params as { configKey: string; resourceId: string };
  const config = bffRegistry.get(configKey);

  if (!config) {
    return reply.status(404).send({ error: 'BFF_CONFIG_NOT_FOUND', key: configKey });
  }

  const tenantId = request.headers['x-tenant-id'] as string;
  const results: Record<string, any> = {};

  // 并行请求所有数据源
  const fetchPromises = config.sources.map(async (source) => {
    try {
      const url = source.url
        .replace(':ticketId', resourceId)
        .replace(':connectionId', resourceId)
        .replace(':pipelineId', resourceId);

      const response = await fetch(`${url}?tenant_id=${tenantId}`, {
        headers: { 'Authorization': `Bearer ${request.headers['authorization']}` },
        signal: AbortSignal.timeout(5000),  // 5s 超时
      });

      if (!response.ok && source.required) {
        throw new Error(`${source.name} returned ${response.status}`);
      }

      results[source.name] = response.ok ? await response.json() : null;
    } catch (err) {
      if (source.required) throw err;
      console.warn(`[BFF] Optional source ${source.name} failed:`, err);
      results[source.name] = null;
    }
  });

  await Promise.allSettled(fetchPromises);

  // 检查是否有必须的数据源失败
  for (const source of config.sources) {
    if (source.required && !results[source.name]) {
      return reply.status(502).send({
        error: 'BFF_REQUIRED_SOURCE_FAILED',
        source: source.name,
      });
    }
  }

  return config.transform(results);
});
```

**BFF 层选择决策树**：

```
需要聚合多个后端数据
    │
    ├── 只需要 2-3 个数据源，逻辑简单？
    │   └── 是 → 方式一：子应用后端内聚合（代码写在 Controller 中）
    │
    ├── 需要为多个子应用提供统一聚合？

    └── 只需要简单合并响应，无需转换？
        └── 是 → 方式三：Gateway 声明式聚合（JSON 配置即可）
```

**BFF 与 Gateway 中间件的职责边界**：

| 维度 | Gateway 中间件 | BFF 层 |
|------|---------------|--------|
| 主要职责 | 认证、鉴权、限流、路由转发 | 数据聚合、格式转换、业务编排 |
| 是否处理业务逻辑 | ❌ 不处理 | ✅ 处理 |
| 是否需要写代码 | 否（配置规则） | 是（聚合逻辑） |
| 响应格式 | 透传后端响应 | 可自定义格式 |
| 适用场景 | 所有请求都要经过 | 只有需要聚合的请求才经过 |


```typescript
// orion-api-gateway/src/proxy.ts
async function proxyToSubapp(request: FastifyRequest, reply: FastifyReply) {
  const apiPath = request.url;  // /api/v1/myapp/config
  const subappKey = extractSubappKey(apiPath);  // myapp

  // 从 subapp_configs 查询后端地址
  const config = await db.query(
    'SELECT backend_service_url FROM subapp_configs WHERE key = $1 AND status = $2',
    [subappKey, 'enabled']
  );

  if (!config) {
    return reply.status(404).send({ error: 'SUBAPP_NOT_FOUND' });
  }

  // 代理请求到后端
  const response = await fetch(`${config.backend_service_url}${apiPath}`, {
    method: request.method,
    headers: {
      ...request.headers,
      'x-tenant-id': request.tenantId,      // 注入租户信息
      'x-user-id': request.userId,           // 注入用户信息
      'x-trace-id': request.traceId,         // 注入追踪 ID
    },
    body: request.body,
  });

  reply.send(await response.json());
}
```

#### 8.3.5 版本配置与绑定

版本管理涉及 3 个表的联动：

```
subapp_configs                subapp_versions               subapp_releases
     │                              │                            │
     │ current_version              │ 版本构建记录                │ 发布策略
     ├─────────────────────────────►│                            │
     │ "2.0.0"                      │ version: "2.0.0"           │ version: "2.0.0"
     │                              │ entry_prod: "/myapp/..."   │ strategy: "canary"
     │                              │ manifest: {...}            │ canary_percent: 10
     │                              │                            │
     │ stable_version               │                            │
     ├──────────────────────────────┼───────────────────────────►│
     │ "1.0.0"                      │ version: "1.0.0"           │ version: "1.0.0"
     │                              │ entry_prod: "/myapp/..."   │ strategy: "full"
     │                              │                            │ status: "complete"
```

**版本发布流程**：

```
1. 构建新版本
   POST /api/v1/subapps/myapp/versions
   { "version": "2.0.0", "entry_dev": "...", "entry_prod": "...", "manifest": {...} }
   → 写入 subapp_versions 表

2. 创建发布策略
   POST /api/v1/subapps/myapp/releases
   { "version": "2.0.0", "strategy": "canary", "canary_percent": 10 }
   → 写入 subapp_releases 表

3. 更新配置（灰度发布不立即更新 current_version）
   - canary 模式: current_version 保持 "1.0.0"，前端通过 release 策略灰度
   - full 模式: current_version 更新为 "2.0.0"

4. 前端加载时获取版本
   GET /api/v1/subapps/enabled
   → 返回 current_version + release 策略
   → VersionAwareLoader 根据策略决定加载哪个版本
```

**版本绑定 API**：

```typescript
// 发布完整流程 API
POST /api/v1/subapps/{key}/release
{
  "action": "publish" | "rollback" | "promote",
  "version": "2.0.0",
  "strategy": "full" | "canary" | "ab",
  "canary_percent": 10,        // 灰度模式可选
  "canary_users": ["user-1"],  // 灰度用户可选
  "canary_tenants": ["t-1"]    // 灰度租户可选
}
```

**API 处理逻辑**：

```typescript
async function releaseSubapp(key: string, body: ReleaseRequest) {
  const { action, version, strategy } = body;

  switch (action) {
    case 'publish':
      // 1. 验证版本存在
      const ver = await db.query(
        'SELECT * FROM subapp_versions WHERE subapp_key = $1 AND version = $2',
        [key, version]
      );
      if (!ver) throw new Error('VERSION_NOT_FOUND');

      // 2. 创建发布记录
      await db.query(
        'INSERT INTO subapp_releases (subapp_key, version, strategy, canary_percent) VALUES ($1, $2, $3, $4)',
        [key, version, strategy, body.canary_percent || 0]
      );

      // 3. 全量发布时更新 current_version
      if (strategy === 'full') {
        await db.query(
          'UPDATE subapp_configs SET current_version = $1, updated_at = NOW() WHERE key = $2',
          [version, key]
        );
      }
      break;

    case 'rollback':
      // 回滚到指定版本
      await db.query(
        'UPDATE subapp_configs SET current_version = $1, stable_version = current_version, updated_at = NOW() WHERE key = $2',
        [version, key]
      );
      await db.query(
        'UPDATE subapp_releases SET status = $1, rollback_to = $2 WHERE subapp_key = $3 AND version = $4',
        ['rolled_back', version, key, version]
      );
      break;

    case 'promote':
      // 灰度提升为全量
      await db.query(
        'UPDATE subapp_configs SET current_version = $1, stable_version = $1, updated_at = NOW() WHERE key = $2',
        [version, key]
      );
      await db.query(
        'UPDATE subapp_releases SET status = $1, completed_at = NOW() WHERE subapp_key = $2 AND version = $3',
        ['complete', key, version]
      );
      break;
  }
}
```

#### 8.3.6 主应用如何加载配置

主应用启动时和运行时如何获取子应用配置：

```typescript
// orion-frontend/src/stores/subAppStore.ts
interface SubAppConfig {
  key: string;
  name: string;
  entry_dev: string;
  entry_prod: string;
  routes: string[];
  backend_service_url: string;
  api_paths: string[];
  current_version: string;
  status: string;
  css_isolation: string;
  use_shared: boolean;
  sse_endpoints: Record<string, string>;
}

// 启动时加载所有启用的子应用
export async function loadSubAppConfigs(): Promise<void> {
  const response = await fetch('/api/v1/subapps/enabled');
  const configs: SubAppConfig[] = await response.json();

  // 存入状态管理
  subAppStore.setConfigs(configs);

  // 动态注册路由
  for (const config of configs) {
    for (const route of config.routes) {
      registerRoute(route, config);
    }
  }

  // 启动配置刷新轮询（可选）
  startConfigPolling();
}

// 获取单个子应用配置
export function getSubAppConfig(key: string): SubAppConfig | undefined {
  return subAppStore.getConfig(key);
}

// 获取后端 URL
export function getSubAppBackendUrl(key: string): string | undefined {
  return subAppStore.getConfig(key)?.backend_service_url;
}

// 获取入口地址（根据环境）
export function getSubAppEntry(key: string): string {
  const config = subAppStore.getConfig(key);
  if (!config) throw new Error(`SubApp ${key} not found`);

  return import.meta.env.DEV ? config.entry_dev : config.entry_prod;
}
```

| 方式 | 实现 | 延迟 | 适用场景 |
|------|------|------|---------|
| 启动时加载 | `loadSubAppConfigs()` | 无 | 首次加载 |
| 定时轮询 | 每 60s 拉取 `GET /subapps/enabled` | 最长 60s | 配置低频变更 |

### 8.4 第三步：实现租户中间件（核心）

所有子应用后端**必须**实现租户中间件，从 Gateway 注入的 header 中读取租户信息。

#### 8.4.1 Fastify（Node.js）

```typescript
// myapp-service/src/middleware/tenant.ts
import { FastifyRequest, FastifyReply, FastifyInstance } from 'fastify';

export async function tenantMiddleware(request: FastifyRequest, reply: FastifyReply) {
  const tenantId = request.headers['x-tenant-id'] as string;
  const userId = request.headers['x-user-id'] as string;
  const permissions = JSON.parse((request.headers['x-permissions'] as string) || '[]');

  if (!tenantId) {
    return reply.status(401).send({
      success: false,
      error: 'MISSING_TENANT',
      message: 'X-Tenant-Id header is required',
    });
  }

  // 存入请求上下文
  (request as any).tenantId = tenantId;
  (request as any).userId = userId;
  (request as any).permissions = permissions;
}

// 注册到 Fastify 实例
```

```typescript
// myapp-service/src/middleware/tenant.ts
import { Request, Response, NextFunction } from 'express';

export function tenantMiddleware(req: Request, res: Response, next: NextFunction) {
  const tenantId = req.headers['x-tenant-id'] as string;
  const userId = req.headers['x-user-id'] as string;

  if (!tenantId) {
    return res.status(401).json({ error: 'MISSING_TENANT' });
  }

  (req as any).tenantId = tenantId;
  (req as any).userId = userId;
  next();
}

// 应用中间件
app.use('/api/v1/myapp', tenantMiddleware);
```

```java
@Component
public class TenantInterceptor implements HandlerInterceptor {
    @Override
    public boolean preHandle(HttpServletRequest request,
                            HttpServletResponse response,
                            Object handler) {
        String tenantId = request.getHeader("X-Tenant-Id");
        String userId = request.getHeader("X-User-Id");

        if (tenantId == null) {
            response.setStatus(401);
            return false;
        }

        // 存入 ThreadLocal（当前线程上下文）
        TenantContext.setTenantId(tenantId);
        TenantContext.setUserId(userId);

    }

    public void afterCompletion(HttpServletRequest request,
                               HttpServletResponse response,
                               Object handler,
                               Exception ex) {
        // 清理 ThreadLocal，防止线程池复用污染
        TenantContext.clear();
    }
}
```

### 8.5 第四步：实现 Repository 层租户隔离

**原则：所有 SQL 查询必须自动附加 `WHERE tenant_id = ?`**

#### 8.5.1 自动注入模式（推荐）

```typescript
// 使用 TenantRepository 基类，自动附加 tenant_id
class ConfigRepository extends TenantRepository<Config> {
  constructor() {
    super('configs'); // 表名
  }

  // 自动变为：SELECT * FROM configs WHERE tenant_id = $1
  // 不需要手动写 WHERE tenant_id = ?
  async findAllByTenant(tenantId: string): Promise<Config[]> {
    return this.findByTenant(tenantId);
  }
}
```

#### 8.5.2 手动注入模式

如果无法使用基类，手动附加租户过滤：

```typescript
// ❌ 禁止：不带租户过滤的查询
const configs = await db.query('SELECT * FROM configs');

// ✅ 正确：从 header 读取并附加
const tenantId = (request as any).tenantId;
const configs = await db.query(
  'SELECT * FROM configs WHERE tenant_id = $1',
  [tenantId]
);
```

#### 11.4.2 通信规范

| 场景 | 推荐方式 | 禁止行为 | 示例 |
|------|---------|---------|------|
| 按钮点击后刷新其他子应用列表 | 事件总线 | 直接操作其他子应用 DOM | DBA 创建数据源后通知 KB 刷新 |

**SSE（Server-Sent Events）—— 单向推送**：

```typescript
// orion-api-gateway/src/routes/sse-proxy.ts
// Gateway 透传 SSE 流，不缓冲
// 使用 @fastify/reply-from（Gateway 已有依赖），正确处理流式传输

app.get('/api/v1/sse/:subapp/:topic', async (request, reply) => {
  const { subapp, topic } = request.params as { subapp: string; topic: string };
  const tenantId = request.headers['x-tenant-id'] as string;

  // ACL 校验：子应用是否允许订阅该 topic
  await checkSseTopicACL(subapp, topic, tenantId);

  // 连接数限制：单用户最多 20 个 SSE 连接
  const userId = (request as any).user?.user_id || 'anonymous';
  const sseConnKey = `sse_connections:${userId}`;
  const currentSseCount = await redis.incr(sseConnKey);
  if (currentSseCount > 20) {
    await redis.decr(sseConnKey);
    return reply.status(429).send({
      error: 'TOO_MANY_SSE_CONNECTIONS',
      message: 'Maximum 20 SSE connections per user',
    });
  }
  redis.expire(sseConnKey, 86400);

  // 连接断开时清理计数
  request.raw.on('close', () => { redis.decr(sseConnKey); });

  // 查找子应用后端 SSE 服务地址
  const targetUrl = await resolveSubAppSseUrl(subapp, topic, tenantId);

  // 使用 @fastify/reply-from 代理 SSE 流
  // 自动处理流式传输、连接断开、重试等
  return reply.from(targetUrl, {
    rewriteRequestHeaders: (originalHeaders, req) => ({
      ...originalHeaders,
      'X-Tenant-Id': tenantId,
      'X-User-Id': req.headers['x-user-id'] as string,
      'Authorization': req.headers['authorization'] as string,
    }),
    // 不缓冲响应
    disableCache: true,
  });
});

// resolveSubAppSseUrl 实现：从 subapp_configs 动态读取
async function resolveSubAppSseUrl(subapp: string, topic: string, tenantId: string): string {
  const config = await getSubAppConfig(subapp);
  // 支持按 topic 路由到不同后端
  const sseEndpoint = config.sse_endpoints?.[topic] || config.backend_service_url;
  return `${sseEndpoint}/api/v1/sse/${topic}?tenant_id=${tenantId}`;
}
```

**WebSocket（双向交互）—— 终端/协作场景**：

```typescript
// orion-api-gateway/src/routes/ws-proxy.ts
import WebSocket from 'ws';
import { verifyJwt } from '../services/auth';

app.get('/api/v1/ws/:subapp/:sessionId', { websocket: true }, (connection, request) => {
  const { subapp, sessionId } = request.params as { subapp: string; sessionId: string };

  // ⚠️ WebSocket 不走常规中间件链，必须在路由内部显式认证
  const token = request.query.token as string || request.headers['sec-websocket-protocol'] as string;
  if (!token) {
    connection.socket.close(1008, 'Authentication required');
    return;
  }

  // 验证 JWT
  let payload: any;
  try {
    payload = verifyJwt(token);
  } catch {
    connection.socket.close(1008, 'Invalid token');
    return;
  }

  const tenantId = payload.tenant_id as string;
  const userId = payload.user_id as string;

  // 连接数限制
  const connKey = `ws_connections:${userId}`;
  const currentCount = await redis.incr(connKey);
  if (currentCount > 10) {
    await redis.decr(connKey);
    connection.socket.close(1008, 'Too many connections');
    return;
  }
  redis.expire(connKey, 86400);

  // ⚠️ 验证 sessionId 归属：防止用户 A 通过已知 sessionId 连接用户 B 的会话
  const session = await db.query(
    'SELECT user_id FROM ws_sessions WHERE id = $1 AND disconnected_at IS NULL',
    [sessionId],
  );
  if (!session || session.user_id !== userId) {
    await redis.decr(connKey);
    connection.socket.close(1008, 'Session mismatch or expired');
    return;
  }

  // 查找子应用 WebSocket 服务地址
  const wsUrl = await resolveSubAppWsUrl(subapp, sessionId);
  if (!wsUrl) {
    connection.socket.close(1008, 'SubApp WebSocket service not found');
    return;
  }

  // 建立后端 WebSocket 连接（携带认证信息）
  const backendWs = new WebSocket(wsUrl, {
    headers: {
      'X-Tenant-Id': tenantId,
      'X-User-Id': userId,
      'X-Session-Id': sessionId,
    },
  });

  // 双向转发
  connection.socket.on('message', (data) => {
    if (data.length > 1024 * 1024) {
      connection.socket.send(JSON.stringify({ error: 'MESSAGE_TOO_LARGE' }));
      return;
    }
    if (backendWs.readyState === WebSocket.OPEN) {
      backendWs.send(data);
    }
  });

  backendWs.on('message', (data) => {
    if (connection.socket.readyState === WebSocket.OPEN) {
      connection.socket.send(data);
    }
  });

  // 连接关闭清理
  connection.socket.on('close', () => {
    backendWs.close();
    redis.decr(connKey);
  });
  backendWs.on('close', () => {
    connection.socket.close();
    redis.decr(connKey);
  });
});

// resolveSubAppWsUrl 实现
async function resolveSubAppWsUrl(subapp: string, sessionId: string): string {
  const config = await getSubAppConfig(subapp);
  return `${config.backend_service_url}/api/v1/ws/${sessionId}`;
}
```

```typescript
// orion-platform-service/src/api/upload-routes.ts
import { S3Client, CreateMultipartUploadCommand, ... } from '@aws-sdk/client-s3';

const s3 = new S3Client({ endpoint: process.env.MINIO_ENDPOINT });

// 初始化上传
router.post('/api/v1/upload/init', async (request, reply) => {
  const { filename, contentType, fileSize, subappKey } = request.body as {
    filename: string; contentType: string; fileSize: number; subappKey: string;
  };

  // ACL 校验：子应用是否有上传权限
  await checkUploadACL(subappKey);

  // 创建分片上传
  const { UploadId } = await s3.send(new CreateMultipartUploadCommand({
    Bucket: process.env.UPLOAD_BUCKET,
    Key: `${subappKey}/${uuid()}/${filename}`,
    ContentType: contentType,
    Metadata: { 'x-tenant-id': request.headers['x-tenant-id'] as string },
  }));

  reply.send({
    uploadId: UploadId,
    partSize: 5 * 1024 * 1024, // 5MB
    presignTemplate: `/api/v1/upload/part/{partNumber}`,
  });
});

// 获取分片上传 presigned URL
router.post('/api/v1/upload/part', async (request, reply) => {
  const { uploadId, partNumber } = request.body as { uploadId: string; partNumber: number };

  // 从 file_uploads 表查询 S3 key
  const upload = await db.query('SELECT s3_key FROM file_uploads WHERE upload_id = $1', [uploadId]);
  if (!upload) {
    return reply.status(404).send({ error: 'UPLOAD_NOT_FOUND' });
  }

  const url = await getSignedUrl(s3, new UploadPartCommand({
    Bucket: process.env.UPLOAD_BUCKET,
    Key: extractKeyFromUploadId(uploadId),
    UploadId: uploadId,
    PartNumber: partNumber,
  }), { expiresIn: 300 });

  reply.send({ url });
});

// 完成上传
router.post('/api/v1/upload/complete', async (request, reply) => {
  const { uploadId, parts } = request.body as { uploadId: string; parts: { PartNumber: number; ETag: string }[] };

  // 从 file_uploads 表查询 S3 key
  const upload = await db.query('SELECT s3_key FROM file_uploads WHERE upload_id = $1', [uploadId]);
  if (!upload) {
    return reply.status(404).send({ error: 'UPLOAD_NOT_FOUND' });
  }

  await s3.send(new CompleteMultipartUploadCommand({
    Bucket: process.env.UPLOAD_BUCKET,
    Key: upload.s3_key,
    UploadId: uploadId,
    MultipartUpload: { Parts: parts },
  }));

  // 触发后续处理（如 SQL 文件导入、制品扫描等）
  await emitEvent('upload.completed', { uploadId, subappKey });

  reply.send({ success: true });
});
```

```typescript
// orion-platform-service/src/services/task/TaskService.ts
import { Queue, Worker, Job } from 'bullmq';
import Redis from 'ioredis';

const redis = new Redis(process.env.REDIS_URL);
const taskQueue = new Queue('async-tasks', { connection: redis });

// 创建异步任务
async function createTask(type: string, payload: Record<string, any>, userId: string, tenantId: string) {
  const job = await taskQueue.add(type, payload, {
    jobId: generateTaskId(),
    attempts: type === 'db-migration' ? 1 : 3, // 迁移类不重试，其他重试 3 次
    backoff: { type: 'exponential', delay: 5000 },
    removeOnComplete: { age: 86400 }, // 24 小时后清理
    removeOnFail: { age: 604800 },    // 7 天后清理
  });

  // 持久化到 PostgreSQL
  await db.query(
    'INSERT INTO async_tasks (id, type, status, payload, user_id, tenant_id) VALUES ($1,$2,$3,$4,$5,$6)',
    [job.id, type, 'pending', payload, userId, tenantId],
  );

  return { taskId: job.id, status: 'pending' };
}

// Worker 执行
new Worker('async-tasks', async (job: Job) => {
  const { type, payload } = job.data;

  // 更新进度（SSE 推送）
  const updateProgress = async (progress: number, message: string) => {
    await job.updateProgress(progress);
    await emitEvent('task.progress', { taskId: job.id, progress, message });
  };

  switch (type) {

    case 'data-import':
      await executeDataImport(payload, updateProgress);
      break;
    case 'report-generation':

      break;
  }
```

```typescript
// orion-platform-service/src/events/EventBus.ts
import Redis from 'ioredis';

const redis = new Redis(process.env.REDIS_URL);

// 发布事件
export async function publishEvent(event: {
  type: string;
  source: string;
  tenantId: string;
  data: Record<string, any>;
}) {
  const envelope = {
    id: generateEventId(),
    timestamp: Date.now(),
    ...event,
  };

  // 发布到 Redis Pub/Sub（实时通知）
  await redis.publish(`events:${event.source}`, JSON.stringify(envelope));

  // 持久化到 PostgreSQL（审计 + 重放）
  await db.query(
    'INSERT INTO event_log (id, type, source, tenant_id, data, created_at) VALUES ($1,$2,$3,$4,$5,NOW())',
    [envelope.id, envelope.type, envelope.source, envelope.tenantId, envelope.data],
  );
}

// 订阅事件（复用单个 Redis Pub/Sub 连接，避免连接泄漏）
let eventSubscriber: Redis | null = null;
const eventHandlers = new Map<string, Array<(event: any) => Promise<void>>>();

export function subscribeEvent(source: string, handler: (event: any) => Promise<void>) {
  // 懒初始化：第一个订阅者创建 Redis 连接
  if (!eventSubscriber) {
    eventSubscriber = new Redis(process.env.REDIS_URL);
  }

  // 注册 handler
  const handlers = eventHandlers.get(source) || [];
  handlers.push(handler);
  eventHandlers.set(source, handlers);

  // 首次订阅时创建 Redis 订阅
  if (handlers.length === 1) {
    eventSubscriber.subscribe(`events:${source}`);
  }

  // 事件分发
  eventSubscriber.on('message', async (_channel, message) => {
    const sourceFromChannel = _channel.replace('events:', '');
    const handlers = eventHandlers.get(sourceFromChannel) || [];
    for (const handler of handlers) {
      try {
        await handler(JSON.parse(message));
      } catch (error) {
        await db.query(
          'INSERT INTO event_dlq (event_id, error, retry_count, created_at) VALUES ($1,$2,0,NOW())',
          [JSON.parse(message).id, String(error)],
        );
      }
    }
  });
}

// 服务启动时重放未处理事件（补偿机制）
export async function replayMissedEvents(lastProcessedAt: Date) {
  const missedEvents = await db.query(
    'SELECT * FROM event_log WHERE created_at > $1 ORDER BY created_at ASC',
    [lastProcessedAt],
  );
  for (const event of missedEvents) {
    const handlers = eventHandlers.get(event.source) || [];
    for (const handler of handlers) {
      try {
        await handler(event);
      } catch {
        // 重放失败进入 DLQ，不阻断后续事件
        await db.query(
          'INSERT INTO event_dlq (event_id, error, retry_count, created_at) VALUES ($1,$2,0,NOW())',
          [event.id, 'replay_failed'],
        );
      }
    }
  }
}
```

```typescript
import { FastifyRequest, FastifyReply } from 'fastify';

export async function tenantScopeMiddleware(request: FastifyRequest, reply: FastifyReply) {
  const payload = (request as any).user;
  const requestedTenantId = request.headers['x-tenant-id'] as string;

  switch (payload.role) {
    case 'platform_admin':
      // 允许访问所有租户，但必须显式指定 tenant_id
      if (!requestedTenantId) {
        // 未指定租户时，返回租户列表供管理员选择
        return reply.status(400).send({
          error: 'TENANT_REQUIRED',
          message: 'Platform admin must specify X-Tenant-Id header',
          hint: 'GET /api/v1/tenants to list available tenants',
        });
      }
      // 注入租户 ID（正常流程），同时记录跨租户审计日志
      request.headers['x-tenant-id'] = requestedTenantId;
      await logCrossTenantAccess(payload.user_id, requestedTenantId, request.raw.url!);
      break;

    case 'tenant_admin':
    case 'tenant_user':
      // 只能访问自己的租户
      if (requestedTenantId && requestedTenantId !== payload.tenant_id) {
        return reply.status(403).send({
          error: 'CROSS_TENANT_DENIED',
          message: `Cannot access tenant ${requestedTenantId}`,
        });
      }
      request.headers['x-tenant-id'] = payload.tenant_id;
      break;

    case 'external_collaborator':
      // 检查临时授权
      const granted = await checkExternalAccess(payload.user_id, requestedTenantId);
      if (!granted) {
        return reply.status(403).send({ error: 'ACCESS_DENIED' });
      }
      request.headers['x-tenant-id'] = requestedTenantId;
      break;

    default:
      return reply.status(403).send({ error: 'UNKNOWN_ROLE' });
  }
}
```

```typescript
// orion-platform-service/src/api/batch-routes.ts

interface BatchOperation {
  method: 'create' | 'update' | 'delete';
  path: string;
  body: Record<string, any>;
}

interface BatchRequest {
  operations: BatchOperation[];
  strategy: 'all_or_nothing' | 'best_effort' | 'stop_on_first';
}

interface BatchResult {
  success_count: number;
  failure_count: number;
  results: { index: number; success: boolean; data?: any; error?: string }[];
}

// executeBatchOperation 实现：根据 method 和 path 路由到具体服务
async function executeBatchOperation(
  client: any,
  op: BatchOperation,
  tenantId: string,
): Promise<any> {
  switch (op.method) {
    case 'create':
      return await client.query(
        `INSERT INTO ${extractTable(op.path)} (tenant_id, data) VALUES ($1, $2) RETURNING *`,
        [tenantId, JSON.stringify(op.body)],
      );
    case 'update':
      return await client.query(
        `UPDATE ${extractTable(op.path)} SET data = $1 WHERE tenant_id = $2 AND id = $3 RETURNING *`,
        [JSON.stringify(op.body), tenantId, op.body.id],
      );
    case 'delete':
      return await client.query(
        `DELETE FROM ${extractTable(op.path)} WHERE tenant_id = $1 AND id = $2`,
        [tenantId, op.body.id],
      );
    default:
      throw new Error(`Unknown batch method: ${op.method}`);
  }
}

// 从 API 路径提取表名（简化示例，生产应使用路由注册表）
function extractTable(path: string): string {
  const mapping: Record<string, string> = {
    '/api/v1/configs': 'configs',
    '/api/v1/alerts': 'alert_rules',
    '/api/v1/permissions': 'permissions',
  };
  for (const [prefix, table] of Object.entries(mapping)) {
    if (path.startsWith(prefix)) return table;
  }
  throw new Error(`No table mapping for path: ${path}`);
}

router.post('/api/v1/batch', async (request, reply) => {
  const { operations, strategy } = request.body as BatchRequest;
  const tenantId = request.headers['x-tenant-id'] as string;

  // 限制单次批量操作数量
  if (operations.length > 100) {
    return reply.status(400).send({
      error: 'BATCH_TOO_LARGE',
      message: 'Maximum 100 operations per request. Use /batch/async for larger batches.',
    });
  }

  const client = await db.getClient();
  const results: BatchResult = { success_count: 0, failure_count: 0, results: [] };

  try {
    if (strategy === 'all_or_nothing') {
      await client.query('BEGIN');
    }

    for (let i = 0; i < operations.length; i++) {
      const op = operations[i];

      try {
        const result = await executeBatchOperation(client, op, tenantId);
        results.results.push({ index: i, success: true, data: result });
        results.success_count++;
      } catch (error) {
        results.results.push({ index: i, success: false, error: String(error) });
        results.failure_count++;

        if (strategy === 'all_or_nothing') {
          await client.query('ROLLBACK');
          return reply.send(results);
        }
        if (strategy === 'stop_on_first') {
          return reply.send(results);
        }
        // best_effort: 继续执行
      }
    }

    if (strategy === 'all_or_nothing') {
      await client.query('COMMIT');
    }

    reply.send(results);
  } finally {
    // 安全释放：如果 all_or_nothing 模式下发生了失败但未 ROLLBACK（如异常跳出），回滚事务
    try {
      if (strategy === 'all_or_nothing' && results.failure_count > 0) {
        await client.query('ROLLBACK');
      }
    } finally {
      client.release();
    }
  }
});

// 大批量异步版本
router.post('/api/v1/batch/async', async (request, reply) => {
```

### 13.3 回滚方案

系统具备**三层回滚能力**，覆盖从中间件开关到版本回退的完整场景。

#### 13.3.1 中间件级回滚（Level 1 - 分钟级）

| 中间件 | 回滚方式 | KILL SWITCH | 回滚耗时 |
|--------|---------|-------------|---------|
| ACL | Feature Flag `api_acl_enabled: false` | 关闭后跳过 ACL 检查，恢复默认允许 | <1 分钟 |
| 限流 | Feature Flag `rate_limit_enabled: false` | 关闭后跳过限流检查 | <1 分钟 |
| 追踪 | 无风险，可直接保留 | N/A | N/A |
| 租户注入 | 保留向后兼容：header 不存在时从 JWT 解析 | N/A | N/A |

```typescript
// ACL 中间件中的 Feature Flag 示例
export async function apiACL(request: FastifyRequest, reply: FastifyReply) {
  if (!isFeatureEnabled('api_acl_enabled')) return;  // 一键关闭 ACL
  // ... 正常 ACL 逻辑
}
```

**触发场景**：
- 新中间件上线后出现大面积 500 错误
- 限流规则过于严格导致正常用户被拦截
- ACL 规则配置错误导致合法请求被拒绝

#### 13.3.2 灰度回滚（Level 2 - 秒级）

新中间件上线时先灰度 10% 流量，观察 24 小时：

```typescript
// 灰度中间件：10% 流量走 ACL，90% 跳过
export async function apiACLCanary(request: FastifyRequest, reply: FastifyReply) {
  if (Math.random() > 0.1) return;  // 90% 跳过
  // 10% 执行 ACL 检查（仅记录，不拒绝）
  const result = await checkACL(request);
  if (!result.allowed) {
    logCanaryDenial(request, result);  // 记录但不拒绝
  }
}
```

**灰度发布流程**：

| 阶段 | 流量比例 | 观察指标 | 持续时间 | 回滚动作 |
|------|---------|---------|---------|---------|
| 灰度 10% | `canary_percent: 0.1` | 错误率 <1% | 24h | `canary_percent: 0` |
| 灰度 30% | `canary_percent: 0.3` | 错误率 <1% | 12h | `canary_percent: 0.1` |
| 灰度 100% | `canary_percent: 1.0` | 错误率 <0.5% | 6h | `canary_percent: 0.3` |
| 全量发布 | 移除灰度中间件 | 正常监控 | N/A | Feature Flag 关闭 |

**触发场景**：
- 灰度期间错误率超过阈值
- 性能指标（P99 延迟）显著恶化
- 用户反馈异常行为

**回滚方式**：将 `canary_percent` 归零，所有流量跳过新中间件。

#### 13.3.3 版本级回滚（Level 3 - 即时生效）

`subapp_releases` 表支持版本回滚：

```sql
-- 回滚表结构
CREATE TABLE subapp_releases (
  id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  subapp_key      VARCHAR(50) NOT NULL,
  version         VARCHAR(20) NOT NULL,
  build_url       TEXT,
  changelog       TEXT,
  status          VARCHAR(20) DEFAULT 'published',
  created_at      TIMESTAMP DEFAULT NOW(),
  created_by      VARCHAR(50),
  rollback_to     VARCHAR(20)                        -- 回滚目标版本
);
```

**回滚 API**：

```
POST /api/v1/subapps/{key}/release
{
  "action": "rollback",
  "target_version": "1.0.0"
}
```

**回滚流程**：

```
1. 管理员发起回滚请求 → target_version = "1.0.0"
2. 更新 subapp_configs.current_version = "1.0.0"
3. 更新 subapp_releases 记录 rollback_to = "1.0.0"
4. 前端 VersionAwareLoader 检测到 rollback_to，立即加载 v1.0.0
5. 所有用户下次加载子应用时自动使用稳定版本
```

**触发场景**：
- 新版本发布后发现严重功能缺陷
- 前端页面崩溃率超过 5%
- 关键 API 不兼容导致数据错误

**回滚耗时**：
- 配置更新：即时生效
- 用户侧生效：下次页面加载（平均 <3s）
- 无需重新构建或部署

**版本回滚与灰度回滚的区别**：

| 维度 | 灰度回滚 | 版本回滚 |
|------|---------|---------|
| 回滚对象 | 中间件/功能开关 | 子应用构建版本 |
| 回滚粒度 | 流量百分比 | 整个应用版本 |
| 生效方式 | 修改 canary_percent | 修改 current_version |
| 适用场景 | 新功能验证失败 | 新版本质量不达标 |
| 回滚耗时 | 秒级 | 即时（用户下次加载生效） |

#### 13.3.4 回滚决策矩阵

| 故障类型 | 影响范围 | 推荐回滚级别 | 示例 |
|---------|---------|-------------|------|
| 中间件 Bug | 全局 | Level 1（Feature Flag 关闭） | ACL 规则解析错误 |
| 性能下降 | 部分用户 | Level 2（灰度回滚） | P99 延迟从 15ms → 50ms |
| 版本缺陷 | 全部用户 | Level 3（版本回滚） | 页面崩溃、API 不兼容 |
| 配置错误 | 特定租户 | Level 1 + Level 3 | 某租户 ACL 规则配置错误 |

回滚能力需要定期验证有效性：

| 演练项 | 频率 | 验证方式 |
|-------|------|---------|

**端口冲突检测**（后端注册时自动校验）：

```typescript
// orion-platform-service/src/services/subapp/SubAppService.ts
async createSubApp(config: CreateSubAppDto) {
  // 提取端口
  const devPort = this.extractPortFromUrl(config.entry_dev);
  const backendPort = this.extractPortFromUrl(config.backend_service_url);

  // 检查端口范围
  if (devPort && !this.isInRange(devPort, 3030, 3039) && !this.isInRange(devPort, 5170, 5179)) {
    throw new BadRequestException(
      `前端开发端口 ${devPort} 不在允许范围 (3030-3039 或 5170-5179)`
    );
  }
  if (backendPort && !this.isInRange(backendPort, 3040, 3049) && !this.isInRange(backendPort, 8090, 8099)) {
    throw new BadRequestException(
      `后端端口 ${backendPort} 不在允许范围 (3040-3049 或 8090-8099)`
    );
  }

  // 检查端口是否已被占用
  const existingApps = await this.subAppRepository.findAll();
  for (const app of existingApps) {
    const existingDevPort = this.extractPortFromUrl(app.entry_dev);
    const existingBackendPort = this.extractPortFromUrl(app.backend_service_url);
    if (devPort && (devPort === existingDevPort || devPort === existingBackendPort)) {
      throw new ConflictException(`前端端口 ${devPort} 已被子应用 "${app.key}" 占用`);
    }
    if (backendPort && (backendPort === existingDevPort || backendPort === existingBackendPort)) {
      throw new ConflictException(`后端端口 ${backendPort} 已被子应用 "${app.key}" 占用`);
    }
  }

  return this.subAppRepository.create(config);
}

private isInRange(port: number, min: number, max: number): boolean {
  return port >= min && port <= max;
}

private extractPortFromUrl(url: string): number | null {
  try {
    const parsed = new URL(url);
    return parsed.port ? parseInt(parsed.port, 10) : null;
  } catch {
    return null;
  }
}
```

新增子应用时，在 `subapp_configs` 中申请端口，**不得随意占用未分配端口**。

### 14.1 限流规则配置

#### 在哪配

**方式一：管理页面** — 访问 `/console/subapps/{key}/rate-limits`

**方式二：API**：

```bash
# 新增限流规则

{
  "api_prefix": "/api/v1/myapp",
  "qps": 1000,
  "burst_qps": 2000,
  "tenant_daily_limit": 10000,
  "global_daily_limit": 1000000
}

# 修改限流规则
PUT /api/v1/subapps/{key}/rate-limits/{rule_id}
{
  "qps": 500
}

# 删除限流规则
DELETE /api/v1/subapps/{key}/rate-limits/{rule_id}
```

**方式三：直接插入数据库**（不推荐，仅紧急情况使用）：

```sql
INSERT INTO api_rate_limits (subapp_key, api_prefix, qps, burst_qps, tenant_daily_limit, global_daily_limit)
VALUES ('myapp', '/api/v1/myapp', 1000, 2000, 10000, 1000000);
```

#### 怎么验证

```bash
# 1. 查询当前限流规则
curl http://api-gateway:3000/api/v1/subapps/myapp/rate-limits

# 2. 触发限流测试（快速连续发请求）
for i in {1..1050}; do curl -s -o /dev/null -w "%{http_code}\n" http://api-gateway:3000/api/v1/myapp/config; done
# 预期：前 1000 个返回 200，后续返回 429

# 3. 查看限流日志

```

#### 不生效怎么查

| 现象 | 排查步骤 | 可能原因 |
|------|---------|---------|
| 规则已配但无限制 | 1. `curl /api/v1/subapps/myapp/rate-limits` 确认规则存在 | 规则未同步到 Gateway 内存 |
| | 2. 检查 Gateway 日志 `grep "rate-limit" gateway.log` | Redis 连接异常 |
| | 3. `redis-cli ping` 确认 Redis 可达 | Lua 脚本未正确加载 |
| 限流过于严格 | 1. 检查 QPS 配置是否过低 | qps 设置过小 |
| | 2. 检查是否命中租户日限制 | tenant_daily_limit 过低 |
| 限流完全无效 | 1. `GET /api/v1/feature-flags` 确认 `rate_limit_enabled: true` | Feature Flag 关闭 |
| | 2. 检查中间件注册顺序 | rate-limit 必须在 proxy 之前 |

### 14.2 ACL 规则配置

#### 在哪配

**方式一：管理页面** — 访问 `/console/subapps/{key}/acl`

**方式二：API**：

#### 怎么验证

```bash
curl http://api-gateway:3000/api/v1/subapps/myapp/acl

# 3. 跨前缀访问测试（应拒绝）
curl -H "Authorization: Bearer <jwt>" \
```

#### 不生效怎么查

|------|---------|---------|
| 规则已配但可越权访问 | 1. `grep "acl" gateway.log` 看是否执行了 ACL 检查 | Feature Flag `api_acl_enabled` 关闭 |
| | 2. 检查 `extractSubappKey()` 返回值 | API 路径无法匹配到子应用 |
| 所有请求都被拒绝 | 1. 检查默认规则（无匹配时应 allow） | 默认规则配置为 deny |

| 新增规则不生效 | 1. 确认规则写入数据库 | SQL 执行失败 |
| | 2. 重启 Gateway 或等待 30s 同步 | 缓存未刷新 |

### 14.3 版本发布与回滚

#### 在哪配

**API 操作**（无管理页面，通过 API 或 CLI 执行）：

```bash
# 1. 构建新版本（CI/CD 自动执行）
POST /api/v1/subapps/{key}/versions
{
  "version": "2.0.0",
  "entry_dev": "http://localhost:3040/remoteEntry.js",
  "entry_prod": "/myapp/v2.0.0/remoteEntry.js",
  "manifest": {"main.js": "...", "style.css": "..."},
  "changelog": "新增 XX 功能"
}

# 2. 全量发布
POST /api/v1/subapps/{key}/release
{
  "action": "publish",
  "version": "2.0.0",
  "strategy": "full"
}

# 3. 灰度发布
POST /api/v1/subapps/{key}/release
{
  "action": "publish",
  "version": "2.0.0",
  "strategy": "canary",
  "canary_percent": 10,
  "canary_users": ["user-1", "user-2"]
}

# 4. 灰度提升为全量
POST /api/v1/subapps/{key}/release
{
  "action": "promote",
  "version": "2.0.0"
}

# 5. 回滚到旧版本
POST /api/v1/subapps/{key}/release
{
  "action": "rollback",
  "version": "1.0.0"
}
```

#### 怎么验证

```bash
# 1. 查询当前版本状态
curl http://api-gateway:3000/api/v1/subapps/myapp/releases
# 返回：当前版本、发布策略、灰度状态

# 2. 查询版本列表
curl http://api-gateway:3000/api/v1/subapps/myapp/versions
# 返回：所有已构建的版本及其状态

# 3. 验证前端加载版本
# 浏览器 DevTools → Network → 查看 remoteEntry.js 的 URL 路径是否包含正确版本号
```

#### 不生效怎么查

| 现象 | 排查步骤 | 可能原因 |
|------|---------|---------|
| 发布后前端仍加载旧版 | 1. `curl /subapps/enabled` 确认 current_version 已更新 | 数据库更新失败 |
| | 2. 检查前端是否缓存了旧配置 | 浏览器缓存未刷新 |
| | 3. 强制刷新页面（Cmd+Shift+R） | 前端 Store 未重新拉取 |
| 灰度用户加载了旧版 | 1. 确认灰度用户 ID 在 canary_users 列表中 | 用户 ID 不匹配 |
| | 2. 检查 canary_percent 是否 > 0 | 灰度比例设置为 0 |
| 回滚后仍显示新版 | 1. 确认 rollback action 执行成功 | API 调用失败 |
| | 2. 检查 subapp_configs.current_version 值 | 数据库未更新 |

#### 回滚操作具体命令

**场景一：紧急回滚（发现严重 Bug，立即回退到上一稳定版本）**

```bash
# Step 1: 查看当前版本和可用历史版本
curl -s http://api-gateway:3000/api/v1/subapps/{key}/versions \
  -H "Authorization: Bearer $TOKEN" | jq '.[] | {version, status, created_at}'

# 输出示例：
# { "version": "2.1.0", "status": "published", "created_at": "2026-05-23T10:00:00Z" }
# { "version": "2.0.0", "status": "published", "created_at": "2026-05-20T08:00:00Z" }  ← 稳定版本
# { "version": "1.9.0", "status": "rollback",  "created_at": "2026-05-15T06:00:00Z" }

# Step 2: 执行紧急回滚（指定目标版本）
curl -s -X POST http://api-gateway:3000/api/v1/subapps/{key}/release \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "action": "rollback",
    "target_version": "2.0.0",
    "reason": "v2.1.0 页面崩溃率 > 5%，紧急回滚"
  }'

# 预期响应：
# { "success": true, "previous_version": "2.1.0", "current_version": "2.0.0", "rollback_at": "..." }

# Step 3: 验证回滚结果
curl -s http://api-gateway:3000/api/v1/subapps/{key} \
  -H "Authorization: Bearer $TOKEN" | jq '.current_version, .rollback_to'
# 预期：current_version = "2.0.0", rollback_to = "2.0.0"

# Step 4: 检查回滚记录（审计用）
curl -s http://api-gateway:3000/api/v1/subapps/{key}/releases \
  -H "Authorization: Bearer $TOKEN" | jq '.[] | select(.action == "rollback")'
```

**场景二：灰度回滚（灰度发布后指标异常，将灰度比例归零）**

```bash
# Step 1: 查看当前灰度状态
curl -s http://api-gateway:3000/api/v1/subapps/{key}/release/status \
  -H "Authorization: Bearer $TOKEN" | jq '.canary_percent, .canary_version'
# 输出示例：{ "canary_percent": 10, "canary_version": "2.1.0" }

# Step 2: 灰度回滚（流量归零）
curl -s -X POST http://api-gateway:3000/api/v1/subapps/{key}/release \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "action": "rollback_canary",
    "reason": "P99 延迟从 15ms 升至 50ms，灰度回滚"
  }'

# 预期响应：
# { "success": true, "canary_percent": 0, "previous_canary_percent": 10 }

# Step 3: 验证灰度已回滚
curl -s http://api-gateway:3000/api/v1/subapps/{key}/release/status \
  -H "Authorization: Bearer $TOKEN" | jq '.canary_percent'
# 预期：0
```

**场景三：CLI 快捷回滚（运维人员通过 CLI 一键回滚）**

```bash
# 回滚到上一个稳定版本（自动查找最近的非 rollback 版本）
npx orion-cli subapp rollback {key} --auto

# 回滚到指定版本
npx orion-cli subapp rollback {key} --version 2.0.0 --reason "紧急回滚"

# 查看回滚历史
npx orion-cli subapp rollback-history {key}

# 输出示例：
# 2026-05-23 10:30:00 | 2.1.0 → 2.0.0 | by admin | reason: 页面崩溃率 > 5%
# 2026-05-15 06:00:00 | 1.9.1 → 1.9.0 | by ops    | reason: API 不兼容
```

**场景四：数据库直接回滚（紧急情况下 API 不可用，直接修改数据库）**

```bash
# Step 1: 连接数据库
psql -h $PG_HOST -U $PG_USER -d $PG_DB

-- Step 2: 确认目标版本存在
SELECT version, status, created_at FROM subapp_releases
WHERE subapp_key = 'myapp' AND status = 'published'
ORDER BY created_at DESC;

-- Step 3: 更新当前版本
UPDATE subapp_configs
SET current_version = '2.0.0',
    updated_at = NOW(),
    updated_by = 'emergency-rollback'
WHERE subapp_key = 'myapp';

-- Step 4: 记录回滚操作
INSERT INTO subapp_releases (subapp_key, version, status, changelog, created_by)
VALUES ('myapp', '2.0.0', 'rollback', '紧急回滚：v2.1.0 页面崩溃', 'emergency');

-- Step 5: 触发 Gateway 路由同步（更新后立即生效）
-- Gateway 默认 30s 轮询，也可手动触发：
curl -s -X POST http://api-gateway:3000/api/v1/gateway/routes/sync \
  -H "Authorization: Bearer $TOKEN"
```

**回滚耗时对比**：

| 回滚方式 | 操作耗时 | 生效时间 | 适用场景 |
|---------|---------|---------|---------|
| API 回滚 | <1s | 下次页面加载（<3s） | 常规回滚 |
| CLI 回滚 | <2s | 下次页面加载（<3s） | 运维快捷操作 |
| 灰度回滚 | <1s | 立即（流量切换） | 灰度验证失败 |
| 数据库直接回滚 | <5s | 30s（下次 route-sync） | API 不可用的紧急情况 |

```bash
# 1. 查询已注册的事件订阅
curl http://api-gateway:3000/api/v1/subapps/myapp/event-subscriptions

# 2. 测试事件发布-订阅链路
# 发布测试事件
curl -X POST http://api-gateway:3000/api/v1/events/test \
  -H "Content-Type: application/json" \
  -d '{"source":"myapp","event":"test.ping","payload":{}}'

# 查看事件日志
curl http://api-gateway:3000/api/v1/events/log?source=myapp&limit=10

# 3. 查询死信队列
curl http://api-gateway:3000/api/v1/events/dlq?source=myapp
```

#### 不生效怎么查

| 现象 | 排查步骤 | 可能原因 |
|------|---------|---------|
| 订阅了但收不到事件 | 1. 检查 Redis Pub/Sub 连接 `redis-cli SUBSCRIBE orion:events:*` | Redis 连接断开 |
| | 2. 确认 channel 名称匹配 | source/event 名称不一致 |
| | 3. 检查 handler 是否抛出异常被静默吞掉 | handler 内部错误 |
| 事件发布后无响应 | 1. `redis-cli PUBLISH orion:events:myapp:test.ping '{}'` 手动测试 | Redis Pub/Sub 正常但订阅者未收到 |
| | 2. 检查 event_log 表是否有记录 | 事件未持久化 |
| 死信队列堆积 | 1. 查询 DLQ 查看失败原因 | handler 持续抛异常 |
| | 2. 重放死信事件 `POST /events/dlq/{id}/replay` | 修复后重新处理 |

### 14.6 灰度发布操作

#### 在哪配

同版本发布 API，使用 `strategy: "canary"`：

```bash
# 创建灰度发布
POST /api/v1/subapps/{key}/release
{
  "action": "publish",
  "version": "2.0.0",
  "strategy": "canary",
  "canary_percent": 10
}

# 调整灰度比例
PUT /api/v1/subapps/{key}/releases/{release_id}
{
  "canary_percent": 30
}

# 灰度回滚（紧急）
POST /api/v1/subapps/{key}/release
{
  "action": "rollback",
  "version": "1.0.0"
}
```

#### 怎么验证

```bash
# 1. 查询灰度状态
curl http://api-gateway:3000/api/v1/subapps/myapp/releases/latest
# 返回：strategy: "canary", canary_percent: 10, status: "rolling"

# 2. 验证灰度用户加载新版本
# 灰度用户访问：检查 remoteEntry.js URL 是否指向新版本
# 非灰度用户访问：检查是否仍加载旧版本

# 3. 观察错误率
curl http://api-gateway:3000/api/v1/subapps/myapp/metrics
# 返回：error_rate, p99_latency 等指标
```

#### 不生效怎么查

| 现象 | 排查步骤 | 可能原因 |
|------|---------|---------|
| 灰度比例已调整但用户未分流 | 1. 确认 canary_percent > 0 | 比例为 0 |
| | 2. 检查前端 VersionAwareLoader 是否读取到最新 release | 前端缓存未刷新 |
| | 3. 清除浏览器缓存后重试 | localStorage 缓存旧配置 |
| 灰度错误率飙升 | 1. 查看 canary 日志 `grep "canary" gateway.log` | 新版本有 Bug |
| | 2. 立即回滚 `canary_percent: 0` | 紧急止血 |
| | 3. 分析错误类型（功能错误/性能下降） | 决定修复还是回滚 |

### 14.7 健康检查配置

#### 在哪配

**子应用后端**（必须实现 `/healthz` 端点）：

```typescript
// myapp-service/src/api/health-routes.ts
app.get('/healthz', async (request, reply) => {
  // 检查数据库
  try { await db.query('SELECT 1'); }
  catch { return reply.status(503).send({ status: 'unhealthy', reason: 'db_error' }); }

  // 检查 Redis
  try { await redis.ping(); }
  catch { return reply.status(503).send({ status: 'unhealthy', reason: 'redis_error' }); }

  reply.send({ status: 'healthy' });
});
```

**Gateway 探活配置**（`gateway-route-sync.ts`，默认 30s 间隔）：

```typescript
const HEALTH_CHECK_INTERVAL = 30_000;  // 可调整
const HEALTH_CHECK_TIMEOUT = 5_000;    // 超时时间
const HEALTH_CHECK_FAILURES = 3;       // 连续失败次数阈值
```

#### 怎么验证

```bash
# 1. 直接测试健康检查端点
curl http://myapp-service:3040/healthz
# 预期：{"status": "healthy"}

# 2. 查看 Gateway 探活日志
tail -f /var/log/gateway/health-check.log | grep myapp

# 3. 查询子应用健康状态
curl http://api-gateway:3000/api/v1/subapps/myapp | jq '.health_status, .last_health_check'
```

#### 不生效怎么查

| 现象 | 排查步骤 | 可能原因 |
|------|---------|---------|
| 探活失败但服务正常 | 1. `curl service:port/healthz` 确认可达 | 网络不通或防火墙拦截 |
| | 2. 检查 `HEALTH_CHECK_TIMEOUT` 是否过短 | 服务响应慢超时 |
| | 3. 检查 healthz 返回格式是否匹配 | 返回格式不是 `{"status":"healthy"}` |
| 服务已挂但未移除路由 | 1. 检查连续失败次数是否达到阈值 | 未达到 HEALTH_CHECK_FAILURES |
| | 2. 检查 Gateway 路由同步是否正常运行 | route-sync 进程异常 |
| 频繁探活/移除路由 | 1. 降低 `HEALTH_CHECK_FAILURES` 阈值 | 阈值过低误判 |
| | 2. 增加探活间隔减少探活频率 | 探活过于频繁影响性能 |

### 14.8 端口分配申请

#### 在哪配

**端口分配规则**（v1.7 修订，对齐实际代码）：

| 范围 | 用途 | 示例 | 说明 |
|------|------|------|------|
| 3000-3009 | 基础设施服务 | Gateway:3000, Platform:3001 | 核心服务，优先分配 |
| 3010-3019 | 前端开发服务器 | orion-frontend dev:3010, knowledge-app:3010 | 主前端 + 子应用管理端 |
| 3020-3029 | 独立微服务 | orion-ai-service:3020, knowledge-admin:3020 | 独立部署的微服务 |
| **3030-3039** | **子应用前端开发服务器** | orion-dba dev:3030 | **新子应用前端在此范围申请** |
| **3040-3049** | **子应用后端服务** | myapp-api:3040 | **新子应用后端在此范围申请** |
| 5170-5179 | Vite 默认端口（历史遗留） | knowledge dev:5173 | 仅历史子应用，新应用不推荐 |
| 8090-8099 | 独立后端服务 | knowledge-api:8090 | 独立微服务的后端 API |
| 3050-3099 | 预留 | 未来扩展 | 按需分配 |

> **注意**：历史子应用 orion-knowledge 使用 5173（Vite 默认）、orion-visor 使用 3003（基础设施范围边缘）属于历史遗留。**新增子应用必须使用 3030-3039（前端）和 3040-3049（后端）**。

**申请流程**：

```bash
# 方式一：注册子应用时指定
POST /api/v1/subapps
{
  "key": "myapp",
  "entry_dev": "http://localhost:3033/assets/remoteEntry.js",     # 前端 3030-3039
  "backend_service_url": "http://localhost:3042",                  # 后端 3040-3049
  ...
}

# 方式二：通过 CLI 查询可用端口
npx orion-cli port check --range 3030-3039  # 查询前端可用端口
npx orion-cli port check --range 3040-3049  # 查询后端可用端口
# 返回：3033 (空闲), 3042 (空闲), 3030 (已占用 by dba)

# 方式三：管理页面查看端口占用
访问 /console/subapps → 查看"后端地址"列
```

#### 怎么验证

```bash
# 1. 检查端口是否被占用
lsof -i :3040
# 或
netstat -tlnp | grep 3040

# 2. 测试端口可达性
curl http://localhost:3040/healthz
# 预期：连接成功并返回健康状态

# 3. 确认 Gateway 代理配置
curl http://api-gateway:3000/api/v1/subapps/myapp | jq '.backend_service_url'
# 预期：返回配置的 URL
```

#### 不生效怎么查

| 现象 | 排查步骤 | 可能原因 |
|------|---------|---------|
| 端口已被占用 | 1. `lsof -i :3040` 查看占用进程 | 其他服务占用了端口 |
| | 2. 更换端口并更新 `backend_service_url` | 选择 3040-3049 范围内空闲端口 |
| 端口不可达 | 1. 确认服务已启动并监听 | 服务未启动或监听地址错误 |
| | 2. 检查防火墙规则 | 端口被 iptables/安全组拦截 |
| | 3. `curl localhost:port/healthz` 本地测试 | 服务正常但外部不可达 |
| 端口冲突 | 1. 检查 subapp_configs 中是否有其他服务使用同端口 | 配置冲突 |
| | 2. 使用 CLI `port check` 确认可用端口 | 未遵循端口分配规则（前端应 3030-3039，后端应 3040-3049） |

### 14.10 子应用市场权限模型（RBAC）

子应用市场采用基于角色的访问控制（RBAC），覆盖子应用的全生命周期操作。

**角色定义**：

| 角色 | 说明 | 典型用户 |
|------|------|---------|
| `platform_admin` | 平台管理员，拥有全部权限 | 运维团队 |
| `subapp_owner` | 子应用负责人，管理自己负责的子应用 | 开发团队负责人 |
| `subapp_developer` | 子应用开发者，可开发和测试 | 开发工程师 |
| `subapp_viewer` | 子应用查看者，只读访问 | 产品经理/测试 |
| `tenant_admin` | 租户管理员，管理租户内的子应用访问 | 租户管理员 |

**权限矩阵**：

| 操作 | platform_admin | subapp_owner | subapp_developer | subapp_viewer | tenant_admin |
|------|:--------------:|:------------:|:----------------:|:-------------:|:------------:|
| 查看子应用列表 | ✅ | ✅ | ✅ | ✅ | ✅ |
| 查看子应用详情 | ✅ | ✅ | ✅ | ✅ | ✅ |
| 创建子应用 | ✅ | ✅ | ❌ | ❌ | ❌ |
| 编辑子应用配置 | ✅ | ✅ | ❌ | ❌ | ❌ |
| 删除子应用 | ✅ | ✅（需确认）| ❌ | ❌ | ❌ |
| 禁用/启用子应用 | ✅ | ✅ | ❌ | ❌ | ❌ |
| 构建子应用版本 | ✅ | ✅ | ✅ | ❌ | ❌ |
| 发布子应用版本 | ✅ | ✅ | ❌ | ❌ | ❌ |
| 回滚子应用版本 | ✅ | ✅ | ❌ | ❌ | ❌ |
| 配置灰度发布 | ✅ | ✅ | ❌ | ❌ | ❌ |
| 查看健康状态 | ✅ | ✅ | ✅ | ✅ | ✅ |
| 查看操作日志 | ✅ | ✅ | ✅ | ✅ | ✅ |
| 管理协作者 | ✅ | ✅ | ❌ | ❌ | ❌ |
| 配置 API ACL 规则 | ✅ | ✅ | ❌ | ❌ | ❌ |
| 配置限流规则 | ✅ | ✅ | ❌ | ❌ | ❌ |

**数据隔离**：

| 维度 | 隔离方式 | 说明 |
|------|---------|------|
| 租户级隔离 | `WHERE tenant_id = ?` | 所有查询必须携带租户 ID |
| 子应用级隔离 | `WHERE subapp_key IN (用户关联的子应用)` | 非平台管理员只能看到授权的子应用 |
| 操作审计 | `INSERT INTO audit_logs` | 所有写操作记录操作人、时间、IP、变更内容 |

**API 鉴权中间件**：

```typescript
// Gateway ACL 中间件：检查用户是否有子应用操作权限
async function checkSubAppPermission(
  request: FastifyRequest,
  requiredRole: string
): Promise<boolean> {
  const userId = request.headers['x-user-id'];
  const tenantId = request.headers['x-tenant-id'];
  const subappKey = request.params.key;

  // 平台管理员跳过检查
  if (await isPlatformAdmin(userId)) return true;

  // 检查用户是否有该子应用的指定角色
  const hasPermission = await db.query(
    `SELECT 1 FROM subapp_members
     WHERE subapp_key = $1 AND user_id = $2 AND tenant_id = $3
     AND role IN (SELECT role FROM role_hierarchy WHERE level >= (SELECT level FROM role_hierarchy WHERE role = $4))`,
    [subappKey, userId, tenantId, requiredRole]
  );

  return hasPermission.rowCount > 0;
}
```

### 14.11 操作链路完整性检查清单

每次新增功能或修改配置时，按此清单检查操作链路是否完整：

| 检查项 | 检查方法 | 通过标准 |
|--------|---------|---------|
| 操作入口明确 | 文档是否说明在哪配（页面/API/CLI/SQL） | 至少提供一种方式 |
| 存储位置清晰 | 是否说明配置存在哪（表名/字段/Redis key） | 能定位到具体存储位置 |
| 消费者明确 | 是否说明谁在用这个配置 | 能列出所有消费者 |
| 生效方式明确 | 是否说明配置变更后多久生效、怎么生效 | 有明确的时间或触发条件 |
| 验证方法具体 | 是否提供运维可用的验证命令或操作步骤 | 能执行并看到预期结果 |
| 排错指南完整 | 是否提供"不生效时怎么查"的排查步骤 | 至少覆盖 2 种常见故障场景 |
