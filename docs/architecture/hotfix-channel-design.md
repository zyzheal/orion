## 执行摘要 (Executive Summary)

### 设计目标

本设计文档详细描述 Orion 平台 Hotfix 通道的完整架构与实施方案。Hotfix 通道是为紧急修复场景设计的特殊发布流程，旨在平衡"快速响应生产问题"与"保障发布质量与安全"之间的矛盾。

### 核心价值主张

| 维度 | 标准发布流程 | Hotfix 通道 | 改善幅度 |
|------|-------------|------------|---------|
| **触发到部署时长** | 4-24 小时 | 15-60 分钟 | 90% |
| **审批等待时间** | 2-8 小时 | 5-30 分钟 | 85% |
| **测试覆盖范围** | 100% 全量测试 | 30% 核心测试 | 针对性裁剪 |
| **审批人数要求** | 3-5 人 | 最少 2 人 | 简化但不缺失 |
| **回滚决策时间** | 30-60 分钟 | 5-15 分钟 | 75% |

### 适用场景

Hotfix 通道仅适用于以下紧急场景：

| 场景类型 | 定义 | 示例 | 优先级 |
|---------|------|------|--------|
| **P0 故障** | 生产服务完全不可用或核心功能失效 | 支付失败、登录崩溃 | P0 |
| **安全漏洞** | 已披露或正在被利用的安全漏洞 | CVE 高危漏洞、数据泄露风险 | P0 |
| **数据修复** | 数据一致性被破坏，需要紧急修复 | 账务数据错误、配置丢失 | P0 |
| **合规要求** | 监管/法律要求的紧急变更 | 数据隐私合规修复 | P1 |

### 设计原则

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│                          Hotfix Channel Design Principles                        │
├─────────────────────────────────────────────────────────────────────────────────┤
│                                                                                 │
│  1. SPEED (速度优先)                                                             │
│     └── 审批简化但不缺失，测试裁剪但不跳过                                       │
│                                                                                 │
│  2. SAFETY (安全兜底)                                                            │
```

### 1.2 组件职责详解

| 组件 | 职责 | 输入 | 输出 | SLA |
|------|------|------|------|-----|
| **触发决策引擎** | 验证 Hotfix 触发条件，决策是否启用 Hotfix 通道 | 告警/报告/请求 | Hotfix 工单、优先级 | 99.9% |
| **分支管理器** | 从生产标签创建 Hotfix 分支，管理合并策略 | Hotfix 工单 | Hotfix 分支、MR | 99.9% |
| **审批控制器** | 执行简化审批流程，管理审批人路由 | MR、审批配置 | 审批结果 | 99.5% |
| **快速测试套件** | 执行核心测试，跳过非关键测试 | 代码变更 | 测试报告 | 99% |
| **发布执行器** | 执行灰度发布，控制发布比例 | 审批通过、测试通过 | 部署状态 | 99.9% |
| **监控增强器** | 加强监控指标采集频率，设置专项告警 | 部署状态 | 监控指标、告警 | 99.99% |
| **回滚控制器** | 监控发布健康度，执行自动/手动回滚 | 监控指标、人工指令 | 回滚状态 | 99.9% |
| **审计日志器** | 记录全链路操作日志，生成审计报告 | 所有组件事件 | 审计日志 | 99.99% |
| **复盘生成器** | 基于审计日志生成故障报告和修复总结 | 审计日志、指标数据 | 复盘报告 | 99% |

### 2.2 触发条件详细定义

#### 2.2.1 P0 故障 (P0 Outage)

| 条件 | 定义 | 检测方式 | 自动触发 |
|------|------|---------|---------|
| **服务完全不可用** | 核心服务 HTTP 错误率>50% 持续 5 分钟 | 监控告警 | ✅ |
| **核心功能失效** | 关键业务路径成功率<80% 持续 10 分钟 | 合成监控 | ✅ |
| **大规模用户影响** | 受影响用户数>10000 或>30% 用户 | 用户反馈聚合 | ❌ |
| **数据丢失/损坏** | 生产数据不一致或丢失 | 数据完整性检查 | ❌ |
| **性能严重下降** | P99 延迟>10s 持续 15 分钟 | APM 监控 | ✅ |

#### 2.2.2 安全漏洞 (Security Vulnerability)

| 条件 | 定义 | 检测方式 | 自动触发 |
|------|------|---------|---------|
| **CVE 高危漏洞** | CVSS 评分≥7.0 的已披露漏洞 | 安全扫描/外部通知 | ❌ |
| **0day 漏洞利用** | 正在被主动利用的漏洞 | 安全事件监控 | ❌ |
| **数据泄露风险** | 敏感数据暴露风险 | 审计日志分析 | ❌ |
| **认证/授权绕过** | 权限校验漏洞 | 安全测试/报告 | ❌ |
| **依赖供应链攻击** | 二方/三方库被植入恶意代码 | 依赖扫描/外部通知 | ❌ |

#### 2.2.4 合规要求 (Compliance Requirement)

| 条件 | 定义 | 检测方式 | 自动触发 |
|------|------|---------|---------|
| **监管要求变更** | 监管机构发布新合规要求 | 合规团队通知 | ❌ |
| **法律合规修复** | 法律法规变更需要的修改 | 法务团队通知 | ❌ |

### 3.5 冲突解决策略

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│                           Merge Conflict Resolution                              │
│                           合并冲突解决策略                                       │
└─────────────────────────────────────────────────────────────────────────────────┘

场景 1: Hotfix → main (通常无冲突)
┌─────────────────────────────────────────────────────────────────┐
│  原因：Hotfix 从 main 的最新标签创建，main 在此期间通常冻结        │
│  处理：如有冲突，Hotfix 优先级最高，main 接受 Hotfix 变更           │
└─────────────────────────────────────────────────────────────────┘

场景 2: Hotfix → develop (可能有冲突)
┌─────────────────────────────────────────────────────────────────┐
│  原因：develop 在此期间可能有新提交                              │
│  处理流程:                                                       │
│                                                                  │
│  1. fetch develop 最新代码                                       │
│     $ git fetch origin develop                                   │
│                                                                  │
│  2. 在 Hotfix 分支上合并 develop                                  │
│     $ git checkout hotfix/ISSUE-1234                             │
│     $ git merge origin/develop                                   │
│                                                                  │
│  3. 解决冲突 (优先保留 Hotfix 修复)                                │
│     - 功能代码：保留 Hotfix 修复                                   │
│     - 新功能代码：保留 develop 变更                                │
│     - 配置文件：人工评审决定                                      │
│                                                                  │
│  4. 测试验证                                                     │
│     $ git push origin hotfix/ISSUE-1234                          │
│     → 触发 CI 验证                                                 │
│                                                                  │
│  5. 创建 MR 合并到 develop                                         │
└─────────────────────────────────────────────────────────────────┘

场景 3: 多个 Hotfix 并行 (罕见)
┌─────────────────────────────────────────────────────────────────┐
│  处理流程:                                                       │
│                                                                  │
│  1. 识别冲突 Hotfix                                              │
│     $ git log --oneline hotfix/*                                 │
│                                                                  │
│  2. 确定优先级                                                   │
│     P0 故障 > 安全漏洞 > 数据修复 > 合规要求                        │
│                                                                  │
│  3. 串行合并按优先级                                              │
│     高优先级 Hotfix 先合并                                         │
│     低优先级 Hotfix 重新基于新基线                                  │
│                                                                  │
│  4. 通知相关开发者协调                                            │
└─────────────────────────────────────────────────────────────────┘
```

### 3.6 分支保护规则

| 规则 | 标准分支 | Hotfix 分支 | 说明 |
|------|---------|-----------|------|
| **强制 PR/MR** | ✅ | ✅ | 禁止直接 push |
| **最少审批人** | 2 人 | 2 人 (紧急审批人) | Hotfix 可快速审批 |
| **CI 必须通过** | ✅ | ✅ (核心测试) | Hotfix 可跳过部分测试 |
| **强制代码审查** | ✅ | ⚠️ (简化) | 至少 1 人详细审查 |
| **签名提交** | ✅ | ❌ (可跳过) | 紧急场景可豁免 |
| **最新分支检查** | ✅ | ❌ (可跳过) | 允许基于标签创建 |

```yaml
# Hotfix 权限配置示例
hotfix_permissions:
  roles:
    hotfix_creator:
      display_name: Hotfix 创建人
      permissions:
        - hotfix:create
        - hotfix:submit
        - code:commit
        - hotfix:view
      members:
        - group: engineering
        - exclude: [intern, contractor]  # 实习生/外包除外
    
    hotfix_approver:
      display_name: Hotfix 审批人
      permissions:
        - hotfix:approve
        - hotfix:view
        - mr:review
      members:
        - group: tech-leads
        - group: architects
        - users: [approved-senior-engineers]  # 特批高级工程师
      requirements:
        - min_experience_years: 3
        - completed_training: true
```
