## 执行摘要 (Executive Summary)

本设计文档详细描述 Orion 平台 API 网关的增强方案。当前 API 网关仅具备基础的路由转发功能，缺乏限流、熔断、版本化管理等企业级能力，无法应对高并发场景、下游服务故障、API 演进等生产环境挑战。

### 当前问题分析

| 问题类别 | 当前状态 | 风险等级 | 影响范围 |
|---------|---------|---------|---------|
| 限流能力 | 无 | 高 | 易受 DDoS 攻击、雪崩效应 |
| 熔断保护 | 无 | 高 | 下游故障导致级联失败 |
| API 版本化 | 无规范 | 中 | 破坏性变更影响所有调用方 |
| 认证鉴权 | 基础 JWT 验证 | 中 | 细粒度权限控制缺失 |
| 监控指标 | 仅基础日志 | 中 | 故障排查困难、无容量规划依据 |

### 增强方案总览

| 增强领域 | 核心能力 | 预期收益 |
|---------|---------|---------|
| **限流策略** | 全局限流 + 租户限流 + 用户限流 | 防止雪崩、公平资源分配 |
| **熔断器设计** | 失败率阈值 + 慢调用比例 + 半开恢复 | 故障隔离、快速失败 |
| **API 版本化** | URL 路径 + Header + 内容协商 | 向后兼容、平滑演进 |
| **版本演进** | v1/v2 并行 + 废弃时间表 | 降低迁移成本 |
| **请求路由** | 动态路由 + 负载均衡 | 高可用、低延迟 |
| **认证鉴权** | JWT 验证 + RBAC/ABAC | 细粒度访问控制 |
| **监控指标** | QPS + 延迟 + 错误率 + 限流次数 | 可观测性、容量规划 |

### 预期收益量化

| 指标 | 当前 | 增强后目标 | 改善幅度 |
|------|------|-----------|---------|
| 最大承载 QPS | 500 | 5000 | 10x |
| 故障恢复时间 (MTTR) | 30 分钟 | 5 分钟 | 83% |
| API 破坏性变更 | 月均 3 次 | 0 次 | 100% |
| 限流触发响应时间 | N/A | <10ms | - |
| 熔断器自动恢复率 | N/A | >90% | - |
| 监控指标覆盖率 | 20% | 95% | 375% |

## 一、API Gateway 架构概览 (Architecture Overview)

### 1.1 网关定位与职责

**服务名称**: `orion-api-gateway`  
**端口**: 8080  
**定位**: Orion 平台的统一入口，负责请求路由、流量控制、安全防护、协议转换。

### 2.2 限流算法详解

#### 2.2.1 令牌桶算法 (Token Bucket) - 全局限流

**适用场景**: 全局限流、突发流量平滑  
**核心特点**: 允许适度突发、稳定输出速率

```
class TokenBucket:
    def __init__(self, capacity, refill_rate):
        self.capacity = capacity           # 桶容量（最大令牌数）
        self.refill_rate = refill_rate     # 补充速率（令牌/秒）
        self.tokens = capacity             # 当前令牌数
        self.last_refill = now()           # 上次补充时间
    
    def try_acquire(self, tokens=1):
        self._refill()                     # 先补充令牌
        
        if self.tokens >= tokens:
            self.tokens -= tokens          # 消费令牌
            return True, None              # 允许通过
        else:
            wait_time = (tokens - self.tokens) / self.refill_rate
            return False, wait_time        # 拒绝，返回建议等待时间
    
    def _refill(self):
        elapsed = now() - self.last_refill
        new_tokens = elapsed * self.refill_rate
        self.tokens = min(self.capacity, self.tokens + new_tokens)
        self.last_refill = now()

┌─────────────────────────────────────────────────────────────────────────────────┐
│                        Token Bucket Configuration                                │
└─────────────────────────────────────────────────────────────────────────────────┘

# 全局限流配置示例
global_rate_limit:
  algorithm: token_bucket
  capacity: 10000           # 桶容量：10000 令牌
  refill_rate: 5000         # 补充速率：5000 令牌/秒
  burst_allowance: 2000     # 允许突发：2000 额外请求
  
# 指标暴露
metrics:
  - bucket_tokens_current   # 当前令牌数
  - bucket_refill_events    # 补充事件次数
  - requests_allowed        # 放行请求数
  - requests_rejected       # 拒绝请求数
```

```
# Redis Sorted Set 实现 (ZSET)
# Key: rate_limit:tenant:{tenant_id}

# Member: 请求 ID (唯一标识)

# Lua 脚本保证原子性

local now = tonumber(ARGV[1])           # 当前时间戳 (ms)

    -- 4. 记录新请求

    redis.call('EXPIRE', key, window / 1000 + 1)  -- 设置过期时间
    return 1  -- ALLOW
else
    return 0  -- REJECT
end
```

#### 2.2.3 滑动窗口计数器算法 (Sliding Window Counter) - 用户限流

**适用场景**: 用户限流、内存敏感场景  
**核心特点**: 内存效率高、存在边界问题但可接受  

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│              Sliding Window Counter Algorithm Flow                               │
└─────────────────────────────────────────────────────────────────────────────────┘

时间轴：固定窗口划分 (每窗口 1 秒)
        |────Window N-1────|────Window N────|────Window N+1────|
        t-1.0              t-0.0            t+0.0              t+1.0
        
用户限流计算 (当前时间：t+0.6):
┌─────────────────────────────────────────────────────────────────────────────────┐
│                                                                                  │
│  Window N-1 (t-1.0 ~ t-0.0): [████████░░░░] = 80 请求 (权重：0.4)                │
│  Window N   (t-0.0 ~ t+0.6): [████████████████] = 150 请求 (权重：1.0)           │
│                                                                                  │
│  加权计数 = (80 × 0.4) + 150 = 32 + 150 = 182 请求                               │
│  Limit = 100 QPS                                                                 │
│  Result: 182 > 100 → REJECT                                                      │
│                                                                                  │
└─────────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────────┐
│              Sliding Window Counter Implementation                               │
└─────────────────────────────────────────────────────────────────────────────────┘

# Redis 实现 (两个计数器)
# Key 格式：rate_limit:user:{user_id}:{window_index}

class SlidingWindowCounter:
    def __init__(self, redis_client, key_prefix, window_size_ms, limit):
        self.redis = redis_client
        self.key_prefix = key_prefix
        self.window_size_ms = window_size_ms
        self.limit = limit
    
    def try_acquire(self, user_id):
        now_ms = current_timestamp_ms()
        current_window = now_ms // self.window_size_ms
        prev_window = current_window - 1
        
        # 获取当前窗口和上一个窗口的计数
        current_key = f"{self.key_prefix}:{user_id}:{current_window}"
        prev_key = f"{self.key_prefix}:{user_id}:{prev_window}"
        
        current_count = self.redis.get(current_key) or 0
        prev_count = self.redis.get(prev_key) or 0
        
        # 计算窗口内经过的时间比例
        elapsed_in_window = now_ms % self.window_size_ms
        prev_window_weight = 1.0 - (elapsed_in_window / self.window_size_ms)
        
        # 加权计算
        weighted_count = current_count + (prev_count * prev_window_weight)
        
        if weighted_count < self.limit:
            # 管道操作：原子递增 + 设置过期时间
            pipe = self.redis.pipeline()
            pipe.incr(current_key)
            pipe.pexpire(current_key, self.window_size_ms * 2)
            pipe.execute()
            return True, int(self.limit - weighted_count)  # ALLOW
        
        return False, int(weighted_count - self.limit)  # REJECT

┌─────────────────────────────────────────────────────────────────────────────────┐
│                   Sliding Window Counter Configuration                           │
└─────────────────────────────────────────────────────────────────────────────────┘

# 用户限流配置

    limit: 500 QPS
```

## 三、熔断器设计 (Circuit Breaker Design)

### 3.1 熔断器状态机

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│                         Circuit Breaker State Machine                            │
└─────────────────────────────────────────────────────────────────────────────────┘

                         ┌─────────────────┐
                         │                 │
                         │    CLOSED       │◀───────┐
                         │    (正常)        │        │
                         │                 │        │
                         └────────┬────────┘        │
                                  │                 │
                                  │ 失败率 > 阈值     │ 半开状态探测成功
                                  │ OR              │
                                  │ 慢调用 > 阈值     │
                                  ▼                 │
                         ┌─────────────────┐        │
                         │                 │        │
                         │    OPEN         │        │
                         │    (熔断)        │        │
                         │                 │        │
                         └────────┬────────┘        │
                                  │                 │
                                  │ 休眠时间到期      │
                                  ▼                 │
                         ┌─────────────────┐        │
                         │                 │        │
                         │    HALF_OPEN    │────────┘
                         │    (半开)        │
                         │                 │
                         └────────┬────────┘
                                  │
                                  │ 失败率 > 0
                                  ▼
                         ┌─────────────────┐
                         │     OPEN        │
                         │    (重新熔断)     │
                         └─────────────────┘

┌─────────────────────────────────────────────────────────────────────────────────┐
│                         State Transition Details                                 │
└─────────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────────┐
│ CLOSED State (闭合状态 - 正常)                                                   │
├─────────────────────────────────────────────────────────────────────────────────┤
│ • 描述：系统正常运行，请求正常转发                                                 │
│ • 监控指标：                                                                     │
│   - 失败率 (Failure Rate): 失败请求数 / 总请求数                                    │
│   - 慢调用率 (Slow Call Rate): 慢调用数 / 总请求数                                  │
│   - 请求总量：滑动窗口内的总请求数                                                 │
│ • 状态转换条件：                                                                 │
│   - IF 失败率 >= failure_rate_threshold (50%) → 转 OPEN                          │
│   - IF 慢调用率 >= slow_call_rate_threshold (80%) → 转 OPEN                      │
│   - IF 请求数 < minimum_number_of_calls (10) → 保持 CLOSED                        │
└─────────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────────┐
│ OPEN State (断开状态 - 熔断)                                                     │
├─────────────────────────────────────────────────────────────────────────────────┤
│ • 描述：系统已熔断，所有请求快速失败，不再调用后端服务                                │
│ • 行为：                                                                         │
│   - 立即返回 HTTP 503 Service Unavailable                                        │
│   - 记录熔断事件日志                                                              │
│   - 启动休眠计时器                                                                │
│ • 状态转换条件：                                                                 │
│   - AFTER sleep_window_in_seconds (30s) → 转 HALF_OPEN                           │
└─────────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────────┐
│ HALF_OPEN State (半开状态 - 探测恢复)                                             │
├─────────────────────────────────────────────────────────────────────────────────┤
│ • 描述：允许有限请求通过，探测后端服务是否恢复                                      │
│ • 行为：                                                                         │
│   - 允许 permitted_calls_in_half_open (10) 个请求通过                            │
│   - 监控这些请求的成功/失败情况                                                    │
│ • 状态转换条件：                                                                 │
│   - IF 所有探测请求成功 → 转 CLOSED (恢复)                                        │
│   - IF 任一探测请求失败 → 转 OPEN (重新熔断)                                       │
└─────────────────────────────────────────────────────────────────────────────────┘
```

### 3.2 熔断器核心参数

#### 3.2.1 参数配置

```yaml
# circuit-breaker-config.yaml

    # 失败率阈值 (0.0 - 1.0)

    # 熔断后配置
    open_state:
      sleep_window: 30s                 # 熔断持续时间
    
    # 半开状态配置
    half_open_state:
      permitted_calls: 10               # 允许的探测请求数
```

#### 3.2.2 熔断器实现逻辑

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│                      Circuit Breaker Implementation                              │
└─────────────────────────────────────────────────────────────────────────────────┘

class CircuitBreaker:
    def __init__(self, config):
        self.config = config
        self.state = CircuitState.CLOSED
        self.failure_count = 0
        self.success_count = 0
        self.total_count = 0
        self.slow_call_count = 0
        self.last_failure_time = None
        self.state_change_time = now()
        self.permitted_calls_remaining = 0
    
    def can_execute(self):
        """检查是否允许执行请求"""
        if self.state == CircuitState.CLOSED:
            return True
        
        if self.state == CircuitState.OPEN:
            if now() - self.state_change_time >= self.config.sleep_window:
                self._transition_to_half_open()
                return True
            return False
        
        if self.state == CircuitState.HALF_OPEN:
            if self.permitted_calls_remaining > 0:
                self.permitted_calls_remaining -= 1
                return True
            return False
    
    def record_success(self, response_time_ms):
        """记录成功响应"""
        self.total_count += 1
        self.success_count += 1
        
        if self.state == CircuitState.HALF_OPEN:
            self.success_count += 1
            if self.success_count >= self.config.success_threshold:
                self._transition_to_closed()
    
    def record_failure(self):
        """记录失败响应"""
        self.total_count += 1
        self.failure_count += 1
        self.last_failure_time = now()
        
        if self.state == CircuitState.HALF_OPEN:
            # 半开状态下任何失败都会重新熔断
            self._transition_to_open()
            return
        
        self._check_thresholds()
    
    def record_slow_call(self, response_time_ms):
        """记录慢调用"""
        self.total_count += 1
        self.slow_call_count += 1
        self._check_thresholds()
    
    def _check_thresholds(self):
        """检查是否达到熔断阈值"""
        if self.total_count < self.config.min_calls:
            return
        
        failure_rate = self.failure_count / self.total_count
        slow_call_rate = self.slow_call_count / self.total_count
        
        if failure_rate >= self.config.failure_rate_threshold:
            self._transition_to_open()
            return
        
        if slow_call_rate >= self.config.slow_call_rate_threshold:
            self._transition_to_open()
    
    def _transition_to_open(self):
        """转换到 OPEN 状态"""
        self.state = CircuitState.OPEN
        self.state_change_time = now()
        log_circuit_open_event()
        emit_metric("circuit_breaker_open", service=self.service_name)
    
    def _transition_to_half_open(self):
        """转换到 HALF_OPEN 状态"""
        self.state = CircuitState.HALF_OPEN
        self.state_change_time = now()
        self.permitted_calls_remaining = self.config.permitted_calls
        self.success_count = 0
        log_circuit_half_open_event()
        emit_metric("circuit_breaker_half_open", service=self.service_name)
    
    def _transition_to_closed(self):
        """转换到 CLOSED 状态"""
        self.state = CircuitState.CLOSED
        self.state_change_time = now()
        self.failure_count = 0
        self.slow_call_count = 0
        self.total_count = 0
        log_circuit_closed_event()
        emit_metric("circuit_breaker_closed", service=self.service_name)
```

```
│  Cons:                                                                          │

│  Use Case: 绝大多数公开 API                                                      │
└─────────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────────┐

│  Cons:                                                                          │

│    - 需要文档说明                                                                │

│  Cons:                                                                          │
│    - 实现复杂度高                                                                │
│    - 调试不便                                                                    │
```

```
支持的负载均衡算法:

┌─────────────────────────────────────────────────────────────────────────────────┐
│  Algorithm 1: Round Robin (轮询) - 默认                                          │
├─────────────────────────────────────────────────────────────────────────────────┤
│  Description: 按顺序将请求分发到每个实例                                           │
│  Use Case: 实例性能相近、请求处理时间相近                                         │
│  Pros: 简单、公平                                                                 │
│  Cons: 不考虑实例负载差异                                                         │
│                                                                                  │
│  ┌─────────────┐    ┌─────────────┐    ┌─────────────┐    ┌─────────────┐       │

│  │  Request 2  │───▶│ Instance B  │    │  Request 5  │───▶│ Instance B  │       │
│  │  Request 3  │───▶│ Instance C  │    │  Request 6  │───▶│ Instance C  │       │
│  └─────────────┘    └─────────────┘    └─────────────┘    └─────────────┘       │
└─────────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────────┐
│  Algorithm 2: Least Connections (最少连接)                                       │
├─────────────────────────────────────────────────────────────────────────────────┤
│  Description: 将请求分发到当前连接数最少的实例                                      │
│  Use Case: 请求处理时间差异大、长连接场景                                         │
│  Pros: 自动适应实例负载                                                           │
│  Cons: 需要维护连接数状态                                                         │

│  Instance A: 15 connections                                                       │
│  Instance B: 3 connections  ◀─── Next request goes here                         │
│  Instance C: 28 connections                                                       │
└─────────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────────┐
│  Algorithm 3: Weighted Round Robin (加权轮询)                                    │
├─────────────────────────────────────────────────────────────────────────────────┤
│  Description: 根据实例权重按比例分发                                               │
│  Use Case: 实例性能不同、混合部署场景                                             │
│  Pros: 可按能力分配流量                                                           │
│  Cons: 权重需要手动配置                                                           │
│                                                                                  │
│  Instance A (Weight: 5): ████████ 40% of traffic                                 │
│  Instance B (Weight: 3): █████ 30% of traffic                                    │
│  Instance C (Weight: 2): ████ 20% of traffic                                     │
│  Instance D (Weight: 2): ████ 10% of traffic                                     │
└─────────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────────┐
│  Algorithm 4: IP Hash (IP 哈希)                                                   │
├─────────────────────────────────────────────────────────────────────────────────┤
│  Description: 根据客户端 IP 哈希值选择实例                                          │
│  Use Case: 需要会话保持、客户端固定路由                                           │
│  Pros: 同一客户端总是路由到同一实例                                                │
│  Cons: 负载可能不均衡                                                             │
│                                                                                  │
│  Client IP: 192.168.1.100 ──hash──▶ Instance B                                   │
│  Client IP: 192.168.1.101 ──hash──▶ Instance A                                   │
│  Client IP: 192.168.1.100 ──hash──▶ Instance B (same as first)                  │
└─────────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────────┐
│  Algorithm 5: Latency-Based (延迟优先)                                           │
├─────────────────────────────────────────────────────────────────────────────────┤
│  Description: 将请求分发到响应延迟最低的实例                                       │
│  Use Case: 对延迟敏感的应用、地理分布式部署                                       │
│  Pros: 最小化响应延迟                                                             │
│  Cons: 需要持续监控延迟、实现复杂                                                  │
│                                                                                  │
│  Instance A: P99 Latency 45ms ────────────────▶ Selected                         │
│  Instance B: P99 Latency 120ms                                                     │
│  Instance C: P99 Latency 80ms                                                      │
└─────────────────────────────────────────────────────────────────────────────────┘
```

```yaml
  jwt:
    enabled: true

    algorithms:
      - RS256
      - ES256
    
    # JWKS 配置
    jwks:
      uri: https://auth.orion.io/.well-known/jwks.json
      cache_ttl: 1h
      refresh_interval: 5m
    
    # Token 验证
    validation:
      issuer: https://auth.orion.io
      audience:
        - orion-api
        - orion-internal
      clock_skew: 30s  # 允许时钟偏差
    
    # Token 吊销检查
    revocation:
      enabled: true
      redis_key_prefix: "auth:revoked:"
      cache_ttl: 5m
    
    # 响应配置
    on_failure:
      status_code: 401
      body:
        error: "authentication_failed"
```

```
│  │  full access        team-scoped         resource-scoped                │    │

│  └─────────────────────────────────────────────────────────────────────────┘    │
│                                                                                  │
└─────────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────────┐
│  ABAC (Attribute-Based Access Control) - 细粒度鉴权                              │
├─────────────────────────────────────────────────────────────────────────────────┤
│                                                                                  │
│  策略定义示例:                                                                    │
│  ┌─────────────────────────────────────────────────────────────────────────┐    │
│  │  Policy: allow-pipeline-own-access                                      │    │
│  │  ├── Description: 用户只能访问自己创建的流水线                               │    │
│  │  ├── Effect: ALLOW                                                      │    │
│  │  ├── Principal: user:*                                                  │    │
│  │  ├── Resource: arn:orion:pipeline:*                                     │    │
│  │  ├── Action: pipeline:read                                              │    │
│  │  └── Condition:                                                         │    │
│  │       - Attribute: resource.creator_id                                  │    │
│  │         Operator: EQUALS                                                │    │
│  │         Value: ${user.id}                                               │    │
│  └─────────────────────────────────────────────────────────────────────────┘    │
│                                                                                  │
│  策略定义示例 (带环境条件):                                                        │
│  ┌─────────────────────────────────────────────────────────────────────────┐    │
│  │  Policy: allow-deploy-production                                        │    │
│  │  ├── Description: 只允许在工作时间部署到生产环境                             │    │
│  │  ├── Effect: ALLOW                                                      │    │
│  │  ├── Principal: role:release-manager                                    │    │
│  │  ├── Resource: arn:orion:environment:production                         │    │
│  │  ├── Action: deploy:execute                                             │    │
│  │  └── Condition:                                                         │    │
│  │       - Attribute: request.time.hour                                    │    │
│  │         Operator: BETWEEN                                               │    │
│  │         Value: [9, 18]  # 9AM - 6PM only                                │    │
│  │       - Attribute: request.day_of_week                                  │    │
│  │         Operator: IN                                                    │    │
│  │         Value: [MON, TUE, WED, THU, FRI]                                │    │
│  └─────────────────────────────────────────────────────────────────────────┘    │
│                                                                                  │
└─────────────────────────────────────────────────────────────────────────────────┘

鉴权决策流程:
┌─────────────────────────────────────────────────────────────────────────────────┐
│                                                                                  │
│  ┌─────────────┐                                                                │
│  │  Request    │ (user_id, action, resource, context)                           │
│  └──────┬──────┘                                                                │
│         │                                                                        │
│         ▼                                                                        │
│  ┌─────────────────────────────────────────────────────────────────────────────┐│
│  │  Step 1: RBAC Check (角色权限检查)                                            ││
│  │  ┌─────────────────────────────────────────────────────────────────────────┐││
│  │  │  Get User Roles: [team-lead, pipeline-operator]                         │││
│  │  │  Get Role Permissions: [pipeline:create, pipeline:read, pipeline:run]   │││
│  │  │  Check: action in permissions?                                          │││
│  │  │  Result: YES → Continue | NO → Deny                                     │││
│  │  └─────────────────────────────────────────────────────────────────────────┘││
│  └─────────────────────────────────────────────────────────────────────────────┘│
│         │ (Passed)                                                               │
│         ▼                                                                        │
│  ┌─────────────────────────────────────────────────────────────────────────────┐│
│  │  Step 2: ABAC Check (属性策略检查)                                            ││
│  │  ┌─────────────────────────────────────────────────────────────────────────┐││
│  │  │  Evaluate Policies:                                                      │││
│  │  │  1. allow-pipeline-own-access: user.id == resource.creator_id?          │││
│  │  │  2. allow-team-scope: user.team_id == resource.team_id?                 │││
│  │  │  3. time-restriction: request.time in allowed_range?                    │││
│  │  │  Result: All policies pass → Allow | Any deny → Deny                    │││
│  │  └─────────────────────────────────────────────────────────────────────────┘││
│  └─────────────────────────────────────────────────────────────────────────────┘│
│         │                                                                        │
│         ▼                                                                        │
│  ┌─────────────┐                                                                │
│  │  Decision   │ (Allow / Deny)                                                 │
│  └─────────────┘                                                                │
│                                                                                  │
└─────────────────────────────────────────────────────────────────────────────────┘
```

### 6.4 鉴权策略配置

```yaml
# authorization-config.yaml
authorization:
  enabled: true
  
  # RBAC 配置
  rbac:
    enabled: true
    mode: hierarchical  # hierarchical | flat
    
    # 角色定义
    roles:
      - name: tenant-admin
        permissions: ["*"]
        scope: tenant
        inherit_from: []
      
      - name: team-lead
        permissions:
          - pipeline:*
          - artifact:*
          - team:read
        scope: team
        inherit_from: [team-member]
      
      - name: team-member
        permissions:
          - pipeline:read
          - pipeline:run
          - artifact:read
        scope: resource
        inherit_from: []
    
    # 角色继承关系
    hierarchy:
      tenant-admin > team-lead > team-member > viewer
  
  # ABAC 配置
  abac:
    enabled: true
    policy_engine: opa  # Open Policy Agent
    
    # 策略存储
    policies:
      source: git  # git | consul | embedded
      repository: https://git.orion.io/policies/authorization.git
      path: /policies/*.rego
      refresh_interval: 1m
    
    # 属性来源
    attributes:
      user:
        - id
        - tenant_id
        - team_ids
        - roles
      resource:
        - id
        - type
        - creator_id
        - team_id
        - tenant_id
      request:
        - method
        - path
        - time
        - ip_address
      environment:
        - current_time
        - current_day
        - deployment_environment
  
  # 鉴权响应
  on_deny:
    status_code: 403
    body:
      error: "authorization_denied"
      message: "您没有权限执行此操作"
      policy: "${denied_policy_name}"
      required_permissions: "${required_permissions}"
```

## 十、附录 (Appendix)

### 10.1 术语表

| 术语 | 定义 |
|------|------|
| **QPS** | Queries Per Second，每秒请求数 |
| **Token Bucket** | 令牌桶算法，允许适度突发的限流算法 |
| **Sliding Window** | 滑动窗口算法，精确统计时间窗口内请求数 |
| **Circuit Breaker** | 熔断器模式，防止级联故障 |
| **RBAC** | Role-Based Access Control，基于角色的访问控制 |
| **ABAC** | Attribute-Based Access Control，基于属性的访问控制 |
| **JWKS** | JSON Web Key Set，公钥集合 |
| **OPA** | Open Policy Agent，开放策略引擎 |
| **HPA** | Horizontal Pod Autoscaler，K8s 水平自动伸缩 |
| **SLA** | Service Level Agreement，服务等级协议 |
