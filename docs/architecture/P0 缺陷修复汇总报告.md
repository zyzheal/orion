## 二、核心修复方案汇总

### 2.1 架构重构（修复 A01）

**问题**：5 层分层架构存在循环依赖（L2↔L3↔L4 网状调用）

**修复方案**：
```
┌─────────────────────────────────────────────────────────────┐
│                    核心域 (Core Domain)                      │
│  ┌─────────────┐ ┌─────────────┐ ┌─────────────┐           │
│  │ Pipeline    │ │ 构建环境    │ │ 多工具链    │           │
│  │ 引擎        │ │             │ │             │           │
│  └─────────────┘ └─────────────┘ └─────────────┘           │
│  ┌─────────────┐ ┌─────────────┐ ┌─────────────┐           │
│  │ 代码管理    │ │ 配置管理    │ │ 智能部署    │           │
│  └─────────────┘ └─────────────┘ └─────────────┘           │
└─────────────────────────────────────────────────────────────┘
                            │
                            ▼ (事件驱动，单向依赖)
┌─────────────────────────────────────────────────────────────┐
│                   支撑域 (Supporting Domain)                 │
│  ┌─────────────┐ ┌─────────────┐ ┌─────────────┐           │
│  │ AI 增强域   │ │ 效能洞察域  │ │ FinOps      │           │
│  └─────────────┘ └─────────────┘ └─────────────┘           │
│  ┌─────────────┐ ┌─────────────┐ ┌─────────────┐           │
│  │ CMDB        │ │ 运维治理    │ │ 工单协同    │           │
│  └─────────────┘ └─────────────┘ └─────────────┘           │
└─────────────────────────────────────────────────────────────┘
```

**调用规则**：
- 核心域 → 支撑域：允许同步调用
- 支撑域 → 核心域：仅允许事件订阅，禁止同步调用
- 支撑域 ↔ 支撑域：禁止直接调用

**部署独立性**：
- 最小部署：5 分钟（仅核心域）
- 增量部署：单域部署不影响其他域

### 2.2 数据库分片与同步（修复 A03/A04/B02）

**问题**：42 张表无分片策略，MySQL→ClickHouse 同步缺失

**修复方案**：

**分片表分类**：
| 表名 | 分片键 | 分片算法 | 归档策略 |
|------|--------|---------|---------|
| audit_log | tenant_id + 时间 | Hash(tenant_id)%10 + 按月分区 | 90 天归档 ClickHouse |
| event_log | 时间 | 按月分区 | 1 年冷存储 |
| cicd_pipeline_run | pipeline_id + 时间 | Hash(pipeline_id)%20 + 按月分区 | 180 天归档 |
| ai_inference_log | 时间 | 按月分区 | 90 天归档 |
| k8s_sync_log | cluster_id + 时间 | 按集群 + 按月分区 | 30 天自动清理 |

**CDC 同步架构**：
```
MySQL Binlog → Flink CDC → Kafka → ETL → ClickHouse
                  │                       │
                  ▼                       ▼
            延迟监控 (<5s)          一致性校验 (每日)
```

**数据一致性**：
- 延迟容忍：5-10 秒最终一致
- 冲突解决：以 MySQL 为准
- 每日校验：自动对账 + 告警

### 2.3 AI 降级方案（修复 A07）

**问题**：15+ 处 LLM 调用无具体降级实现

**修复方案**：

**LLM 分级治理**：
| 级别 | 场景数 | 降级要求 | 示例 |
|------|--------|---------|------|
| P0 核心 | 3 | 必须降级且可验证 | Aegis 风险评估、AI 自动排单 |
| P1 重要 | 7 | 可以降级但允许功能缺失 | AI Code Review、根因诊断 |
| P2 锦上添花 | 6 | 不降级直接禁用 | 变更日志生成、文档生成 |

**降级触发条件**（量化）：
- 超时：P95 > 2s (Code Review) / > 30s (风险评估)
- 错误率：5 分钟滑动窗口 > 15%
- 置信度：< 0.5 (风险评估) / < 0.7 (Code Review)
- 熔断器：连续失败 5 次

**降级实现方式**：
```
LLM 调用 → AI Gateway → 健康检查 → 正常 → LLM
                          ↓
                       异常 → 降级路由 → 规则引擎/模板/缓存/人工
```

**16 个场景降级决策树**：详见 `docs/ai/AI 降级方案设计.md`

### 2.5 NATS 高可用（修复 A06/S01）

**问题**：NATS 成为新的单点故障，故障切换策略缺失

**修复方案**：

**集群配置**：
- 3 节点 JetStream 集群
- R=3 副本（数据持久化）
- Raft 选举（Leader < 15 秒恢复）

**Stream 分区**：
```
按租户 + 事件类型复合分区：
- tenant_id % 10 → Stream-0 ~ Stream-9
- 每 Stream 内按事件类型分 Subject
```

**故障切换流程**：
```
心跳检测 (2s) → 6s 无响应 → 判定故障 → Raft 选举 (5s)
                                           ↓
                                    新 Leader 就职
                                           ↓
                                    客户端重连 (3s)
                                           ↓
                                    恢复 (< 15s)
```

**降级方案**：
- NATS 不可用时写本地 SQLite（缓存 10 万事件）
- 网络恢复后异步重放
- P0 事件至少一次投递，P1 事件可丢失

### 2.6 多租户隔离（修复 A08/E03）

**问题**：1000 团队=1000 Namespace 不可行

**修复方案**：

**网络隔离**：
- 10 团队/Namespace 分组
- 共 100 个 Namespace（而非 1000 个）
- NetworkPolicy 跨组默认拒绝

**数据隔离**：
- 单 Schema + tenant_id 列 + RLS（Row-Level Security）
- 42 表（而非 42,000 表）
- RLS 性能损耗：简单查询 1-2%，复杂 JOIN 3-5%

**计算隔离**：
- Runner 按团队配额调度
- 共享 Namespace
- 软限制可超卖 3:1

**千租户性能评估**：
| 指标 | 原方案 | 优化方案 | 改善 |
|------|--------|---------|------|
| etcd 内存 | ~70 MB | ~7 MB | 90%↓ |
| API Server QPS | ~100,000 | ~10,510 | 89%↓ |
| PostgreSQL 表数 | 42,000 | 42 | 99.9%↓ |

### 2.7 自愈引擎权限治理（修复 A09）

**问题**：Kintsugi 可执行 DDL/回滚/流量切换，权限风险未治理

**修复方案**：

**高危操作分类**：
| 级别 | 操作 | 审批要求 |
|------|------|---------|
| P0 | 流量切换、回滚部署 | 双签 + 沙箱验证 |
| P1 | 添加索引 (DDL) | 双签 + 沙箱验证 |
| P2 | 限流熔断 | 单人审批 |
| P3 | 重启服务 | 自动执行 + 审计 |
| P4 | 配置变更 | 自动执行 + 审计 |

**双签机制**：
```
自愈请求 → 创建工单 → 通知审批人 A → 审批通过
                                      ↓
                              通知审批人 B → 审批通过
                                      ↓
                                  执行修复
```

**沙箱验证流程**：
1. 复制生产配置到沙箱
2. 执行修复操作
3. 验证预期效果
4. 通过后执行生产

**自毁开关**：
- 6 类异常检测（错误率>50%、连续失败 3 次、非预期变更等）
- 状态机：ENABLED → THROTTLED → DISABLED → PERMANENTLY_DISABLED

### 2.8 AI 安全加固（修复 E04/E05/E06）

**问题**：Prompt 注入可绕过、AI Skill 无沙箱、输出无 DLP

**修复方案**：

**Prompt 注入防护体系**：
```
输入 → Unicode NFKC 标准化 → 编码检测 → 控制字符过滤
        ↓
    规则匹配 (多语言规则库)
        ↓
    ML 语义检测 (Embedding + FAISS)
        ↓
    通过 → LLM 推理
        ↓
    输出 DLP (敏感信息脱敏)
```

**多语言规则库**：
- 英文规则：10 条（ignore/disregard 等）
- 中文规则：8 条（忽略/无视等）
- 日文规则：6 条
- 韩文规则：6 条

**AI Skill 沙箱**：
- gVisor（轻量，启动<1s）：用于低风险 Skill
- Firecracker（强隔离，启动<5s）：用于高风险 Skill
- 资源配额：CPU 2 核、内存 2GB、时长 60s

**输出 DLP**：
- 敏感词检测：密码/密钥/PII
- 正则匹配：手机号/身份证/银行卡
- 自动脱敏：`138****1234`

### 2.9 JWT 并发刷新保护（修复 E01）

**问题**：Refresh Token 并发刷新可被劫持

**修复方案**：

**设备指纹绑定**：
```
设备指纹 = SHA256(User-Agent + IP / 24 + 设备 ID)
Refresh Token 写入时绑定设备指纹
刷新时校验设备指纹一致
```

**并发刷新检测**：
```lua
-- Redis Lua 原子操作
local current = redis.call('GET', key)
if current == token then
    return redis.call('SET', key, new_token)
else
    -- 并发刷新检测，全部吊销
    redis.call('DEL', key)
    return 'REVOKED'
end
```

**异常处理**：
- 同一 Token 并发刷新 → 全部吊销 + 告警
- 异地同时登录 → 短信确认 + 告警
- Access Token 有效期：15 分钟 → 5 分钟

### 2.10 API 分页与错误码规范（修复 B01/B06/B07）

**问题**：分页策略混用、错误码笼统、N+1 查询

**修复方案**：

**分页策略分离**：
| 分页类型 | 适用场景 | 响应结构 |
|---------|---------|---------|
| Offset | 静态数据、需要总数量 | page/total/total_pages |
| Cursor | 实时数据、大数据量 | cursor/has_more |

**分页决策树**：
```
需要"跳页"功能？
├─ 是 → Offset 分页
└─ 否 →
    ├─ 数据实时变化？→ Cursor 分页
    └─ 数据量>100 万？→ Cursor 分页
```

**错误码二级分类**：
```
格式：XYYZZ
X: 系统类别 (1=通用，2=认证，3=参数...)
YY: 一级分类
ZZ: 二级分类

示例：
30101 = 参数错误。参数缺失 (pipeline_id 必填)
30202 = 参数错误。格式错误 (时间格式无效)
```

**N+1 查询解决方案**：
- 方案 1：JOIN 查询（一对一关系）
- 方案 2：批量查询/DataLoader（一对多关系）
- 方案 3：冗余存储（空间换时间）
- 方案 4：应用层缓存

### 2.11 前端性能优化（修复 F01-F05）

**问题**：WebSocket 内存泄漏、图表卡顿、虚拟滚动缺失

**修复方案**：

**WebSocket 生命周期管理**：
```
连接中 → 已连接 → 心跳检测 → 断开 → 重连
  │         │         │         │       │
  │         │         │         │       └─ 指数退避
  │         │         │         └─ 清理回调
  │         │         └─ 30s 心跳
  │         └─ 5s 超时
  └─ 3s 超时
```

**图表库选型**：
| 库 | 包大小 | 性能 | 可定制性 | 推荐场景 |
|---|---|---|---|---|
| Recharts | 75KB | 中 | 高 | 小数据量简单图表 |
| ECharts | 300KB | 高 | 中 | 大数据量复杂图表 |
| Visx | 50KB | 高 | 极高 | 自定义可视化 |

**推荐**：ECharts（性能最优，支持百万数据点）

**虚拟滚动实现**：
- react-window 或 tanstack-virtual
- 固定行高 48px
- 仅渲染可视区域 + 缓冲区（10 行）
- 1000 行列表 DOM 节点从 200,000 降至 2,000

**表单持久化**：
```
输入 → debounce(500ms) → localStorage
刷新页面 → 检测草稿 → 提示恢复 → 提交成功 → 清除
```

**多 Tab 同步**：
```
Tab1 ─┬─ BroadcastChannel ──┬─ Tab2
      │                     │
      └─────────────────────┴─ Tab3

未读数同步：主 Tab 负责维护连接，广播到所有 Tab
```

### 2.12 SRE 运维加固（修复 S02-S07）

**问题**：故障切换无 runbook、告警风暴、备份缺失

**修复方案**：

**MySQL 主从延迟分级降级**：
| 级别 | 延迟阈值 | 告警级别 | 降级动作 |
|------|---------|---------|---------|
| Level 1 | >10s | P2 | 暂停从库分析查询 |
| Level 2 | >30s | P1 | 从库读请求降至 20% |
| Level 3 | >60s | P0 | 从库读请求 100% 切断 |

**Redis 哨兵脑裂处理**：
```
检测多 Master → 冻结写入 → 投票选择保留 Master
                                    ↓
                              重建主从关系
                                    ↓
                              数据冲突解决 (时间戳优先)
```

**ClickHouse 备份方案**：
```
clickhouse-backup 工具:
- 全量备份：每天 2:00 AM
- 增量备份：每小时
- PITR 恢复：任意时间点
```

**告警抑制规则**：
1. 维护窗口静默
2. 节点故障抑制所有相关告警
3. 数据库故障抑制应用层告警
4. 网络故障抑制下游告警
5. 级联故障只报根因
6. 重复告警 4 小时内不重复通知
7. 已知问题静默（关联 Issue）

**DR 切换演练计划**：
| 类型 | 频率 | 范围 | 目标 RTO |
|------|------|------|---------|
| Light Drill | 月度 | 单组件 | < 15 分钟 |
| Full Drill | 季度 | 机房级 | < 30 分钟 |
| Compliance Drill | 年度 | 带真实流量 | < 15 分钟 |
