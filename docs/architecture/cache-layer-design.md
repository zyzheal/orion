## 执行摘要 (Executive Summary)

本设计文档详细描述 Orion 平台缓存层的完整架构方案。随着平台用户规模和访问量的增长，数据库压力日益增大，热点数据访问延迟、高并发场景下的系统稳定性问题逐渐凸显。缓存层作为提升系统性能、保护后端存储的关键基础设施，需要统一规划和设计。

### 设计目标

| 目标类别 | 具体目标 | 衡量指标 |
|---------|---------|---------|
| **性能提升** | 降低热点数据访问延迟 | P99 延迟 < 10ms |
| **吞吐量提升** | 支撑高并发读取场景 | QPS > 100,000 |
| **数据库保护** | 减少数据库读压力 | 数据库 QPS 降低 70% |
| **可用性保障** | 缓存故障不影响核心业务 | 降级成功率 100% |
| **一致性保障** | 缓存与数据库数据一致 | 不一致窗口 < 1 秒 |

### 核心设计决策

| 决策项 | 选择方案 | 备选方案 | 选择理由 |
|-------|---------|---------|---------|
| 缓存中间件 | Redis Cluster | Redis Sentinel、Memcached | 水平扩展、高可用、丰富数据结构 |
| 缓存模式 | Cache-Aside 为主 | Read-Through、Write-Through | 简单可控、适应复杂业务 |
| 集群规模 | 9 节点 (3 主 3 从 3 哨兵) | 6 节点、12 节点 | 成本与可用性平衡 |
| 本地缓存 | Caffeine | Guava、Ehcache | 高性能、K8s 友好 |
| 一致性方案 | 延迟双删 + Binlog 订阅 | 直接失效、消息队列 | 兼顾性能与一致性 |

### 预期收益量化

| 指标 | 无缓存 | 目标缓存层 | 改善幅度 |
|------|--------|-----------|---------|
| 热点数据延迟 | 50-100ms (DB) | 1-5ms (Redis) | 95% |
| 数据库读 QPS | 5,000 | 1,500 | 70% |
| 系统吞吐量 | 3,000 RPS | 15,000 RPS | 400% |
| 数据库 CPU | 70% | 30% | 57% |
| 会话查询延迟 | 30ms | 2ms | 93% |

### 1.2 热点数据缓存 (Hot Data Caching)

#### 1.2.1 场景描述

热点数据是指被频繁访问但变更频率较低的数据。这类数据通常具有以下特征：
- **访问频率高**: 单条数据 QPS 可能超过 1000
- **读多写少**: 读写比例通常在 10:1 到 100:1 之间
- **数据量适中**: 单条数据大小通常小于 10KB
- **一致性要求宽松**: 秒级甚至分钟级延迟可接受

#### 1.2.2 典型用例

| 数据类型 | 具体示例 | 访问频率 | 变更频率 | 缓存策略 | TTL |
|---------|---------|---------|---------|---------|-----|
| 用户基础信息 | 用户名、邮箱、部门 | 极高 | 低 | Cache-Aside | 5m |
| 租户配置 | 租户配额、功能开关 | 高 | 中 | Cache-Aside + 事件失效 | 10m |
| 全局标签 | 标签定义、标签树 | 高 | 低 | Cache-Aside | 30m |
| 角色权限 | 角色定义、权限列表 | 极高 | 低 | Cache-Aside | 5m |
| 工具配置 | 工具模板、默认配置 | 中 | 中 | Cache-Aside | 15m |

### 1.3 会话状态缓存 (Session State Caching)

#### 1.3.1 场景描述

会话状态用于存储用户登录状态、认证信息、临时令牌等。这类数据的特点是：
- **生命周期短**: 通常有过期时间 (30 分钟 -24 小时)
- **访问频繁**: 每次请求都需要验证
- **一致性要求高**: 登出/失效需要立即生效
- **安全性敏感**: 涉及用户认证和授权

#### 1.3.2 典型用例

| 数据类型 | 具体示例 | 存储结构 | 过期策略 | 特殊要求 |
|---------|---------|---------|---------|---------|
| 用户 Session | 登录状态、用户 ID | Hash | TTL + 主动删除 | 支持强制下线 |
| JWT Token | 令牌信息、签发时间 | String | TTL | 支持黑名单 |
| 刷新令牌 | Refresh Token | String | 长 TTL | 并发刷新保护 |
| 验证码 | 登录/注册验证码 | String | 短 TTL (5m) | 一次性使用 |
| CSRF Token | 跨站请求防护 | String | 会话级 | 请求绑定 |

#### 1.3.3 会话状态设计

```
会话状态存储结构:

### 1.4 API 响应缓存 (API Response Caching)

#### 1.4.1 场景描述

API 响应缓存用于缓存完整的 API 响应结果，适用于：
- **计算成本高**: 需要多表 JOIN 或复杂聚合
- **数据变化慢**: 数据更新频率低于访问频率
- **响应较大**: 减少网络传输和序列化开销
- **一致性要求低**: 分钟级延迟可接受

#### 1.4.2 典型用例

| API 类型 | 具体示例 | 缓存 Key 设计 | TTL | 失效条件 |
|---------|---------|-------------|-----|---------|
| 列表查询 | `/api/v1/artifacts?tenant=xxx&page=1` | `api:artifacts:tenant_001:page:1` | 1m | 数据变更 |
| 统计查询 | `/api/v1/stats/efficiency?team=xxx` | `api:stats:efficiency:team_100` | 5m | 定时刷新 |
| 仪表盘 | `/api/v1/dashboard/overview` | `api:dashboard:overview:user_12345` | 2m | 用户切换 |
| 配置列表 | `/api/v1/tools/configs` | `api:tools:configs:global` | 10m | 配置变更 |
| 依赖关系 | `/api/v1/libraries/{id}/dependencies` | `api:library:deps:lib_001` | 30m | 库发布 |

#### 1.4.3 缓存 Key 设计规范

```
API 响应缓存 Key 命名规范:
┌─────────────────────────────────────────────────────────────────────────┐
│                                                                         │
│  格式：api:{resource}:{identifier}:{params_hash}                        │
│                                                                         │
│  示例:                                                                  │
│  ├── api:artifacts:tenant_001:page:1:size:20                            │
│  ├── api:stats:efficiency:team_100:range:7d                             │
│  ├── api:dashboard:overview:user_12345:tz:UTC8                          │
│  ├── api:tools:configs:global:type:ci                                   │
│  └── api:library:deps:lib_001:depth:2                                   │
│                                                                         │
│  注意事项:                                                              │
│  ├── 参数顺序固定 (按字母排序)，避免相同请求不同 Key                      │
│  ├── 敏感参数排除 (如 token、timestamp) 不参与缓存                       │
│  ├── 分页参数包含在 Key 中                                               │
│  └── 大 Key 使用 Hash 缩短 (SHA256 前 16 位)                               │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

### 1.5 计算结果缓存 (Computation Result Caching)

#### 1.5.1 场景描述

计算结果缓存用于缓存耗时计算的输出结果，适用于：
- **CPU 密集型**: AI 推理、复杂算法、数据分析
- **可重复计算**: 相同输入产生相同输出
- **结果复用性强**: 多个用户/场景可能请求相同计算
- **一致性要求低**: 可以接受一定程度的过期

#### 1.5.2 典型用例

| 计算类型 | 具体示例 | 计算耗时 | 缓存价值 | TTL |
|---------|---------|---------|---------|-----|
| AI 推理 | Code Review 结果 | 2-10s | 极高 | 1h |
| 风险评估 | 流水线风险评分 | 500ms-2s | 高 | 30m |
| 效能分析 | 团队效能指标计算 | 1-5s | 高 | 1h |
| 根因分析 | 故障根因定位 | 1-3s | 中 | 30m |
| 依赖分析 | 二方库影响范围 | 200ms-1s | 中 | 15m |

#### 1.5.3 缓存设计要点

```
计算结果缓存流程:

│      ┌─────────┐                   ┌─────────┐                          │
│      │ 客户端   │ ────────────────> │ 缓存层  │                          │
│      └─────────┘                   └────┬────┘                          │
│                                         │                                │
│                    ┌────────────────────┴────────────────────┐          │
│                    │                                         │          │
│                    ▼                                         ▼          │

### 2.2 Cache-Aside 模式 (旁路缓存)

#### 2.2.1 模式描述

Cache-Aside 是最常用的缓存模式，应用层直接管理缓存和数据库的交互。

```
┌─────────────────────────────────────────────────────────────────────────┐
│                         Cache-Aside Pattern                              │
│                                                                          │
│  读操作 (Read Operation):                                               │
│  ┌─────────────────────────────────────────────────────────────────┐    │
│  │                                                                  │    │
│  │   应用层                    缓存层              数据库            │    │
│  │     │                         │                   │              │    │
│  │     │  ① 请求数据              │                   │              │    │
│  │     │────────────────────────>│                   │              │    │

#### 2.2.2 实现要点

| 要点 | 说明 | 实现方式 |
|-----|------|---------|
| **读逻辑** | 先查缓存，未命中再查 DB | `getFromCache() ?? getFromDB()` |
| **写逻辑** | 先写 DB，再删除缓存 | `updateDB(); deleteCache();` |
| **缓存空值** | 防止缓存穿透 | 缓存 null 值，TTL=5m |
| **异步填充** | 避免阻塞主流程 | 异步线程/事件驱动 |
| **降级策略** | 缓存不可用时 | 直接查 DB + 日志告警 |

### 4.3 TTL 设计规范

#### 4.3.1 TTL 分级策略

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│                              TTL Grading Strategy                                │
├─────────────────────┬─────────────────────┬─────────────────────┬───────────────┤
│       级别           │     TTL 范围         │     适用场景         │   典型用例    │
│       (Level)        │     (Duration)      │     (Scenarios)     │   (Examples)  │
├─────────────────────┼─────────────────────┼─────────────────────┼───────────────┤
│  L1: 超短期          │  10s - 1m           │  防抖/限流/验证码    │  验证码、锁    │
│  (Ultra Short)       │                     │                     │  防重放 Key   │
├─────────────────────┼─────────────────────┼─────────────────────┼───────────────┤
│  L2: 短期            │  1m - 10m           │  高频读、低频写      │  热点数据、    │
│  (Short)             │                     │  可能存在短暂不一致  │  API 响应缓存   │
├─────────────────────┼─────────────────────┼─────────────────────┼───────────────┤
│  L3: 中期            │  10m - 1h           │  配置类、用户信息    │  用户 Profile、 │
│  (Medium)            │                     │  变更频率适中        │  角色权限、    │
│                      │                     │                     │  租户配置      │
├─────────────────────┼─────────────────────┼─────────────────────┼───────────────┤
│  L4: 长期            │  1h - 24h           │  计算结果、会话      │  会话 Session、 │
│  (Long)              │                     │  相对稳定数据        │  AI 推理结果   │
├─────────────────────┼─────────────────────┼─────────────────────┼───────────────┤
│  L5: 可过期          │  24h - 7d           │  临时数据、备份      │  临时文件、    │
│  (Extended)          │                     │  非关键数据          │  导出结果      │
├─────────────────────┼─────────────────────┼─────────────────────┼───────────────┤
│  L0: 永不过期        │  无 TTL             │  不推荐使用          │  仅在特殊      │
│  (Persistent)        │  (需主动删除)        │  (内存泄漏风险)      │  场景使用      │
└─────────────────────┴─────────────────────┴─────────────────────┴───────────────┘

TTL 设置原则:
├── 1. 默认所有 Key 都设置 TTL，避免内存泄漏
├── 2. TTL 应该大于数据的预期生命周期 + 缓冲时间
├── 3. 热点数据使用短 TTL + 主动失效
├── 4. 会话状态使用滑动过期 (每次访问刷新 TTL)
└── 5. 大 Key 使用独立 TTL，避免批量过期影响性能
```

#### 4.3.2 典型场景 TTL 配置

| 场景 | Key 示例 | TTL | 过期策略 | 说明 |
|-----|---------|-----|---------|------|
| 验证码 | `system:auth:captcha:xxx` | 5m | 固定 TTL | 一次性使用，过期自动失效 |
| 分布式锁 | `system:lock:resource:id` | 30s | 固定 TTL | 防止死锁，业务需保证释放 |
| 会话状态 | `tenant:xxx:auth:session:uid` | 30m | 滑动过期 | 每次访问刷新 TTL |
| 用户信息 | `tenant:xxx:user:profile:uid` | 5m | 固定 TTL + 事件失效 | 用户更新时主动失效 |
| 权限数据 | `tenant:xxx:auth:role:rid` | 10m | 固定 TTL + 事件失效 | 角色变更时主动失效 |
| API 响应 | `system:cache:api:xxx` | 2m | 固定 TTL | 定期自动刷新 |
| 计算结果 | `system:cache:compute:hash` | 1h | 固定 TTL | 计算成本高，长 TTL |
| 配置数据 | `global:config:feature:xxx` | 30m | 固定 TTL + 事件失效 | 配置变更时主动失效 |
| 限流计数 | `system:ratelimit:api:uid` | 1s | 固定 TTL | 每秒重置计数器 |
| 布隆过滤器 | `system:bloom:artifact` | - | 无过期 | 重建时整体替换 |

### 5.3 延迟双删策略

#### 5.3.1 问题背景

在高并发场景下，简单的"写 DB+ 删缓存"可能导致数据不一致：

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│                      Cache-DB Inconsistency Problem                              │
├─────────────────────────────────────────────────────────────────────────────────┤
│                                                                                  │
│  并发场景下的数据不一致问题:                                                      │
│                                                                                  │
│  时间     线程 A (读请求)          线程 B (写请求)                                │
│  ─────────────────────────────────────────────────────────────────               │
│  T1       读取缓存 (miss)                                                         │
│  T2                            更新数据库 (val=100)                               │
│  T3       读取数据库 (val=50, 旧值)                                               │
│  T4                            删除缓存                                           │
│  T5       写入缓存 (val=50, 脏数据!)  ◄──── 问题：缓存了旧值                       │
│                                                                                  │
│  结果：缓存中仍然是旧数据，直到下次删除或 TTL 过期                                   │
│                                                                                  │
└─────────────────────────────────────────────────────────────────────────────────┘
```

#### 5.3.2 延迟双删方案

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│                         Delayed Double Delete Solution                           │
├─────────────────────────────────────────────────────────────────────────────────┤
│                                                                                  │
│  解决方案：延迟双删 (Delayed Double Delete)                                      │
│                                                                                  │
│  ┌──────────────────────────────────────────────────────────────────────────┐   │
│  │   写操作时序：                                                            │   │
│  │                                                                          │   │
│  │   T1: 删除缓存 (先删，避免读请求读到旧数据后写入)                            │   │
│  │        DEL cache_key                                                     │   │
│  │                                                                          │   │
│  │   T2: 更新数据库                                                         │   │
│  │        UPDATE table SET val=100 WHERE id=xxx                             │   │
│  │                                                                          │   │
│  │   T3: 延迟 N 秒后再次删除缓存 (删除可能在此期间写入缓存 的旧数据)              │   │
│  │        SLEEP(500ms)                                                      │   │
│  │        DEL cache_key                                                     │   │
│  │                                                                          │   │
│  │   延迟时间建议：业务读耗时 P99 + 缓冲 (通常 300-1000ms)                      │   │
│  │                                                                          │   │
│  └──────────────────────────────────────────────────────────────────────────┘   │
│                                                                                  │
│  改进方案：异步延迟删除 (推荐)                                                    │
│  ┌──────────────────────────────────────────────────────────────────────────┐   │
│  │                                                                          │   │
│  │   ① 删除缓存                                                             │   │
│  │   ② 更新数据库                                                           │   │
│  │   ③ 发送延迟消息到 MQ (延迟 500ms)                                        │   │
│  │   ④ MQ 消费者收到消息后再次删除缓存                                         │   │
│  │                                                                          │   │

| 消息队列 | 事件驱动架构 | 100ms-1s | 中 | 高 |
| 直接失效 | 低并发场景 | 0 | 低 | 中 |

### 7.3 Orion 推荐方案

### 10.1 术语表

| 术语 | 英文 | 定义 |
|-----|------|------|
| 缓存穿透 | Cache Penetration | 查询不存在的 Key，请求直接打到数据库 |
| 缓存击穿 | Cache Breakdown | 热点 Key 过期瞬间，大量请求打到数据库 |
| 缓存雪崩 | Cache Avalanche | 大量 Key 同时过期，数据库压力激增 |
| 布隆过滤器 | Bloom Filter | 判断元素是否存在的概率型数据结构 |
| 延迟双删 | Delayed Double Delete | 写前后两次删除缓存，保证一致性 |
| 滑动过期 | Sliding Expiration | 每次访问刷新 TTL，延长有效期 |
| 本地缓存 | Local Cache | 应用进程内缓存 (如 Caffeine) |
| 分布式缓存 | Distributed Cache | 跨进程的缓存服务 (如 Redis) |
