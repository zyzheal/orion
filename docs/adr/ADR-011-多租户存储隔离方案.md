## 1. 背景与问题

### 1.1 现有决策（ADR-0004）

ADR-0004（2026-06-28 Accepted）已决策**共享数据库 + tenant_id 列过滤**模式：

> "采用共享数据库 + tenant_id 列过滤的隔离模式，所有数据访问必须包含 tenant_id 过滤条件。"

**核心原则**：
1. `tenant_id` 无处不在（所有数据表必须包含）
2. Repository 层统一过滤（`WHERE tenant_id = $1`）
3. API 层传递 `X-Tenant-ID` header
4. 中间件校验 + 事件层传递

**已落地证据**（`reports/tenant-boundary-spread-fix-2026-09-17.md`）：
- Audit 19 处 + Efficiency 21 处 + Backup 3 处 tenant_id 补齐
- RepositoryInterface 31 个子测 + 5 组变异全灭
- Notification/Alert 服务层残留（待修）

### 1.2 NeatLogic 一手对比

NeatLogic 使用与 ADR-0004 **完全不同**的存储隔离方案：**DB-per-tenant**（每租户一个独立数据库，
经 `AbstractRoutingDataSource` 按 `tenantUuid` 路由），而非同库多 schema。

真实代码（`neatlogic-framework` @ `1fa8b28ecf`，`store/mysql/NeatLogicRoutingDataSource.java`，38 行）：

```java
public class NeatLogicRoutingDataSource extends AbstractRoutingDataSource {
    @Override
    protected Object determineCurrentLookupKey() {
        if (TenantContext.get() != null && StringUtils.isNotBlank(TenantContext.get().getTenantUuid())) {
            String key = TenantContext.get().getTenantUuid();
            // 按 tenantUuid 路由到该租户的独立 DataSource
```

`TenantContext`（`neatlogic-framework` + `neatlogic-runner` 各一份，共 **2** 处）：

```java
private static final ThreadLocal<TenantContext> instance = new ThreadLocal<>();
```

**机械验证（2026-10-11，44 仓库 @ 固定 SHA）**：

| 检索 | 结果 |
|---|---|
| `extends AbstractRoutingDataSource` | **1** 处（`NeatLogicRoutingDataSource`）|
| `ThreadLocal<TenantContext>` | **2** 处（framework + runner）|
| Mapper XML 含 `tenant_id`（213 个 XML 中）| **0** 处 → **不存在列过滤** |
| `mysql-connector-j` / `ON DUPLICATE KEY UPDATE` | 存在 / **45** 文件 → 底层是 **MySQL** |

> **术语修正（2026-10-11）**：原本文档写作「Schema-per-tenant（同库多 schema）」。
> 实测 NeatLogic 的路由目标是**整个 DataSource（独立数据库）**，MySQL 本身无 schema 概念；
> 且全仓 213 个 Mapper XML 中 `tenant_id` 出现 0 次，证明不存在同库内的逻辑隔离。
> 详见 `reports/reference/adr-neatlogic-reference-audit-2026-10-11.md` §2。

**关键差异**：

| 维度 | NeatLogic（NL-8）| Orion ADR-0004 |
|------|-------------------|----------------|
| 隔离单位 | DB-per-tenant（独立数据库）| Single-schema + tenant_id |
| 表结构 | 每租户独立库、独立表，表内无 tenant_id | 全局共享表 + tenant_id 列 |
| 隔离强度 | ⭐⭐⭐⭐⭐ 强（物理）| ⭐⭐⭐ 中（逻辑）|
| 数据量增长影响 | 每租户独立 | 全表一起 |
| 迁移复杂度 | 高（每租户跑一次 migration）| 低（全局跑一次）|
| 大客户 SLA 保障 | ✅ | ❌（可能受影响）|

### 1.3 决策驱动问题

**Q1**：ADR-0004 的 Shared-schema 是否满足所有场景？
- 中小客户：✅ 满足
- 大客户（数据量 > 1000 万行）：⚠️ 查询性能可能受影响
- 合规敏感客户（等保 3 级 / SOC2 / 金融监管）：⚠️ 强隔离需求
- 数据跨境（GDPR 数据主权）：⚠️ 需物理隔离

**Q2**：是否需要为特定客户类型提供强隔离？
- 若"是"，需引入混合隔离方案
- 若"否"，保持现状

**Q3**：Schema-per-tenant 的迁移成本是否可接受？
- Repository 需重写（连接串动态切换 schema）
- Migration 管理复杂（多 schema 版本对齐）
- 备份恢复（每 schema 独立备份）

### 1.4 决策目标

明确多租户存储隔离的**分层策略**：
1. 默认方案（保持 ADR-0004 Shared-schema）
2. 增强方案（何时升级 Schema-per-tenant）
3. 混合方案（大小客户差异化）

## 2. 备选方案对比

### 2.1 方案 A：Shared-schema + tenant_id（Orion 现状，ADR-0004）

**实现**：
```sql
CREATE TABLE pipelines (
    id UUID PRIMARY KEY,
    tenant_id TEXT NOT NULL,       -- 逻辑隔离
    project_id TEXT NOT NULL,
    ...
);
CREATE INDEX idx_pipelines_tenant ON pipelines(tenant_id);
```

**优点**：
- ✅ 无迁移成本（已落地）
- ✅ Repository 统一实现（`WHERE tenant_id = $1`）
- ✅ Migration 全局单次执行
- ✅ 备份恢复简单（单库 dump）
- ✅ 中小客户性价比高

**缺点**：
- ❌ 大租户数据量影响全表查询性能（即使有索引）
- ❌ 逻辑隔离，无法通过架构层面证明"零数据泄露"
- ❌ GDPR 数据主权场景无法满足（跨境数据混在单库）
- ❌ 大客户 SLA 争抢风险

**性能指标**：
- 单租户 < 500 万行：查询性能正常
- 单租户 500 万-1000 万行：索引查询仍流畅
- 单租户 > 1000 万行：可能触发全表扫描（若索引失效）

### 2.2 方案 B：物理隔离 per-tenant（对齐 NeatLogic 隔离策略；PG 实现为 schema-per-tenant）

**实现要点**：NeatLogic 的隔离策略是「每租户一个独立存储单元」，其 MySQL 实现为独立 database。
Orion 使用 PG（ADR-005），PG 的等价实现是**独立 schema**（共享连接池、开销低于独立 database）。
二者隔离语义等价，落地载体不同。

```sql
-- 每租户独立 schema（PG）
CREATE SCHEMA tenant_001;
CREATE TABLE tenant_001.pipelines (
    id UUID PRIMARY KEY,
    project_id TEXT NOT NULL,
    ...  -- 无 tenant_id 列
);
```

**运行时切换**：
```go
// Repository 连接池按租户分片
schema := "tenant_" + tenantID
r.db.SetSearchPath(ctx, schema)
// 或每次 SQL 前缀 schema
query := fmt.Sprintf(`SELECT * FROM %q.pipelines WHERE id=$1`, schema, id)
```

**优点**：
- ✅ 强物理隔离（架构层面证明零泄露）
- ✅ 大客户 SLA 保障（独立 schema 互不影响）
- ✅ 单租户数据量增长不影响其他租户
- ✅ 合规友好（GDPR 数据主权 / 等保强隔离）

**缺点**：
- ❌ **迁移复杂**：Repository 需重写（连接串 schema 前缀）
- ❌ **Migration 复杂**：每个 schema 独立执行（需 schema_version 表管理）
- ❌ **备份复杂**：每 schema 独立备份
- ❌ **表膨胀**：100 租户 = 100 份 pipelines 表，DDL 变更需 100 次
- ❌ **成本**：DB 连接数 = N × 单 schema 连接数

**性能指标**：
- 单租户任意数据量：查询性能稳定
- 但连接池 / 内存开销随租户数线性增长

### 2.3 方案 C：Database-per-tenant

**实现**：每租户独立 PostgreSQL database。

**优点**：
- ✅ 最强隔离
- ✅ 独立备份 / 独立运维

**缺点**：
- ❌ 极高运维成本（N 个 DB 实例）
- ❌ 迁移地狱（每个 DB 独立版本）
- ❌ 不适合本项目 SaaS 规模

**结论**：❌ **不推荐**（过度设计）

### 2.4 方案 D：混合方案（分层隔离）

**实现**：
- **默认层**（90% 客户）：方案 A Shared-schema
- **增强层**（10% 大客户）：方案 B Schema-per-tenant
- **管理表**：`tenants` 表标注 `isolation_mode` 字段

```sql
CREATE TABLE tenants (
    id UUID PRIMARY KEY,
    name TEXT,
    isolation_mode TEXT CHECK (isolation_mode IN ('shared', 'schema')),
    schema_name TEXT,  -- 若 isolation_mode = 'schema'
    ...
);
```

**Repository 抽象**：
```go
type TenantAwareRepository interface {
    // 内部自动按 isolation_mode 路由
    GetByID(ctx context.Context, tenantID, id string) (*Model, error)
}

// 实现：
type RepoImpl struct {
    sharedDB *sql.DB       // 方案 A
    schemaDBs map[string]*sql.DB  // 方案 B
    tenants *TenantRepo   // 查 isolation_mode
}
```

**优点**：
- ✅ 兼容 ADR-0004（现有客户零迁移）
- ✅ 支持大客户强隔离（合规 / SLA 场景）
- ✅ 渐进式引入（先共享，需要时切 schema）
- ✅ 大客户可"预购"schema 隔离作为高价值服务

**缺点**：
- ⚠️ Repository 复杂度提升（需抽象层）
- ⚠️ 迁移工具需支持两种模式
- ⚠️ 测试覆盖翻倍（双模式都要测）

### 2.5 方案对比矩阵

| 维度 | A: Shared | B: Schema | C: Database | D: 混合 |
|------|-----------|-----------|-------------|---------|
| 隔离强度 | ⭐⭐⭐ 中 | ⭐⭐⭐⭐⭐ 强 | ⭐⭐⭐⭐⭐⭐ 最强 | ⭐⭐⭐⭐ 分层 |
| 迁移成本 | 0（已落地）| 高（重写 Repo）| 极高 | 中（渐进） |
| 运维复杂度 | 低 | 中 | 高 | 中 |
| 大客户 SLA | ❌ | ✅ | ✅ | ✅ |
| 合规友好 | 部分 | ✅ | ✅ | ✅ |
| 成本 | 低 | 中 | 高 | 中 |
| ADR-0004 兼容 | ✅ 完全 | ❌ 需重写 | ❌ | ✅ 默认兼容 |
| NeatLogic 对齐 | ⭐⭐ | ⭐⭐⭐⭐⭐ | — | ⭐⭐⭐ |

## 3. 决策

### 3.1 选定方案

**方案 D：混合方案（分层隔离）**

理由：
1. **兼容性**：完全兼容 ADR-0004 现状，90% 客户零迁移
2. **扩展性**：支持大客户切到 Schema-per-tenant（强隔离场景）
3. **渐进式**：先建立抽象层，客户有需要再切
4. **商业价值**：Schema 隔离可作为大客户增值付费项
5. **合规友好**：为 GDPR / 等保 / 金融行业预留能力

### 3.2 关键设计决定

#### 3.2.1 `tenants` 表扩展

Migration 追加：
```sql
ALTER TABLE tenants 
  ADD COLUMN isolation_mode TEXT NOT NULL DEFAULT 'shared' 
    CHECK (isolation_mode IN ('shared', 'schema')),
  ADD COLUMN schema_name TEXT,  -- 若 schema 模式，指向独立 schema
  ADD COLUMN schema_created_at TIMESTAMPTZ;
```

#### 3.2.2 Repository 抽象层

新增 `TenantAwareDB` 接口：

```go
type TenantAwareDB interface {
    // 根据 tenantID 路由到 shared 或 schema 连接
    GetConn(ctx context.Context, tenantID string) (*sql.DB, error)
    
    // 执行 SQL，自动加 schema 前缀（若 schema 模式）
    Query(ctx context.Context, tenantID, query string, args ...interface{}) (*sql.Rows, error)
    
    // 执行事务
    BeginTx(ctx context.Context, tenantID string, opts *sql.TxOptions) (*sql.Tx, error)
}
```

**实现要点**：
- 连接池按 schema 分片（`map[schemaName]*sql.DB`）
- 首次访问新 schema 时 lazy 创建连接
- 定期清理长期未用的 schema 连接

#### 3.2.3 新租户创建流程

```
新租户注册
    │
    ├─ 判定隔离模式（依套餐 / 合规要求 / 手动指定）
    │
    ├─ 若 Shared: 
    │    → 直接使用主库连接（现状）
    │
    └─ 若 Schema:
         → CREATE SCHEMA tenant_xxx
         → 跑一次该 schema 的 baseline migration（所有表创建）
         → 记录 schema_name 到 tenants 表
         → 加入连接池 map
```

#### 3.2.4 现有 Repository 兼容改造

现有代码：
```go
// 现状：r.db 直接是 *sql.DB
func (r *PipelineRepo) GetByID(ctx context.Context, tenantID, id string) (*Pipeline, error) {
    err := r.db.QueryRowContext(ctx, 
        `SELECT * FROM pipelines WHERE id=$1 AND tenant_id=$2`, id, tenantID).Scan(...)
}
```

改造后：
```go
// 抽象层封装
func (r *PipelineRepo) GetByID(ctx context.Context, tenantID, id string) (*Pipeline, error) {
    db, err := r.tenantDB.GetConn(ctx, tenantID)
    if err != nil { return nil, err }
    
    query := r.queryBuilder.BuildGetQuery(tenantID)  // 自动处理 schema 前缀 + tenant_id 过滤
    err = db.QueryRowContext(ctx, query, id).Scan(...)
}
```

#### 3.2.5 Migration 管理

新增 Migration 版本表：
```sql
CREATE TABLE schema_migrations (
    schema_name TEXT PRIMARY KEY,   -- 'public' 或 'tenant_xxx'
    version INT NOT NULL,
    applied_at TIMESTAMPTZ DEFAULT now()
);
```

Migration 执行：
- `public` schema：全局跑（现有流程）
- `tenant_xxx` schema：新租户创建时跑一次 baseline
- 增量 Migration：所有活跃 schema 都跑

### 3.3 触发升级的条件

以下任一条件触发从 shared 升级到 schema：

| 触发条件 | 阈值 |
|---------|------|
| 单租户数据量 | > 1000 万行 |
| 单租户 QPS | > 500 且影响其他租户 |
| 合规要求 | GDPR / 等保 3 级 / 金融监管 |
| 客户主动要求 | 大客户增值付费项 |
| 数据安全事件 | 疑似数据泄露触发 |

### 3.4 降级策略

- Schema → Shared：**不支持**（数据已迁移，回退风险高）
- Shared → Shared：**支持**（无变化）
- 若强制降级需求：导出 schema 数据 → 合并到 public.tenants 表 → 删除 schema

## 4. 风险与缓解

### 4.1 已知风险

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|---------|
| Repository 改造遗漏 | 中 | 高 | 全量 grep `r.db.` 逐文件审查；引入静态分析规则 |
| Schema 连接池爆炸 | 低 | 中 | 连接池上限 + LRU 淘汰长期未用 schema |
| Migration 多 schema 失败 | 中 | 中 | Migration 事务 + 版本表校验 + 手动回滚剧本 |
| 租户切换误用 | 低 | 高 | 中间件强制注入 tenantID；单测覆盖 TenantAwareDB 路由 |
| 混合模式复杂度 | 中 | 中 | 抽象层集中管理；文档 + lint 规则强制 |

### 4.2 监控指标

| 指标 | 类型 | 阈值 |
|------|------|------|
| `tenant_isolation_mode_distribution` | Gauge | shared/schema 比例告警 |
| `tenant_schema_connection_count` | Gauge | > 100 告警 |
| `tenant_query_cross_mode_total` | Counter | > 0 告警（不应发生）|
| `tenant_migration_schema_applied_total` | Counter | 每租户每版本 1 次 |
| `tenant_data_leak_risk_events_total` | Counter | > 0 严重告警 |

## 5. 影响面

### 5.1 对 ADR-0004 的影响

- ✅ **ADR-0004 继续有效**（Shared-schema 是默认方案）
- ✅ **本 ADR 是 ADR-0004 的扩展**（增加 Schema-per-tenant 增强路径）
- ⚠️ Repository 接口从 `*sql.DB` 抽象为 `TenantAwareDB`

### 5.2 对执行阶段的影响

| 阶段 | 影响 | 门控 |
|------|------|------|
| S0 基础设施 | 新增 TenantAwareDB 抽象层 | 必须完成 |
| S1 CMDB | Repository 改造（首个切换）| 迁移到 TenantAwareDB |
| S2 ITSM | Repository 改造 | 迁移到 TenantAwareDB |
| S3-S6 各模块 | 同上 | 新增表使用 TenantAwareDB |

### 5.3 对风险登记册的影响

- 新增 **R-P2-15**：Repository 改造遗漏（概率中影响高，用静态分析缓解）
- 新增 **R-P2-16**：Schema 连接池爆炸（概率低影响中，连接池上限 + LRU 缓解）
- 新增 **R-P2-17**：多 schema Migration 失败（概率中影响中，事务 + 回滚剧本缓解）

## 6. 与 NeatLogic 的对齐细节

### 6.1 语义对齐

NeatLogic 使用 DB-per-tenant（MySQL 独立 database）。Orion 采用**混合方案**：
- **Shared-schema 部分**：偏离 NL 隔离策略（成本与迁移复杂度权衡）
- **Schema 增强部分**：与 NL 的**隔离语义**对齐（每租户独立存储单元），
  载体由 MySQL database 改为 PG schema（ADR-005 约束下的等价实现）

### 6.2 差异点

| 维度 | NeatLogic | Orion ADR-011 |
|------|-----------|---------------|
| 默认方案 | DB-per-tenant | Shared-schema |
| ThreadLocal TenantContext | ✅ | ✅（ADR-0004 已有）|
| 运行时存储单元切换 | ✅ DataSource 路由 | ✅ Schema 增强模式 |
| Migration 管理 | 每租户库独立 | 每 schema 独立（语义对齐）|
