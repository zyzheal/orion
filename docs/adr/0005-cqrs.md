# ADR-0005: CQRS 模式采用

## Status

**Accepted** — 2026-06-28

## Context

Orion 平台在以下场景需要读写分离：

1. **Pipeline 执行**：写操作（启动 Pipeline）和读操作（查询 Pipeline 状态）负载差异大
2. **告警评估**：写操作（记录告警指标）高频，读操作（查询告警历史）低频
3. **审批流程**：写操作（提交审批）和读操作（查询审批状态）并发模式不同
4. **制品仓库**：写操作（上传制品）和读操作（下载制品）I/O 模式不同

传统 CRUD 模式中，读和写共享同一数据模型和查询路径，存在以下问题：

- **写性能受限**：复杂查询影响写性能
- **读性能受限**：写锁阻塞读操作
- **模型冲突**：写模型（规范化）和读模型（反规范化）需求冲突
- **扩展困难**：读写负载不均衡，无法独立扩展

## Decision

采用 **CQRS (Command Query Responsibility Segregation)** 模式，将写操作（Command）和读操作（Query）分离为不同的模型和存储路径。

### 架构概览

```
┌─────────────┐     ┌──────────────┐     ┌─────────────┐
│  Command    │     │   NATS       │     │   Query     │
│  Handler    │────▶│  Event Bus   │────▶│   Handler   │
│  (写)       │     │              │     │   (读)      │
└─────────────┘     └──────────────┘     └─────────────┘
       │                                         │
       ▼                                         ▼
┌─────────────┐                         ┌─────────────┐
│ Write DB    │                         │ Read DB     │
│ (PostgreSQL)│                         │ (PostgreSQL)│
│  规范化     │◀────── Event ───────────│  反规范化   │
└─────────────┘                         └─────────────┘
```

### Command 层 (写)

```go
// handler/command.go
type CreatePipelineCommand struct {
    TenantID      string
    ProjectID     string
    Name          string
    YamlDefinition string
}

func (h *CommandHandler) Handle(ctx context.Context, cmd CreatePipelineCommand) (*models.Pipeline, error) {
    // 1. 业务逻辑验证
    if cmd.Name == "" {
        return nil, ErrInvalidName
    }

    // 2. 写入数据库
    pipeline := &models.Pipeline{
        ID:   uuid.New().String(),
        Name: cmd.Name,
    }
    err := h.repo.Create(ctx, cmd.TenantID, cmd.YamlDefinition, pipeline)
    if err != nil {
        return nil, err
    }

    // 3. 发布事件
    h.publisher.Publish(ctx, models.Event{
        Type:    "pipeline.created",
        TenantID: cmd.TenantID,
        Payload: pipeline,
    })

    return pipeline, nil
}
```

### Query 层 (读)

```go
// handler/query.go
type GetPipelineQuery struct {
    TenantID string
    ID       string
}

func (h *QueryHandler) Handle(ctx context.Context, q GetPipelineQuery) (*models.Pipeline, error) {
    // 直接查询数据库（规范化模型）
    return h.repo.GetByID(ctx, q.TenantID, q.ID)
}
```

### 适用场景

| 场景 | 适用 CQRS | 理由 |
|------|----------|------|
| Pipeline 执行 | 是 | 读写负载差异大，需要独立扩展 |
| 告警评估 | 是 | 写高频，读低频 |
| 审批流程 | 是 | 状态机复杂，读写模式不同 |
| 用户管理 | 否 | 读写负载均衡，CQRS 增加复杂度 |
| 配置管理 | 否 | 低频读写，CRUD 足够 |

### 实施策略

1. **渐进式实施**：先在 Pipeline 和告警模块实施，验证效果后再扩展
2. **共享数据库**：初期使用同一 PostgreSQL 数据库，Command 和 Query 共享表
3. **事件驱动同步**：Command 处理完成后发布事件，Query 层通过事件更新读模型
4. **最终一致性**：读模型可能存在短暂不一致，通过事件确保最终一致

## Consequences

### 正面
- **性能优化**：读写独立扩展，互不影响
- **模型优化**：写模型和读模型可按各自需求优化
- **事件驱动**：Command 处理完成后发布事件，驱动下游更新
- **审计完整**：所有写操作记录为事件，可追溯

### 负面
- **复杂度增加**：需要维护两套模型和查询路径
- **最终一致性**：读模型可能存在短暂不一致
- **学习曲线**：团队需要学习 CQRS 模式
- **不适用于所有场景**：低频读写场景 CRUD 更简单

### 实施原则

1. **只在必要时使用**：读写负载差异大时才采用 CQRS
2. **共享数据库**：初期不引入新数据库，降低运维复杂度
3. **事件驱动同步**：通过事件确保读模型最终一致
4. **监控一致性**：监控读写延迟，及时发现不一致
