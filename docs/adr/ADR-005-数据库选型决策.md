## 1. 背景与问题

### 1.1 问题陈述

当前 Orion 平台文档中存在数据库选型不一致的问题：

| 文档 | 声明的数据库 | 版本 |
|------|-------------|------|
| 架构设计详解.md | PostgreSQL | 14+ |
| 数据库 Schema 设计.md | MySQL | 8.0+ |
| ADR-004-备份恢复策略设计.md | MySQL | 8.0+ |

这种不一致会导致：
- 开发团队无法确定正确的技术栈
- Schema 设计可能返工
- 运维团队无法准备正确的部署方案
- 备份策略可能不适用

### 1.2 决策目标

统一 Orion 平台的数据库选型，明确：
1. 主数据库选型（PostgreSQL vs MySQL）
2. 辅助数据库的使用场景（ClickHouse、MongoDB、Redis）
3. 各数据库的部署架构和边界

### 1.3 约束条件

- 必须支持多租户数据隔离
- 必须支持高可用和灾难恢复
- 必须与 Kubernetes 生态兼容
- 团队现有技术栈偏好
- 开源优先，控制成本

## 2. 技术对比分析

### 2.1 PostgreSQL vs MySQL 8.0 核心差异

| 特性 | PostgreSQL 14+ | MySQL 8.0+ |
|------|---------------|-----------|
| **事务隔离** | 完整 MVCC，支持 Serializable | 支持 RR/RC，Serializable 限制较多 |
| **并发控制** | 真 MVCC，读写不阻塞 | 伪 MVCC，读可能阻塞 |
| **复杂查询** | 优秀的 JOIN 优化器，支持 CTE | JOIN 优化较弱，8.0 支持 CTE |
| **JSON 支持** | JSONB（二进制索引化） | JSON（文本存储，虚拟列索引） |
| **全文搜索** | 内置 GIN/GiST 索引 | 支持全文索引，功能较基础 |
| **扩展性** | 丰富的扩展生态 (PostGIS 等) | 扩展较少，主要靠插件 |
| **复制方式** | 流复制，逻辑复制 | 主从复制，组复制 (MGR) |
| **GIS 支持** | PostGIS (行业标准) | 基础 GIS 支持 |

### 2.2 JSON 支持对比

| 特性 | PostgreSQL | MySQL 8.0 |
|------|-----------|----------|
| 存储格式 | JSONB（二进制） | JSON（文本） |
| 索引支持 | GIN 索引，路径索引 | 虚拟列 + 普通索引 |
| 查询性能 | 优秀（原生索引） | 一般（需虚拟列） |
| 操作函数 | 丰富 (->, ->>, @>, ?) | 基础 (JSON_EXTRACT 等) |
| 部分更新 | 支持 | 不支持（需整字段更新） |

**PostgreSQL 示例**:
```sql
CREATE TABLE users (
    id SERIAL PRIMARY KEY,
    data JSONB NOT NULL
);
CREATE INDEX idx_users_data ON users USING GIN (data);
-- 查询包含特定键的数据
SELECT * FROM users WHERE data ? 'email';
-- 包含查询
SELECT * FROM users WHERE data @> '{"department": "engineering"}';
```

**MySQL 示例**:
```sql
CREATE TABLE users (
    id INT PRIMARY KEY,
    data JSON NOT NULL,
    email_virtual VARCHAR(255) AS (data->>'$.email') STORED
);
CREATE INDEX idx_email ON users(email_virtual);
```

### 2.3 运维复杂度对比

| 维度 | PostgreSQL | MySQL 8.0 |
|------|-----------|----------|
| **学习曲线** | 较陡峭 | 较平缓 |
| **调优复杂度** | 较高（参数多） | 中等 |
| **备份工具** | pg_basebackup, pgBackRest | XtraBackup, mysqldump |
| **高可用方案** | Patroni, repmgr | MGR, Orchestrator |
| **监控生态** | pg_stat 视图丰富 | performance_schema |
| **升级难度** | 大版本升级较复杂 | 大版本升级相对简单 |
| **人才储备** | 相对较少 | 相对丰富 |

### 2.4 社区生态对比

| 维度 | PostgreSQL | MySQL 8.0 |
|------|-----------|----------|
| **社区活跃度** | 非常高（ASF 风格治理） | 高（Oracle 主导） |
| **扩展生态** | 极丰富（PostGIS, TimescaleDB 等） | 一般 |
| **云厂商支持** | 主流云厂商均支持 | 主流云厂商均支持 |
| **企业版** | EDB（可选，非必须） | MySQL Enterprise（商业许可） |
| **许可协议** | PostgreSQL License（宽松） | GPL v2（copyleft） |

### 2.5 成本对比

| 项目 | PostgreSQL | MySQL 8.0 |
|------|-----------|----------|
| **软件许可** | 完全免费（PostgreSQL License） | 开源免费（GPL） |
| **企业版费用** | EDB 约 $30K/年（可选） | Enterprise 约 $60K/年（可选） |
| **云服务费用** | 相近（RDS/Aurora） | 相近（RDS/Aurora） |
| **运维成本** | 略高（人才较少） | 略低（人才较多） |
| **长期风险** | 低（社区驱动） | 中（Oracle 控制） |

## 3. 决策结果

### 3.1 选定方案

**主数据库：MySQL 8.0+**

**决策理由**:

1. **团队技术栈匹配**
   - 团队对 MySQL 更熟悉，运维经验更丰富
   - MySQL 人才储备更充足，招聘和学习成本更低
   - 现有监控和运维工具链对 MySQL 支持更完善

2. **满足 Orion 核心需求**
   - MySQL 8.0 的 JSON 支持已足够满足 Orion 的配置存储需求
   - 效能指标计算可通过合理设计和索引优化达到性能要求
   - MySQL 8.0 已支持 CTE 和窗口函数，复杂查询能力大幅提升

3. **生态成熟度**
   - MySQL Operator 成熟，Kubernetes 部署方案完善
   - 云厂商支持广泛，RDS/Aurora 均有成熟服务
   - 备份工具（XtraBackup）成熟可靠

4. **统一技术栈**
   - 现有文档中多个已使用 MySQL（Schema 设计、备份恢复策略）
   - 避免技术栈分裂，降低维护成本

### 3.2 否决 PostgreSQL 的原因

1. **团队学习成本**：团队需要学习 PostgreSQL 运维知识，短期影响开发进度
2. **运维生态差异**：现有监控/备份工具需要切换，增加运维复杂度
3. **文档一致性**：Schema 设计和备份恢复已基于 MySQL，切换导致返工

### 4.4 ClickHouse 分析数据库设计

**使用场景**:
- 效能指标聚合（DORA 指标、MTTR、部署频率）
- 成本数据采集和分析
- 日志分析（替代部分 ELK 功能）
- 用户行为分析

**不使用场景**:
- 事务型业务数据
- 需要频繁更新的场景
- 强一致性要求的场景

**部署架构**:

### 4.5 MongoDB 文档数据库设计

**使用场景边界**:
| 场景 | 是否使用 | 说明 |
|------|---------|------|
| 审计日志 | 使用 | 日志结构不固定，需要灵活 Schema |

| 流水线运行日志 | 使用 | 日志量大，结构可能变化 |

| 配置数据 | 不使用 | 需要复杂查询，用 PostgreSQL |

### 4.6 Redis 缓存层设计

**使用场景**:
- Session 存储
- 热点数据缓存（用户信息、团队配置）
- 分布式锁（审批并发控制）
- 限流计数器
- 发布订阅（NATS 的补充）

**数据结构设计**:
```
# Session
SESS:{user_id} → Hash {token, expires_at, ip, last_accessed}

# 热点数据缓存
CACHE:user:{user_id} → JSON {id, name, email, ...}  TTL=1h
CACHE:team:{team_id} → JSON {id, name, members, ...} TTL=5m

# 分布式锁
LOCK:approval:{approval_id} → String (owner)  TTL=5m

# 限流计数
RATE:api:{user_id}:{endpoint} → Counter  TTL=1m

# 发布订阅
PUBSUB:pipeline:{pipeline_id} → Channel (状态更新)
```

**部署架构**:
```yaml

  name: orion-redis
```

## 5. Schema 转换建议

### 5.1 MySQL → PostgreSQL 关键差异

| MySQL 语法/特性 | PostgreSQL 等效 | 注意事项 |
|----------------|----------------|---------|
| `AUTO_INCREMENT` | `GENERATED ALWAYS AS IDENTITY` | 或使用 `SERIAL` |
| `DATETIME` | `TIMESTAMP` | PostgreSQL 的 TIMESTAMP 包含时区信息 |
| `TINYINT(1)` | `BOOLEAN` | MySQL 的 TINYINT(1) 通常用于布尔值 |
| `JSON` | `JSONB` | 推荐使用 JSONB 以获得索引支持 |
| `ENUM` | `ENUM` | PostgreSQL 需要预先创建 ENUM 类型 |
| `ENGINE=InnoDB` | 无（默认） | PostgreSQL 只有一种存储引擎 |
| `UNIQUE KEY` | `UNIQUE CONSTRAINT` | 语法略有不同 |
| `FULLTEXT INDEX` | `GIN INDEX` + `tsvector` | 全文搜索实现方式不同 |
| `ON UPDATE CURRENT_TIMESTAMP` | `TRIGGER` | PostgreSQL 需要触发器实现 |

### 5.2 Schema 转换示例

**MySQL 原文**:
```sql
CREATE TABLE users (
    id              CHAR(36) PRIMARY KEY DEFAULT (UUID()),
    email           VARCHAR(255) UNIQUE NOT NULL,
    status          ENUM('active', 'inactive', 'suspended') DEFAULT 'active',
    quota           JSON,
    created_at      DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at      DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    
    INDEX idx_users_email (email),
    INDEX idx_users_status (status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

**PostgreSQL 转换**:
```sql
-- 创建 ENUM 类型
CREATE TYPE user_status AS ENUM ('active', 'inactive', 'suspended');

-- 创建更新时间的触发器函数
CREATE OR REPLACE FUNCTION update_updated_at_column()
RETURNS TRIGGER AS $$
BEGIN
    NEW.updated_at = NOW();
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

-- 表定义
CREATE TABLE users (
    id              CHAR(36) PRIMARY KEY DEFAULT gen_random_uuid(),
    email           VARCHAR(255) UNIQUE NOT NULL,
    status          user_status DEFAULT 'active',
    quota           JSONB,
    created_at      TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at      TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- 创建索引
CREATE INDEX idx_users_email ON users(email);
CREATE INDEX idx_users_status ON users(status);
CREATE INDEX idx_users_quota ON users USING GIN (quota);

-- 创建触发器
CREATE TRIGGER update_users_updated_at
    BEFORE UPDATE ON users
    FOR EACH ROW
    EXECUTE FUNCTION update_updated_at_column();
```

## 7. 影响分析

### 7.1 对其他模块的影响

| 模块 | 影响类型 | 需要配合的工作 |
|------|---------|---------------|
| 后端 API | ORM 配置 | 更新 GORM/SQLAlchemy 连接配置 |
| 数据库 Schema | 语法转换 | 按 5.2 节示例转换 |
| 运维部署 | 部署脚本 | 更新 Helm Chart 和 CI/CD |
| 监控告警 | 指标采集 | 更新 Prometheus exporter |
| 备份恢复 | 备份工具 | 从 XtraBackup 切换到 pg_basebackup |

### 7.2 对运维的影响

- **新的运维技能要求**：团队需要学习 PostgreSQL 运维知识
- **监控指标变化**：从 MySQL metrics 切换到 PostgreSQL metrics
- **备份工具变化**：使用 pg_basebackup 或 CloudNativePG 的备份方案
- **高可用方案**：使用 Patroni 替代 MySQL 的 MGR

### 7.3 对安全的影响

- **权限模型差异**：PostgreSQL 的 RBAC 更细粒度
- **加密方式**：支持列级加密（pgcrypto）
- **审计能力**：通过 pgAudit 扩展实现审计日志

## 9. Revisit 条件

在以下情况下应重新审视本决策：

1. **业务规模变化**：当单机 PostgreSQL 无法承载业务负载，且分片方案成本过高时，可重新评估 MySQL 8.0 的分片方案
2. **团队技能变化**：如果团队 PostgreSQL 技能严重不足且无法在短期内提升
3. **技术演进**：如果 MySQL 在未来版本中显著改进 JSON 支持和复杂查询优化
4. **云厂商限制**：如果目标部署环境的云厂商对 PostgreSQL 支持不佳
