## 一、背景

### 1.1 问题陈述

Orion 平台作为企业级 DevOps 平台，承载着代码、流水线、审批、部署等核心业务数据。当前存在以下风险：

1. **数据丢失风险**：硬件故障、人为误操作、恶意攻击可能导致数据丢失
2. **服务中断风险**：单点故障、区域灾难可能导致服务长时间不可用
3. **合规要求**：等保 2.0、SOC2 等要求数据备份和灾难恢复能力

### 1.2 决策目标

设计一套完整的备份恢复与灾难重建方案，实现：
- RPO (恢复点目标) < 5 分钟
- RTO (恢复时间目标) < 30 分钟
- 数据持久性 > 99.999999999% (11 个 9)
- 符合等保三级、SOC2 合规要求

## 二、备份策略

### 2.1 备份对象与频率

| 数据类型 | 备份方式 | 频率 | 保留策略 | 存储位置 |
|---------|---------|------|---------|---------|
| MySQL 数据库 | 全量 + Binlog | 全量每日，Binlog 实时 | 30 天 | S3 + 本地 SSD |
| ClickHouse | 分区备份 | 每小时 | 7 天 | S3 |
| MongoDB | Oplog + 快照 | 持续 Oplog，快照每日 | 30 天 | S3 |
| Redis | RDB + AOF | RDB 每小时，AOF 每秒 | 7 天 | 本地 SSD |
| 配置文件 | Git 版本控制 | 实时 | 永久 | Git 仓库 |
| 构建产物 | 镜像仓库 | 实时 | 按策略 | Harbor/Nexus |
| 日志数据 | 实时同步 | 持续 | 90 天 | S3 Glacier |

### 2.2 3-2-1 备份原则

```
3 份数据副本:
  - 1 份生产数据 (主集群)
  - 1 份本地备份 (同城备份集群)
  - 1 份异地备份 (跨区域灾备)

2 种存储介质:
  - 高性能 SSD (生产 + 本地备份)
  - 对象存储 S3 (异地备份 + 归档)

1 个异地副本:
  - 跨区域复制到其他 AWS Region
```

## 三、数据库备份实现

### 3.1 MySQL 备份方案

```yaml
# 使用 Percona XtraBackup 进行物理备份
# 备份脚本：/scripts/backup/mysql_backup.sh

#!/bin/bash
set -euo pipefail

BACKUP_DIR="/backup/mysql"
DATE=$(date +%Y%m%d_%H%M%S)
S3_BUCKET="s3://orion-backup/mysql"

# 全量备份 (每日凌晨 2 点)
if [ "$(date +%H)" == "02" ]; then
    echo "Starting full backup..."
    xtrabackup --backup \
        --target-dir=${BACKUP_DIR}/full_${DATE} \
        --user=backup_user \
        --password=${BACKUP_PASSWORD}
    
    # 压缩备份
    tar -czf ${BACKUP_DIR}/full_${DATE}.tar.gz -C ${BACKUP_DIR} full_${DATE}
    
    # 上传到 S3
    aws s3 cp ${BACKUP_DIR}/full_${DATE}.tar.gz ${S3_BUCKET}/full/
    
    # 清理本地备份 (保留 7 天)
    find ${BACKUP_DIR} -name "full_*.tar.gz" -mtime +7 -delete
fi

# Binlog 备份 (每 5 分钟)
aws s3 cp /var/lib/mysql/mysql-bin.${CURRENT_BIN} \
    ${S3_BUCKET}/binlog/ \
    --storage-class STANDARD_IA

# 验证备份完整性
xtrabackup --prepare \
    --target-dir=${BACKUP_DIR}/full_${DATE} \
    --user=backup_user
```

### 3.2 MySQL 备份配置 (Operator)

```yaml
# MySQL Operator 备份配置
apiVersion: mysql.oracle.com/v2
kind: MySQLBackup
metadata:
  name: orion-mysql-backup
  namespace: orion-prod
spec:
  clusterName: orion-db-cluster
  
  # 备份计划
  schedule:
    fullBackup: "0 2 * * *"      # 每天 2 点全量备份
    binlogBackup: "*/5 * * * *"   # 每 5 分钟备份 Binlog
  
  # 备份存储
  storage:
    type: s3
    s3:
      bucket: orion-backup
      prefix: mysql/
      region: us-west-2
      
    # 本地缓存
    localCache:
      path: /backup/mysql
      retentionDays: 7
  
  # 备份策略
  backupPolicy:
    fullBackupRetentionDays: 30
    binlogRetentionDays: 7
    compression: gzip
    encryption: AES256
  
  # 备份验证
  verification:
    enabled: true
    schedule: "0 4 * * *"  # 每天 4 点验证
    method: restore_test   # 恢复测试验证

---
# 备份监控
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: mysql-backup-alerts
spec:
  groups:
  - name: backup
    rules:
    # 备份失败告警
    - alert: MySQLBackupFailed
      expr: mysql_backup_status{status="failed"} == 1
      for: 5m
      labels:
        severity: critical
      annotations:
        summary: "MySQL 备份失败"
    
    # 备份延迟告警
    - alert: MySQLBackupDelayed
      expr: |
        (time() - mysql_backup_last_success_timestamp) > 86400
      for: 1h
      labels:
        severity: warning
      annotations:
        summary: "MySQL 备份超过 24 小时未执行"
    
    # 备份存储空间不足
    - alert: BackupStorageLow
      expr: |
        (backup_storage_available / backup_storage_total) < 0.2
      for: 30m
      labels:
        severity: warning
      annotations:
        summary: "备份存储空间不足 20%"
```

### 3.3 ClickHouse 备份方案

```yaml
# ClickHouse 备份配置
apiVersion: clickhouse.altinity.com/v1
kind: ClickHouseBackup
metadata:
  name: orion-clickhouse-backup
  namespace: orion-prod
spec:
  backupType: incremental  # 增量备份
  
  # 备份计划
  schedule:
    - name: hourly_incremental
      cron: "0 * * * *"
      type: incremental
      retention:
        hours: 168  # 7 天
      
    - name: daily_full
      cron: "0 3 * * *"
      type: full
      retention:
        days: 30
  
  # 备份存储
  storage:
    type: s3
    s3:
      bucket: orion-backup
      prefix: clickhouse/
      endpoint: s3.us-west-2.amazonaws.com
  
  # 备份表
  tables:
    include:
      - "orion_cost.*"      # 成本数据
      - "orion_logs.*"      # 日志数据
      - "orion_metrics.*"   # 指标数据
  
  # 备份验证
  check:
    enabled: true
    command: "SELECT count() FROM system.backup_list WHERE status='OK'"
```

### 3.4 MongoDB 备份方案

```yaml
# MongoDB 备份配置
apiVersion: mongodb.com/v1
kind: MongoDBBackup
metadata:
  name: orion-mongodb-backup
  namespace: orion-prod
spec:
  clusterName: orion-mongodb
  
  # 备份模式
  backupMode: continuous   # 持续备份 (基于 Oplog)
  
  # 快照计划
  snapshotSchedule:
    - scheduleType: hourly
      retention:
        hours: 24
    - scheduleType: daily
      retention:
        days: 30
    - scheduleType: weekly
      retention:
        weeks: 12
    - scheduleType: monthly
      retention:
        months: 12
  
  # 存储配置
  storage:
    s3:
      bucket: orion-backup
      prefix: mongodb/
      encryption: AES256
  
  # 时间点恢复 (PITR)
  pointInTimeRecovery:
    enabled: true
    windowHours: 168  # 支持恢复到 7 天内任意时间点
```

### 4.3 故障转移流程

```yaml
# 灾难恢复流程定义
disaster_recovery:
  # 故障检测
  detection:
    method: health_check
    interval: 30s
    threshold: 3  # 连续 3 次失败触发
    
  # 告警通知
  alerting:
    channels: [pagerduty, slack, phone]
    escalation:
      - time: 0m
        notify: [oncall]
      - time: 15m
        notify: [oncall, team_lead]
      - time: 30m
        notify: [oncall, team_lead, director]
    
  # 故障转移决策
  failover:
    auto_failover: true  # 数据库自动故障转移
    manual_approval: required_for_app  # 应用切换需审批
    
    # 故障转移条件
    conditions:
      - primary_unreachable: true
      - replica_healthy: true
      - data_lag < 5min  # 数据延迟小于 5 分钟
    
  # 故障转移步骤
  steps:
    - name: stop_primary
      description: 确认主库不可达
      command: mysqladmin -h primary ping
      
    - name: promote_replica
      description: 提升从库为主库
      command: |
        STOP REPLICA;
        RESET REPLICA ALL;
        SET GLOBAL read_only = OFF;
      
    - name: update_dns
      description: 更新 DNS 指向新主库
      command: aws route53 change-resource-record-sets
      
    - name: restart_application
      description: 重启应用连接新主库
      command: kubectl rollout restart deployment/orion-api
      
    - name: verify
      description: 验证故障转移成功
      command: |
        mysql -h new_primary -e "SELECT @@global.read_only"
        curl http://orion-api/health
```

## 五、恢复操作手册

### 5.1 MySQL 恢复

```bash
#!/bin/bash
# MySQL 恢复脚本

set -euo pipefail

BACKUP_FILE=$1
S3_BUCKET="s3://orion-backup/mysql"

# 1. 从 S3 下载备份
echo "Downloading backup from S3..."
aws s3 cp ${S3_BUCKET}/full/${BACKUP_FILE} /tmp/

# 2. 解压备份
echo "Extracting backup..."
tar -xzf /tmp/${BACKUP_FILE} -C /tmp/

# 3. 停止 MySQL 服务
echo "Stopping MySQL..."
mysqladmin shutdown -u root -p${ROOT_PASSWORD}

# 4. 清空数据目录
echo "Cleaning data directory..."
rm -rf /var/lib/mysql/*

# 5. 恢复数据
echo "Restoring data..."
xtrabackup --copy-back \
    --target-dir=/tmp/${BACKUP_FILE%.tar.gz}

# 6. 修复权限
chown -R mysql:mysql /var/lib/mysql

# 7. 启动 MySQL
echo "Starting MySQL..."
systemctl start mysqld

# 8. 应用 Binlog (PITR)
echo "Applying binlogs..."
mysqlbinlog /backup/mysql/binlog/*.bin | mysql -u root -p${ROOT_PASSWORD}

# 9. 验证恢复
echo "Verifying recovery..."
mysql -u root -p${ROOT_PASSWORD} -e "
    SELECT COUNT(*) FROM information_schema.tables 
    WHERE table_schema = 'orion_public'
"
```

### 5.2 完整灾难恢复

```bash
#!/bin/bash
# 完整灾难恢复脚本 (DR Site)

set -euo pipefail

REGION="us-west-2"
CLUSTER="orion-dr"

echo "=== 开始灾难恢复 ==="

# Step 1: 验证灾备环境
echo "[1/8] 验证灾备环境..."
aws eks update-kubeconfig --name ${CLUSTER} --region ${REGION}

# Step 2: 提升数据库
echo "[2/8] 提升数据库..."
kubectl apply -f /scripts/dr/promote-mysql.yaml
kubectl wait --for=condition=Complete job/promote-mysql --timeout=300s

# Step 3: 启动应用服务
echo "[3/8] 启动应用服务..."
kubectl scale deployment orion-api --replicas=6
kubectl scale deployment orion-worker --replicas=3

# Step 4: 验证服务健康
echo "[4/8] 验证服务健康..."
kubectl wait --for=condition=available deployment/orion-api --timeout=300s

# Step 5: 切换 DNS
echo "[5/8] 切换 DNS..."
aws route53 change-resource-record-sets \
    --hosted-zone-id ${HOSTED_ZONE_ID} \
    --change-batch file:///scripts/dr/dns-failover.json

# Step 6: 验证 DNS 生效
echo "[6/8] 验证 DNS 生效..."
until dig +short orion.internal | grep -q ${DR_IP}; do
    sleep 10
done

# Step 7: 发送通知
echo "[7/8] 发送通知..."
curl -X POST ${SLACK_WEBHOOK} -d '{
    "text": "灾难恢复完成，服务已切换到灾备站点"
}'

# Step 8: 记录恢复时间
echo "[8/8] 记录恢复时间..."
echo "RTO: $(($(date +%s) - ${DR_START_TIME})) seconds"

echo "=== 灾难恢复完成 ==="
```

### 6.2 Prometheus 告警规则

```yaml
groups:
- name: disaster_recovery
  rules:
  # 备份失败

      severity: critical
    annotations:
      summary: "备份失败"
```

## 八、合规要求

### 8.1 等保三级要求

- ✅ 数据备份制度：建立数据备份与恢复管理制度
- ✅ 备份介质管理：备份介质存放在不同物理位置
- ✅ 恢复演练：定期进行恢复演练并记录
- ✅ 加密存储：备份数据加密存储

### 8.2 SOC2 要求

- ✅ 可用性：确保系统可用性和灾难恢复能力
- ✅ 保密性：备份数据加密和访问控制
