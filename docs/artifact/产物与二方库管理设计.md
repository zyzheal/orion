## 一、产物管理 (Artifact Management)

### 1.1 产物类型

```
Orion 管理的所有产物类型:

📦 容器镜像 (Container Images)
   ├── 应用镜像 (payment-service:v2.3.0)
   ├── 基础镜像 (company-base:ubuntu-22.04)
   └── Builder 镜像 (orion/builder:java-17-maven-3.9)

📦 依赖包 (Dependencies)
   ├── Java: JAR/WAR (payment-api-2.3.0.jar)
   ├── Node.js: NPM 包 (@company/payment-sdk)
   ├── Python: Wheel (company_auth-1.0.0-py3-none-any.whl)
   ├── Go: Go Module (git.company.com/common/utils v1.2.0)
   └── Rust: Crate (company-crypto v0.5.0)

📦 基础设施产物 (Infrastructure Artifacts)
   ├── Helm Chart (payment-service-2.3.0.tgz)
   ├── Terraform Module (rds-cluster v1.0.0)
   ├── K8s Manifests (deployment.yaml, service.yaml)
   └── Docker Compose (docker-compose.yml)

📦 测试产物 (Test Artifacts)
   ├── 测试报告 (test-results.xml)
   ├── 覆盖率报告 (coverage.html)
   ├── 性能测试报告 (jmeter-results.jtl)
   └── 截图/录屏 (e2e-screenshot.png)

📦 安全产物 (Security Artifacts)
   ├── SBOM (bom.spdx.json)
   ├── 签名 (cosign.sig)
   ├── 扫描报告 (trivy-results.json)
   └── 合规报告 (compliance-report.pdf)

📦 文档产物 (Documentation Artifacts)
   ├── API 文档 (openapi.yaml)
   ├── CHANGELOG.md
   └── Release Notes
```

### 1.2 产物生命周期

```yaml
artifact_lifecycle:
  # ── 创建 ──
  creation:
    trigger: pipeline_build_completed
    process:
      1. 构建产物 (镜像/JAR/包)
      2. 生成元数据 (版本、构建时间、Git SHA、构建者)
      3. 生成 SBOM (软件物料清单)
      4. 安全扫描 (Trivy/Snyk)
      5. 数字签名 (Cosign)
      6. 推送到仓库 (Harbor/Nexus)
      7. 注册到产物注册表 (Orion Artifact Registry)
  
  # ── 存储 ──
  storage:
    primary:
      container_images: harbor.internal
      java_artifacts: nexus.internal/repository/maven-releases
      npm_packages: nexus.internal/repository/npm-releases
      python_packages: pypi.internal
      go_modules: goproxy.internal
    metadata:
      store: postgresql (artifact_registry 表)
      search: elasticsearch (全文检索)
  
  # ── 提升 (Promotion) ──
  promotion:
    stages:
      - name: snapshot
        description: "开发中版本，随时可能被覆盖"
        retention: 7d
      - name: release-candidate
        description: "候选发布版，通过 CI 测试"
        retention: 30d
      - name: stable
        description: "稳定版，通过所有测试和扫描"
        retention: 90d
      - name: production
        description: "生产版本，已部署到生产环境"
        retention: 365d
      - name: archived
        description: "归档版本，只读保留"
        retention: forever  # 合规要求
    
    promotion_rules:
      snapshot → release-candidate:
        require:
          - ci_passed
          - security_scan_passed (no critical)
          - sbom_generated
      release-candidate → stable:
        require:
          - all_tests_passed
          - integration_tests_passed
          - performance_tests_passed
          - security_scan_passed (no high)
          - code_review_approved
      stable → production:
        require:
          - approval_from_tech_lead
          - deployment_to_staging_verified
          - rollback_plan_ready
  
  # ── 部署 ──
  deployment:
    process:
      1. 从仓库拉取指定版本产物
      2. 验签 (验证签名确保未被篡改)
      3. 部署到目标环境
      4. 记录部署元数据 (环境、时间、部署者)
      5. 更新产物状态 (stable → production)
  
  # ── 清理 ──
  cleanup:
    policies:
      - name: snapshot_cleanup
        condition: "age > 7d AND not_referenced"
        action: delete
      
      - name: rc_cleanup
        condition: "age > 30d AND superseded"
        action: delete
      
      - name: stable_cleanup
        condition: "age > 90d AND not_in_prod"
        action: archive_then_delete
      
      - name: prod_retention
        condition: "deployed_to_prod"
        action: retain_forever
```

## 二、二方库管理 (Internal Library Management)

### 2.1 二方库定义

```
二方库 = 公司内部开发的共享库/组件

与三方库的区别:
├── 三方库: 外部开源/商业库 (Spring Boot, React, lodash)
├── 二方库: 公司内部开发的共享库 (company-auth, company-utils)
└── 一方库: 项目私有的库 (不共享)

二方库的特点:
├── 版本由公司内部团队控制
├── 可以快速响应业务需求
├── 可能有 API 不兼容变更
├── 需要内部审批才能发布
└── 通常有 SLA 和技术支持
```

### 2.2 二方库生命周期

```yaml
internal_library_lifecycle:
  # ── 创建 ──
  creation:
    process:
      1. 创建仓库 (git.company.com/libs/{library-name})
      2. 初始化项目模板 (根据语言选择模板)
      3. 配置 CI/CD 流水线 (自动构建、测试、发布)
      4. 注册到二方库注册表 (Orion Library Registry)
      5. 设置维护者 (owner, reviewers)
    
    templates:
      java:
        name: company-lib-template
        includes: [maven-pom, junit, spotbugs, checkstyle]
        publishes_to: nexus.internal/repository/maven-releases
      
      node:
        name: company-npm-template
        includes: [tsconfig, jest, eslint, npm-publish]
        publishes_to: nexus.internal/repository/npm-releases
      
      python:
        name: company-python-template
        includes: [pyproject.toml, pytest, ruff]
        publishes_to: pypi.internal
      
      go:
        name: company-go-template
        includes: [go.mod, golangci-lint, go-test]
        publishes_to: goproxy.internal
  
  # ── 开发 ──
  development:
    versioning:
      scheme: semver  # Major.Minor.Patch
      branch_strategy: trunk_based
      pre_release:
        - snapshot     # 开发中
        - alpha        # 内部测试
        - beta         # 公开测试
        - rc           # 候选发布
    
    ci_pipeline:
      stages:
        - lint
        - test           # 覆盖率 ≥ 80%
        - build
        - security-scan
        - publish-snapshot
    
    code_review:
      required_reviewers: 2
      must_include:
        - changelog_updated
        - version_bumped
        - tests_added_for_new_features
  
  # ── 发布 ──
  release:
    process:
      1. 创建 Release Tag
      2. 运行完整 CI (含集成测试)
      3. 生成 CHANGELOG
      4. 生成 SBOM
      5. 安全扫描
      6. 发布到正式仓库
      7. 通知依赖项目 (自动创建升级 PR)
    
    approval:
      required:
        - 维护者审批 (至少 1 人)
        - 架构师审批 (Major 版本)
        - 安全扫描通过 (无 Critical/High)
    
    notification:
      channels:
        - slack: "#lib-releases"
        - orion: 自动创建依赖项目的升级 PR
  
  # ── 依赖追踪 ──
  dependency_tracking:
    # 谁在用这个二方库
    dependents:
      discover:
        method: code_scan  # 扫描所有仓库的依赖声明
        schedule: "daily"
      
      metadata:
        - dependent_repo
        - dependent_team
        - current_version
        - latest_version
        - upgrade_available
        - last_updated
    
    # 版本兼容性声明
    compatibility:
      major_releases:
        - version: 2.0.0
          breaking_changes:
            - "认证接口从 OAuth2 改为 OIDC"
            - "移除 deprecated 方法 auth.login()"
          migration_guide: "https://wiki.company.com/libs/auth/migrate-v2"
          deprecation_period: "6 months"
  
  # ── 废弃与下线 ──
  deprecation:
    process:
      1. 标记为 deprecated (在仓库和注册表中)
      2. 发布公告 (提前 90 天)
      3. 提供迁移指南
      4. 自动通知所有依赖项目
      5. 90 天后停止维护
      6. 180 天后从仓库移除 (仅保留归档)
```

### 2.5 自动升级 PR

```yaml
# 当二方库发布新版本时，Orion 自动为依赖项目创建升级 PR
auto_upgrade_pr:
  trigger: internal_library_released
  process:
    1. 扫描所有依赖该二方库的项目
    2. 对每个项目创建升级分支
    3. 更新依赖版本 (pom.xml / package.json / go.mod)
    4. 运行 CI 验证 (编译 + 测试)
    5. 如果 CI 通过 → 创建 PR
    6. 如果 CI 失败 → 创建 Issue 通知维护者
  
  pr_template:
    title: "chore(deps): 升级 {library} {old_version} → {new_version}"
    body: |
      ## 依赖升级
      
      | 库名 | {library} |
      |------|-----------|
      | 当前版本 | {old_version} |
      | 目标版本 | {new_version} |
      | 变更类型 | {Patch / Minor / Major} |
      
      ## 变更内容
      {changelog}
      
      ## CI 验证结果
      ✅ 编译通过
      ✅ 单元测试通过 (142/142)
      ✅ 集成测试通过 (48/48)
      
      ## 注意事项
      {breaking_changes_warning_or_none}
      
      ---
      _此 PR 由 Orion 自动创建_
  
  auto_merge:
    enabled: true
    conditions:
      - change_type: patch  # 只自动合并 Patch 版本
      - ci_passed: true
      - no_breaking_changes: true
      - approval: auto_approved  # 自动审批
```

## 三、AI Skill 管理 (AI Skill Management)

### 3.1 AI Skill 定义

```
AI Skill = Orion 平台中可复用的 AI 能力单元

与 Prompt 的区别:
├── Prompt: 一次性的指令 ("请审查这段代码")
├── Skill: 结构化的、可配置的、可复用的 AI 能力

Skill 的特点:
├── 有明确的输入/输出定义
├── 可配置 (参数、模型、规则)
├── 可版本化
├── 可组合 (Skill 之间可以互相调用)
├── 可评估 (准确率、延迟、成本)
└── 可共享 (团队间分享和复用)
```

### 3.2 Skill 类型

```yaml
skill_types:
  # ── 代码类 ──
  code_skills:

        format: json
        fields: [file, line, severity, suggestion]

    - name: code-explain
      description: "解释复杂代码的逻辑"
      input:
        type: code_snippet
        format: source_code
      output:
        type: explanation
        format: markdown
      model: qwen3-8b  # 简单任务用小模型
      category: understand
    
    - name: code-generate-tests
      description: "为给定代码生成单元测试"
      input:
        type: code_snippet
      output:
        type: test_code
        format: source_code
      model: qwen3-235b
      category: test
    
    - name: code-refactor
      description: "重构代码，改善结构和可读性"
      input:
        type: code_snippet
      output:
        type: refactored_code
        format: source_code
      model: qwen3-235b
      category: refactor

  # ── 运维类 ──
  ops_skills:
    - name: log-analysis
      description: "分析日志，发现异常模式和根因"
      input:
        type: log_entries
        format: json_lines
        max_lines: 10000
      output:
        type: analysis_report
        format: json
        fields: [patterns, anomalies, root_cause, recommendations]
      model: qwen3-235b
      category: diagnose
    
    - name: incident-postmortem
      description: "生成事故复盘报告"
      input:
        type: incident_data
        format: json

        type: postmortem

      model: qwen3-235b

    - name: capacity-planning

        type: metrics_timeseries

### 3.3 Skill 生命周期

```yaml
skill_lifecycle:
  # ── 创建 ──
  creation:
    process:
      1. 定义 Skill 元数据 (名称、描述、输入/输出)
      2. 编写 Prompt 模板 (支持变量插值)
      3. 选择模型 (qwen3-8b / qwen3-235b / 其他)
      4. 配置参数 (温度、最大 token、超时)
      5. 定义评估指标 (准确率、延迟、成本)
      6. 测试验证 (用测试集验证效果)
      7. 发布到 Skill 注册表
    
    skill_definition:
      apiVersion: orion.dev/v1alpha1
      kind: AISkill
      metadata:
        name: code-review
        version: 2.1.0
        author: platform-team
      spec:
        description: "代码审查，发现安全漏洞和性能问题"
        category: review
        model: qwen3-235b
        prompt_template: |
          你是资深代码审查专家。审查以下代码变更:
          
          ```diff
          {{diff}}
          ```
          
          审查重点:
          1. 安全性 (SQL 注入、XSS、硬编码密钥等)
          2. 性能 (N+1 查询、内存泄漏、不必要的循环等)
          3. 可读性 (命名、注释、复杂度等)
          4. 架构合理性 (职责分离、依赖注入等)
          
          输出格式: JSON 数组，每项包含:
          - file: 文件名
          - line: 行号
          - severity: CRITICAL/HIGH/MEDIUM/LOW/INFO
          - type: 问题类型
          - suggestion: 修复建议
        parameters:
          temperature: 0.3
          max_tokens: 4096
          timeout: "30s"
          retry_on_failure: 2
          fallback: rule_engine  # LLM 失败时降级到规则引擎
        
        input:
          type: code_diff
          format: unified_diff
          max_size: "100KB"
          validation:
            - not_empty
            - valid_diff_format
        
        output:
          type: review_comments
          format: json
          schema:
            type: array
            items:
              type: object
              properties:
                file: {type: string}
                line: {type: integer}
                severity: {enum: [CRITICAL, HIGH, MEDIUM, LOW, INFO]}
                type: {type: string}
                suggestion: {type: string}
          validation:
            - valid_json
            - schema_conformance
        
        evaluation:
          dataset: "test-code-review-500.json"  # 500 条标注数据
          metrics:
            - name: precision
              target: "> 0.85"
            - name: recall
              target: "> 0.80"
            - name: false_positive_rate
              target: "< 10%"
            - name: avg_latency
              target: "< 15s"
            - name: cost_per_review
              target: "< ¥0.50"
  
  # ── 测试 ──
  testing:
    process:
      1. 单元测试 (Prompt 模板渲染正确性)
      2. 集成测试 (调用 LLM API 验证输出格式)
      3. 效果评估 (用测试集计算准确率/召回率)
      4. 性能测试 (延迟、并发、成本)
      5. 回归测试 (与上一版本对比，确保不劣化)
    
    test_dataset:
      storage: git  # 测试集存在 Git 中，可版本化
      update_schedule: "monthly"  # 每月更新测试集
  
  # ── 发布 ──
  release:
    process:
      1. 通过所有测试
      2. 生成 Skill 文档
      3. 发布到 Skill 注册表
      4. 通知相关团队
    
    versioning:
      scheme: semver
      breaking_change:
        - 输入格式变更
        - 输出格式变更
        - 模型变更导致输出风格显著变化
      deprecation_period: "3 months"
  
  # ── 监控 ──
  monitoring:
    metrics:
      - invocation_count
      - success_rate
      - avg_latency
      - cost_per_invocation
      - accuracy (如果有标注数据)
      - user_satisfaction (用户反馈)
    
    alerting:
      - accuracy_drop > 5% → 调查原因
      - latency_p95 > 30s → 考虑换模型或优化 Prompt
      - cost_spike > 200% → 检查是否有异常调用
  
  # ── 组合 ──
  composition:
    # Skill 可以组合使用
    skill_chains:
      - name: full-code-review
        description: "完整的代码审查流程"
        steps:
          - skill: code-review        # LLM 审查
          - skill: security-scan      # 安全工具扫描
          - skill: merge-review-results # 合并结果
          - skill: generate-summary   # 生成审查摘要
```
