## 执行摘要 (Executive Summary)

本设计文档定义 Orion 平台的数据库迁移策略，覆盖从迁移场景分类、Flyway 集成、零停机策略到监控告警的完整生命周期。目标是建立标准化、自动化、可回滚的数据库迁移体系，确保数据库变更的安全性和可靠性。

### 核心设计原则

| 原则 | 描述 | 验证标准 |
|------|------|---------|
| **零停机优先** | 所有迁移支持在线执行 | 迁移期间服务可用性 100% |
| **向后兼容** | Schema 变更保持向后兼容 | 新旧代码可同时运行 |
| **可回滚** | 每个迁移都有明确回滚方案 | RTO < 30 分钟 |
| **可观测** | 迁移过程全链路可观测 | 关键指标 100% 覆盖 |
| **自动化** | 尽可能自动化执行 | 人工干预 < 5% |

### 迁移类型总览

| 迁移类型 | 频率 | 风险等级 | 典型耗时 | 审批要求 |
|---------|------|---------|---------|---------|
| 新建迁移 (Greenfield) | 高 | 低 | 分钟级 | 自动审批 |
| 存量迁移 (Brownfield) | 中 | 中 | 小时级 | Tech Lead 审批 |
| Schema 变更 | 中 | 中 | 分钟级 | DBA 审批 |
| 数据迁移 | 低 | 高 | 天级 | 架构委员会审批 |

### 1.3 各场景详细说明

#### 1.3.1 S1: 新建迁移 (Greenfield Migration)

**定义**: 创建全新的数据库对象（表、索引、视图、序列等），不影响现有数据结构。

**适用场景**:
- 新功能需要的新表
- 性能优化需要的新索引
- 报表系统需要的新视图
- ID 生成器需要的序列

**风险等级**: 低

**特点**:
- 不影响现有业务逻辑
- 可立即回滚（DROP 即可）
- 无需停机窗口
- 自动化程度高

**审批流程**:
```
开发提交 → 自动化检查 → CI/CD 部署 → 生产执行
         (语法/规范)    (自动)       (自动)
```

**示例迁移脚本**:
```sql
-- V20260410.001__create_user_preferences_table.sql
CREATE TABLE user_preferences (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    user_id BIGINT NOT NULL,
    preference_key VARCHAR(100) NOT NULL,
    preference_value JSON NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    UNIQUE KEY uk_user_key (user_id, preference_key),
    INDEX idx_user_id (user_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

#### 1.3.2 S2: 存量迁移 (Brownfield Migration)

**定义**: 对现有表结构进行修改，通常涉及添加字段、修改字段属性等。

**适用场景**:
- 业务扩展需要新增字段
- 字段类型调整（VARCHAR 扩容）
- 添加新的索引优化查询
- 添加外键约束

**风险等级**: 中

**特点**:
- 可能影响现有代码
- 需要向后兼容考虑
- 大表操作可能需要限流
- 部分操作需要停机窗口

**审批流程**:
```
开发提交 → Tech Lead 审批 → DBA 审批 → 自动化检查 → 生产执行
                      (影响分析)    (语法/规范)
```

**向后兼容变更示例**:
```sql
-- 安全：添加可为空的字段
ALTER TABLE orders ADD COLUMN discount_amount DECIMAL(10,2) NULL;

-- 安全：添加有默认值的字段
ALTER TABLE users ADD COLUMN notification_enabled BOOLEAN DEFAULT TRUE;

-- 不安全：添加 NOT NULL 无默认值字段 (需要双写过渡)
-- ALTER TABLE users ADD COLUMN phone VARCHAR(20) NOT NULL; -- 禁止!
```

#### 1.3.3 S3: Schema 变更 (Schema Alteration)

**定义**: 修改现有表的核心结构，可能影响数据兼容性。

**适用场景**:
- 字段类型变更（INT → BIGINT）
- 字符集变更（utf8 → utf8mb4）
- 存储引擎变更（MyISAM → InnoDB）
- 分区策略调整

**风险等级**: 中 - 高

**特点**:
- 通常需要表级锁
- 可能阻塞读写操作
- 需要严格测试
- 回滚复杂

**审批流程**:
```
开发提交 → Tech Lead 审批 → DBA 审批 → 架构审批 → 变更窗口执行
                      (影响分析)    (风险评估)    (夜间/低峰)
```

#### 1.3.4 S4: 数据迁移 (Data Migration)

**定义**: 大规模数据移动、转换或重分布。

**适用场景**:
- 历史数据归档
- 跨数据库迁移
- 分库分表数据重分布
- 数据格式转换

**风险等级**: 高 - 极高

**特点**:
- 数据量大（GB/TB 级）
- 耗时长（小时/天级）
- 需要严格一致性校验
- 回滚方案复杂

**审批流程**:
```
方案设计 → 架构委员会审批 → DBA 审批 → 演练验证 → 变更窗口执行
         (风险评估)        (资源评估)   (回归测试)   (周末/夜间)
```

### 2.2 版本号规则 (Version Numbering Rules)

#### 2.2.1 版本号格式

采用 `V{YYYYMMDD}.{Sequence}__{Description}` 的命名规范：

```
版本号格式:
┌─────────────────────────────────────────────────────────────────┐
│  V YYYYMMDD . NNN __ description_kebab_case.sql                  │
│  │ │      │   │    │                                           │
│  │ │      │   │    └─ 描述：小写 + 下划线，简明表达变更内容       │
│  │ │      │   └────── 分隔符：双下划线                          │
│  │ │      └────────── 序列号：3 位数字，从 001 开始                │
│  │ └───────────────── 日期：YYYYMMDD 格式                        │
│  └───────────────────── 版本前缀：V 大写                          │
└─────────────────────────────────────────────────────────────────┘

示例:
├── V20260410.001__create_users_table.sql
├── V20260410.002__add_email_index.sql
├── V20260411.001__create_orders_table.sql
├── V20260415.001__add_discount_column.sql
└── V20260420.001__migrate_legacy_data.sql
```

#### 2.2.2 版本号分配规则

| 场景 | 规则 | 示例 |
|------|------|------|
| 同天多个迁移 | 递增序列号 | V20260410.001, V20260410.002 |
| 跨天迁移 | 使用新日期 | V20260410.003, V20260411.001 |
| 紧急修复 | 使用当天日期 + 新序列 | V20260410.004__fix_null_constraint |
| 跨环境同步 | 版本全局唯一 | 所有环境共享版本序列 |

#### 2.2.3 版本冲突预防

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│                        Version Conflict Prevention                               │
└─────────────────────────────────────────────────────────────────────────────────┘

问题场景:
  开发者 A (2026-04-10)        开发者 B (2026-04-10)
       │                            │
       ▼                            ▼
  V20260410.001__aaa.sql       V20260410.001__bbb.sql  ← 冲突!
       │                            │
       ▼                            ▼
  提交到 main                    提交到 main

预防机制:
┌─────────────────────────────────────────────────────────────────┐
│  CI 阶段版本检查                                                  │
│  ├── 检查新迁移版本号是否唯一                                     │
│  ├── 检查版本号是否连续（允许 gaps，但告警）                        │
│  ├── 检查是否有重复 checksum                                      │
│  └── 检查版本是否大于当前最大版本                                  │
└─────────────────────────────────────────────────────────────────┘

解决方案:
1. Git 钩子预检查 → 提交前验证版本号
2. CI 阶段校验 → 合并前拦截冲突
3. 开发规范 → 分支同步后重新生成版本号
```

### 2.5 回滚策略 (Rollback Strategy)

#### 2.5.1 回滚类型分类

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│                           Rollback Strategy Matrix                               │
└─────────────────────────────────────────────────────────────────────────────────┘

                    可逆性 (Reversibility)
                    高 ←────────────────→ 低
                ┌─────────┬─────────┬─────────┐
                │         │         │         │
     低         │  Type A │  Type B │  Type C │
     风险       │  简单   │  中等   │  复杂   │
                │  DROP   │  ALTER  │  数据   │
                ├─────────┼─────────┼─────────┤
     中         │  Type D │  Type E │  Type F │
     风险       │  索引   │  约束   │  类型   │
                │  删除   │  移除   │  变更   │
                ├─────────┼─────────┼─────────┤
     高         │  Type G │  Type H │  Type I │
     风险       │  视图   │  存储   │  数据   │
                │  重建   │  过程   │  迁移   │
                │         │         │         │
                └─────────┴─────────┴─────────┘
```

#### 2.5.2 各类型回滚方案

| 类型 | 变更 | 回滚方案 | 停机要求 | 示例 |
|------|------|---------|---------|------|
| **Type A** | 新建表 | DROP TABLE | 无 | 删除新表 |
| **Type B** | 加字段 | 标记废弃 + 延迟删除 | 无 | 先标记，后清理 |
| **Type C** | 删字段 | 从备份恢复 | 是 | 数据恢复 |
| **Type D** | 加索引 | DROP INDEX | 无 | 删除索引 |
| **Type E** | 加约束 | ALTER DROP CONSTRAINT | 低 | 移除约束 |
| **Type F** | 改类型 | 双写迁移回滚 | 是 | 复杂回滚 |
| **Type G** | 新建视图 | DROP VIEW | 无 | 删除视图 |
| **Type H** | 存储过程 | 恢复旧版本 | 低 | 版本替换 |
| **Type I** | 数据迁移 | 反向迁移脚本 | 是 | 数据回滚 |

#### 2.5.3 回滚脚本模板

```sql
-- ============================================================================
-- Flyway Rollback Script
-- ============================================================================
-- Original:   V20260410.001__add_phone_column.sql
-- Rollback:   R20260410.001__remove_phone_column.sql
-- Reason:     回滚条件触发（业务需求变更/性能问题）
-- Downtime:   No
-- Impact:     Low
-- ============================================================================

START TRANSACTION;

-- Step 1: 验证回滚条件
SELECT COUNT(*) INTO @phone_count FROM users WHERE phone IS NOT NULL;
-- 如果有数据，需要先处理（通知用户/迁移数据/删除）

-- Step 2: 执行回滚
ALTER TABLE users DROP COLUMN phone;

-- Step 3: 清理相关索引（如果有）
-- DROP INDEX IF EXISTS idx_users_phone ON users;

-- Step 4: 记录回滚
INSERT INTO migration_metadata (version, executed_at, status, notes)
VALUES ('R20260410.001', NOW(), 'COMPLETED', 'Rollback of phone column');

COMMIT;
```

## 三、零停机迁移策略 (Zero-Downtime Migration Strategy)

### 3.1 零停机迁移架构

零停机迁移的核心思想是通过渐进式变更，确保在迁移过程中服务始终可用。

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│                    Zero-Downtime Migration Architecture                          │
└─────────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────────┐
│ Phase 0: Preparation                                                            │
│ ┌─────────────────────────────────────────────────────────────────────────────┐ │
│ │ • Schema analysis (identify dependencies)                                   │ │
│ │ • Impact assessment (affected services)                                     │ │
│ │ • Rollback plan preparation                                                  │ │
│ │ • Monitoring dashboard setup                                                 │ │
│ └─────────────────────────────────────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────────────────────────────────────┘
                                    │
                                    ▼
┌─────────────────────────────────────────────────────────────────────────────────┐
│ Phase 1: Dual Write (双写模式)                                                  │
│ ┌─────────────────────────────────────────────────────────────────────────────┐ │
│ │ Application Layer:                                                           │ │
│ │ ┌──────────────┐     ┌──────────────┐                                      │ │
│ │ │ Write Old    │────▶│ Write New    │                                      │ │
│ │ │ Schema       │ AND │ Schema       │                                      │ │
│ │ └──────────────┘     └──────────────┘                                      │ │
│ │                                                                              │ │
│ │ • Both writes succeed → continue                                            │ │
│ │ • New write fails → log error, continue with old                            │ │
│ │ • Old write fails → abort (critical)                                        │ │
│ └─────────────────────────────────────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────────────────────────────────────┘
                                    │
                                    ▼
┌─────────────────────────────────────────────────────────────────────────────────┐
│ Phase 2: Data Sync (增量同步)                                                   │
│ ┌─────────────────────────────────────────────────────────────────────────────┐ │
│ │ • Backfill historical data to new schema                                    │ │
│ │ • CDC captures ongoing changes                                              │ │
│ │ • Gradually sync until lag < threshold                                      │ │
│ └─────────────────────────────────────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────────────────────────────────────┘
                                    │
                                    ▼
┌─────────────────────────────────────────────────────────────────────────────────┐
│ Phase 3: Traffic Switch (流量切换)                                              │
│ ┌─────────────────────────────────────────────────────────────────────────────┐ │
│ │ Step 1: Read from new schema (10% traffic)                                   │ │
│ │ Step 2: Read from new schema (50% traffic)                                   │ │
│ │ Step 3: Read from new schema (100% traffic)                                  │ │
│ │ Step 4: Stop writing to old schema                                          │ │
│ └─────────────────────────────────────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────────────────────────────────────┘
                                    │
                                    ▼
┌─────────────────────────────────────────────────────────────────────────────────┐
│ Phase 4: Cleanup (清理)                                                         │
│ ┌─────────────────────────────────────────────────────────────────────────────┐ │
│ │ • Remove old schema columns/tables                                          │ │
│ │ • Archive old data                                                           │ │
│ │ • Update documentation                                                       │ │
│ └─────────────────────────────────────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────────────────────────────────────┘
```

```
│         oldSchemaResult = db_old.save(user)                                      │
│                                                                                  │
│         if dualWriteEnabled:                                                     │
│             try:                                                                 │

│             // 部分流量读新 Schema                                                 │
│             return db_new.findById(id)                                           │
│                                                                                  │
│         // 默认读旧 Schema                                                         │
│         return db_old.findById(id)                                               │
│                                                                                  │
```

### 5.3 分批迁移脚本模板

```sql
-- ============================================================================
-- 大数据量表分批迁移脚本
-- 表：orders (50,000,000 行)
-- 策略：按 ID 范围分批，每批 5,000,000 行
-- ============================================================================

-- 分批配置
SET @batch_size = 5000000;
SET @delay_seconds = 60;

-- 获取 ID 范围
SELECT MIN(id) INTO @min_id FROM orders;
SELECT MAX(id) INTO @max_id FROM orders;

-- 分批迁移存储过程
DELIMITER $$

CREATE PROCEDURE migrate_orders_in_batches()
BEGIN
    DECLARE current_id INT DEFAULT @min_id;
    DECLARE batch_count INT DEFAULT 0;
    
    WHILE current_id <= @max_id DO
        -- 执行本批次迁移
        INSERT INTO orders_new
        SELECT * FROM orders
        WHERE id >= current_id AND id < current_id + @batch_size;
        
        -- 记录进度
        INSERT INTO migration_progress (batch_id, migrated_rows, timestamp)
        VALUES (batch_count, ROW_COUNT(), NOW());
        
        -- 更新进度
        SET current_id = current_id + @batch_size;
        SET batch_count = batch_count + 1;
        
        -- 限流等待
        DO SLEEP(@delay_seconds);
    END WHILE;
END$$

DELIMITER ;

-- 执行迁移
CALL migrate_orders_in_batches();
```

```
│ SELECT MD5(CONCAT_WS(',', id, column1, column2, ...)) AS row_checksum           │
│ FROM table_name                                                                  │
│ GROUP BY id;                                                                     │
│                                                                                  │
│ 优点：精确到行级别                                                                │
│ 缺点：计算开销大，不适合超大表                                                    │
└─────────────────────────────────────────────────────────────────────────────────┘

方法 2: CRC32 校验和 (适用于快速比对)
┌─────────────────────────────────────────────────────────────────────────────────┐
│ SELECT SUM(CRC32(CONCAT_WS(',', id, column1, column2))) AS table_checksum       │
│ FROM table_name;                                                                 │
│                                                                                  │
│ 优点：计算快速                                                                   │
│ 缺点：碰撞概率略高                                                                │
└─────────────────────────────────────────────────────────────────────────────────┘

方法 3: 分块校验和 (适用于大表)
┌─────────────────────────────────────────────────────────────────────────────────┐
│ -- 按 ID 范围分块计算校验和                                                       │
│ SELECT                                                                          │
│     FLOOR(id / 1000000) AS block_id,                                           │
│     COUNT(*) AS row_count,                                                      │
│     SUM(CRC32(CONCAT_WS(',', id, col1, col2))) AS block_checksum               │
│ FROM table_name                                                                 │
│ GROUP BY block_id;                                                              │
│                                                                                  │
│ 优点：可定位具体不一致块                                                          │
│ 缺点：需要额外存储校验结果                                                        │
└─────────────────────────────────────────────────────────────────────────────────┘

方法 4: pt-table-checksum (Percona Toolkit)
┌─────────────────────────────────────────────────────────────────────────────────┐
│ $ pt-table-checksum \                                                           │
│     --host=master \                                                             │
│     --replicate=percona.checksums \                                             │
│     --databases=orion_prod \                                                    │
│     --tables=users,orders \                                                     │
│     --chunk-size=10000 \                                                        │
│     --max-lag=30s                                                                │
│                                                                                  │
│ 优点：专业工具，自动分块，支持从库校验                                            │
│ 缺点：需要安装工具，配置复杂                                                      │
└─────────────────────────────────────────────────────────────────────────────────┘
```

### 6.4 抽样对比策略

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│                           Sampling Verification Strategy                         │
└─────────────────────────────────────────────────────────────────────────────────┘

抽样方法:
┌─────────────────────────────────────────────────────────────────────────────────┐
│ 1. 随机抽样 (Random Sampling)                                                   │
│    SELECT * FROM table_name ORDER BY RAND() LIMIT 1000;                         │
│    适用场景：数据分布均匀                                                         │
│                                                                                  │
│ 2. 分层抽样 (Stratified Sampling)                                               │
│    -- 按状态分层                                                                 │
│    SELECT * FROM orders WHERE status = 'pending' LIMIT 100;                     │
│    SELECT * FROM orders WHERE status = 'completed' LIMIT 100;                   │
│    SELECT * FROM orders WHERE status = 'cancelled' LIMIT 100;                   │
│    适用场景：数据有明显分类                                                       │
│                                                                                  │
│ 3. 边界抽样 (Boundary Sampling)                                                 │
│    -- 抽样最小/最大 ID 的行                                                        │
│    SELECT * FROM table_name WHERE id = (SELECT MIN(id) FROM table_name);        │
│    SELECT * FROM table_name WHERE id = (SELECT MAX(id) FROM table_name);        │
│    适用场景：检测边界问题                                                         │
│                                                                                  │
│ 4. 关键数据抽样 (Critical Data Sampling)                                        │
│    -- 抽样 VIP 用户、大额订单等关键数据                                             │
│    SELECT * FROM users WHERE user_type = 'vip';                                 │
│    SELECT * FROM orders WHERE amount > 10000;                                   │
│    适用场景：核心业务数据                                                         │
└─────────────────────────────────────────────────────────────────────────────────┘

抽样验证检查清单:
┌─────────────────────────────────────────────────────────────────────────────────┐
│ □ 样本量足够 (至少 1000 行或 1%)                                                   │
│ □ 覆盖所有数据分类                                                                │
│ □ 包含边界值                                                                     │
│ □ 包含关键业务数据                                                                │
│ □ 新旧数据逐字段比对                                                              │
│ □ 记录不一致详情                                                                  │
└─────────────────────────────────────────────────────────────────────────────────┘
```

### 7.2 向后兼容设计原则

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│                           Backward Compatibility Principles                      │
└─────────────────────────────────────────────────────────────────────────────────┘

核心原则:
┌─────────────────────────────────────────────────────────────────────────────────┐
│                                                                                 │
│  1. 扩展优先 (Expand First)                                                     │
│     ┌─────────────────────────────────────────────────────────────────────┐    │
│     │ 正确做法：先添加新字段，保持旧字段                                   │    │
│     │ ALTER TABLE users ADD COLUMN phone_new VARCHAR(20);                  │    │
│     │ → 代码支持双读 → 数据迁移 → 删除旧字段                               │    │
│     └─────────────────────────────────────────────────────────────────────┘    │
│                                                                                 │
│  2. 禁止破坏性变更 (No Breaking Changes)                                        │
│     ┌─────────────────────────────────────────────────────────────────────┐    │
│     │ 错误做法：直接删除/修改现有字段                                       │    │
│     │ ALTER TABLE users DROP COLUMN phone;  -- 禁止!                      │    │
│     │ ALTER TABLE users MODIFY COLUMN email INT;  -- 禁止!                │    │
│     └─────────────────────────────────────────────────────────────────────┘    │
│                                                                                 │
│  3. 默认值策略 (Default Value Strategy)                                         │
│     ┌─────────────────────────────────────────────────────────────────────┐    │
│     │ 新增字段必须有默认值或允许 NULL                                       │    │
│     │ ALTER TABLE users ADD COLUMN notification_enabled BOOLEAN DEFAULT TRUE;│    │
│     └─────────────────────────────────────────────────────────────────────┘    │
│                                                                                 │
│  4. 双写过渡 (Dual Write Transition)                                            │
│     ┌─────────────────────────────────────────────────────────────────────┐    │
│     │ 字段变更前后的双写过渡期至少 24 小时                                     │    │
│     │ 确保新旧代码可同时正常运行                                            │    │
│     └─────────────────────────────────────────────────────────────────────┘    │
│                                                                                 │
└─────────────────────────────────────────────────────────────────────────────────┘
```

### 10.1 术语表

| 术语 | 定义 |
|------|------|
| **Flyway** | 数据库版本控制工具，管理迁移脚本的执行 |
| **CDC** | Change Data Capture，变更数据捕获 |
| **双写 (Dual Write)** | 同时写入新旧两套 Schema 的迁移策略 |
| **零停机 (Zero-Downtime)** | 迁移期间服务保持可用 |
| **向后兼容 (Backward Compatible)** | 新变更不破坏旧代码的正常运行 |
| **Saga** | 分布式事务模式，通过补偿操作实现最终一致性 |
| **pt-table-checksum** | Percona Toolkit 的表校验工具 |
| **RTO** | Recovery Time Objective，恢复时间目标 |
| **RPO** | Recovery Point Objective，恢复点目标 |
| **binlog** | MySQL 二进制日志，记录所有数据变更 |
