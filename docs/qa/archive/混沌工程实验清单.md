## 1. 概述

### 1.1 混沌工程目标

通过受控的故障注入实验，验证 Orion 平台的韧性、自愈能力和故障恢复机制。

### 1.2 实验原则

| 原则 | 说明 |
|------|------|
| 生产环境对等 | 实验环境应尽可能模拟生产配置 |
| 最小爆炸半径 | 实验影响范围可控，可快速回滚 |
| 可中止 | 任何实验可随时中止 |
| 可观测 | 实验过程完整监控和记录 |
| 渐进式 | 从单点故障到系统级故障逐步升级 |

### 1.3 实验成熟度等级

```
Level 1: 基础实验 (当前 Phase 2)
├── 单点故障注入
├── 非核心服务
└── 非高峰期执行

Level 2: 进阶实验 (Phase 3)
├── 多点并发故障
├── 核心服务
└── 任意时间执行

Level 3: 自动化实验 (Phase 4)
├── 持续混沌实验
├── 生产环境
└── 无人值守自动执行
```

## 2. 实验分类

### 2.1 实验分类矩阵

| 分类 | 实验对象 | 故障类型 | 预期验证 |
|------|---------|---------|---------|
| **基础设施层** | K8s 节点/Pod/网络 | 节点故障、网络延迟、DNS 故障 | 服务迁移、负载均衡 |

## 3. 实验详细清单

### 3.1 基础设施层实验

#### EXP-INFRA-01: Pod 随机终止

| 属性 | 值 |
|------|-----|
| 实验 ID | EXP-INFRA-01 |
| 实验名称 | Pod 随机终止 |
| 实验对象 | 核心服务 Pod |
| 注入方式 | `kubectl delete pod --force` |
| 爆炸半径 | 单个 Pod |
| 执行频率 | 每周 1 次 |

**实验步骤**：
```bash
# 1. 选择目标 Pod（非生产高峰期）
TARGET_POD=$(kubectl get pods -n orion -l app=pipeline-service -o jsonpath='{.items[0].metadata.name}')

# 2. 记录实验前状态
kubectl top pod $TARGET_POD -n orion > /tmp/pre_experiment.log

# 3. 终止 Pod
kubectl delete pod $TARGET_POD -n orion --force --grace-period=0

# 4. 监控服务恢复
kubectl rollout status deployment/pipeline-service -n orion --timeout=300s

# 5. 验证服务可用性
curl -s https://orion.internal/api/v1/health | jq .status
```

**预期结果**：
- K8s 自动重启 Pod（< 30 秒）
- 服务无感知（错误率 < 0.1%）
- HPA 根据负载调整副本数

**成功标准**：
- ✅ Pod 在 60 秒内恢复 Running 状态
- ✅ 服务错误率 < 1%
- ✅ 无用户投诉

#### EXP-INFRA-02: 节点故障模拟

| 属性 | 值 |
|------|-----|
| 实验 ID | EXP-INFRA-02 |
| 实验名称 | K8s 节点故障 |
| 实验对象 | K8s Worker 节点 |
| 注入方式 | `kubectl cordon + drain` |
| 爆炸半径 | 单节点所有 Pod |
| 执行频率 | 每月 1 次 |

**实验步骤**：
```bash
# 1. 选择非关键节点
TARGET_NODE=$(kubectl get nodes | grep worker | awk '{print $1}' | shuf -n 1)

# 2. 标记节点不可调度
kubectl cordon $TARGET_NODE

# 3. 驱逐 Pod
kubectl drain $TARGET_NODE --ignore-daemonsets --delete-emptydir-data --timeout=300s

# 4. 验证 Pod 在其他节点重建
kubectl get pods -o wide | grep -v $TARGET_NODE

# 5. 恢复节点
kubectl uncordon $TARGET_NODE
```

**预期结果**：
- Pod 自动迁移到其他节点（< 2 分钟）
- 服务无中断
- 节点恢复后自动加入调度池

#### EXP-INFRA-03: 网络延迟注入

| 属性 | 值 |
|------|-----|
| 实验 ID | EXP-INFRA-03 |
| 实验名称 | Pod 间网络延迟 |
| 实验对象 | 服务间通信 |
| 注入方式 | `tc netem delay` |
| 爆炸半径 | 指定服务 Pod |
| 执行频率 | 每双周 1 次 |

**实验步骤**：
```bash
# 使用 Chaos Mesh 注入网络延迟
apiVersion: chaos-mesh.org/v1alpha1
kind: NetworkChaos
metadata:
  name: network-delay-experiment
  namespace: orion
spec:
  action: delay
  mode: one
  selector:
    labelSelectors:
      app: pipeline-service
  delay:
    latency: 200ms  # 注入 200ms 延迟
    jitter: 50ms
  duration: 5m
```

**预期结果**：
- 服务间调用延迟增加
- 熔断器可能触发
- 错误率轻微上升但服务不中断
