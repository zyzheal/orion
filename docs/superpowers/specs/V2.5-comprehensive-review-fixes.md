# V2.5 补丁：综合评估修复 — 代码库资产校正 + 双层防幻觉

> **版本**: V2.5
> **触发原因**: 逐行验证代码库后发现上一轮评估存在关键遗漏（handler-registry 模块误判为不存在），且防幻觉机制缺少后端状态校验层

## 二、双层防幻觉机制（替代单层 Link Verifiability）

### 2.1 原方案缺陷

V2.2 的 Link Verifiability Engine 仅验证**前端路由存在性**（3 层：路由/交互模式/Action），但**没有验证后端 API 状态**。当系统发生以下变更时，RAG 仍可能返回已失效的 API：

| 场景 | 前端路由状态 | 后端 API 状态 | 原方案行为 | 用户后果 |
|------|-------------|-------------|-----------|---------|
| API 下线（代码删除但前端未同步） | ✅ 路由存在 | ❌ API 已删除 | 返回可点击链接 → 404 | 用户点击后失败 |
| API 禁用（`status='disabled'`） | ✅ 路由存在 | ⚠️ 已禁用 | 返回可点击链接 → 无权限 | 用户操作被拒 |
| 功能回滚（API 版本回退） | ✅ 路由存在 | ❌ 新参数已回退 | 返回过时参数说明 | 用户按错误参数操作 |

### 2.3 Layer A 实现（后端状态校验器）

```go
package verifier

import (
    "context"
    "database/sql"
)

// BackendVerifier 在 RAG 答案返回前，实时校验每个 API 引用的后端状态
type BackendVerifier struct {
    db *sql.DB
}

// VerificationResult 单个 API 节点的后端校验结果
type VerificationResult struct {
    EntityID       string  `json:"entity_id"`
    Status         string  `json:"status"` // active / degraded / removed
    HandlerStatus  string  `json:"handler_status,omitempty"`
    DegradedReason string  `json:"degraded_reason,omitempty"`
}

// Verify 对单个 API 节点执行后端状态校验
func (v *BackendVerifier) Verify(ctx context.Context, tenantID, domain, name string) VerificationResult {
    var handlerStatus string
    err := v.db.QueryRowContext(ctx,
        `SELECT status FROM handler_registry_entries
         WHERE tenant_id = $1 AND domain = $2 AND name = $3`,
        tenantID, domain, name,
    ).Scan(&handlerStatus)

    if err == sql.ErrNoRows {
        return VerificationResult{
            Status:         "removed",
            DegradedReason: "api_not_registered",
        }
    }
    if err != nil {
        return VerificationResult{
            Status:         "degraded",
            DegradedReason: "verification_error",
        }
    }

    switch handlerStatus {
    case "active":
        return VerificationResult{Status: "active"}
    case "disabled":
        return VerificationResult{
            Status:         "degraded",
            HandlerStatus:  "disabled",
            DegradedReason: "api_disabled",
        }
    default:
        return VerificationResult{
            Status:         "degraded",
            HandlerStatus:  handlerStatus,
            DegradedReason: "unknown_status",
        }
    }
}

// VerifyBatch 批量校验（单次 SQL，减少查询次数）
func (v *BackendVerifier) VerifyBatch(ctx context.Context, tenantID string, apis []APICheck) []VerificationResult {

    // WHERE tenant_id=$1 AND (domain, name) IN (($2,$3), ($4,$5), ...)

    // ...
}

type APICheck struct {

    Name   string
}
```

### 2.4 索引一致性保证（双层索引策略）

```
┌─────────────────────────────────────────────────────────────────┐
│ rag_knowledge_nodes 表新增字段（支持 Layer A 离线快速校验）        │
│                                                                  │
│ ALTER TABLE rag_knowledge_nodes                                  │
│   ADD COLUMN backend_status VARCHAR(20) DEFAULT 'active',       │
│   ADD COLUMN backend_verified_at TIMESTAMPTZ,                    │
│   ADD COLUMN handler_domain VARCHAR(100),                        │
│   ADD COLUMN handler_name VARCHAR(100);                          │
│                                                                  │
│ -- 对于非 API 节点（runbook/db_table 等），backend_status 始终为   │
│ -- 'n/a'，不参与后端状态校验                                       │
└─────────────────────────────────────────────────────────────────┘

增量同步（每小时）负责维护 backend_status 字段:
  1. 对每个 api_endpoint 节点，查询 handler_registry_entries
  2. 更新 backend_status / backend_verified_at
  3. 已删除的 API → backend_status='removed' → 检索时 WHERE backend_status != 'removed'

实时校验（每次提问）作为兜底:
  Layer A 在检索后、答案生成前再次查询 handler_registry_entries
  即使增量同步延迟，实时校验也能阻止过时信息返回
```

### 2.5 回滚场景的完整链路

```
运维执行: 回滚 pipeline 模块（从 v2.3.1 回退到 v2.2.0）
    │
    ├── handler-registry 自动响应:
    │   └── v2.3.1 独有的 POST /pipeline/:id/schedule → status 变更为 'disabled'
    │       或 DELETE 该条目
    │
    ├── 用户提问"如何调度流水线":
    │   ├── Hybrid Search 返回候选:
    │   │   └── api_endpoint: POST /pipeline/:id/schedule (node.backend_status='active')
    │   │       ← 增量同步尚未更新（在 1 小时窗口内）
    │   │
    │   ├── Layer A 实时校验:
    │   │   SELECT status FROM handler_registry_entries
    │   │   WHERE domain='pipeline' AND name='schedule'
    │   │   → 返回: status='disabled'（或无记录）
    │   │
    │   ├── Layer A 过滤结果:
    │   │   → 该节点标记为 removed
    │   │   → 从上下文移除
    │   │
    │   └── LLM 生成答案:
    │       "Orion 当前不支持流水线调度功能。你可以：
    │        [查看流水线管理页面] [查看操作手册]"
    │       → 不包含已回滚的 schedule API
    │       → 用户不看到失效链接
    │
    └── 增量同步（下一次执行时）:
        └── 更新节点 backend_status='removed'
            └── 下次检索时直接 WHERE backend_status != 'removed' 过滤
                （不再需要实时校验）
```

**时间窗口分析**:

| 阶段 | 延迟 | 防幻觉保障 |
|------|------|-----------|
| 回滚执行 → handler-registry 状态变更 | < 1s | 实时（API 调用） |
| handler-registry 状态变更 → 用户提问 | 任意时间 | **Layer A 实时校验**（< 2ms 查询） |
| handler-registry 状态变更 → 索引更新 | < 1h | 增量同步兜底（非实时路径已不返回） |

**结论**: 回滚后**立即**（0 秒）就能通过 Layer A 实时校验阻止过时信息返回，不依赖增量同步的 1h 窗口。

### 3.3 handler-registry 的 `config` 字段利用

`HandlerRegistryEntry.config` 为 `map[string]interface{}`（JSONB），可直接用于 RAG 元数据存储：

## 四、§3 检索管道修正

### 4.1 BM25 层：基于 semantic-search 扩展

原设计假定 BM25 需从零实现。实际 `semantic-search` 模块已存在，在其 `Search` 方法基础上扩展：

```go
// 原实现 (semantic-search/repository.go:26)
func (r *SemanticSearchRepository) Search(ctx context.Context, query string, topK int, filters string) {
    // 当前: ILIKE 模糊匹配
    // WHERE title ILIKE '%' || $1 || '%' OR content ILIKE '%' || $1 || '%'
}

// 扩展后: 替换 ILIKE 为 to_tsvector + GIN 索引
func (r *SemanticSearchRepository) Search(ctx context.Context, query string, topK int, filters string) {
    // 扩展:
    // WHERE to_tsvector('simple', title || ' ' || content) @@ plainto_tsquery('simple', $1)
    //   AND (tenant_id = $2)
    // ORDER BY ts_rank(to_tsvector('simple', title || ' ' || content), plainto_tsquery('simple', $1)) DESC
    // LIMIT $3
}
```

所需数据库变更:
```sql
-- 在现有 semantic_search_results 表上增加 GIN 索引
CREATE INDEX idx_semantic_search_bm25 ON semantic_search_results
    USING GIN (to_tsvector('simple', title || ' ' || content));
```

```go
// 原实现: 向量存为 JSON
func (r *Repository) UpsertVector(ctx context.Context, tenantID, storeID string, vec []float64, meta map[string]string) {
    vectorJSON, _ := json.Marshal(vec)  // ❌ JSON 存储
    r.db.NamedExecContext(ctx,
        `INSERT INTO vector_record (store_id, vector, metadata) VALUES (:store_id, :vector, :metadata)`,
        map[string]interface{}{
            "store_id": storeID,
            "vector":   vectorJSON,  // JSON 无法做向量运算

// 改造后: 使用 pgvector VECTOR 类型
func (r *Repository) UpsertVector(ctx context.Context, tenantID, storeID string, vec []float64, meta map[string]string) {
    // 创建/获取 RAG 专用 store（如不存在则新建）
    var storeID = "rag-primary"

    // 使用 pgvector 原生类型
    r.db.NamedExecContext(ctx,
        `INSERT INTO vector_record (store_id, vector, metadata)
         VALUES (:store_id, :vector::vector, :metadata)
         ON CONFLICT (store_id, metadata->>'id') DO UPDATE SET vector = EXCLUDED.vector`,
        map[string]interface{}{
            "store_id": storeID,
```

### 4.3 LLM 推理层：新建方案

`llm` 模块是 Trace（调用追踪），不可用于推理。新建独立 LLM Gateway：

```
新建模块: internal/llm-gateway/

职责:
  • 统一的 LLM API 抽象层
  • 支持多模型路由（Claude / GPT / 开源模型）
  • 流式输出（SSE）
  • 成本追踪（与现有 llm-trace 模块集成）

核心接口:
  Chat(ctx, request) → (response, error)        -- 同步调用

与现有 llm 模块的关系:
  llm-gateway 调用 LLM API → llm 模块记录 Trace → llm-trace 表
  即: gateway 负责推理，llm 负责追踪，两者解耦
```
