# V2.6 补丁：大厂专家二次评审修复

> **版本**: V2.6
> **触发原因**: 两轮专家评审发现 6 个 P0 漏洞（3 个架构 + 3 个安全），当前双层防幻觉机制存在系统性缺口
> **评审专家**: AIGC 架构师 / 安全运维架构师
> **核心原则**: 防幻觉必须覆盖"上下文层 + 答案层 + 运行时层"三层，不能仅依赖检索前过滤

## 二、P0 修复方案

### 2.1 P0-1 修复：新增 Layer C（答案输出层校验）

**问题根因**: Layer A/B 仅过滤检索节点，LLM 可在答案自由文本中凭预训练知识提及不在白名单中的 API。

**解决方案**: 答案生成后，对输出文本做 API 引用扫描 + 白名单比对。

```go
package verifier

import "regexp"

var apiPathPattern = regexp.MustCompile(`(/api/v\d+/\S+|POST\s+\S+|GET\s+\S+)`)

// LayerCAnswerVerifier 对 LLM 输出的自由文本做 API 引用校验
type LayerCAnswerVerifier struct {
    allowedAPIs map[string]struct{} // Layer A 过滤后的白名单 API 集合
}

// VerifyAnswer 扫描答案文本，提取所有 API 引用并与白名单比对
func (v *LayerCAnswerVerifier) VerifyAnswer(answer string) VerifiedAnswer {
    matches := apiPathPattern.FindAllString(answer, -1)
    var violations []string
    var sanitized string

    for _, match := range matches {
        if _, ok := v.allowedAPIs[match]; !ok {
            violations = append(violations, match)
            // 替换为占位符，阻止不可信 API 出现在答案中
            sanitized = replaceInText(answer, match, "[该操作已不可用]")
        }
    }

    return VerifiedAnswer{
        Answer:     sanitized,
        Violations: violations,
        Safe:       len(violations) == 0,
    }
}

// VerifiedAnswer 校验结果
type VerifiedAnswer struct {
    Answer     string   `json:"answer"`
    Violations []string `json:"violations,omitempty"` // 被拦截的 API 引用
    Safe       bool     `json:"safe"`
}
```

**完整的三层防幻觉架构**:

```
检索阶段:
    Layer A: 后端状态校验（handler_registry.status 查询）
    Layer B: 前端路由校验（routes.tsx 存在性验证）
    │
    ▼
生成阶段:
    LLM 仅接收 Layer A + Layer B 过滤后的节点作为上下文
    Prompt 中强制注入 negative instruction:
    "以下内容不可推荐：{removed_list}"
    │
    ▼
输出阶段:
    Layer C: 答案文本 API 引用扫描（regex 提取 + 白名单比对）
    ├── Safe=true  → 正常返回
    └── Safe=false → 替换违规引用 + 记录审计日志
```

### 2.2 P0-2 修复：运行时健康检查

```go
package verifier

import (
    "context"
    "net/http"
    "time"
)

// RuntimeHealthChecker 在 Layer A 校验通过后，对 API 做轻量可达性探测
type RuntimeHealthChecker struct {
    httpClient *http.Client
}

func NewRuntimeHealthChecker() *RuntimeHealthChecker {
    return &RuntimeHealthChecker{
        httpClient: &http.Client{Timeout: 500 * time.Millisecond},
    }
}

// Check 对已注册 API 做 HTTP HEAD 探测（500ms 超时）
func (c *RuntimeHealthChecker) Check(ctx context.Context, apiURL string) RuntimeStatus {
    req, err := http.NewRequestWithContext(ctx, http.MethodHead, apiURL+"/health", nil)
    if err != nil {
        return RuntimeStatus{Reachable: false, Reason: "request_failed"}
    }
    resp, err := c.httpClient.Do(req)
    if err != nil || resp.StatusCode >= 500 {
        return RuntimeStatus{Reachable: false, Reason: "unreachable"}
    }
    return RuntimeStatus{Reachable: true}
}

// 在 Layer A 校验链中增加运行时检查
// Verify 流程: registry_status=active → health_check → final_status
//   registry_status=active + health_check=reachable → status=active
//   registry_status=active + health_check=unreachable → status=degraded (标记"服务暂时不可用")
//   registry_status=disabled → status=removed
//   registry 无记录 → status=removed
```

### 2.3 P0-3 修复：handler_registry 投毒防御

```go
package verifier

import "os"

// RegistryPoisonGuard 对 handler_registry_entries 做交叉验证
type RegistryPoisonGuard struct {
    repoSourceRoot string // Go 源码根目录路径
}

// ValidateHandlerFile 验证 handler_file 字段指向的文件在源码库中实际存在
func (g *RegistryPoisonGuard) ValidateHandlerFile(handlerFile string) bool {
    fullPath := g.repoSourceRoot + "/" + handlerFile
    _, err := os.Stat(fullPath)
    return err == nil // 文件存在 → 通过；文件不存在 → 可能是投毒
}

// VerifyEntry 完整的防投毒校验链
func (g *RegistryPoisonGuard) VerifyEntry(ctx context.Context, entry HandlerRegistryEntry) VerificationResult {
    // Step 1: Layer A 基础校验（status 检查）
    baseResult := VerifyBaseStatus(ctx, entry)
    if baseResult.Status == "removed" {
        return baseResult
    }

    // Step 2: handler_file 路径存在性校验（防投毒核心）
    handlerFile := entry.Config["handler_file"].(string)
    if !g.ValidateHandlerFile(handlerFile) {
        return VerificationResult{
            Status:         "degraded",
            DegradedReason: "handler_file_not_found", // 可能是投毒
        }
    }

    // Step 3: registered_by 审计（投毒溯源）
    // 记录: 谁在何时注册了此 handler
    // 如果 registered_by 不在白名单中（如 CI/CD bot），标记为 suspicious

    return VerificationResult{
        Status:        "active",
        Poisoned:      false,
        VerifiedChain: []string{"status_check", "file_existence", "auditor_check"},
    }
}
```

**三阶段防投毒校验**:

| 阶段 | 检查项 | 通过条件 | 失败后果 |
|------|--------|---------|---------|
| 1 | `status` 字段 | `status='active'` | removed |
| 2 | `handler_file` 路径存在 | 文件在源码库中存在 | degraded（疑似投毒） |
| 3 | `registered_by` 审计 | 注册者为可信来源（CI/CD bot） | suspicious（需人工审核） |

### 2.5 P0-5 修复：CDC 替代轮询

```go
package sync

import "github.com/jackc/pgx/v5"

// CDCConsumer 使用 PostgreSQL LISTEN/NOTIFY 实现零遗漏的增量同步
type CDCConsumer struct {
    conn *pgx.Conn
    notifyChan <-chan pgx.Notify
}

// Start 启动 LISTEN 监听，接收 handler_registry 表变更通知
func (c *CDCConsumer) Start(ctx context.Context) error {
    // 订阅 handler_registry_entries 表的变更通知
    _, err := c.conn.Exec(ctx, "LISTEN handler_registry_changes")
    if err != nil {
        return err
    }

    // 异步消费通知
    go func() {
        for {
            select {
            case <-ctx.Done():
                return
            case notify := <-c.notifyChan:
                // notify.Payload = 变更的 domain+name
                c.processChange(ctx, notify.Payload)
            }
        }
    }()

    return nil
}

// 在 handler-registry 的写入操作中增加 NOTIFY 触发器
// CREATE TRIGGER trg_handler_registry_notify
//   AFTER INSERT OR UPDATE OR DELETE ON handler_registry_entries
//   FOR EACH ROW EXECUTE FUNCTION notify_handler_registry_change();

// 函数实现:
// CREATE OR REPLACE FUNCTION notify_handler_registry_change()
// RETURNS TRIGGER AS $$
// BEGIN
//   PERFORM pg_notify('handler_registry_changes',
//     NEW.domain || ':' || NEW.name || ':' || NEW.status);
//   RETURN NEW;
// END;
// $$ LANGUAGE plpgsql;
```

**CDC vs 轮询对比**:

| 维度 | 轮询（原方案） | CDC LISTEN/NOTIFY（修复后） |
|------|---------------|---------------------------|
| 延迟 | 最高 1h | < 10ms（实时通知） |
| 数据竞争 | 有（检查→执行窗口） | 无（数据库触发器保证） |
| 遗漏风险 | 有（并发写入） | 无（PostgreSQL 事务保证） |
| 实现复杂度 | 低 | 中（需创建触发器 + LISTEN 连接） |
| 基础设施依赖 | 无 | PostgreSQL（已有） |

## 五、算法专家关键发现（P0 级别 SQL/分词错误）

### 5.1 P0-7: `ON CONFLICT` 语法错误

**问题**: V2.5 §4.2 的 `UpsertVector` 方法使用了非法语法：

```sql
-- ❌ 错误：PostgreSQL 不允许在 metadata->>'id' 表达式上直接定义冲突目标
ON CONFLICT (store_id, metadata->>'id') DO UPDATE ...
```

**修复**: 新增 `entity_id` 显式列作为唯一键，避免使用表达式：

```sql
-- 先扩展表结构
ALTER TABLE vector_record ADD COLUMN entity_id VARCHAR(500);

-- 创建唯一索引
CREATE UNIQUE INDEX uq_vector_record_entity
    ON vector_record(store_id, entity_id);

-- 正确的 Upsert SQL
INSERT INTO vector_record (store_id, entity_id, vector, metadata, tenant_id)
VALUES ($1, $2, $3::vector, $4, $5)
ON CONFLICT (store_id, entity_id)
DO UPDATE SET vector = EXCLUDED.vector, updated_at = NOW();
```

### 5.2 P0-8: HNSW 索引定义缺失

**问题**: V2.5 §4.2 仅提到"使用 HNSW 索引"但全文未给出 `CREATE INDEX ... USING hnsw` 语句。

**修复**: 补充完整的索引 DDL：

```sql
-- 向量索引（归一化向量使用内积）
CREATE INDEX idx_vector_record_embedding_ip
    ON vector_record
    USING hnsw (vector vector_ip_ops)
    WITH (m = 16, ef_construction = 64);

-- 非归一化向量使用 L2 距离
CREATE INDEX idx_vector_record_embedding_l2
    ON vector_record
    USING hnsw (vector vector_l2_ops)
    WITH (m = 16, ef_construction = 64);
```

**注意**: `<#>`（负内积）要求向量已归一化（`||vec|| = 1`），否则结果不等于余弦相似度。推荐方案：Upsert 时对向量做 L2 归一化，使用 `<#>` + `vector_ip_ops`。

### 5.3 P0-9: `to_tsvector('simple')` 对中文完全失效

**问题**: V2.5 §4.1 使用 `to_tsvector('simple', ...)` 作为 BM25 方案，但 `simple` 配置仅按空白/标点分词。中文文本无空格分隔，整段被当作一个 token：

```
"如何回滚流水线" → 1 个 token "如何回滚流水线"
搜索 "回滚" → 0 匹配（❌）
```

**严重度**: 致命。Orion 系统的 Runbook/Pandawiki 含大量中文内容，BM25 分支对中文检索完全失效，Hybrid Search 的 35% BM25 权重归零。

**修复方案**（按推荐顺序）:

```
方案 A（推荐）: 应用层 jieba 预分词
  在 Upsert 时将中文文本用 jieba 分词，以空格分隔后存入 title/content
  然后继续使用 to_tsvector('simple', ...)（simple 能正确分词空格分隔的文本）
  优点: 无需安装 PostgreSQL 扩展，零数据库依赖
  缺点: 需要 Go 端 jieba 绑定（gojieba 可用）

方案 B: pgroonga 全文引擎
  CREATE EXTENSION pgroonga;
  pgroonga 原生支持中文/日文分词
  优点: 数据库层解决，应用层无感
  缺点: 需要额外安装 pgroonga 扩展

方案 C: zhparser
  CREATE EXTENSION zhparser;
  支持 to_tsvector('zhcfg', ...) 的中文分词
  优点: 标准 PostgreSQL 接口
  缺点: 分词质量不如 jieba
```

**推荐方案 A（jieba 预分词）**，与当前轻量化的本地 ONNX 方向一致，无需安装数据库扩展。

### 5.4 P1: RRF 权重修正

**问题**: V2.5 §3 RRF 权重 `0.4 vector + 0.35 bm25 + 0.25 graph` 中，graph 占比 25% 过高。14600 节点的知识图谱数据稀疏（大量节点无边关联），graph 路径召回率低，高权重引入噪声。

**修复**:
```
修正后权重:
  Vector:  0.50  (↑)
  BM25:    0.35  (保持，待中文分词修复后可上调)
  Graph:   0.15  (↓ 从 0.25)
```
