# V2.4 补丁：AIGC 自反馈闭环 — 可量化验证设计

> **版本**: V2.4  
> **触发原因**: 当前系统零 RAG 反馈能力，👍👎 仅有 UI 无后端闭环  
> **核心原则**: 每次反馈必须在 24h 内可量化验证其对系统能力的提升

---

## 一、验证结果

系统搜索确认：当前 Orion 平台**不存在**任何 RAG 用户反馈机制。所有 `feedback` 匹配均为无关模块（alert-rule-engine evaluator、plugin marketplace rating 等）。

**结论**: 👍👎 从 0 到 1 构建，且必须设计可验证的自优化链路。

---

## 二、自反馈闭环架构（Feedback-Driven AIGC Self-Optimization）

### 2.1 核心数据流

```
用户反馈 (👍/👎)
    │
    ▼
┌─────────────────────────────────────────────────────────────────┐
│ Phase 1: 反馈采集 (实时, < 100ms)                                │
│                                                                  │
│ POST /api/v1/ai/agent/feedback                                   │
│ {                                                                 │
│   "feedback_token": "fb-xxx",                                    │
│   "rating": "positive" | "negative",                             │
│   "comment": "..."  (可选),                                      │
│   "corrected_answer": "..."  (可选, 仅👎时提供),                  │
│   "corrected_links": [...]  (可选, 用户修正链接)                  │
│ }                                                                 │
│                                                                  │
│ → 写入 rag_conversation_turns (feedback 字段)                    │
│ → 写入 rag_feedback_events (独立事件表，供下游消费)               │
│ → 返回 { accepted: true, action_preview: "已记录，正在优化" }   │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────────────────┐
│ Phase 2: 信号处理 (实时, < 1s)                                    │
│                                                                  │
│ 正向信号 (👍):                                                    │
│   1. 提升本轮检索到的所有节点的 relevance_boost (+0.05)           │
│      → 下次同类查询排名更高                                       │
│   2. 将 (query, answer, retrieved_nodes) 写入 semantic_cache    │
│      → 下次相似查询直接命中                                       │
│   3. 如果 corrected_answer 为空 → 使用原答案作为 ground_truth    │
│      → 扩充评估基准集                                             │
│   4. 提升答案中每个 citation 的 citation_weight (+0.02)          │
│      → 该来源权威性评分提升                                       │
│                                                                  │
│ 负向信号 (👎):                                                    │
│   1. 分类问题根源（LLM 轻量模型, < 500ms）:                      │
│      - stale_data:    答案过时                                     │
│      - wrong_answer:  答案错误                                     │
│      - incomplete:    答案不完整                                   │
│      - wrong_link:    链接不可用                                   │
│      - wrong_role:    权限判断错误                                 │
│      - capability_gap:功能不存在                                   │
│                                                                  │
│   2. 执行即时优化动作:                                            │
│      - 降低本轮检索节点 relevance_boost (-0.1)                   │
│      - 如果 corrected_answer 存在 → 写入 ground_truth            │
│      - 如果 corrected_links 存在 → 更新知识图谱节点               │
│      - 标记 affected_nodes 为 needs_review                        │
│                                                                  │
│   3. 创建优化追踪任务:                                           │
│      → rag_feedback_actions (异步处理队列)                        │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────────────────┐
│ Phase 3: 聚合分析 (每日, 凌晨 2:00)                               │
│                                                                  │
│ 1. 统计过去 24h 反馈:                                            │
│    - total / positive / negative / positive_rate                 │
│    - top_negative_categories (按问题类型)                         │
│    - top_negative_queries (被踩最多的问题)                        │
│    - top_negative_sources (导致最多次👎的知识节点)                 │
│                                                                  │
│ 2. 触发批量优化:                                                  │
│    - 同一节点被关联 👎 ≥ 3 次 → 标记 stale → 触发同步            │
│    - 同一领域 👎 ≥ 5 次 → 调整该领域检索策略 (Top-K +2)         │
│    - 同一链接 wrong_link ≥ 2 次 → 自动修复路由                   │
│    - 同一问题 capability_gap ≥ 3 次 → 创建功能需求工单           │
│                                                                  │
│ 3. Ground Truth 自动扩充:                                        │
│    - 所有 👍 且无 corrected_answer → 加入 ground_truth          │
│    - 所有 👎 且 corrected_answer → 加入 ground_truth (待审核)    │
│    - 每周扩充 20-50 条                                           │
│                                                                  │
│ 4. 检索策略自适应:                                                │
│    - 计算各领域 positive_rate                                    │
│    - positive_rate < 50% 的领域 → 触发该领域索引重建              │
│    - BM25/Vector 权重按领域 positive_rate 动态调整               │
│                                                                  │
│ 5. 生成每日优化报告:                                             │
│    → POST /rag/eval/feedback-report                              │
│    → 推送到管理后台 + 飞书/钉钉                                   │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────────────────┐
│ Phase 4: 效果验证 (每周, 周期: 7天)                               │
│                                                                  │
│ 对比优化前后的指标:                                               │
│                                                                  │
│ ┌─────────────────────────────────────────────────────────────┐ │
│ │ 优化前 (Week N-1)            优化后 (Week N)               │ │
│ ├─────────────────────────────────────────────────────────────┤ │
│ │ positive_rate: 62%             positive_rate: 71% (+9pp)   │ │
│ │ P99 latency: 1.8s              P99 latency: 1.4s (-22%)    │ │
│ │ cache_hit_rate: 8%             cache_hit_rate: 18% (+10pp) │ │
│ │ avg_citations: 2.3             avg_citations: 2.8 (+22%)   │ │
│ │ hallucination_rate: 3.2%       hallucination_rate: 1.8%    │ │
│ │ ground_truth_size: 120         ground_truth_size: 156      │ │
│ └─────────────────────────────────────────────────────────────┘ │
│                                                                  │
│ 判定标准:                                                         │
│   • positive_rate 提升 ≥ 3pp → 自优化生效 ✅                     │
│   • positive_rate 提升 < 3pp → 需要人工干预 ⚠️                   │
│   • positive_rate 下降 → 回滚本周优化 ❌                         │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

## 三、数据库设计

### 3.1 反馈事件表

```sql
CREATE TABLE rag_feedback_events (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    feedback_token  VARCHAR(255) NOT NULL,
    conversation_id UUID REFERENCES rag_conversations(id),
    turn_id         UUID REFERENCES rag_conversation_turns(id),
    user_id         VARCHAR(255) NOT NULL,
    tenant_id       VARCHAR(255) NOT NULL,
    rating          VARCHAR(10) NOT NULL,  -- positive / negative
    comment         TEXT,
    corrected_answer TEXT,
    corrected_links JSONB,
    -- 关联的检索上下文快照
    query_text      TEXT NOT NULL,
    answer_text     TEXT,
    retrieved_nodes JSONB,
    citations       JSONB,
    -- 下游处理状态
    processed       BOOLEAN DEFAULT false,
    processed_at    TIMESTAMPTZ,
    created_at      TIMESTAMPTZ DEFAULT NOW()
);

CREATE INDEX idx_rag_feedback_time ON rag_feedback_events(created_at);
CREATE INDEX idx_rag_feedback_rating ON rag_feedback_events(rating);
CREATE INDEX idx_rag_feedback_tenant ON rag_feedback_events(tenant_id);
CREATE INDEX idx_rag_feedback_processed ON rag_feedback_events(processed) WHERE processed = false;
```

### 3.2 优化动作追踪表

```sql
CREATE TABLE rag_feedback_actions (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    event_id        UUID REFERENCES rag_feedback_events(id),
    action_type     VARCHAR(50) NOT NULL,
       -- boost_node / demote_node / cache_answer / add_ground_truth
       -- / mark_stale / rebuild_source / fix_link / create_ticket
       -- / adjust_topk / adjust_weight
    target_type     VARCHAR(30),   -- node / source / link / domain / strategy
    target_id       VARCHAR(500),
    params          JSONB,
    status          VARCHAR(20) DEFAULT 'pending',  -- pending / applied / failed / rolled_back
    created_at      TIMESTAMPTZ DEFAULT NOW(),
    applied_at      TIMESTAMPTZ
);

CREATE INDEX idx_rag_actions_status ON rag_feedback_actions(status) WHERE status = 'pending';
CREATE INDEX idx_rag_actions_type ON rag_feedback_actions(action_type);
```

### 3.3 节点权重表

```sql
CREATE TABLE rag_node_weights (
    node_id     UUID PRIMARY KEY REFERENCES rag_knowledge_nodes(id),
    node_type   VARCHAR(30) NOT NULL,
    -- 正向信号累积
    positive_count    INT DEFAULT 0,
    positive_sum_boost NUMERIC(6,4) DEFAULT 0,
    -- 负向信号累积
    negative_count    INT DEFAULT 0,
    negative_sum_boost NUMERIC(6,4) DEFAULT 0,
    -- 最终权重（0.0 ~ 2.0，1.0 = 基准）
    relevance_weight  NUMERIC(3,2) DEFAULT 1.00,
    citation_weight   NUMERIC(3,2) DEFAULT 1.00,
    -- 状态标记
    needs_review      BOOLEAN DEFAULT false,
    stale_flag        BOOLEAN DEFAULT false,
    last_feedback_at  TIMESTAMPTZ,
    updated_at        TIMESTAMPTZ DEFAULT NOW()
);

CREATE INDEX idx_rag_weights_review ON rag_node_weights(needs_review) WHERE needs_review;
CREATE INDEX idx_rag_weights_stale ON rag_node_weights(stale_flag) WHERE stale_flag;
```

### 3.4 每日反馈统计表

```sql
CREATE TABLE rag_feedback_daily_stats (
    date                DATE PRIMARY KEY,
    tenant_id           VARCHAR(255),
    total_feedback      INT DEFAULT 0,
    positive_count      INT DEFAULT 0,
    negative_count      INT DEFAULT 0,
    positive_rate       NUMERIC(5,4),
    top_negative_categories JSONB,
       -- [{ category: "stale_data", count: 5 }, ...]
    top_negative_queries JSONB,
       -- [{ query: "...", count: 3 }, ...]
    top_negative_sources JSONB,
       -- [{ node_id: "...", count: 4 }, ...]
    actions_applied     INT DEFAULT 0,
    actions_pending     INT DEFAULT 0,
    actions_rolled_back INT DEFAULT 0,
    ground_truth_added  INT DEFAULT 0,
    created_at          TIMESTAMPTZ DEFAULT NOW()
);

CREATE INDEX idx_rag_stats_tenant ON rag_feedback_daily_stats(tenant_id);
```

### 3.5 周度优化效果表

```sql
CREATE TABLE rag_weekly_optimization (
    week_start          DATE PRIMARY KEY,
    -- 优化前基线 (Week N-1)
    baseline_positive_rate NUMERIC(5,4),
    baseline_p99_latency_ms INT,
    baseline_cache_hit_rate NUMERIC(5,4),
    baseline_hallucination_rate NUMERIC(5,4),
    baseline_ground_truth_size INT,
    -- 优化后 (Week N)
    current_positive_rate NUMERIC(5,4),
    current_p99_latency_ms INT,
    current_cache_hit_rate NUMERIC(5,4),
    current_hallucination_rate NUMERIC(5,4),
    current_ground_truth_size INT,
    -- 变化
    positive_rate_delta NUMERIC(5,4),
    optimization_verdict VARCHAR(20),  -- effective / needs_attention / rollback
    actions_this_week JSONB,
       -- [{ action_type, target, before_metric, after_metric }]
    created_at TIMESTAMPTZ DEFAULT NOW()
);
```

## 四、反馈分类引擎

### 4.1 轻量分类模型

```python
# 使用轻量模型 (或规则引擎) 对 👎 进行分类
# 输入: comment + query_text + answer_text + retrieved_nodes
# 输出: category

分类规则 (规则引擎 fallback):
  包含 "过时"/"过期"/"old"/"outdated" → stale_data
  包含 "错误"/"wrong"/"不正确"         → wrong_answer
  包含 "不完整"/"缺少"/"miss"          → incomplete
  包含 "打不开"/"404"/"不存在"          → wrong_link
  包含 "没权限"/"cannot"/"forbidden"   → wrong_role
  包含 "没有这个功能"/"不支持"          → capability_gap

LLM 分类 Prompt (首选):
===SYSTEM_START===
你是一个反馈分类器。将用户反馈分类为以下之一:
stale_data | wrong_answer | incomplete | wrong_link | wrong_role | capability_gap

输出纯类别名，不要任何其他文字。
===SYSTEM_END===

===CONTEXT_START===
用户问题: {query_text}
系统答案: {answer_text}
用户反馈: {comment}
用户修正: {corrected_answer}
===CONTEXT_END===
```

## 五、可量化验证的自优化实验

### 5.1 实验设计

```
实验周期: 4 周
对照组: 关闭自反馈闭环 (👍👎 仅记录不触发优化)
实验组: 开启自反馈闭环 (完整 Phase 1-4)

指标:
  主指标: positive_rate 变化
  次指标: P99 延迟 / cache_hit_rate / hallucination_rate / ground_truth_size

实验流程:
  Week 0: 建立基线 (收集 1 周无干预数据)
  Week 1-4: 实验组开启自反馈，对照组关闭
  每周末: 对比两组指标差异
  Week 4: 统计显著性检验 (t-test, p < 0.05)
```

### 5.2 预期效果模型

```
假设:
  • 日活 50 用户 × 3 次查询 = 150 次/天
  • 反馈率 15% = 22 次反馈/天
  • 其中 60% 正面 = 13 次👍/天, 40% 负面 = 9 次👎/天

Week 1 预期:
  • ground_truth 扩充: +91 条 (13👍 × 7天)
  • semantic_cache 新增: +130 条 (13👍 + 部分👎 with corrected_answer)
  • cache_hit_rate: 8% → 12% (+4pp)
  • positive_rate: 基线 62% → 65% (+3pp)

Week 2 预期:
  • 节点权重调整生效 (高👎节点降权, 高👍节点升权)
  • retrieval_quality 提升
  • positive_rate: 65% → 68% (+3pp)
  • hallucination_rate: 3.2% → 2.5% (-0.7pp)

Week 4 预期:
  • positive_rate: 62% → 75% (+13pp) ✅ 目标达成
  • P99 latency: 1.8s → 1.3s (-28%) ✅ 缓存命中提升
  • ground_truth: 120 → 280 (+160 条)
  • hallucination_rate: 3.2% → 1.5% (-1.7pp)

判定:
  positive_rate 提升 ≥ 10pp → 自反馈闭环有效 ✅
  positive_rate 提升 5-9pp → 部分有效，需调优参数 ⚠️
  positive_rate 提升 < 5pp → 需重新设计优化策略 ❌
```

### 5.3 回滚机制

```
如果某周 positive_rate 下降 > 2pp:
  1. 自动回滚本周所有 feedback_actions (status → rolled_back)
  2. 恢复节点权重到上周快照
  3. 清空本周新增的 semantic_cache 条目
  4. 恢复检索策略参数到上周值
  5. 生成回滚报告 → 通知管理员
  6. 触发人工审查: 为什么优化导致质量下降？

节点权重快照 (每周日自动备份):
  CREATE TABLE rag_node_weights_weekly_snapshot (
      snapshot_week DATE,
      node_id UUID,
      relevance_weight NUMERIC(3,2),
      citation_weight NUMERIC(3,2),
      created_at TIMESTAMPTZ DEFAULT NOW()
  );
```

## 六、防作弊与防滥用

| 风险 | 防护措施 |
|------|---------|
| **刷👍**（同一用户反复给同一答案👍） | 每 feedback_token 仅接受 1 次反馈；同一用户同一 query 24h 内仅计 1 次 |
| **恶意👎**（竞争对手降低系统评分） | 新注册用户 7 天内反馈权重 0.5x；企业 IP 段限制 |
| **反馈轰炸**（短时间大量反馈） | 每用户每分钟最多 10 次反馈；超过则 rate limit |
| **反馈伪造**（模拟 API 调用） | 反馈必须关联有效 feedback_token（仅真实回答才生成） |
| **负反馈滥用**（恶意填入 corrected_answer 污染 ground_truth） | corrected_answer 进入 ground_truth 前标记 `pending_review=true`，人工审核 48h 后生效 |

## 八、与 V2.2/V2.3 的关系

| 版本 | 能力 | 关系 |
|------|------|------|
| V2.2 | Link Verifiability + Feedback UI | V2.4 是 V2.2 的后端实现 |
| V2.3 | 架构修复 (租户隔离/降级/部署) | V2.4 依赖 V2.3 的 `rag_knowledge_nodes.tenant_id` |
| V2.4 | **本补丁** | 补齐从 UI 到优化的完整闭环 |

**依赖关系**: V2.2 (UI) → V2.4 (后端闭环) → 可量化验证自优化效果
