# V2.2 补丁：链接可执行性验证 + 反馈闭环优化

> **版本**: V2.2  
> **触发原因**: Demo 验证发现 3 个跳转入口中有 2 个路由不存在（`/infrastructure`、`/tickets/new`）、1 个功能不存在（`contact_team`）  
> **核心原则**: RAG 答案中的每个链接/操作必须是"可执行性验证通过"的真实系统入口

---

## 一、链接可执行性验证（Link Verifiability Engine）

### 1.1 问题描述

Demo 验证发现：
- `/infrastructure` → 路由不存在（真实路径是 `/iac`）
- `/tickets/new` → 路由不存在（新建工单是 Modal 弹窗，无独立路由）
- `contact_team` action → 系统中无对应功能实现

这些是 **LLM 幻觉链接**——看似合理但用户点击后 404 或无响应。

### 1.2 可执行性验证流程

```
RAG Agent 生成答案，包含 N 个 graph_links
    │
    ▼
┌─────────────────────────────────────────────────────────────────┐
│ Link Verifiability Engine                                        │
│                                                                  │
│ 对每个 graph_link 执行 3 层验证：                                 │
│                                                                  │
│ ── Layer 1: 路由存在性验证 ─────────────────────────────────     │
│   • 查询 rag_knowledge_nodes WHERE node_type='frontend_page'    │
│     AND entity_id = link.url                                     │
│   • 节点存在且 status='active' → 通过                            │
│   • 节点不存在 → 标记 invalid_route → 移除该链接                 │
│                                                                  │
│ ── Layer 2: 交互模式验证 ──────────────────────────────────     │
│   • 检查节点 metadata.interaction_mode:                          │
│     - "direct": 路由直达 → link.url 可直接跳转                   │
│     - "modal":  需触发页面内弹窗 → link.action = "open_modal"   │
│       示例: /tickets + action:open_modal → 打开 CreateTicketModal│
│     - "drawer": 需触发侧栏面板 → link.action = "open_drawer"    │
│     - "inline": 页面内操作 → link.action = "click_button"       │
│   • 根据 interaction_mode 生成正确的跳转指令                    │
│                                                                  │
│ ── Layer 3: Action 可执行性验证 ────────────────────────────     │
│   • 检查 link.action 对应的后端 handler 是否存在：               │
│     查询 handler_registry_entries WHERE name = action_name       │
│   • handler 存在且 status='active' → 标记 executable=true       │
│   • handler 不存在 → 标记 executable=false → 移除该链接         │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────────────────┐
│ 验证结果分类                                                       │
│                                                                  │
│ ✅ executable=true  → 保留，正常展示（主色按钮）                   │
│ ⚠️ executable=false → 标记为"无权限/不可用"（灰色禁用态）          │
│ ❌ invalid          → 从答案中完全移除，不展示                     │
│                                                                  │
│ 统计:                                                            │
│ • 移除的无效链接数 > 0 → 记录审计日志                            │
│ • 移除原因分类统计（invalid_route / no_handler / disabled）      │
└─────────────────────────────────────────────────────────────────┘
```

## 二、反馈闭环优化（Feedback-Driven Learning Loop）

### 2.1 问题描述

原设计 §15.3 仅定义了反馈 UI（👍👎 + 文本输入），但**缺少反馈如何驱动系统优化的数据流**。用户反馈后，系统应该：

1. 正面反馈 → 强化当前检索/生成策略
2. 负面反馈 → 诊断问题根源 → 触发优化动作

### 2.2 反馈数据流架构

```
用户反馈 (👍/👎 + 可选文本)
    │
    ▼
┌─────────────────────────────────────────────────────────────────┐
│ Feedback Ingestion Service                                       │
│                                                                  │
│ 1. 解析反馈:                                                     │
│    { feedback_token, rating, comment, corrected_answer, user_id }│
│                                                                  │
│ 2. 关联查询:                                                     │
│    通过 feedback_token 找到对应的 conversation_turn               │
│    获取: query / answer / retrieved_nodes / citations            │
│                                                                  │
│ 3. 写入反馈记录:                                                  │
│    rag_conversation_turns.feedback = positive/negative           │
│    rag_conversation_turns.feedback_text = comment                │
│    rag_feedback_actions 表记录优化动作                           │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
    │
    ├──▶ 正面反馈 → Positive Signal Processor
    │       │
    │       ├── 增加检索到的节点的 relevance_boost（+0.1）
    │       │     下次同类查询时这些节点排名更高
    │       │
    │       ├── 增加答案中引用来源的 citation_weight（+0.05）
    │       │     该来源的权威性评分提升
    │       │
    │       ├── 将 (query, answer) 对加入 semantic_cache
    │       │     下次相似查询直接命中缓存
    │       │
    │       └── 记录到 rag_eval_ground_truth（自动标记 verified=true）
    │             如果 corrected_answer 为空，使用原答案作为正确答案
    │
    └──▶ 负面反馈 → Negative Signal Processor
            │
            ├── Step 1: 问题分类
            │     使用轻量模型分析 comment，分类为:
            │     - stale_data:   答案过时/数据不准确
            │     - wrong_answer: 答案错误/引用错误
            │     - incomplete:   答案不完整/缺少关键步骤
            │     - wrong_link:   链接不可用/路由不存在
            │     - permission:   权限相关困惑
            │
            ├── Step 2: 诊断 + 优化动作
            │
            │     stale_data →
            │       • 标记相关 rag_knowledge_nodes 为 needs_review
            │       • 触发对应数据源的增量同步（/rag/index/sync/{source}）
            │       • 创建工单通知数据源维护者
            │
            │     wrong_answer →
            │       • 将 (query, corrected_answer) 加入 ground_truth
            │       • 标记当前检索策略对该 query 失效
            │       • 如果 corrected_answer 存在 → 用其更新 semantic_cache
            │
            │     incomplete →
            │       • 分析缺失信息对应的 node_type
            │       • 记录为 retrieval_gap（某类节点未被召回）
            │       • 调整该领域的 Top-K 参数
            │
            │     wrong_link →
            │       • 验证链接是否存在于 frontend_route_registry
            │       • 如果不存在 → 标记为 hallucinated_link → 删除
            │       • 如果存在但路由变更 → 更新节点 metadata
            │       • 如果功能不存在 → 记录为 capability_gap
            │
            │     permission →
            │       • 检查 RBAC 过滤是否正确执行
            │       • 如果是误过滤 → 修正权限规则
            │
            └── Step 3: 聚合分析（每日）
                    • 统计负面反馈 Top-10 查询主题
                    • 统计 retrieval_gap 按 node_type 分布
                    • 统计 hallucinated_link 按来源分布
                    • 生成每日反馈报告 → /rag/eval/feedback-report
```

### 2.3 反馈驱动的系统优化规则

| 反馈模式 | 系统响应 | 自动化程度 |
|---------|---------|-----------|
| 单条 👍 | 强化节点权重 + 缓存答案 | 全自动 |
| 单条 👎 + 纠正文 | 更新 ground_truth + 缓存修正答案 | 全自动 |
| 单条 👎 无文本 | 记录待分析 | 全自动（次日聚合） |
| 同一查询 3 次 👎 | 触发检索策略审查 | 半自动（生成诊断报告） |
| 同一节点 5 次关联 👎 | 标记节点 needs_review | 半自动（通知管理员） |
| 同一领域 10 次 👎 | 触发该领域索引重建 | 半自动（需确认） |
| 同一链接 3 次 wrong_link | 自动移除链接 + 修复路由 | 全自动 |
| 同一数据源 10 次 stale_data | 触发数据源全量同步 | 半自动（需确认） |

### 2.4 反馈表设计

```sql
-- 反馈动作追踪表
CREATE TABLE rag_feedback_actions (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    feedback_id     UUID NOT NULL REFERENCES rag_conversation_turns(id),
    action_type     VARCHAR(50) NOT NULL,
       -- boost_node / boost_citation / cache_answer / mark_stale
       -- / rebuild_source / remove_link / update_ground_truth
    target_type     VARCHAR(30),   -- node / citation / link / source / strategy
    target_id       VARCHAR(500),
    params          JSONB,
    status          VARCHAR(20) DEFAULT 'pending',  -- pending / applied / failed
    created_at      TIMESTAMPTZ DEFAULT NOW(),
    applied_at      TIMESTAMPTZ
);

-- 反馈聚合统计表（每日）
CREATE TABLE rag_feedback_daily_stats (
    date            DATE PRIMARY KEY,
    total_feedback  INT,
    positive_count  INT,
    negative_count  INT,
    positive_rate   NUMERIC(5,4),
    top_negative_categories JSONB,
       -- [{ category: "stale_data", count: 5, top_queries: [...] }]
    retrieval_gaps  JSONB,
       -- [{ node_type: "api_endpoint", gap_count: 3 }]
    actions_applied INT,
    actions_pending INT
);
```

### 2.5 反馈驱动的检索优化

```
每日反馈聚合后:

1. 检索策略自适应调优:
   • 如果某个领域的 retrieval_gap > 5 → 增加该领域的 Top-K（+2）
   • 如果某个 node_type 频繁出现在负面反馈中 → 降低其检索权重（-0.1）
   • 如果某类查询的 confidence 持续偏低 → 调整 BM25/Vector 权重

2. 知识库更新工单:
   • retrieval_gap 聚合 → 生成"缺失知识"报告
   • stale_data 聚合 → 生成"数据过期"报告
   • 报告推送至工单系统 → 人工审核后更新知识库

3. Ground Truth 集自动扩充:
   • 所有 👍 且无 corrected_answer 的查询 → 自动加入 ground_truth
   • 所有 👎 且有 corrected_answer 的查询 → 加入 ground_truth（标记需人工审核）
   • 每周 ground_truth 集自动扩充 20-50 条

4. Embedding 模型效果评估:
   • 对比不同 embedding_model 版本的反馈率
   • 如果新版本的 positive_rate 下降 > 5% → 自动回滚到旧版本
```

## 三、前端跳转实现规范

### 3.1 跳转指令协议

```json
// RAG 返回的 graph_link 标准化格式
{
  "label": "提交工单",
  "target": "/tickets",                    // 目标路由（必须存在）
  "node_type": "frontend_page",
  "interaction_mode": "modal",             // direct | modal | drawer | inline
  "action": "open_modal:CreateTicketModal", // 非 direct 模式时的具体操作
  "action_params": {                       // 操作参数（如预填表单数据）
    "title": "Istio mTLS 配置咨询",
    "category": "infrastructure"
  },
  "executable": true,
  "verified": true                         // 经过 Link Verifiability Engine 验证
}
```

### 3.2 前端跳转处理器

```tsx
// RAGFrontendLink.tsx - 标准化跳转组件
interface RAGLink {
  label: string;
  target: string;
  interaction_mode: 'direct' | 'modal' | 'drawer' | 'inline';
  action?: string;
  action_params?: Record<string, unknown>;
  executable: boolean;
  verified: boolean;
}

function RAGFrontendLink({ link }: { link: RAGLink }) {
  // 未经过验证的链接不渲染
  if (!link.verified) return null;

  // 不可执行的链接展示为禁用态
  if (!link.executable) {
    return <DisabledLink label={link.label} reason="无执行权限" />;
  }

  switch (link.interaction_mode) {
    case 'direct':
      return <Link href={link.target}>{link.label}</Link>;

    case 'modal':
      // 跳转到目标页面 + 触发 Modal
      return (
        <Button onClick={() => {
          navigate(link.target);
          dispatch({ type: 'OPEN_MODAL', payload: link.action });
        }}>
          {link.label}
        </Button>
      );

    case 'drawer':
      return (
        <Button onClick={() => {
          navigate(link.target);
          dispatch({ type: 'OPEN_DRAWER', payload: link.action });
        }}>
          {link.label}
        </Button>
      );

    case 'inline':
      return (
        <Button onClick={() => {
          navigate(link.target);
          dispatch({ type: 'CLICK_BUTTON', payload: link.action_params });
        }}>
          {link.label}
        </Button>
      );
  }
}
```

### 3.3 验证失败的降级行为

| 场景 | 系统行为 | 用户体验 |
|------|---------|---------|
| 全部链接验证通过 | 正常展示所有链接 | 标准交互 |
| 部分链接失效（如 contact_team） | 移除失效链接，保留有效链接 | 少一个按钮，无感知 |
| 全部链接失效 | 移除链接区域，答案中增加文字描述 | "你可以通过菜单进入基础设施文档查看" |
| 目标路由存在但用户无权限 | 保留链接，标记为禁用态 | 灰色按钮 + "需要 XX 权限" |
| 跳转后 Modal 不存在 | 回退为 direct 模式（仅跳转页面） | 用户到页面后自行操作 |
