### 2.2 链路追踪流程

```
┌─────────────────────────────────────────────────────────────────┐
│              链路追踪生成流程                                    │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  步骤 1: TraceID 生成                                            │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │ • 请求进入 API Gateway 时生成 TraceID                      │   │
│  │ • TraceID 格式：32 位 16 进制字符串 (如 abc123def456...)     │   │
│  │ • TraceID 通过 HTTP 头传递：X-Trace-ID                     │   │
│  └─────────────────────────────────────────────────────────┘   │
│                          │                                      │
│                          ▼                                      │
│  步骤 2: Span 创建                                               │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │ • 每个服务入口创建根 Span                                 │   │
│  │ • Span 包含：服务名、操作名、开始时间、标签                │   │
│  │ • 子 Span 通过 Parent SpanID 关联                          │   │
│  └─────────────────────────────────────────────────────────┘   │
│                          │                                      │
│                          ▼                                      │
│  步骤 3: 跨服务传递                                              │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │ • HTTP 调用：TraceID 通过 HTTP 头传递                       │   │
│  │   请求头：X-Trace-ID, X-Span-ID, X-Parent-Span-ID       │   │
│  │                                                         │   │
│  │ • 消息队列：TraceID 通过消息属性传递                       │   │
│  │   消息头：trace_id, span_id, parent_span_id             │   │
│  │                                                         │   │
│  │ • 数据库调用：TraceID 通过会话变量传递                     │   │
│  │   SET @trace_id = 'abc123'                              │   │
│  └─────────────────────────────────────────────────────────┘   │
│                          │                                      │
│                          ▼                                      │
│  步骤 4: Span 结束                                               │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │ • 请求处理完成后结束 Span                                 │   │
│  │ • 记录结束时间、状态码、错误信息                          │   │
│  │ • 添加响应时间、数据大小等指标                            │   │
│  └─────────────────────────────────────────────────────────┘   │
│                          │                                      │
│                          ▼                                      │
│  步骤 5: 数据上报                                                │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │ • Span 数据异步批量上报 (每 100 条或每 5 秒)                  │   │
│  │ • 上报到 Tempo 后端存储                                    │   │
│  │ • 上报失败不影响主业务流程                                 │   │
│  └─────────────────────────────────────────────────────────┘   │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 2.3 必打 Span 规范

| 场景 | Span 名称 | 必打标签 | 必打日志 |
|------|---------|---------|---------|
| **API 入口** | `{METHOD} {PATH}` | method, path, user_id | 请求参数、响应状态 |
| **数据库调用** | `DB {operation} {table}` | db.type, db.operation, db.table | SQL 语句 (脱敏)、执行时间 |
| **AI 服务调用** | `AI {skill_name}` | ai.model, ai.skill, ai.tokens | 输入摘要、输出摘要、Token 数 |
| **外部 API** | `HTTP {method} {host}` | http.method, http.url, http.status | 请求体摘要、响应体摘要 |
| **消息队列** | `MQ {operation} {queue}` | mq.operation, mq.queue, mq.message_id | 消息体摘要、处理时间 |
| **缓存操作** | `Cache {operation} {key}` | cache.operation, cache.key, cache.hit | 键名、命中状态、数据大小 |

### 3.2 告警收敛策略

```
┌─────────────────────────────────────────────────────────────────┐
│              告警收敛流程                                        │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  步骤 1: 告警聚合                                                │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │ • 时间窗口：5 分钟内相同告警合并为 1 条                       │   │
│  │ • 合并规则：相同告警名称 + 相同服务 + 相同环境             │   │
│  │ • 计数统计：合并后显示触发次数                            │   │
│  │                                                         │   │
│  │ 示例：                                                    │   │
│  │ 原始：PodNotReady × 10 条 (5 分钟内)                        │   │
│  │ 聚合后：PodNotReady [触发 10 次，影响 10 个 Pod]              │   │
│  └─────────────────────────────────────────────────────────┘   │
│                          │                                      │
│                          ▼                                      │
│  步骤 2: 告警关联                                                │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │ • 根因分析：识别告警间的因果关系                          │   │
│  │ • 优先级排序：根因告警优先通知                            │   │
│  │ • 派生告警标记为"可能由 X 引起"                            │   │
│  │                                                         │   │
│  │ 示例：                                                    │   │
│  │ 告警 A: NodeNotReady (根因)                              │   │
│  │ 告警 B: PodNotReady × 10 (由 A 引起)                       │   │
│  │ 告警 C: ServiceDegraded (由 A 引起)                        │   │
│  │                                                         │   │
│  │ 通知策略：优先通知告警 A，B 和 C 标记为关联告警                │   │
│  └─────────────────────────────────────────────────────────┘   │
│                          │                                      │
│                          ▼                                      │
│  步骤 3: 告警抑制                                                │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │ • 维护期间抑制：计划维护期间暂停相关告警                  │   │
│  │ • 依赖抑制：上游服务故障时抑制下游告警                    │   │
│  │ • 静默规则：已知问题可设置静默期                          │   │
│  │                                                         │   │
│  │ 示例：                                                    │   │
│  │ • 数据库维护期间 → 抑制数据库相关告警                     │   │
│  │ • API 服务故障 → 抑制依赖 API 的业务告警                    │   │
│  │ • 已知 Bug #123 → 静默 7 天                                │   │
│  └─────────────────────────────────────────────────────────┘   │
│                          │                                      │
│                          ▼                                      │
│  步骤 4: 告警去重                                                │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │ • 跨数据源去重：同一问题在指标/日志/追踪中只通知 1 次        │   │
│  │ • 跨环境去重：多环境同时故障只通知 1 次 (标记影响环境数)      │   │
│  │                                                         │   │
│  │ 示例：                                                    │   │
│  │ 指标告警：API 错误率高                                    │   │
│  │ 日志告警：ERROR 日志激增                                  │   │
│  │ 去重后：API 异常 [错误率↑ + ERROR 日志↑]                     │   │
│  └─────────────────────────────────────────────────────────┘   │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 3.3 告警规则示例

## 四、SLO 与错误预算设计

### 4.1 SLO 定义

```
┌─────────────────────────────────────────────────────────────────┐
│              Orion SLO 定义                                      │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  可用性 SLO                                                     │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │ 指标名称：Service Availability                          │   │
│  │                                                         │   │
│  │ 计算公式：                                               │   │
│  │ 可用性 = (成功请求数 / 总请求数) × 100%                 │   │
│  │                                                         │   │
│  │ 目标值：99.9% (月度)                                     │   │
│  │                                                         │   │
│  │ 测量窗口：滚动 30 天                                       │   │
│  │                                                         │   │
│  │ 排除项：                                                 │   │
│  │ • 计划维护期间                                           │   │
│  │ • 客户侧网络问题                                         │   │
│  │ • 第三方依赖故障 (LLM/GitLab)                            │   │
│  └─────────────────────────────────────────────────────────┘   │
│                                                                 │
│  延迟 SLO                                                       │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │ 指标名称：Request Latency                               │   │
│  │                                                         │   │
│  │ 计算公式：                                               │   │
│  │ P99 延迟 = 99% 的请求在此时间内完成                       │   │
│  │                                                         │   │
│  │ 目标值：                                                 │   │
│  │ • API 请求：P99 < 500ms                                  │   │
│  │ • Pipeline 创建：P99 < 5 秒                               │   │
│  │ • AI 审查：P99 < 30 秒                                    │   │
│  │                                                         │   │
│  │ 测量窗口：滚动 7 天                                        │   │
│  └─────────────────────────────────────────────────────────┘   │
│                                                                 │
│  准确性 SLO                                                     │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │ 指标名称：AI Review Accuracy                            │   │
│  │                                                         │   │
│  │ 计算公式：                                               │   │
│  │ 准确率 = (AI 审查正确数 / 总审查数) × 100%               │   │
│  │                                                         │   │
│  │ 目标值：≥ 85%                                            │   │
│  │                                                         │   │
│  │ 测量窗口：每批次审查后计算，月度汇总                      │   │
│  │                                                         │   │
│  │ 验证方法：                                               │   │
│  │ • 人工抽检 (每日 100 条)                                  │   │
│  │ • 用户反馈统计                                           │   │
│  └─────────────────────────────────────────────────────────┘   │
│                                                                 │
│  数据一致性 SLO                                                 │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │ 指标名称：Data Replication Lag                          │   │
│  │                                                         │   │
│  │ 计算公式：                                               │   │
│  │ 复制延迟 = 从库时间 - 主库时间                          │   │
│  │                                                         │   │
│  │ 目标值：< 1 秒                                           │   │
│  │                                                         │   │
│  │ 测量窗口：实时检测，5 分钟聚合                            │   │
│  └─────────────────────────────────────────────────────────┘   │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 4.2 错误预算管理

```
┌─────────────────────────────────────────────────────────────────┐
│              错误预算管理流程                                    │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  错误预算计算                                                    │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │                                                         │   │
│  │ 月度错误预算 = (1 - SLO 目标) × 当月总分钟数              │   │
│  │                                                         │   │
│  │ 示例 (可用性 SLO 99.9%):                                  │   │
│  │ • 当月总分钟数 = 30 天 × 24 小时 × 60 分钟 = 43,200 分钟     │   │
│  │ • 错误预算 = (1 - 0.999) × 43,200 = 43.2 分钟             │   │
│  │ • 即：每月允许 43.2 分钟的不可用时间                       │   │
│  │                                                         │   │
│  └─────────────────────────────────────────────────────────┘   │
│                          │                                      │
│                          ▼                                      │
│  错误预算消耗追踪                                                │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │                                                         │   │
│  │ 实时计算：                                               │   │
│  │ • 当前周期已用错误预算                                   │   │
│  │ • 剩余错误预算                                           │   │
│  │ • 预计月底消耗 (基于当前速率)                            │   │
│  │                                                         │   │
│  │ 告警阈值：                                               │   │
│  │ • 预算使用 > 50% → 提醒通知                              │   │
│  │ • 预算使用 > 80% → 警告通知，暂停非关键发布              │   │
│  │ • 预算使用 > 100% → 严重告警，冻结所有发布               │   │
│  │                                                         │   │
│  └─────────────────────────────────────────────────────────┘   │
│                          │                                      │
│                          ▼                                      │
│  预算耗尽处理                                                    │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │                                                         │   │
│  │ 自动措施：                                               │   │
│  │ • 暂停非紧急发布                                         │   │
│  │ • 限制实验性功能                                         │   │
│  │ • 增加监控频率                                           │   │
│  │                                                         │   │
│  │ 管理措施：                                               │   │
│  │ • 召开稳定性评审会                                       │   │
│  │ • 制定改进计划                                           │   │
│  │ • 申请额外预算 (需 CTO 批准)                              │   │
│  │                                                         │   │
│  │ 预算恢复：                                               │   │
│  │ • 新周期自动重置                                         │   │
│  │ • 连续 3 个月超支 → 调整 SLO 目标或增加资源投入            │   │
│  │                                                         │   │
│  └─────────────────────────────────────────────────────────┘   │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```
